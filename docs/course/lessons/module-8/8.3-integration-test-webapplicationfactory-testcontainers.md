## **Nội dung chính**

### **1. Vì sao unit test mock không đủ**

*Lý thuyết · 15 phút*

Ở bài 8.1, bạn đã test CreateCourseCommandHandler và UpdateCourseCommandHandler bằng cách mock ICourseRepository. Ở bài 8.2, bạn test invariant của Course Aggregate — không có Lesson thì không publish được — mà không đụng gì đến hạ tầng cả. Cả hai đều đúng đắn và nên tiếp tục làm vì chúng chạy trong mili-giây. Nhưng chúng có một lỗ hổng cố định: mock ICourseRepository nghĩa là bạn đang tin tưởng interface đó phản ánh đúng hành vi thật của EF Core, của migration, của ràng buộc trên Postgres. Nếu tin tưởng đó sai — ví dụ migration quên tạo unique index, hoặc CourseConfiguration.cs (bài 1.4) cấu hình sai kiểu Owned Type cho Pricing — unit test mock vẫn xanh 100%, nhưng ứng dụng chạy thật sẽ vỡ.

Integration test giải quyết đúng khoảng trống này: gọi thật qua toàn bộ pipeline — Minimal API Endpoint → MediatR → ValidationBehavior → Handler → EF Core → Postgres thật — rồi assert trên response HTTP thật. Đánh đổi là chạy chậm hơn unit test (giây, không phải mili-giây), nên bạn không viết integration test cho mọi permutation input như unit test, mà chỉ cho những luồng nghiệp vụ quan trọng nhất: CRUD Course và Checkout.

> **📘 Ghi chú giảng viên:** *Tôi hay hỏi học viên ở đây: "Nếu Handler test mock repository đã pass, sao còn cần test thêm?" — rồi cho xem trực tiếp một migration cố tình thiếu NOT NULL constraint. Unit test mock vẫn xanh, nhưng integration test insert dữ liệu null vào Postgres thật sẽ fail ngay ở bước migrate hoặc ở bước insert. Đây là khoảnh khắc học viên thực sự hiểu integration test dùng để làm gì, không phải chỉ nghe định nghĩa suông.*

### **2. Vì sao Testcontainers, không phải InMemory/SQLite**

Tài liệu chính thức của Microsoft có gợi ý dùng EF Core InMemory provider hoặc SQLite in-memory cho integration test — và với một Razor Pages app đơn giản thì việc đó ổn. Nhưng TEDU Market có 2 lý do cụ thể khiến cách đó không đủ:

- Query side (bài 0.8, 1.6, 1.7) dùng Dapper viết raw SQL trực tiếp cho Postgres — cú pháp OFFSET/FETCH, multi-mapping, các hàm Postgres-specific. SQLite không hiểu cùng dialect, câu SQL sẽ lỗi hoặc chạy sai kết quả mà bạn không biết.
- Optimistic concurrency bằng RowVersion (bài 2.9) dựa vào cơ chế concurrency token thật của Postgres. EF Core InMemory provider không enforce concurrency token đúng như một database quan hệ thật — test có thể pass giả trên InMemory nhưng fail thật trên production.

Testcontainers giải quyết bằng cách tự động pull Docker image postgres, start container thật khi test bắt đầu, và dispose khi test xong — không có bước cài đặt thủ công, không có Postgres "giả lập". Package dùng là Testcontainers.PostgreSql, cung cấp PostgreSqlBuilder và PostgreSqlContainer.

### **3. Setup Postgres container cho test**

*Demo · 15 phút*

Cài package vào project TeduMarket.Api.IntegrationTests:

```bash
dotnet add package Testcontainers.PostgreSql
dotnet add package Npgsql
dotnet add package Microsoft.AspNetCore.Mvc.Testing
```

Viết fixture dùng chung cho cả class test — implement IAsyncLifetime để Testcontainers start container trước khi test chạy, và dispose sau khi xong:

```csharp
// TeduMarketApiFactory.cs
public class TeduMarketApiFactory
    : WebApplicationFactory<Program>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _dbContainer =
        new PostgreSqlBuilder()
            .WithImage("postgres:17-alpine")
            .WithDatabase("tedumarket_test")
            .WithUsername("tedu")
            .WithPassword("tedu_test_pwd")
            .Build();
 
    public async Task InitializeAsync()
    {
        await _dbContainer.StartAsync();
    }
 
    public new async Task DisposeAsync()
    {
        await _dbContainer.DisposeAsync();
    }
 
    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.ConfigureAppConfiguration((_, config) =>
        {
            // Ghi đè connection string Command side (EF Core)
            // và Query side (Dapper) cùng trỏ về container test
            var overrides = new Dictionary<string, string?>
            {
                ["ConnectionStrings:Default"] = _dbContainer.GetConnectionString()
            };
            config.AddInMemoryCollection(overrides);
        });
 
        builder.ConfigureTestServices(services =>
        {
            // Auth giả cho test — không chạy OpenIddict thật (xem mục 4)
            services.AddAuthentication("TestScheme")
                .AddScheme<AuthenticationSchemeOptions, TestAuthHandler>(
                    "TestScheme", _ => { });
        });
    }
 
    public async Task MigrateAsync()
    {
        using var scope = Services.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        await db.Database.MigrateAsync();
    }
}
```

Điểm quan trọng nhất trong đoạn code trên là db.Database.MigrateAsync() — đây chính là bước bắt lỗi migration thật, thay vì EnsureCreated() vốn tự sinh schema từ model hiện tại và bỏ qua toàn bộ lịch sử migration (bài 1.5). Nếu migration nào đó chạy fail trên Postgres thật, bước này báo lỗi ngay, không đợi đến khi deploy production mới phát hiện.

> **📘 Ghi chú giảng viên:** *Học viên hay hỏi: "Sao không set ConnectionStrings:Default trong ConfigureServices như ví dụ InMemory của Microsoft?" — vì appsettings.json đọc connection string ở bước Configuration, trước khi services build. Dùng ConfigureAppConfiguration đảm bảo cả AppDbContext (EF Core, đăng ký ở bài 0.6) lẫn Dapper connection factory (Query side, bài 0.8) đều nhận đúng connection string container — nếu chỉ override DbContext qua ConfigureServices như ví dụ Razor Pages của Microsoft, Query side Dapper vẫn trỏ về Postgres dev thật, dễ gây lẫn dữ liệu giữa test và môi trường dev.*

### **4. TestAuthHandler — không chạy OpenIddict thật trong test CRUD**

Từ Module 3, mọi endpoint Course đều được bảo vệ bằng Policy-based Authorization (bài 3.7) và Resource-based Authorization (bài 3.8) — chỉ Instructor sở hữu Course mới sửa được. Integration test ở bài này tập trung vào đúng luồng CRUD Course và Checkout, không phải test lại OAuth2 flow (đã test riêng ở bài 3.2–3.4). Vì vậy bạn dùng một AuthenticationHandler giả để gắn sẵn claims cần thiết, bỏ qua bước xin token qua /connect/token:

```csharp
// TestAuthHandler.cs
public class TestAuthHandler : AuthenticationHandler<AuthenticationSchemeOptions>
{
    public const string InstructorId = "11111111-1111-1111-1111-111111111111";
 
    public TestAuthHandler(
        IOptionsMonitor<AuthenticationSchemeOptions> options,
        ILoggerFactory logger, UrlEncoder encoder)
        : base(options, logger, encoder) { }
 
    protected override Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        var claims = new[]
        {
            new Claim(ClaimTypes.NameIdentifier, InstructorId),
            new Claim(ClaimTypes.Role, "Instructor"),
            new Claim("instructor_id", InstructorId)
        };
        var identity = new ClaimsIdentity(claims, "TestScheme");
        var principal = new ClaimsPrincipal(identity);
        var ticket = new AuthenticationTicket(principal, "TestScheme");
        return Task.FromResult(AuthenticateResult.Success(ticket));
    }
}
```

Claim instructor_id ở đây phải trùng tên với claim mà bài 3.5 (Custom Claims & Scope) đã cấu hình đưa vào Access Token thật — nếu Resource-based Authorization Handler (bài 3.8) đọc claim tên khác, test sẽ pass giả nhưng production fail thật. Đây là điểm hay bị bỏ sót nhất khi mock auth cho integration test.

### **5. Integration test luồng CRUD Course**

*Lab · 15 phút*

Test class dùng IClassFixture\<TeduMarketApiFactory> để dùng chung 1 container Postgres cho toàn bộ test trong class — tránh start/stop container cho từng test method, vốn rất chậm:

```csharp
// CourseEndpointsTests.cs
public class CourseEndpointsTests : IClassFixture<TeduMarketApiFactory>, IAsyncLifetime
{
    private readonly TeduMarketApiFactory _factory;
    private readonly HttpClient _client;
 
    public CourseEndpointsTests(TeduMarketApiFactory factory)
    {
        _factory = factory;
        _client = _factory.CreateClient();
        _client.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("TestScheme");
    }
 
    public Task InitializeAsync() => _factory.MigrateAsync();
    public Task DisposeAsync() => Task.CompletedTask;
 
    [Fact]
    public async Task CreateCourse_ThenGetDetail_ReturnsCourseWithCorrectData()
    {
        // Arrange
        var command = new CreateCourseCommand(
            Title: "ASP.NET Core 10 CQRS Toàn Tập",
            Price: 799_000m,
            InstructorId: Guid.Parse(TestAuthHandler.InstructorId));
 
        // Act
        var createResponse = await _client.PostAsJsonAsync(
            "/api/v1/courses", command);
 
        // Assert bước tạo
        Assert.Equal(HttpStatusCode.Created, createResponse.StatusCode);
        var created = await createResponse.Content
            .ReadFromJsonAsync<CourseDto>();
 
        // Act — gọi lại Query side (Dapper) để xác nhận dữ liệu
        // thật sự nằm trên Postgres, không chỉ nằm trong response
        var detailResponse = await _client.GetAsync(
            $"/api/v1/courses/{created!.Id}");
        var detail = await detailResponse.Content
            .ReadFromJsonAsync<CourseDetailDto>();
 
        // Assert
        Assert.Equal(HttpStatusCode.OK, detailResponse.StatusCode);
        Assert.Equal(command.Title, detail!.Title);
        Assert.Equal(command.Price, detail.Price);
    }
}
```

Chú ý test này đi qua cả Command side (POST tạo Course bằng EF Core) lẫn Query side (GET đọc lại bằng Dapper, bài 1.7). Đây chính là kiểu lỗi mà unit test mock không bao giờ bắt được: nếu CourseConfiguration.cs ánh xạ cột giá sai tên so với câu SQL Dapper viết tay ở GetCourseDetailQuery, Command side vẫn insert thành công, nhưng Query side đọc ra giá trị sai hoặc null — chỉ integration test đi qua cả hai chiều mới lộ ra.

### **6. Integration test luồng Checkout**

*Lab · 10 phút*

Checkout (bài 2.2) là luồng nhiều bước — AddToCart rồi Checkout, tạo Order ở trạng thái Pending — và có Idempotency key (bài 2.9) cần test đúng bằng Postgres thật vì optimistic concurrency dựa vào RowVersion:

```csharp
[Fact]
public async Task Checkout_CalledTwiceWithSameIdempotencyKey_CreatesOnlyOneOrder()
{
    // Arrange: AddToCart trước
    var courseId = await SeedPublishedCourseAsync();
    await _client.PostAsJsonAsync("/api/v1/cart/items",
        new AddToCartCommand(courseId));
 
    var idempotencyKey = Guid.NewGuid().ToString();
    var checkoutCommand = new CheckoutCommand(IdempotencyKey: idempotencyKey);
 
    // Act: gọi Checkout 2 lần liên tiếp, mô phỏng double-click
    var first = await _client.PostAsJsonAsync(
        "/api/v1/orders/checkout", checkoutCommand);
    var second = await _client.PostAsJsonAsync(
        "/api/v1/orders/checkout", checkoutCommand);
 
    // Assert: cả 2 request đều thành công, nhưng chỉ 1 Order được tạo
    Assert.Equal(HttpStatusCode.Created, first.StatusCode);
    Assert.Equal(HttpStatusCode.Created, second.StatusCode);
 
    var firstOrder = await first.Content.ReadFromJsonAsync<OrderDto>();
    var secondOrder = await second.Content.ReadFromJsonAsync<OrderDto>();
    Assert.Equal(firstOrder!.Id, secondOrder!.Id);
}
```

Test này không thể tin cậy trên EF Core InMemory provider: InMemory không kiểm tra ràng buộc unique trên idempotency key theo đúng ngữ nghĩa transaction như Postgres thật, nên race condition có thể "biến mất" một cách giả tạo trên InMemory trong khi vẫn tồn tại trên production.

> **📘 Ghi chú giảng viên:** *Tôi thường dừng ở bài tập Checkout để hỏi cả lớp: "Nếu Postgres container start chậm 2-3 giây mỗi lần, cả bộ test 8.3 và 8.4 (Payment Webhook, bài kế tiếp) có nên share chung 1 container không?" — dẫn tới giới thiệu ICollectionFixture của xUnit để nhiều test class dùng chung 1 TeduMarketApiFactory, tiết kiệm thời gian CI đáng kể. Đây là điểm sẽ dùng lại ở bài 9.6 (CI/CD GitHub Actions) khi build gate phải chạy hết bộ test trước khi deploy.*

### **Bài tập thực hành**

> **✏️ Thực hành:** Viết thêm integration test cho luồng áp Coupon hết hạn trong Checkout (dựa trên ApplyCouponCommand của bài 2.3).
