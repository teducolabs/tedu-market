## **1. Vấn đề hiện tại trong apps/admin**

*Thời lượng: 5 phút | Loại: Lý thuyết ngắn*

Từ bài 6.3, mỗi màn hình CRUD đang tự xử lý loading/error theo cách riêng: chỗ thì if (isLoading) return \<div>Loading...\</div>, chỗ thì render error.message thẳng ra UI (có khi là JSON ProblemDetails thô), chỗ lại không xử lý gì — submit lỗi mà UI im lặng. Hệ quả: học viên tự làm dự án thật sẽ có N cách xử lý lỗi khác nhau trong cùng 1 app, mỗi cách một kiểu UX.

Bài này không thêm tính năng mới — nó dọn nợ kỹ thuật đó bằng cách tận dụng đúng 2 thứ đã có sẵn: format ProblemDetails nhất quán từ bài 4.5 ở backend, và cơ chế global callback của TanStack Query v5 ở frontend.

> **📘 Ghi chú giảng viên:** *Tôi thường mở lại 1-2 màn hình đã làm ở bài 6.3, cố tình bấm submit sai dữ liệu để học viên tự thấy UI hiện tại xấu ở đâu — im lặng, hiện JSON thô, hay treo loading vô thời hạn. Vấn đề tự thấy sẽ nhớ lâu hơn tôi liệt kê.*

## **2. Chuẩn hóa lỗi & toast toàn cục**

*Thời lượng: 10 phút | Loại: Demo*

### **2.1. Parse ProblemDetails về 1 hàm dùng chung**

ASP.NET Core trả lỗi theo ProblemDetails (bài 0.9, 4.5): title, status, detail, và với lỗi 400 do FluentValidation (bài 0.5) còn có thêm errors — dictionary field → danh sách message. Khi dùng @hey-api/client-fetch (bài 5.2) với throwOnError, error ném ra ở query/mutation chính là object JSON này. Tạo apps/admin/src/lib/api-error.ts:

```typescript
// apps/admin/src/lib/api-error.ts
export interface ProblemDetails {
  type?: string;
  title?: string;
  status?: number;
  detail?: string;
  errors?: Record<string, string[]>;
  traceId?: string;
}
 
function isProblemDetails(error: unknown): error is ProblemDetails {
  return typeof error === 'object' && error !== null && 'title' in error;
}
 
// Dùng cho toast: 1 message duy nhất, ưu tiên detail > title
export function getErrorMessage(error: unknown): string {
  if (isProblemDetails(error)) {
    return error.detail || error.title || 'Đã có lỗi xảy ra, thử lại sau.';
  }
  if (error instanceof Error) return error.message;
  return 'Đã có lỗi không xác định xảy ra.';
}
```

Lưu ý: error ở đây có thể không phải Error thật (JS Error) mà là object JSON thuần do client-fetch throw ra — nên phải check bằng "title" in error thay vì instanceof Error trước.

### **2.2. Toast lỗi 1 chỗ duy nhất bằng QueryCache/MutationCache**

TanStack Query v5 đã bỏ onError trên từng useQuery/useMutation (khác v4). Cách đúng của v5 là đăng ký onError ở cấp QueryCache và MutationCache khi khởi tạo QueryClient — chạy đúng 1 lần cho mỗi query/mutation lỗi, không phụ thuộc component nào đang render hook đó.

```typescript
// apps/admin/src/lib/query-client.ts
import { QueryClient, QueryCache, MutationCache } from '@tanstack/react-query';
import { toast } from 'sonner';
import { getErrorMessage } from './api-error';
 
export const queryClient = new QueryClient({
  queryCache: new QueryCache({
    onError: (error, query) => {
      // Chỉ toast khi cache đã có data cũ (background refetch lỗi)
      // — lỗi lần load đầu tiên đã được UI tự xử lý bằng isError (mục 3)
      if (query.state.data !== undefined) {
        toast.error(getErrorMessage(error));
      }
    },
  }),
  mutationCache: new MutationCache({
    onError: (error) => {
      toast.error(getErrorMessage(error));
    },
  }),
  defaultOptions: {
    queries: { retry: 1, staleTime: 30_000 },
  },
});
```

Thêm \<Toaster /> của sonner (1 lần duy nhất ở root) và cài đặt:

```bash
pnpm --filter admin add sonner
// apps/admin/src/main.tsx
import { Toaster } from 'sonner';
import { QueryClientProvider } from '@tanstack/react-query';
import { queryClient } from './lib/query-client';
 
root.render(
  <QueryClientProvider client={queryClient}>
    <App />
    <Toaster position="top-right" richColors />
  </QueryClientProvider>,
);
```

> **📘 Ghi chú giảng viên:** *Điểm học viên hay hỏi: "Sao onError ở QueryCache không có, phải viết ở đâu?" — vì v4 quen dùng onError ngay trong useQuery(...). Nhấn mạnh đây là breaking change có chủ đích của v5: side-effect (toast) không nên gắn vào từng Observer component, mà gắn vào Query/Mutation instance dùng chung — đúng tinh thần "1 nguồn sự thật" mà khóa học theo xuyên suốt.*

## **3. Loading & skeleton chuẩn với React Query**

*Thời lượng: 10 phút | Loại: Demo*

TanStack Query v5 có 2 cờ loading dễ nhầm — dùng sai chỗ nào cũng ra UI lỗi:

- isPending: chưa có data nào trong cache — đúng nghĩa "đang tải lần đầu". Dùng để hiện skeleton toàn màn hình.
- isFetching: đang có request chạy nền (refetch khi focus lại tab, invalidateQueries sau khi mutate...), có thể data cũ vẫn đang hiển thị. Dùng để hiện 1 spinner nhỏ, không che nội dung cũ.

Áp dụng cho danh sách Course (bài 6.3):

```tsx
// apps/admin/src/features/courses/CourseListSkeleton.tsx
export function CourseListSkeleton() {
  return (
    <div className="space-y-2">
      {Array.from({ length: 6 }).map((_, i) => (
        <div key={i} className="h-14 animate-pulse rounded-md bg-slate-200" />
      ))}
    </div>
  );
}
// apps/admin/src/features/courses/CourseList.tsx
export function CourseList() {
  const { data, isPending, isFetching, isError } = useGetCoursesQuery(filters);
 
  if (isPending) return <CourseListSkeleton />;
 
  // isError: lỗi đã được toast tự động ở QueryCache (mục 2.2)
  // — không render lại thông báo lỗi lần 2 trong nội dung chính.
  if (isError) return <EmptyState message="Không tải được danh sách khóa học." />;
 
  return (
    <div>
      {isFetching && <TopProgressBar />}
      <CourseTable courses={data.items} />
    </div>
  );
}
```

Với nút submit của form (CreateCourseCommand, bài 1.2), dùng mutation.isPending — khác isPending của query, đây là "đang gửi request", không phải "chưa có data":

```typescript
const createCourse = useCreateCourseMutation();
 
<Button type="submit" disabled={createCourse.isPending}>
  {createCourse.isPending ? 'Đang lưu...' : 'Lưu khóa học'}
</Button>
```

> **📘 Ghi chú giảng viên:** *Lỗi phổ biến nhất tôi thấy học viên mắc: dùng isPending của query để disable nút Save trong form — nhầm giữa "đang tải danh sách" và "đang gửi form". 2 state khác nhau, đến từ 2 hook khác nhau (useQuery vs useMutation). Cho học viên tự bấm nút Save nhiều lần liên tiếp khi chưa disable đúng để thấy hậu quả: double-submit — nối thẳng sang vấn đề Idempotency sẽ học kỹ ở bài 2.9.*

## **4. Lỗi validation 400 hiển thị theo field**

*Thời lượng: 5 phút | Loại: Demo*

Toast chung là đủ cho lỗi hệ thống (404, 401, 500), nhưng lỗi 400 do FluentValidation (CreateCourseCommandValidator, bài 0.5) nên hiện ngay dưới từng field trong form — đúng chỗ người dùng cần sửa, không bắt họ tự đoán field nào sai từ 1 dòng toast.

```typescript
// apps/admin/src/lib/api-error.ts (thêm)
export function getFieldError(error: unknown, field: string): string | undefined {
  if (!isProblemDetails(error) || !error.errors) return undefined;
  const key = Object.keys(error.errors).find(
    (k) => k.toLowerCase() === field.toLowerCase(),
  );
  return key ? error.errors[key][0] : undefined;
}
// Trong CourseForm.tsx
const createCourse = useCreateCourseMutation();
const titleError = getFieldError(createCourse.error, 'Title');
 
<Input name="title" aria-invalid={!!titleError} />
{titleError && <p className="text-sm text-red-600">{titleError}</p>}
```

Vì global MutationCache.onError (mục 2.2) đã toast rồi, field error ở đây là hiển thị bổ sung — không tắt toast đi, 2 kênh phục vụ 2 mục đích: toast báo "có lỗi", field error chỉ đúng chỗ cần sửa.

## **Bài tập thực hành**

> **✏️ Thực hành:** Áp dụng đúng pattern trên cho trang Order list (bài 6.4, GetOrderHistoryQuery): (1) thêm OrderListSkeleton hiện khi isPending; (2) không tự render lỗi trong OrderList khi isError — xác nhận toast tự động chạy qua QueryCache; (3) form áp Coupon (ApplyCouponCommand, bài 2.3) hiển thị lỗi "mã coupon hết hạn/không hợp lệ" ngay dưới ô nhập mã bằng getFieldError, không chỉ toast chung.

Hint: nếu ApplyCouponCommandValidator ở backend không trả lỗi theo field CouponCode (ví dụ trả qua 1 exception nghiệp vụ như CouponExpiredException thay vì FluentValidation), error.errors sẽ undefined — lúc đó getFieldError trả về undefined và bạn cần fallback: đọc error.detail để hiện ngay dưới ô nhập, không chỉ ở toast. Đây là điểm hay bị bỏ sót vì khác luồng lỗi validation thông thường.

## **Tổng kết**

> **✅ Tóm tắt:** getErrorMessage() / getFieldError() là 2 hàm duy nhất parse ProblemDetails trong toàn bộ Admin app — không viết lại logic parse lỗi ở từng component.
>
> **✅ Tóm tắt:** QueryCache.onError và MutationCache.onError (TanStack Query v5) là nơi duy nhất gọi toast.error — không còn try/catch rải rác.
>
> **✅ Tóm tắt:** 3 state loading tách biệt: query.isPending (skeleton toàn màn hình), query.isFetching (spinner nhỏ, giữ data cũ), mutation.isPending (disable nút submit).
>
> **✅ Tóm tắt:** Lỗi 400 có errors dict hiện theo field ngay trên form; lỗi khác (401/404/500) chỉ cần toast chung là đủ.

**Bước tiếp theo:**

Bài 7.4 (Auth OIDC cho Next.js) sẽ gặp lại cùng vấn đề loading/error nhưng ở Server Component — nơi không có QueryCache client-side, nên cách tiếp cận sẽ khác (xử lý lỗi ngay trong Server Action / error.tsx boundary của Next.js). Pattern parse ProblemDetails (getErrorMessage) ở bài này vẫn tái sử dụng được nguyên vẹn vì nó không phụ thuộc React Query.
