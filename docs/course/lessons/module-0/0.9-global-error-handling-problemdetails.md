## **Nội dung chính**

### **1. Vấn đề: lỗi đang được trả về không nhất quán**

*8 phút · Lý thuyết ngắn*

Tính đến bài 0.8, dự án TEDU Market đã chạy được CreateCategoryCommand (0.4), validate input tự động qua ValidationBehavior (0.5), lưu xuống Postgres (0.6), expose qua Minimal API (0.7), và đọc danh sách qua Dapper (0.8). Nhưng có một lỗ hổng: khi ValidationBehavior ở bài 0.5 ném FluentValidation.ValidationException, chưa có bất kỳ ai bắt exception đó. Mặc định, ASP.NET Core trả về 500 Internal Server Error cho mọi exception không được xử lý — kể cả lỗi validate 400 rất bình thường.

Tương tự, nếu Query hoặc Command tìm một Category theo Id không tồn tại, code hiện tại không có cách nào báo 404 Not Found một cách nhất quán. Mỗi Handler tự xử lý theo cách riêng sẽ dẫn đến format response lỗi khác nhau giữa các endpoint — điều tối kỵ với một API mà 2 frontend (React Admin, Next.js) sẽ cùng gọi ở Module 6, 7.

> **📘 Ghi chú giảng viên:** *Tôi hay demo trực tiếp: gọi POST /api/v1/categories với body rỗng ngay trên Scalar, chỉ ra học viên thấy màn hình lỗi 500 xấu xí, không có thông tin field nào sai. Sau đó hỏi: "Nếu bạn là dev React Admin ở Module 6, bạn parse lỗi này thế nào?" — câu trả lời là không thể, vì chưa có format cố định.*

### **2. ProblemDetails — chuẩn hóa response lỗi (RFC 9457)**

*Lý thuyết*

Outline gốc của khóa ghi "chuẩn RFC 7807" — cần đính chính: RFC 7807 (2016) đã bị RFC 9457 (2023) thay thế và tuyên bố obsolete. Hai RFC gần như giống hệt nhau về cấu trúc JSON (type, title, status, detail, instance), RFC 9457 chỉ làm rõ thêm vài điểm (ví dụ việc localize title/detail theo Accept-Language, cách mở rộng field). Toàn bộ code mẫu trong bài này build ra đúng JSON shape tương thích cả hai RFC, nhưng khi nói/viết tài liệu, khóa học dùng RFC 9457 vì đây mới là bản đang có hiệu lực.

```
// Response mẫu — application/problem+json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5",
  "title": "Không tìm thấy tài nguyên",
  "status": 404,
  "detail": "Không tìm thấy Category với Id: 3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "instance": "/api/v1/categories/3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "traceId": "00-8f2a...-01"
}
```

ASP.NET Core 10 có sẵn IProblemDetailsService để sinh ra đúng format này. Cách hiện đại nhất để nối exception với ProblemDetails là interface IExceptionHandler (giới thiệu từ .NET 8, vẫn là cách tiếp cận khuyến nghị ở .NET 10) — thay vì viết middleware try/catch thủ công.

### **3. Domain Exception: định nghĩa lỗi nghiệp vụ ở đúng layer**

*Demo · TeduMarket.Domain*

Theo mục 7 (Quy ước đặt tên) của outline: {Thực thể}{LoạiLỗi}Exception, định nghĩa ở Application layer hoặc Domain, map sang ProblemDetails ở Api layer. Vì "không tìm thấy Category" là một khái niệm nghiệp vụ (invariant: thao tác phải nhắm vào một Category có thật), ta đặt exception này ở Domain layer — đúng nguyên tắc Dependency Inversion đã học ở bài 0.2: Domain không phụ thuộc gì cả, kể cả cách nó được xử lý ở tầng trên.

Tạo lớp cơ sở NotFoundException trong Domain trước — đây là lớp mà Module 1 (CourseNotFoundException), Module 2 (OrderNotFoundException...) sẽ tái sử dụng, nên làm đúng ngay từ bài này.

```csharp
// TeduMarket.Domain/Exceptions/NotFoundException.cs
namespace TeduMarket.Domain.Exceptions;
 
/// <summary>
/// Base exception cho mọi trường hợp "không tìm thấy entity" trong Domain.
/// Message ở đây sẽ được dùng trực tiếp làm "detail" trong ProblemDetails,
/// nên viết message cho người dùng cuối đọc được — không phải log kỹ thuật.
/// </summary>
public abstract class NotFoundException(string message) : Exception(message);
```

```csharp
// TeduMarket.Domain/Exceptions/CategoryNotFoundException.cs
namespace TeduMarket.Domain.Exceptions;
 
public sealed class CategoryNotFoundException(Guid categoryId)
    : NotFoundException($"Không tìm thấy Category với Id: {categoryId}")
{
    public Guid CategoryId { get; } = categoryId;
}
```

> **📘 Ghi chú giảng viên:** *Điểm hay bị hỏi: "Sao không dùng exception filter của MVC?" — vì TEDU Market dùng Minimal API (bài 0.7), không có MVC filter pipeline. IExceptionHandler là cách trung lập, hoạt động với cả Minimal API lẫn Controller, đây cũng là lý do Microsoft đưa nó thành khuyến nghị chính từ .NET 8 trở đi.*

### **4. Dùng lại Query side (0.8) để tạo tình huống "not found" thật**

*Demo · TeduMarket.Application + Api*

Để test CategoryNotFoundException với dữ liệu thật, ta thêm một Query nhỏ GetCategoryByIdQuery — lặp lại đúng pattern Dapper Query đã học ở bài 0.8 (lần lặp thứ 2, để pattern thấm dần), khác biệt duy nhất là throw exception khi không tìm thấy row. Category CRUD đầy đủ (Update/Delete) sẽ được hoàn thiện ở bài 1.9; ở đây ta chỉ thêm phần đọc theo Id để có một chỗ thật sự sinh ra lỗi 404.

```csharp
// TeduMarket.Application/Categories/Queries/GetCategoryById/GetCategoryByIdQuery.cs
namespace TeduMarket.Application.Categories.Queries.GetCategoryById;
 
public sealed record GetCategoryByIdQuery(Guid Id) : IRequest<CategoryDto>;
```

```csharp
// TeduMarket.Application/Categories/Queries/GetCategoryById/GetCategoryByIdQueryHandler.cs
using Dapper;
using Npgsql;
using TeduMarket.Domain.Exceptions;
 
namespace TeduMarket.Application.Categories.Queries.GetCategoryById;
 
public sealed class GetCategoryByIdQueryHandler(NpgsqlDataSource dataSource)
    : IRequestHandler<GetCategoryByIdQuery, CategoryDto>
{
    public async Task<CategoryDto> Handle(
        GetCategoryByIdQuery request, CancellationToken cancellationToken)
    {
        const string sql = """
            SELECT id AS "Id", name AS "Name", slug AS "Slug", created_at AS "CreatedAt"
            FROM categories
            WHERE id = @Id
            """;
 
        await using var connection = await dataSource.OpenConnectionAsync(cancellationToken);
 
        var category = await connection.QuerySingleOrDefaultAsync<CategoryDto>(
            new CommandDefinition(sql, new { request.Id }, cancellationToken: cancellationToken));
 
        // Đây chính là chỗ Domain Exception được "kích hoạt" — Handler không tự trả 404,
        // nó chỉ throw đúng lỗi nghiệp vụ, việc map sang HTTP status code là trách nhiệm của Api layer.
        return category ?? throw new CategoryNotFoundException(request.Id);
    }
}
```

```csharp
// TeduMarket.Api/Endpoints/CategoryEndpoints.cs — bổ sung route GET theo Id
group.MapGet("/{id:guid}", async (Guid id, ISender sender, CancellationToken ct) =>
{
    var category = await sender.Send(new GetCategoryByIdQuery(id), ct);
    return Results.Ok(category);
})
.WithName("GetCategoryById")
.Produces<CategoryDto>(StatusCodes.Status200OK)
.ProducesProblem(StatusCodes.Status404NotFound);
```

### **5. GlobalExceptionHandler — nơi xử lý tập trung duy nhất**

*Demo · TeduMarket.Api*

Đây là phần lõi của bài học. GlobalExceptionHandler implement IExceptionHandler, được middleware xử lý exception gọi đến khi có exception không bắt được ở bất kỳ đâu trong pipeline — từ ValidationBehavior (0.5), từ Handler (mục 4 ở trên), hay từ bất kỳ Command/Query nào ở các Module sau.

```csharp
// TeduMarket.Api/ExceptionHandling/GlobalExceptionHandler.cs
using Microsoft.AspNetCore.Diagnostics;
using Microsoft.AspNetCore.Mvc;
using TeduMarket.Domain.Exceptions;
using ValidationException = FluentValidation.ValidationException;
 
namespace TeduMarket.Api.ExceptionHandling;
 
public sealed class GlobalExceptionHandler(
    IProblemDetailsService problemDetailsService,
    ILogger<GlobalExceptionHandler> logger) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken cancellationToken)
    {
        var (statusCode, title) = MapException(exception);
 
        httpContext.Response.StatusCode = statusCode;
 
        // Chỉ log đầy đủ stack trace cho lỗi hệ thống thật sự (500+).
        // Lỗi nghiệp vụ dự kiến trước (400 validate, 404 not found) không cần làm ồn log,
        // vì .NET 10 đã tự suppress diagnostics khi TryHandleAsync trả về true.
        if (statusCode >= StatusCodes.Status500InternalServerError)
        {
            logger.LogError(exception, "Unhandled exception khi xử lý {Path}", httpContext.Request.Path);
        }
 
        var problemDetails = new ProblemDetails
        {
            Status = statusCode,
            Title = title,
            Detail = exception.Message,
            Instance = httpContext.Request.Path
        };
 
        if (exception is ValidationException validationException)
        {
            problemDetails.Extensions["errors"] = validationException.Errors
                .GroupBy(e => e.PropertyName)
                .ToDictionary(g => g.Key, g => g.Select(e => e.ErrorMessage).ToArray());
        }
 
        return await problemDetailsService.TryWriteAsync(new ProblemDetailsContext
        {
            HttpContext = httpContext,
            ProblemDetails = problemDetails,
            Exception = exception
        });
    }
 
    private static (int StatusCode, string Title) MapException(Exception exception) => exception switch
    {
        ValidationException => (StatusCodes.Status400BadRequest, "Dữ liệu không hợp lệ"),
        NotFoundException => (StatusCodes.Status404NotFound, "Không tìm thấy tài nguyên"),
        _ => (StatusCodes.Status500InternalServerError, "Đã có lỗi xảy ra khi xử lý yêu cầu")
    };
}
```

> **📘 Ghi chú giảng viên:** *Lỗi phổ biến học viên hay mắc: import nhầm System.ComponentModel.DataAnnotations.ValidationException thay vì FluentValidation.ValidationException — code vẫn biên dịch được (vì cùng tên lớp khác namespace) nhưng switch expression sẽ không bao giờ khớp, mọi lỗi validate rơi vào nhánh 500. Luôn nhắc học viên kiểm tra using ở đầu file, và tôi luôn alias rõ ràng bằng "using ValidationException = FluentValidation.ValidationException;" để tránh mơ hồ.*

### **6. Đăng ký middleware đúng thứ tự trong Program.cs**

*Demo*

IExceptionHandler không tự hoạt động — phải đăng ký ở DI container VÀ thêm middleware UseExceptionHandler() vào pipeline. Nếu chỉ AddExceptionHandler\<T>() mà quên UseExceptionHandler(), handler không bao giờ được gọi (đây là điểm Microsoft Learn nhấn mạnh riêng bằng khung "Important").

```csharp
// TeduMarket.Api/Program.cs
using TeduMarket.Api.ExceptionHandling;
 
var builder = WebApplication.CreateBuilder(args);
 
// ... các đăng ký DI khác từ bài 0.2 - 0.8 (DbContext, MediatR, FluentValidation, NpgsqlDataSource...)
 
builder.Services.AddProblemDetails(options =>
{
    // AddProblemDetails() ở đây có 2 vai trò:
    // 1) Thỏa điều kiện bắt buộc để UseExceptionHandler() không cần path fallback.
    // 2) Tự động sinh ProblemDetails cho các lỗi KHÔNG do exception gây ra
    //    (vd route không khớp -> 404 trống, do UseStatusCodePages() sinh ra).
    options.CustomizeProblemDetails = context =>
    {
        context.ProblemDetails.Extensions["traceId"] =
            System.Diagnostics.Activity.Current?.Id ?? context.HttpContext.TraceIdentifier;
    };
});
 
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
 
var app = builder.Build();
 
// GlobalExceptionHandler xử lý toàn bộ exception (luôn trả về true từ TryHandleAsync),
// nên app.UseExceptionHandler() không cần truyền path/lambda fallback.
app.UseExceptionHandler();
 
// Sinh ProblemDetails cho status code lỗi (400-599) chưa có body —
// ví dụ route không tồn tại, method không được phép.
app.UseStatusCodePages();
 
// ... UseHttpsRedirection, MapEndpoints... (giữ nguyên từ bài 0.7)
 
app.Run();
```

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở dòng app.UseExceptionHandler() và hỏi: "Nếu đổi thứ tự, đưa dòng này xuống dưới MapEndpoints thì sao?" — middleware order trong ASP.NET Core luôn theo thứ tự khai báo, đặt exception handler quá muộn nghĩa là các middleware/endpoint chạy trước nó không được bảo vệ. Quy tắc chung: exception handling middleware nên đứng gần đầu pipeline nhất có thể.*

### **7. Kiểm chứng thực tế trên Scalar/Postman**

*Demo*

Chạy docker compose (Postgres đã có từ bài 0.6) và dotnet run, sau đó test lần lượt 3 tình huống để chứng minh format nhất quán:

- 400 — POST /api/v1/categories với body { "name": "" } → ProblemDetails có status 400, title "Dữ liệu không hợp lệ", extension "errors" liệt kê đúng field Name.
- 404 — GET /api/v1/categories/{id-không-tồn-tại} → ProblemDetails có status 404, detail chứa đúng Id vừa gọi.
- 500 — tạm thời throw new InvalidOperationException("test") ngay trong GetCategoryByIdQueryHandler để xem response 500 generic, không rò rỉ stack trace ra client — sau đó xoá dòng test này.

Cả 3 response đều cùng shape JSON (type/title/status/detail/instance/traceId) — đây chính là deliverable của bài học: mọi lỗi trả về đúng format ProblemDetails nhất quán, sẵn sàng để 2 frontend app ở Module 6 và 7 parse bằng đúng 1 logic duy nhất.

> **✏️ Thực hành: Chuẩn bị pattern cho Module 1 và xử lý thêm 1 loại lỗi mới**
>
> • Thêm nhánh switch cho DbUpdateException (Npgsql báo lỗi trùng unique constraint khi tạo Category trùng tên) → map sang 409 Conflict thay vì rơi vào nhánh 500 mặc định.
>
> • Viết thử CourseNotFoundException kế thừa NotFoundException (chưa cần dùng ngay, chỉ để quen tay trước khi vào Module 1.1).
>
> • Gọi thử endpoint GET /api/v1/categories/{id} với một Id có định dạng GUID sai (vd "abc") — quan sát ASP.NET Core route constraint {id:guid} tự trả 404 qua UseStatusCodePages() mà không cần chạm vào GlobalExceptionHandler. Giải thích vì sao lại như vậy.
>
> • Hint: DbUpdateException từ Npgsql thường bọc PostgresException bên trong qua thuộc tính InnerException — kiểm tra SqlState "23505" (unique_violation) để phân biệt với các lỗi DB khác.

> **✅ Tóm tắt: Những gì bài học đã hoàn thành**
>
> • Chuẩn hóa response lỗi API theo ProblemDetails (RFC 9457, obsoletes RFC 7807) — không còn mỗi endpoint trả lỗi một kiểu.
>
> • NotFoundException / CategoryNotFoundException ở Domain layer — pattern tái sử dụng xuyên suốt các Module sau (CourseNotFoundException, OrderNotFoundException...).
>
> • GlobalExceptionHandler implement IExceptionHandler, map ValidationException → 400, NotFoundException → 404, còn lại → 500.
>
> • Đăng ký đúng thứ tự: AddProblemDetails() + AddExceptionHandler\<T>() ở DI, UseExceptionHandler() + UseStatusCodePages() ở pipeline.
>
> • Bước tiếp theo — Bài 0.10: Docker Compose Dev Environment, verify toàn bộ Module 0 (bao gồm cả luồng lỗi vừa xây) chạy end-to-end trên hạ tầng Postgres + Redis thật.
