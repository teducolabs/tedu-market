## **1. Từ Handler tới HTTP Endpoint**

*Lý thuyết · 15 phút*

Sau 3 bài liên tiếp (0.4 – 0.6), bạn đã có một CreateCategoryCommandHandler chạy hoàn chỉnh: nhận Command, validate, lưu Category xuống Postgres qua ICategoryRepository. Vấn đề là Handler đó hiện vẫn chỉ được gọi từ code test hoặc console — chưa có cách nào để một client bên ngoài (Postman, React Admin, Next.js) gửi HTTP request vào được. Bài này đóng nốt mắt xích cuối cùng: Api layer.

Ở khóa nền tảng ASP.NET Core, bạn quen với Controller — class kế thừa ControllerBase, action method gắn attribute [HttpPost]. Ở TEDU Market, ta dùng Minimal API vì hai lý do thực tế, không phải vì "nó mới hơn":

- Handler CQRS đã đóng gói toàn bộ logic nghiệp vụ — Controller truyền thống buộc bạn viết thêm một class trung gian chỉ để gọi lại đúng 1 dòng mediator.Send(command). Minimal API cho phép endpoint là 1 static method gọn, không cần class bọc ngoài.
- .NET 10 generate OpenAPI schema từ Minimal API chính xác hơn khi dùng TypedResults — điều này quan trọng vì ở Module 5, schema này sẽ được đọc bởi @hey-api/openapi-ts để sinh TypeScript client dùng chung cho cả 2 frontend. Sai kiểu dữ liệu ở đây sẽ lan ra cả React Admin lẫn Next.js.

Vấn đề tiếp theo: nếu viết thẳng app.MapPost("/api/v1/categories", ...) trong Program.cs, dự án sẽ phình to không kiểm soát được khi có thêm Course, Order, Payment, Enrollment — mỗi entity vài endpoint, nhân lên hàng chục dòng đổ vào 1 file. MapGroup giải quyết đúng vấn đề này:

- Tạo 1 prefix route dùng chung cho mọi endpoint của Category: /api/v1/categories.
- Áp metadata dùng chung 1 lần cho cả nhóm — ví dụ .WithTags("Categories") cho OpenAPI, và sau này ở Module 3 là .RequireAuthorization(...) cho cả nhóm endpoint cần đăng nhập.
- Mỗi entity có 1 file \*Endpoints.cs riêng dưới TeduMarket.Api/Endpoints/ — đúng tinh thần tách nhỏ theo bounded context như Domain layer đã làm.

Về response: Minimal API cho phép trả về gần như bất kỳ kiểu gì (kể cả string, object thô), nhưng compiler và OpenAPI generator không biết trước endpoint sẽ trả về status code nào. TypedResults giải quyết việc này bằng cách khai báo tường minh — ví dụ Results\<Created\<CreateCategoryResponse>, ValidationProblem> nghĩa là "endpoint này chỉ có thể trả 201 kèm CreateCategoryResponse, hoặc 400 dạng ValidationProblem", không hơn không kém. OpenAPI schema sinh ra từ khai báo này chính xác 100%, khác với việc trả IResult chung chung.

> **📘 Ghi chú giảng viên:** *Học viên hay hỏi "vậy Controller có còn dùng được không?" — có, ASP.NET Core 10 vẫn hỗ trợ song song cả hai. Nhưng khóa này chọn Minimal API xuyên suốt để khớp với triết lý CQRS: Handler đã là đơn vị xử lý nghiệp vụ hoàn chỉnh, Endpoint chỉ còn nhiệm vụ là 1 lớp mỏng chuyển đổi HTTP request/response — thêm Controller vào giữa chỉ tạo thêm 1 tầng không cần thiết.*

## **2. Demo: Viết CategoryEndpoints.cs**

*Demo · 20 phút*

Trước khi viết endpoint mới, nhắc nhanh 3 thành phần đã có sẵn từ các bài trước — không viết lại, chỉ tham chiếu:

```csharp
// TeduMarket.Application/Categories/Commands/CreateCategoryCommand.cs (bài 0.4)
public sealed record CreateCategoryCommand(string Name) : IRequest<Guid>;
 
// TeduMarket.Application/Categories/Commands/CreateCategoryCommandValidator.cs (bài 0.5)
public sealed class CreateCategoryCommandValidator : AbstractValidator<CreateCategoryCommand>
{
    public CreateCategoryCommandValidator()
    {
        RuleFor(x => x.Name).NotEmpty().MaximumLength(200);
    }
}
 
// TeduMarket.Application/Categories/Commands/CreateCategoryCommandHandler.cs (bài 0.4 + 0.6)
public sealed class CreateCategoryCommandHandler(ICategoryRepository repository)
    : IRequestHandler<CreateCategoryCommand, Guid>
{
    public async Task<Guid> Handle(CreateCategoryCommand request, CancellationToken cancellationToken)
    {
        var category = Category.Create(request.Name);
        await repository.AddAsync(category, cancellationToken);
        return category.Id;
    }
}
```

Handler này nhận Command, đã chạy qua ValidationBehavior (0.5) trước khi tới đây, và lưu xuống Postgres qua repository (0.6). Việc còn lại ở Api layer chỉ là: nhận HTTP request → tạo Command → gọi ISender.Send() → map kết quả thành HTTP response.

### **Tạo file TeduMarket.Api/Endpoints/CategoryEndpoints.cs**

```csharp
using FluentValidation;
using MediatR;
using Microsoft.AspNetCore.Http.HttpResults;
using TeduMarket.Application.Categories.Commands;
 
namespace TeduMarket.Api.Endpoints;
 
public static class CategoryEndpoints
{
    public static IEndpointRouteBuilder MapCategoryEndpoints(this IEndpointRouteBuilder app)
    {
        var group = app.MapGroup("/api/v1/categories")
            .WithTags("Categories");
 
        group.MapPost("/", CreateCategory);
 
        return app;
    }
 
    private static async Task<Results<Created<CreateCategoryResponse>, ValidationProblem>> CreateCategory(
        CreateCategoryRequest request,
        ISender sender,
        CancellationToken cancellationToken)
    {
        var command = new CreateCategoryCommand(request.Name);
 
        try
        {
            var categoryId = await sender.Send(command, cancellationToken);
            var response = new CreateCategoryResponse(categoryId, request.Name);
 
            return TypedResults.Created($"/api/v1/categories/{categoryId}", response);
        }
        catch (ValidationException ex)
        {
            var errors = ex.Errors
                .GroupBy(e => e.PropertyName)
                .ToDictionary(g => g.Key, g => g.Select(e => e.ErrorMessage).ToArray());
 
            return TypedResults.ValidationProblem(errors);
        }
    }
}
 
public sealed record CreateCategoryRequest(string Name);
 
public sealed record CreateCategoryResponse(Guid Id, string Name);
```

Vài điểm cần nói rõ để học viên không chép máy móc:

- CreateCategoryRequest là DTO của tầng Api — cố tình tách khỏi CreateCategoryCommand. Hôm nay 2 record này giống hệt nhau, nhưng khi Category có thêm field chỉ dành riêng cho HTTP (ví dụ file upload, header) mà Domain không cần biết, tách sẵn từ đầu giúp không phải refactor sau.
- try/catch ValidationException ở đây là giải pháp tạm thời cho riêng endpoint này. Bài 0.9 (Global Error Handling) sẽ chuyển toàn bộ logic bắt lỗi này vào 1 middleware dùng chung cho mọi endpoint, để không phải lặp lại try/catch như thế này ở từng Command. Cứ để nguyên như vậy cho đến bài 0.9.
- Route "/" bên trong group.MapPost thực ra là "/api/v1/categories/" đầy đủ — MapGroup đã cộng prefix vào, không cần lặp lại /categories trong MapPost.

> **📘 Ghi chú giảng viên:** *Điểm hay bị hỏi: "Sao không throw exception thẳng ra ngoài cho middleware mặc định xử lý?" — vì middleware mặc định của ASP.NET Core trả về trang lỗi 500 kèm stack trace (hoặc trắng trơn ở production), không phải ProblemDetails có cấu trúc. Bài 0.5 đã cam kết deliverable là "lỗi 400 có cấu trúc", nên endpoint phải tự xử lý tạm cho đến khi có middleware tập trung ở 0.9. Đây là ví dụ tốt để giải thích khái niệm "nợ kỹ thuật có chủ đích, có deadline rõ ràng" — khác với nợ kỹ thuật bị quên.*

## **3. Lab: Đăng ký endpoint & chạy thử end-to-end**

### **3.1. Đăng ký endpoint trong Program.cs**

Thêm 1 dòng vào Program.cs, ngay trước app.Run(), cùng khu vực với các lệnh app.Map... khác nếu có:

```csharp
// Program.cs
app.MapCategoryEndpoints();
 
app.Run();
```

Nếu Program.cs được scaffold từ template .NET 10 mặc định (dotnet new web) ở bài 0.2, khối OpenAPI/Scalar cho môi trường Development thường đã có sẵn dạng:

```csharp
if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
    app.MapScalarApiReference();
}
```

Cứ để nguyên khối này — Module 4.2 sẽ quay lại cấu hình chi tiết hơn cho Scalar (title, auth). Bài này chỉ cần nó chạy để xem nhanh danh sách endpoint tại /scalar/v1, việc test thật vẫn ưu tiên qua Postman/curl để thấy rõ request/response thô.

### **3.2. Test case thành công — 201 Created**

```bash
curl -i -X POST http://localhost:5000/api/v1/categories \
  -H "Content-Type: application/json" \
  -d '{"name": "Lập trình Backend"}'
```

Kết quả mong đợi: HTTP 201, header Location: /api/v1/categories/{id}, body chứa { "id": "...", "name": "Lập trình Backend" }.

### **3.3. Test case lỗi — 400 có cấu trúc**

```bash
curl -i -X POST http://localhost:5000/api/v1/categories \
  -H "Content-Type: application/json" \
  -d '{"name": ""}'
```

Kết quả mong đợi: HTTP 400, body dạng ProblemDetails validation với errors.Name chứa thông báo từ CreateCategoryCommandValidator (bài 0.5) — chứng minh pipeline validate vẫn chạy đúng khi gọi qua HTTP, không chỉ khi gọi trực tiếp mediator.Send() như lúc test ở bài 0.5.

### **3.4. Xác minh dữ liệu thật trong Postgres**

```
psql -h localhost -U postgres -d tedumarket -c \
  "SELECT id, name FROM categories ORDER BY id DESC LIMIT 1;"
```

Đây là bước hay bị bỏ qua: nhiều bạn dừng lại ở việc thấy response 201 là coi như xong, nhưng deliverable của bài này ghi rõ "chạy thử thật, không phải sơ đồ trên giấy" — nghĩa là phải tận mắt thấy dòng dữ liệu nằm trong bảng categories, chứng minh cả chuỗi Endpoint → MediatR → ValidationBehavior → Handler → Repository → Postgres đã chạy đúng, không có mắt xích nào bị mock ngầm.

## **Bài tập thực hành**

> **✏️ Yêu cầu:** Mở rộng CreateCategoryCommand để tự sinh thêm trường Slug từ Name (ví dụ "Lập trình Backend" → "lap-trinh-backend": chuyển thường, bỏ dấu tiếng Việt, khoảng trắng thành dấu gạch ngang), và trả Slug ra trong CreateCategoryResponse.

Input: POST /api/v1/categories với body { "name": "Lập Trình Web Nâng Cao" }.

Expected output: HTTP 201, body { "id": "...", "name": "Lập Trình Web Nâng Cao", "slug": "lap-trinh-web-nang-cao" }.

> **✏️ Hint:** Câu hỏi quan trọng nhất không phải là "code chuyển chuỗi thế nào" mà là "logic sinh Slug nên đặt ở layer nào?". Gợi ý: Category là Aggregate Root (bài 0.3) — nơi đảm bảo invariant của chính nó. Đặt logic trong static factory method Category.Create(string name), không đặt trong Endpoint hay Handler. Endpoint chỉ nên là lớp mỏng chuyển đổi HTTP, không chứa business logic.

Solution (tóm tắt hướng làm, không phải copy nguyên văn):

- Domain: Category.Create(string name) tự tính Slug và gán vào property Slug (chỉ có setter private), thêm unit test kiểm tra Slug sinh đúng cho tên có dấu.
- Application: CreateCategoryCommandHandler không đổi — vẫn chỉ gọi Category.Create(request.Name), vì Slug do Domain tự lo.
- Api: CreateCategoryResponse thêm field Slug, lấy từ category.Slug do Handler trả về (cần đổi Handler trả về cả object Category thay vì chỉ Guid, hoặc trả thêm Slug qua 1 kiểu response nhỏ ở Application — tự quyết định, miễn Endpoint không tự tính Slug).

## **Tổng kết**

- Api layer là lớp mỏng cuối cùng nối HTTP request vào chain CQRS đã dựng từ 0.4 đến 0.6 — không chứa business logic, chỉ chuyển đổi request/response.
- MapGroup gom endpoint theo entity, giữ Program.cs gọn và áp metadata dùng chung (tag, sau này là authorization ở Module 3).
- TypedResults khai báo tường minh các response type có thể trả về — nền tảng để OpenAPI schema chính xác, phục vụ codegen client ở Module 5.
- Xử lý ValidationException ngay tại endpoint là giải pháp tạm thời, có deadline rõ ràng: sẽ được tập trung hóa ở bài 0.9.
- Deliverable đạt được: POST /api/v1/categories chạy thật, trả 201 Created, dữ liệu xác minh được trong Postgres.

> **✅ Tóm tắt:** Module 0 gần như hoàn chỉnh vòng lặp CQRS end-to-end cho Command side. Bài tiếp theo (0.8) mở mắt xích còn thiếu: Query side độc lập bằng Dapper — lý do CQRS ở khóa này "có thật", không chỉ tách tên class.

*Bước tiếp theo: Bài 0.8 — Query Side riêng biệt với Dapper.*
