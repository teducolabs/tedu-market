## **Nội dung chính**

### **1. Vì sao Repository Interface phải sống ở Application, không phải Infrastructure**

*Lý thuyết · 10 phút*

Ở bài 0.2, bạn đã thiết lập chiều phụ thuộc: Domain không phụ thuộc gì cả, Application phụ thuộc Domain, Infrastructure implement các interface được định nghĩa ở Application, và Api phụ thuộc cả Application lẫn Infrastructure. Đây chính là Dependency Inversion Principle (DIP) — layer chứa business logic (Application) định nghĩa "nó cần gì" bằng interface, còn layer hạ tầng (Infrastructure) phải tuân theo bản hợp đồng đó.

Nếu bạn định nghĩa ICategoryRepository ngay trong Infrastructure, thì CreateCategoryCommandHandler (đang nằm ở Application) muốn gọi repository sẽ buộc phải reference ngược sang Infrastructure — phá vỡ đúng chiều phụ thuộc đã dựng ở bài 0.2. Application sẽ "biết" EF Core tồn tại, và toàn bộ lý do xây Clean Architecture (tách business logic khỏi chi tiết công nghệ) sụp đổ.

Theo đúng quy ước đặt tên ở mục 7 của outline khóa học, interface repository đặt tên I{Aggregate}Repository — ở bài này là ICategoryRepository, định nghĩa ở Application, implement ở Infrastructure.

> **📘 Ghi chú giảng viên:** *Tôi hay đặt câu hỏi mở đầu phần này: "Nếu mai công ty đổi từ PostgreSQL sang MySQL, hoặc đổi từ EF Core sang Dapper cho write side, Handler code có phải sửa dòng nào không?" Với thiết kế đúng, câu trả lời là KHÔNG — chỉ cần viết một class CategoryRepository mới trong Infrastructure, implement lại đúng ICategoryRepository, Application không đổi một dòng nào. Đây là lúc nhấn mạnh lại giá trị thực của DIP, không phải lý thuyết suông.*

### **2. Định nghĩa ICategoryRepository ở Application**

*Demo · 5 phút (gộp vào phần cấu hình AppDbContext)*

Tạo interface trong TeduMarket.Application, thư mục Categories/Repositories (hoặc theo cấu trúc feature folder bạn đã chọn từ bài 0.4):

```csharp
// TeduMarket.Application/Categories/Repositories/ICategoryRepository.cs
namespace TeduMarket.Application.Categories.Repositories;
 
public interface ICategoryRepository
{
    Task AddAsync(Category category, CancellationToken cancellationToken = default);
 
    Task<Category?> GetByIdAsync(Guid id, CancellationToken cancellationToken = default);
 
    Task SaveChangesAsync(CancellationToken cancellationToken = default);
}
```

> **📘 Ghi chú giảng viên:** *SaveChangesAsync đặt ngay trong ICategoryRepository là một cách đơn giản hoá Unit of Work cho giai đoạn này — repository vừa track thay đổi vừa commit. Khi khóa học đến bài 2.6 (Outbox Pattern), bạn sẽ thấy tình huống cần ghi Order và OutboxMessage trong CÙNG một transaction — lúc đó Unit of Work thật sự (dùng chung 1 DbContext qua nhiều repository) mới cần thiết. Ở Module 0, đừng over-engineer trước khi có lý do.*

### **3. Cấu hình AppDbContext (Write Model) trong Infrastructure**

*Demo · 10 phút*

Cài 2 package vào TeduMarket.Infrastructure (phiên bản khớp .NET 10 / EF Core 10):

```bash
dotnet add TeduMarket.Infrastructure package Microsoft.EntityFrameworkCore --version 10.0.0
dotnet add TeduMarket.Infrastructure package Npgsql.EntityFrameworkCore.PostgreSQL --version 10.0.0
```

Tạo AppDbContext trong thư mục Persistence:

```csharp
// TeduMarket.Infrastructure/Persistence/AppDbContext.cs
using Microsoft.EntityFrameworkCore;
using TeduMarket.Domain.Categories;
 
namespace TeduMarket.Infrastructure.Persistence;
 
public sealed class AppDbContext(DbContextOptions<AppDbContext> options) : DbContext(options)
{
    public DbSet<Category> Categories => Set<Category>();
 
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Category>(builder =>
        {
            builder.ToTable("Categories");
            builder.HasKey(c => c.Id);
            builder.Property(c => c.Name)
                .IsRequired()
                .HasMaxLength(200);
        });
 
        base.OnModelCreating(modelBuilder);
    }
}
```

> **📘 Ghi chú giảng viên:** *AppDbContext dùng primary constructor — cú pháp có từ C# 12, vẫn hoàn toàn hợp lệ và được khuyến khích trên C# 14/.NET 10, chỉ là cách viết gọn cho constructor gán field. Đừng để học viên nhầm đây là feature riêng của C# 14. Ngoài ra, cấu hình Fluent API ở đây chỉ ở mức tối thiểu đủ chạy — Category là Aggregate đơn giản nhất khóa học. Fluent Configuration đầy đủ cho Aggregate phức tạp (Owned Type cho Value Object, quan hệ 1-nhiều, cascade delete) sẽ học kỹ ở bài 1.4 khi làm Course Aggregate.*

### **4. Implement CategoryRepository**

*Demo · 10 phút*

```csharp
// TeduMarket.Infrastructure/Persistence/Repositories/CategoryRepository.cs
using Microsoft.EntityFrameworkCore;
using TeduMarket.Application.Categories.Repositories;
using TeduMarket.Domain.Categories;
 
namespace TeduMarket.Infrastructure.Persistence.Repositories;
 
public sealed class CategoryRepository(AppDbContext context) : ICategoryRepository
{
    public async Task AddAsync(Category category, CancellationToken cancellationToken = default)
    {
        await context.Categories.AddAsync(category, cancellationToken);
    }
 
    public Task<Category?> GetByIdAsync(Guid id, CancellationToken cancellationToken = default)
        => context.Categories.FirstOrDefaultAsync(c => c.Id == id, cancellationToken);
 
    public Task SaveChangesAsync(CancellationToken cancellationToken = default)
        => context.SaveChangesAsync(cancellationToken);
}
```

Để ý: CategoryRepository nằm trong Infrastructure, reference TeduMarket.Application (để implement interface) và TeduMarket.Domain (để biết kiểu Category) — đúng chiều phụ thuộc đã vẽ ở bài 0.2. Ngược lại, Application không hề reference Infrastructure, không có dòng using nào trỏ tới EF Core.

### **5. Đăng ký DI — connection string & AddDbContext**

*Demo · 5 phút*

Thêm connection string vào TeduMarket.Api/appsettings.Development.json:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Port=5432;Database=tedumarket;Username=postgres;Password=postgres"
  }
}
```

Gom việc đăng ký DI của Infrastructure vào 1 extension method, tránh Program.cs phình to dần qua từng bài:

```csharp
// TeduMarket.Infrastructure/DependencyInjection.cs
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;
using TeduMarket.Application.Categories.Repositories;
using TeduMarket.Infrastructure.Persistence;
using TeduMarket.Infrastructure.Persistence.Repositories;
 
namespace TeduMarket.Infrastructure;
 
public static class DependencyInjection
{
    public static IServiceCollection AddInfrastructure(
        this IServiceCollection services, IConfiguration configuration)
    {
        var connectionString = configuration.GetConnectionString("DefaultConnection")
            ?? throw new InvalidOperationException(
                "Connection string 'DefaultConnection' chưa được cấu hình.");
 
        services.AddDbContext<AppDbContext>(options =>
            options.UseNpgsql(connectionString));
 
        services.AddScoped<ICategoryRepository, CategoryRepository>();
 
        return services;
    }
}
```

Trong TeduMarket.Api/Program.cs, gọi extension method này:

```csharp
builder.Services.AddInfrastructure(builder.Configuration);
```

> **📘 Ghi chú giảng viên:** *Nhắc học viên KHÔNG commit password thật trong appsettings.Development.json lên Git — file này nên nằm trong .gitignore, hoặc dùng \`dotnet user-secrets\` cho môi trường máy cá nhân. Khóa học không đi sâu User Secrets vì không phải trọng tâm, nhưng nên nhắc 1 câu để học viên có thói quen đúng ngay từ đầu.*

### **6. Cập nhật CreateCategoryCommandHandler — lưu thật xuống Postgres**

*Demo · 5 phút*

Ở bài 0.4, CreateCategoryCommandHandler mới chỉ log ra console khi xử lý xong, vì lúc đó chưa có Infrastructure. Giờ đã có ICategoryRepository, thay Console.WriteLine bằng lưu dữ liệu thật:

```csharp
// TeduMarket.Application/Categories/Commands/CreateCategoryCommandHandler.cs
using MediatR;
using TeduMarket.Application.Categories.Repositories;
using TeduMarket.Domain.Categories;
 
namespace TeduMarket.Application.Categories.Commands;
 
public sealed class CreateCategoryCommandHandler(ICategoryRepository categoryRepository)
    : IRequestHandler<CreateCategoryCommand, Guid>
{
    public async Task<Guid> Handle(
        CreateCategoryCommand request, CancellationToken cancellationToken)
    {
        var category = Category.Create(request.Name);
 
        await categoryRepository.AddAsync(category, cancellationToken);
        await categoryRepository.SaveChangesAsync(cancellationToken);
 
        // Đã bỏ Console.WriteLine tạm từ bài 0.4 — giờ Category được lưu
        // thật xuống Postgres, không chỉ log ra màn hình nữa.
        return category.Id;
    }
}
```

Category.Create(request.Name) là factory method giữ nguyên từ bài 0.3, vẫn đảm bảo invariant "tên không rỗng" ngay tại Domain — Handler ở Application không cần validate lại logic này, ValidationBehavior (bài 0.5) đã chặn input rỗng trước khi Handler chạy tới đây.

### **7. Tạo bảng tạm bằng EnsureCreatedAsync & chạy thử end-to-end**

*Demo · 5 phút*

Migration Workflow chuẩn (dotnet ef migrations) chỉ được học chính thức ở bài 1.5. Để có bảng Categories ngay bây giờ mà chạy thử được, dùng EnsureCreatedAsync như một giải pháp tạm thời trong Program.cs:

```csharp
// TeduMarket.Api/Program.cs — SAU builder.Build(), TRƯỚC app.Run()
using (var scope = app.Services.CreateScope())
{
    var dbContext = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    await dbContext.Database.EnsureCreatedAsync();
}
```

Chạy lại chính đoạn test tạm đã tạo ở bài 0.4 (gọi mediator.Send(new CreateCategoryCommand("Lập trình Web")) khi ứng dụng khởi động) — lần này kiểm tra kết quả bằng DB client thay vì đọc console:

```sql
SELECT * FROM "Categories";
```

Bạn sẽ thấy 1 dòng dữ liệu thật trong Postgres. Endpoint HTTP thật (POST /api/v1/categories) chưa tồn tại — đó là nội dung bài 0.7, lúc đó đoạn test tạm trong Program.cs sẽ được gỡ bỏ hoàn toàn.

> **📘 Ghi chú giảng viên:** *Đây là điểm bắt buộc phải nói rõ với học viên: EnsureCreatedAsync và dotnet ef migrations KHÔNG được dùng song song trên cùng một database — EnsureCreated tạo schema trực tiếp từ model hiện tại và không ghi lịch sử migration, nếu sau đó chạy migration vào cùng DB sẽ xung đột. Nhắc học viên: đến bài 1.5, xoá hẳn đoạn EnsureCreatedAsync này và thay bằng MigrateAsync() dựa trên migration thật. Nếu không nhắc, học viên sẽ mang thói quen này đi sai suốt khóa.*

Nếu chưa có Postgres chạy sẵn, dùng lệnh sau để có ngay một instance tạm cho tới khi Docker Compose chính thức ở bài 0.10:

```bash
docker run --name tedumarket-postgres -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=tedumarket -p 5432:5432 -d postgres:17
```

## **Bài tập thực hành**

Đề bài: Chặn tạo Category trùng tên (case-insensitive) bằng cách kết hợp Repository vừa xây với ValidationBehavior đã có từ bài 0.5.

**Yêu cầu:**

- Thêm Task\<bool> ExistsByNameAsync(string name, CancellationToken cancellationToken = default) vào ICategoryRepository.
- Implement trong CategoryRepository bằng EF.Functions.ILike(c.Name, name) để so sánh không phân biệt hoa/thường trên Postgres.
- Trong CreateCategoryCommandValidator (bài 0.5), thêm rule RuleFor(x => x.Name).MustAsync(...) gọi ExistsByNameAsync, trả lỗi nếu tên đã tồn tại.

**Input / Expected output:**

- Gọi CreateCategoryCommand("Lập trình Web") lần 1 → tạo thành công, trả về Id.
- Gọi CreateCategoryCommand("lập trình web") lần 2 (khác hoa/thường) → ValidationBehavior chặn lại, trả lỗi 400 dạng ProblemDetails, không có bản ghi thứ 2 trong bảng Categories.

> **✏️ Hint:** FluentValidation có 2 API khác nhau: Must (đồng bộ) và MustAsync (bất đồng bộ). Vì ExistsByNameAsync gọi xuống Postgres, bắt buộc dùng MustAsync — dùng Must với 1 lambda async sẽ không await đúng cách và luôn trả về true.
>
> **✏️ Solution (tóm tắt):** RuleFor(x => x.Name).MustAsync(async (name, cancellationToken) => !await categoryRepository.ExistsByNameAsync(name, cancellationToken)).WithMessage("Tên danh mục đã tồn tại."); — Validator cần inject ICategoryRepository qua constructor, giống cách Handler đã làm ở mục 6.
