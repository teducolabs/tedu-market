## Nội dung chính

### Phần 1 — Vì sao 4 project, không phải 1 project?

*Lý thuyết · 15 phút*

Ở Bài 0.1 bạn đã thấy sơ đồ kiến trúc 4 lớp đồng tâm của TEDU Market. Bài này biến sơ đồ đó thành 4 project .NET thật, và quan trọng hơn: thành 4 project reference đúng chiều — vì chiều reference chính là thứ ép buộc kiến trúc, không phải cái tên thư mục.

Chiều phụ thuộc bắt buộc xuyên suốt khóa học (đã chốt ở mục 5–6 outline):

- TeduMarket.Domain — không tham chiếu bất kỳ project nào khác trong solution. Đây là lớp trong cùng, chỉ chứa Entity, Value Object, Aggregate Root, Domain Event.
- TeduMarket.Application — tham chiếu Domain. Chứa Command, Query, Handler, Validator, Pipeline Behavior, và các interface như ICourseRepository — Application chỉ khai báo "tôi cần gì", không khai báo "làm bằng công nghệ gì".
- TeduMarket.Infrastructure — tham chiếu Application. Implement các interface đó bằng công nghệ cụ thể: EF Core, Dapper, OpenIddict, Hangfire, adapter VNPay.
- TeduMarket.Api — tham chiếu cả Application và Infrastructure. Đây là composition root — nơi duy nhất trong hệ thống "biết" đầy đủ mọi thứ và ráp chúng lại với nhau qua DI container ở Program.cs.

Điểm mấu chốt: mũi tên reference chỉ đi một chiều, từ ngoài vào trong. Domain không bao giờ biết đến sự tồn tại của EF Core hay Postgres.

### Dependency Inversion Principle — ví dụ thật, không phải định nghĩa sách vở

Nhầm lẫn phổ biến nhất: đánh đồng Dependency Inversion Principle (DIP) với Dependency Injection (DI).

- DI (Dependency Injection) là một kỹ thuật: cung cấp dependency cho một class từ bên ngoài (thường qua constructor) thay vì để class tự new ra nó.
- DIP (Dependency Inversion Principle) là một nguyên tắc thiết kế kiến trúc: module cấp cao (business logic) không phụ thuộc trực tiếp vào module cấp thấp (chi tiết kỹ thuật); cả hai cùng phụ thuộc vào một abstraction.

Áp vào TEDU Market: TeduMarket.Application định nghĩa interface ICourseRepository — một abstraction thể hiện "tôi cần lưu và lấy Course", không nói gì về EF Core. TeduMarket.Infrastructure viết class CourseRepository : ICourseRepository, bên trong dùng EF Core để thao tác Postgres thật.

Giá trị thực tế: nếu 2 năm sau bạn quyết định đổi từ EF Core sang Dapper thuần cho write model, hoặc đổi PostgreSQL sang một database khác, thì toàn bộ TeduMarket.Application — nơi chứa business logic quan trọng nhất của hệ thống — không phải sửa một dòng nào. Chỉ viết lại class CourseRepository trong Infrastructure.

Nếu làm ngược lại — Handler trong Application gọi thẳng AppDbContext của EF Core — thì business logic bị khóa cứng vào một công nghệ cụ thể. Đây chính là kiểu kiến trúc layered truyền thống mà outline khóa học này chủ động tránh ngay từ Module 0, thay vì đợi đến cuối khóa mới "refactor sang kiến trúc đúng".

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi ngược lại học viên: "Nếu Application project của bạn có PackageReference tới Microsoft.EntityFrameworkCore, thì DIP đã bị vi phạm chưa, dù bạn chưa viết dòng code nào dùng nó?" — câu trả lời là ĐÃ vi phạm, vì việc thêm package đã tạo ra sự phụ thuộc biên dịch (compile-time dependency), bất kể có dùng nó hay không. Đây là chỗ học viên hay nhầm nhất giữa DIP và DI.*

### Phần 2 — Demo: Khởi tạo solution & 4 project

*Demo · 15 phút*

Tạo thư mục gốc và khởi tạo solution file, đúng theo cấu trúc monorepo ở mục 6 outline (thư mục backend/ nằm cạnh frontend/ sẽ tạo ở Module 5):

```bash
mkdir tedu-market && cd tedu-market
mkdir backend && cd backend
 
dotnet new sln -n TeduMarket
```

Tạo 4 project vào thư mục src/. Ba project Domain/Application/Infrastructure dùng template classlib (thư viện thuần, không có endpoint). Project Api dùng template web — ASP.NET Core Empty, đúng baseline cho Minimal API sẽ viết ở Bài 0.7, không dùng webapi (template này sinh sẵn Controller mẫu, không hợp với hướng Minimal API của khóa):

```bash
dotnet new classlib -n TeduMarket.Domain -o src/TeduMarket.Domain --framework net10.0
dotnet new classlib -n TeduMarket.Application -o src/TeduMarket.Application --framework net10.0
dotnet new classlib -n TeduMarket.Infrastructure -o src/TeduMarket.Infrastructure --framework net10.0
dotnet new web -n TeduMarket.Api -o src/TeduMarket.Api --framework net10.0
```

Add cả 4 project vào solution (glob \*\* cần bật globstar trên bash, nếu không hỗ trợ thì add từng project như bên dưới):

```
dotnet sln TeduMarket.sln add src/TeduMarket.Domain/TeduMarket.Domain.csproj
dotnet sln TeduMarket.sln add src/TeduMarket.Application/TeduMarket.Application.csproj
dotnet sln TeduMarket.sln add src/TeduMarket.Infrastructure/TeduMarket.Infrastructure.csproj
dotnet sln TeduMarket.sln add src/TeduMarket.Api/TeduMarket.Api.csproj
```

Thiết lập project reference — đúng 4 lệnh, đúng chiều đã phân tích ở Phần 1:

```bash
dotnet add src/TeduMarket.Application reference src/TeduMarket.Domain
dotnet add src/TeduMarket.Infrastructure reference src/TeduMarket.Application
dotnet add src/TeduMarket.Api reference src/TeduMarket.Application
dotnet add src/TeduMarket.Api reference src/TeduMarket.Infrastructure
```

Dọn sạch file mẫu Class1.cs mà template classlib tự sinh ra trong 3 project — chưa cần code gì ở bài này, Bài 0.3 mới bắt đầu viết Category Aggregate:

```csharp
rm src/TeduMarket.Domain/Class1.cs
rm src/TeduMarket.Application/Class1.cs
rm src/TeduMarket.Infrastructure/Class1.cs
```

Build thử toàn bộ solution để xác nhận 4 project đã lên đúng và reference hợp lệ:

```bash
dotnet build
```

Kết quả mong đợi: "Build succeeded", 0 Error, 0 Warning (có thể có cảnh báo NETSDK do project classlib chưa có file .cs nào — bỏ qua, sẽ hết khi Bài 0.3 thêm Category.cs).

### Phần 3 — Lab: Tự kiểm tra chiều dependency

*Lab · 10 phút*

Liệt kê lại toàn bộ project reference của Api để xác nhận đúng 2 dòng:

```xml
dotnet list src/TeduMarket.Api/TeduMarket.Api.csproj reference
```

Kết quả đúng phải gồm đúng TeduMarket.Application và TeduMarket.Infrastructure — không có project nào khác.

Bây giờ cố tình vi phạm DIP để thấy rõ .NET CLI không hề chặn việc này:

```bash
dotnet add src/TeduMarket.Domain reference src/TeduMarket.Infrastructure
dotnet build
```

# → build vẫn PASS bình thường, không có lỗi hay cảnh báo nào

Gỡ lại reference sai ngay sau khi quan sát xong:

```bash
dotnet remove src/TeduMarket.Domain reference src/TeduMarket.Infrastructure
dotnet build
```

> **📘 Ghi chú giảng viên:** *Đây là điểm hay bị hiểu lầm: nhiều học viên nghĩ cứ đặt đúng tên thư mục Domain/Application/Infrastructure/Api là kiến trúc "tự động an toàn". Thực tế project reference của .NET chỉ là rào chắn đầu tiên, dễ vi phạm bằng 1 lệnh dotnet add reference. Kỷ luật thật sự nằm ở code review và ở Architecture Test tự động — sẽ học ở Bài 8.3 (Integration Test) khi viết test kiểm tra assembly nào được phép reference assembly nào.*

> **✏️ Thực hành: Tự dựng lại solution và giải thích DIP bằng lời của bạn**
>
> Yêu cầu: (1) Xóa toàn bộ thư mục backend/ vừa tạo trong Demo. Tự gõ lại toàn bộ quy trình từ đầu — không copy/paste — theo đúng thứ tự lệnh đã học ở Phần 2. (2) Chạy dotnet list src/TeduMarket.Api/TeduMarket.Api.csproj reference, lưu lại kết quả. (3) Viết 3–5 câu tiếng Việt giải thích: vì sao TeduMarket.Application không có PackageReference nào tới Microsoft.EntityFrameworkCore, dù Handler trong đó sẽ thao tác dữ liệu Course/Order ở các bài sau.
>
> Input: một thư mục trống, chỉ có .NET 10 SDK đã cài sẵn.
>
> Expected output: dotnet build ở thư mục backend/ chạy "Build succeeded"; dotnet list reference của Api trả về đúng 2 dòng TeduMarket.Application và TeduMarket.Infrastructure; đoạn giải thích DIP nhắc đúng đến khái niệm abstraction/interface (không cần đúng từng chữ, nhưng phải thể hiện đúng ý "phụ thuộc vào interface do Application định nghĩa, không phụ thuộc EF Core").
>
> Hint: Nếu dotnet build báo lỗi "type or namespace not found" ở project Api, gần như chắc chắn là thiếu 1 trong 4 lệnh dotnet add reference, hoặc gõ sai đường dẫn .csproj. Dùng dotnet sln list để xem lại danh sách project đã add vào solution.
>
> Solution: đối chiếu từng lệnh với danh sách ở Phần 2 — nếu làm đúng thứ tự (tạo project → add solution → set reference → build), kết quả sẽ khớp 100% với Demo. Giải thích DIP tham khảo lại ví dụ ICourseRepository ở Phần 1.

> **✅ Tóm tắt**
>
> • 4 project cố định xuyên suốt khóa: TeduMarket.Domain, TeduMarket.Application, TeduMarket.Infrastructure, TeduMarket.Api — namespace và tên project giữ nguyên không đổi (mục 7 outline).
>
> • Chiều reference chỉ đi một hướng vào trong: Application → Domain; Infrastructure → Application; Api → Application + Infrastructure. Domain không tham chiếu ai cả.
>
> • DIP ≠ DI: DIP là nguyên tắc kiến trúc (ai phụ thuộc ai qua abstraction do Application định nghĩa), DI (constructor injection...) chỉ là kỹ thuật runtime để nối các abstraction đó lại.
>
> • Project reference của .NET là rào chắn đầu tiên nhưng không phải duy nhất — kỷ luật kiến trúc thật sự sẽ được tự động hóa bằng Architecture Test ở Bài 8.3.
>
> • Deliverable đã đạt: TeduMarket.sln với 4 project rỗng, build sạch, reference đúng chiều — nền tảng cho toàn bộ 71 bài còn lại của khóa.
