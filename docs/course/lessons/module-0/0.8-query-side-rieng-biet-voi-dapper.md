## **1. Vì sao Query side phải tách khỏi Command side (15 phút)**

*Lý thuyết*

Ở bài 0.6, bạn đã có CategoryRepository dùng EF Core để lưu Category — đó là Command side, tối ưu cho tính toàn vẹn nghiệp vụ: change tracking, Aggregate boundary, transaction. Nếu giờ bạn dùng lại chính Category entity đó để trả danh sách category cho client, bạn đang gánh 3 thứ không cần thiết cho việc đọc:

- Change tracking của EF Core — theo dõi từng property dù bạn chỉ đọc để hiển thị, không sửa gì cả
- Ràng buộc theo hình dạng Aggregate — Category entity được thiết kế để bảo vệ invariant khi ghi, không phải để tối ưu hình dạng JSON trả về client
- Query LINQ phức tạp dần theo thời gian khi cần join nhiều bảng, dễ dính N+1 nếu không kiểm soát kỹ Include()

Đây chính là điểm phân biệt CQRS thật với "CQRS hình thức": nhiều dự án chỉ tách tên class thành XxxCommand và XxxQuery nhưng bên dưới cả hai vẫn gọi chung 1 DbContext, chung 1 Entity. Ở khóa này, Query side dùng Dapper — thực thi raw SQL, map thẳng ra DTO phẳng, không qua Aggregate, không qua change tracking. Đó là lý do CQRS tồn tại: hai mô hình dữ liệu khác nhau cho hai mục đích khác nhau, không phải một model dùng chung rồi đặt 2 cái tên.

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi ngược học viên: "Nếu Query cũng dùng EF Core entity Category, thì tách Command/Query để làm gì?" — phần lớn học viên mới học CQRS sẽ trả lời được cấu trúc thư mục nhưng chưa trả lời được lý do kỹ thuật. Đây là lúc chốt lại: tách vì hai bên có yêu cầu tối ưu ngược nhau (ghi cần toàn vẹn, đọc cần tốc độ), không phải tách vì "pattern nói vậy".*

## **2. Cài đặt Dapper và IDbConnectionFactory (10 phút)**

*Demo*

Thêm 2 package vào Infrastructure project — đây là nơi duy nhất được biết đến Dapper và Npgsql, giống hệt nguyên tắc đã áp dụng cho EF Core ở bài 0.6 (Application không phụ thuộc công nghệ cụ thể):

```bash
cd backend/src/TeduMarket.Infrastructure
dotnet add package Dapper
dotnet add package Npgsql
```

Định nghĩa interface ở Application — cùng nguyên tắc Dependency Inversion đã dùng cho ICategoryRepository:

```csharp
// TeduMarket.Application/Common/Interfaces/IDbConnectionFactory.cs
namespace TeduMarket.Application.Common.Interfaces;
 
public interface IDbConnectionFactory
{
    IDbConnection CreateConnection();
}
```

Implement ở Infrastructure, dùng connection string đã cấu hình từ bài 0.6:

```csharp
// TeduMarket.Infrastructure/Persistence/NpgsqlConnectionFactory.cs
namespace TeduMarket.Infrastructure.Persistence;
 
public sealed class NpgsqlConnectionFactory(string connectionString) : IDbConnectionFactory
{
    public IDbConnection CreateConnection() => new NpgsqlConnection(connectionString);
}
```

Đăng ký DI trong extension method DependencyInjection.cs của Infrastructure — đặt cạnh dòng AddDbContext\<AppDbContext> đã có từ bài 0.6:

```
services.AddScoped<IDbConnectionFactory>(_ =>
    new NpgsqlConnectionFactory(configuration.GetConnectionString("Postgres")!));
```

> **📘 Ghi chú giảng viên:** *Dùng chung 1 connection string cho cả EF Core và Dapper là chủ ý — cùng 1 database Postgres, chỉ khác đường truy cập dữ liệu. Học viên hay hỏi "vậy có cần 2 database riêng cho Command và Query không?" — trả lời rõ: CQRS ở mức đọc/ghi tách model trong cùng 1 database là đủ cho quy mô khóa học này; tách hẳn database (CQRS + Event Sourcing toàn phần) là bài toán khác, không nằm trong phạm vi khóa.*

## **3. GetCategoriesQuery — Query + Handler với Dapper (20 phút)**

*Demo + Lab*

Tạo DTO phẳng cho read model — không tái sử dụng Category entity của Command side:

```csharp
// TeduMarket.Application/Categories/Queries/GetCategories/CategoryDto.cs
namespace TeduMarket.Application.Categories.Queries.GetCategories;
 
public sealed record CategoryDto(Guid Id, string Name, DateTime CreatedAtUtc);
```

Query — theo đúng quy ước đặt tên ở mục 7 outline: Get{Thực thể}Query cho trường hợp này (danh sách category không phân trang/filter, khác với GetCoursesListQuery ở Module 1.6 sẽ có phân trang):

```csharp
// TeduMarket.Application/Categories/Queries/GetCategories/GetCategoriesQuery.cs
namespace TeduMarket.Application.Categories.Queries.GetCategories;
 
public sealed record GetCategoriesQuery : IRequest<IReadOnlyList<CategoryDto>>;
```

Handler — mở connection, chạy raw SQL, Dapper tự map cột sang property CategoryDto theo tên (không phân biệt hoa thường):

```csharp
// TeduMarket.Application/Categories/Queries/GetCategories/GetCategoriesQueryHandler.cs
namespace TeduMarket.Application.Categories.Queries.GetCategories;
 
public sealed class GetCategoriesQueryHandler(IDbConnectionFactory connectionFactory)
    : IRequestHandler<GetCategoriesQuery, IReadOnlyList<CategoryDto>>
{
    public async Task<IReadOnlyList<CategoryDto>> Handle(
        GetCategoriesQuery request, CancellationToken cancellationToken)
    {
        const string sql = """
            SELECT
                id             AS "Id",
                name           AS "Name",
                created_at_utc AS "CreatedAtUtc"
            FROM categories
            ORDER BY name
            """;
 
        using var connection = connectionFactory.CreateConnection();
        var command = new CommandDefinition(sql, cancellationToken: cancellationToken);
        var categories = await connection.QueryAsync<CategoryDto>(command);
 
        return categories.ToList();
    }
}
```

Đăng ký endpoint GET trong nhóm endpoint Category đã tạo ở bài 0.7 — chỉ thêm 1 MapGet cạnh MapPost đã có:

```csharp
// TeduMarket.Api/Endpoints/CategoryEndpoints.cs
categoryGroup.MapGet("/", async (ISender sender, CancellationToken cancellationToken) =>
{
    var categories = await sender.Send(new GetCategoriesQuery(), cancellationToken);
    return Results.Ok(categories);
})
.WithName("GetCategories")
.Produces<IReadOnlyList<CategoryDto>>(StatusCodes.Status200OK);
```

> **📘 Ghi chú giảng viên:** *Điểm hay bị hỏi: "cột trong Postgres là snake_case (created_at_utc), tại sao alias phải để trong dấu ngoặc kép "CreatedAtUtc"?" — vì Postgres mặc định hạ chữ thường mọi identifier không có ngoặc kép, nên nếu không có ngoặc kép quanh alias PascalCase, Postgres sẽ trả về cột tên là "createdatutc" (viết liền, chữ thường), Dapper không map đúng vào property CreatedAtUtc. Đây là lỗi rất hay gặp khi học viên quen SQL Server (không phân biệt hoa thường identifier) chuyển sang Postgres.*

> **✏️ Thực hành:** Thêm GetCategoryByIdQuery + Handler dùng Dapper (QueryFirstOrDefaultAsync\<CategoryDto>), truy vấn theo WHERE id = @Id với parameter object new { Id = id }, trả về null nếu không tìm thấy thay vì ném exception. Đăng ký endpoint GET /api/v1/categories/{id:guid} trả 404 khi kết quả null, 200 kèm CategoryDto khi tìm thấy. Hint: dùng CommandDefinition với cả sql, param và cancellationToken cùng lúc để giữ nhất quán với GetCategoriesQueryHandler. Solution tham khảo: xem GetCategoriesQueryHandler ở trên, thay QueryAsync bằng QueryFirstOrDefaultAsync và thêm điều kiện WHERE.

## **4. Benchmark: Dapper vs EF Core LINQ tương đương (15 phút)**

*Demo*

Để chứng minh bằng số liệu thay vì chỉ nói lý thuyết, viết tạm 1 LINQ query EF Core tương đương ngay trong file test hoặc 1 endpoint tạm /api/v1/categories/benchmark-ef (xóa sau khi demo xong, không đưa vào production code):

```csharp
// Chỉ dùng để so sánh, KHÔNG đưa vào Query side chính thức
var stopwatchEf = Stopwatch.StartNew();
var categoriesEf = await dbContext.Categories
    .AsNoTracking()
    .OrderBy(c => c.Name)
    .Select(c => new CategoryDto(c.Id, c.Name, c.CreatedAtUtc))
    .ToListAsync(cancellationToken);
stopwatchEf.Stop();
 
var stopwatchDapper = Stopwatch.StartNew();
var categoriesDapper = await mediator.Send(new GetCategoriesQuery(), cancellationToken);
stopwatchDapper.Stop();
 
logger.LogInformation(
    "EF Core: {EfMs}ms | Dapper: {DapperMs}ms",
    stopwatchEf.ElapsedMilliseconds, stopwatchDapper.ElapsedMilliseconds);
```

Với vài chục dòng dữ liệu category, chênh lệch thời gian sẽ nhỏ, thậm chí không ổn định giữa các lần chạy — đó là kết quả bình thường, không phải bạn làm sai. Điểm cần nhấn mạnh với học viên không phải con số milliseconds ở bảng nhỏ, mà là:

- AsNoTracking() là bắt buộc khi dùng EF Core cho mục đích đọc thuần túy — nếu quên, EF Core vẫn snapshot từng entity để phục vụ change tracking dù bạn không update gì
- SQL do EF Core LINQ sinh ra không phải lúc nào cũng là SQL tối ưu nhất — có thể xem bằng cách log SQL (ToQueryString() hoặc bật logging) rồi so với SQL raw viết tay ở Dapper
- Khi bảng có nhiều join (sẽ gặp ở Module 1.7 — Course Detail tránh N+1), khoảng cách hiệu năng giữa 2 cách càng rõ, đặc biệt khi EF Core sinh ra SQL với nhiều JOIN không cần thiết cho use case chỉ cần vài cột

> **📘 Ghi chú giảng viên:** *Tôi thường chạy demo này với EXPLAIN ANALYZE trực tiếp trên câu SQL raw trong psql hoặc DBeaver để học viên thấy execution plan thật, không chỉ tin lời tôi nói. Lệnh: EXPLAIN ANALYZE SELECT id, name, created_at_utc FROM categories ORDER BY name; — chỉ ra rõ Postgres dùng Seq Scan hay Index Scan, effort thực tế bỏ ra cho từng bước.*

## **Tổng kết**

> Query side dùng Dapper đọc thẳng qua SQL, map ra DTO phẳng — không đi qua Aggregate, không qua EF Core change tracking.
>
> IDbConnectionFactory định nghĩa ở Application, implement ở Infrastructure — giữ đúng Dependency Inversion Principle như đã áp dụng cho ICategoryRepository ở bài 0.6.
>
> Alias cột trong SQL Postgres cần đặt trong dấu ngoặc kép nếu muốn giữ PascalCase khớp với property của DTO, vì Postgres hạ chữ thường identifier không có ngoặc kép theo mặc định.
>
> Benchmark bằng số liệu thật (Stopwatch, EXPLAIN ANALYZE) là cách xác nhận CQRS có lý do tồn tại — không dừng ở giải thích lý thuyết suông.
>
