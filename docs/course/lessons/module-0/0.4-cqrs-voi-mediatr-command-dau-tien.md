## **Nội dung chính**

### **1. Vì sao Command là khung xương, không phải phần thêm vào sau**

*Lý thuyết · 15 phút*

Cách dạy truyền thống thường đi theo trình tự: viết Controller gọi thẳng vào Service hoặc DbContext, chạy được sản phẩm, rồi mới “refactor sang CQRS” ở một module riêng cuối khóa. Vấn đề của cách này là học viên chỉ thấy CQRS như một lớp áo khoác thêm vào bên ngoài, không hiểu được nó thay đổi cách tư duy thiết kế ra sao.

TEDU Market đi ngược lại: ngay từ Module 0, bài 0.4 này, class đầu tiên gọi vào Domain không phải Controller mà là một Command Handler. Endpoint (sẽ viết ở bài 0.7) sau này chỉ đóng vai trò rất mỏng — nhận HTTP request, gói thành Command, gửi qua MediatR. Toàn bộ logic nghiệp vụ nằm trong Handler, tách biệt hoàn toàn khỏi hạ tầng HTTP.

MediatR đóng vai trò Mediator pattern trong tiến trình (in-process): nơi gửi Command (Endpoint, sau này có thể là Background Job ở bài 2.7) không cần biết Handler nào sẽ xử lý, không cần new trực tiếp Handler. MediatR tra trong DI container để tìm đúng Handler implement IRequestHandler\<TRequest, TResponse> tương ứng với Command, rồi gọi phương thức Handle.

Hai interface cốt lõi cần nhớ:

- IRequest\<TResponse> — Command hoặc Query implement interface này, TResponse là kiểu dữ liệu trả về sau khi xử lý xong
- IRequestHandler\<TRequest, TResponse> — nơi chứa logic xử lý thật sự, có đúng một Handler cho mỗi Command hoặc Query

Quy ước đặt tên bắt buộc xuyên suốt khóa học (đã chốt ở mục 7 outline), áp dụng ngay từ bài này:

- Command: {Động từ}{Thực thể}Command — ví dụ CreateCategoryCommand
- Command Handler: {Tên Command}Handler — ví dụ CreateCategoryCommandHandler

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi học viên: “nếu Command chỉ là một class dữ liệu (record), vậy ai gọi Handler?” — phần lớn học viên mới học CQRS nghĩ Command tự gọi Handler. Nhấn mạnh: Command chỉ mang dữ liệu (intent), MediatR mới là nơi tra cứu và gọi Handler qua DI container. Đây là điểm hay bị hiểu lầm nhất trong buổi đầu học CQRS.*

### **2. Cài đặt MediatR — và điều bắt buộc phải biết về license**

*Demo · 10 phút*

MediatR được cài vào project TeduMarket.Application, vì đây là nơi định nghĩa Command, Query và Handler — đúng theo cấu trúc 4 layer đã dựng ở bài 0.2 (Application không phụ thuộc Infrastructure, chỉ phụ thuộc Domain).

```bash
cd backend/src/TeduMarket.Application
dotnet add package MediatR --version 14.2.0
```

Project TeduMarket.Api không cần add package MediatR trực tiếp — vì Api đã có Project Reference tới Application (thiết lập từ bài 0.2), nên nhận package MediatR một cách bắc cầu (transitive) qua NuGet. Đây cũng là một minh chứng thực tế cho việc dựng đúng chiều phụ thuộc ngay từ bài 0.2.

> **⚠️ Lưu ý quan trọng:** Kể từ bản 13.0.0 (phát hành 07/2025), MediatR chuyển sang mô hình dual-license: mã nguồn mở nhưng bắt buộc khai báo license key khi gọi AddMediatR. Có một “Community edition” miễn phí cho công ty có doanh thu dưới 5 triệu USD, tổ chức phi lợi nhuận, mục đích giáo dục và môi trường non-production — đăng ký miễn phí tại mediatr.io. Đây là thay đổi lớn xảy ra sau khi nhiều tài liệu CQRS/MediatR cũ trên mạng được viết, học viên tự tra Google rất dễ gặp hướng dẫn dùng bản 12.x không còn đúng với bản mới nhất.

Cách khai báo license key khi đăng ký MediatR — sẽ làm ở phần 4 của bài này:

- Set trực tiếp trong code qua cfg.LicenseKey — không khuyến khích, dễ lộ key khi commit code lên Git
- Set qua biến môi trường MEDIATR_LICENSE_KEY — MediatR tự đọc nếu không set trong code, phù hợp thực hành cấu hình theo môi trường sẽ học sâu hơn ở Module 9 (production)
- Nếu chưa có key, MediatR vẫn chạy được ở môi trường Development kèm cảnh báo (warning) trong log — không chặn học tập, nhưng bắt buộc phải có key hợp lệ khi chạy production thật

> **📘 Ghi chú giảng viên:** *TEDU Market trong khóa học là dự án học tập/demo nên Community edition là đủ dùng suốt khóa. Nhưng nếu học viên định đưa source code này lên làm sản phẩm thật để kinh doanh, cần tự kiểm tra lại điều khoản doanh thu tại mediatr.io tại thời điểm triển khai — điều khoản license có thể thay đổi theo thời gian, không dạy học viên coi đây là quy tắc cố định vĩnh viễn.*

### **3. CreateCategoryCommand và Handler — đúng quy ước TEDU Market**

*Demo + Lab · 15 phút*

Tạo thư mục theo kiểu vertical slice trong Application layer, gom Command, Handler của cùng một nghiệp vụ vào chung một thư mục — cách tổ chức này sẽ lặp lại cho mọi Command/Query trong suốt khóa học:

```csharp
backend/src/TeduMarket.Application/
  Categories/
    Commands/
      CreateCategory/
        CreateCategoryCommand.cs
        CreateCategoryCommandHandler.cs
```

Command — chỉ mang dữ liệu, dùng record để đảm bảo bất biến (immutable), đúng bản chất của một “intent” đã gửi đi thì không nên sửa lại giữa chừng:

```csharp
namespace TeduMarket.Application.Categories.Commands.CreateCategory;

public sealed record CreateCategoryCommand(string Name) : IRequest<Guid>;
```

Handler — nơi xử lý thật. Ở bài này, Repository (bài 0.6) và Validation Behavior (bài 0.5) chưa tồn tại, nên Handler chỉ gọi factory method Category.Create(name) đã xây ở bài 0.3, rồi log kết quả ra console — đúng như deliverable của bài 0.4 yêu cầu, chưa lưu xuống Postgres:

```csharp
namespace TeduMarket.Application.Categories.Commands.CreateCategory;

public sealed class CreateCategoryCommandHandler : IRequestHandler<CreateCategoryCommand, Guid>
{
    private readonly ILogger<CreateCategoryCommandHandler> _logger;

    public CreateCategoryCommandHandler(ILogger<CreateCategoryCommandHandler> logger)
    {
        _logger = logger;
    }

    public Task<Guid> Handle(CreateCategoryCommand request, CancellationToken cancellationToken)
    {
        var category = Category.Create(request.Name);

        _logger.LogInformation(
            "Đã tạo Category {CategoryId} với tên {CategoryName} " +
            "(chưa lưu DB — sẽ nối Repository ở bài 0.6)",
            category.Id, category.Name);

        return Task.FromResult(category.Id);
    }
}
```

> **📘 Ghi chú giảng viên:** *Nhắc lại nhanh cho học viên: Category.Create(name) đã viết ở bài 0.3, ném ArgumentException khi name rỗng hoặc chỉ toàn khoảng trắng — đó là invariant của Aggregate, nằm trong Domain, không phải trong Handler. Ở bài 0.4 này Handler chưa bắt exception đó, học viên sẽ tự thấy hệ quả ở phần Bài tập thực hành bên dưới — đây là cầu nối tự nhiên sang bài 0.5 (Validation) và bài 0.9 (Global Error Handling).*

Muốn viết gọn hơn, class Handler có thể dùng primary constructor (cú pháp có từ C# 12, không phải tính năng mới của C# 14) thay cho constructor tường minh phía trên. Bài này giữ constructor tường minh để học viên mới làm quen CQRS nhìn rõ luồng Dependency Injection từng bước; có thể giới thiệu primary constructor như một cách viết gọn hơn khi học viên đã quen.

### **4. Đăng ký MediatR trong Api layer**

*Demo · 10 phút*

Việc đăng ký MediatR luôn thực hiện ở composition root — tức Program.cs của TeduMarket.Api, không phải ở Application hay Infrastructure. Quét toàn bộ Handler nằm trong assembly của Application bằng typeof(CreateCategoryCommand).Assembly:

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddMediatR(cfg =>
{
    cfg.RegisterServicesFromAssembly(typeof(CreateCategoryCommand).Assembly);

    // License key: nếu không set ở đây, MediatR tự đọc biến môi trường
    // MEDIATR_LICENSE_KEY. Community edition (miễn phí) là đủ dùng
    // cho TEDU Market ở giai đoạn học/dự án nhỏ — xem phần 2.
});

var app = builder.Build();
```

> **📘 Ghi chú giảng viên:** *Nhấn mạnh: chỉ cần đăng ký assembly của Application, MediatR sẽ tự quét và đăng ký mọi IRequestHandler\<,> tìm thấy trong assembly đó — không cần đăng ký thủ công từng Handler một. Từ bài này về sau, mỗi Command/Query mới viết ra sẽ tự động được MediatR nhận diện, học viên không cần sửa lại đoạn code đăng ký này.*

### **5. Chạy thử — xác nhận luồng chạy qua console**

*Lab · 10 phút*

Endpoint thật (Minimal API) chưa được dạy tới bài 0.7. Để xác nhận Command đã chạy được qua MediatR ngay bây giờ, tạm thời gọi thử ngay trong Program.cs, chỉ khi chạy ở môi trường Development:

```csharp
// TODO: xoá đoạn smoke test này ở bài 0.7 khi đã có endpoint thật
if (app.Environment.IsDevelopment())
{
    using var scope = app.Services.CreateScope();
    var mediator = scope.ServiceProvider.GetRequiredService<IMediator>();

    var categoryId = await mediator.Send(new CreateCategoryCommand("Lập trình Web"));
    Console.WriteLine($"[Smoke test] Category tạo thành công với Id = {categoryId}");
}

app.Run();
```

Chạy dự án và quan sát console:

```bash
cd backend/src/TeduMarket.Api
dotnet run
```

Kết quả mong đợi trong console (log của ILogger sẽ hiện trước, dòng Console.WriteLine hiện sau):

```
info: TeduMarket.Application.Categories.Commands.CreateCategory.CreateCategoryCommandHandler[0]
      Đã tạo Category 3f2e1a9c-... với tên Lập trình Web (chưa lưu DB — sẽ nối Repository ở bài 0.6)
[Smoke test] Category tạo thành công với Id = 3f2e1a9c-...
```

> **📘 Ghi chú giảng viên:** *Điểm kỹ thuật quan trọng cần giải thích kỹ: dùng app.Services.CreateScope() rồi resolve IMediator từ scope.ServiceProvider, KHÔNG resolve thẳng từ app.Services (root provider). IMediator và các Handler được MediatR đăng ký ở scope transient/scoped bên trong container con; resolve trực tiếp từ root provider hiện tại chưa lỗi vì Handler bài này chỉ phụ thuộc ILogger (singleton-safe), nhưng từ bài 0.6 khi Handler cần DbContext (đăng ký scoped) thì resolve từ root provider sẽ ném exception. Xây thói quen dùng scope đúng ngay từ bài 4, tránh phải sửa lại sau.*

## **Bài tập thực hành**

> **✏️ Thực hành — Quan sát lỗi khi vi phạm invariant:** Sửa tạm dòng gọi smoke test thành new CreateCategoryCommand("") (tên rỗng). Chạy lại dotnet run, quan sát ArgumentException từ Category.Create (bài 0.3) văng ra console như thế nào. Ghi lại: hiện tại ai là người bắt lỗi này? Handler có bắt không? Giữ nguyên câu trả lời trong đầu — bài 0.5 (FluentValidation) và bài 0.9 (Global Error Handling) sẽ giải quyết đúng vấn đề này.
>
> **✏️ Thực hành — Tự kiểm tra quy ước đặt tên:** Thử đổi tên class CreateCategoryCommandHandler thành CategoryHandler (bỏ chữ Command). Chạy lại — ứng dụng vẫn chạy bình thường vì MediatR resolve Handler theo interface IRequestHandler\<,>, không theo tên class. Tự trả lời: nếu một đồng nghiệp khác đọc code TeduMarket sau này, đặt tên sai quy ước như vậy có gây khó khăn gì khi họ tìm Handler tương ứng với một Command? Đổi lại đúng tên CreateCategoryCommandHandler trước khi sang bài 0.5.

*Hint: nếu chạy dotnet run mà thấy lỗi “No service for type IMediator has been registered”, kiểm tra lại xem builder.Services.AddMediatR(...) đã được gọi trước app.Build() chưa, và assembly truyền vào RegisterServicesFromAssembly có đúng là assembly chứa CreateCategoryCommand không.*

## **Tổng kết**

> **✅ Tóm tắt:** 
> • Command mang dữ liệu bất biến (record), Handler chứa logic xử lý — MediatR là cầu nối, tra Handler qua DI container dựa trên interface IRequestHandler\<,>, không dựa trên tên class
> • Quy ước đặt tên {Động từ}{Thực thể}Command / {Tên Command}Handler áp dụng từ bài này, giữ nguyên suốt khóa học
> • MediatR 13 trở lên bắt buộc khai báo license key; Community edition miễn phí đủ dùng cho TEDU Market ở giai đoạn học tập
> • Handler ở bài này chỉ log ra console, CHƯA lưu Postgres (chờ Repository ở bài 0.6) và CHƯA validate input (chờ FluentValidation Pipeline Behavior ở bài 0.5)
> • Luôn resolve IMediator qua CreateScope() thay vì root provider, chuẩn bị sẵn cho khi Handler cần dependency scoped như DbContext

Bước tiếp theo: Bài 0.5 — FluentValidation Pipeline Behavior, nơi ValidationBehavior\<TRequest,TResponse> sẽ tự động chặn CreateCategoryCommand có Name rỗng TRƯỚC KHI chạm tới Handler, giải quyết đúng vấn đề học viên vừa quan sát ở phần Bài tập thực hành.
