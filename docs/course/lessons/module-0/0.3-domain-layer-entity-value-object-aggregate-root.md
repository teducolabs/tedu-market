## **Nội dung chính**

### **1. Vì sao Domain layer không chỉ là "POCO + [Required]"**

*Lý thuyết · ~8 phút*

Ở khóa nền tảng "Xây dựng website học trực tuyến với ASP.NET Core", Course là một class rỗng gắn Data Annotation, còn logic kiểm tra nằm rải rác trong Controller. Ở khóa này, bạn đã dựng 4 project Clean Architecture từ bài 0.2 — và TeduMarket.Domain là project không phụ thuộc bất kỳ project nào khác, kể cả EF Core.

Domain layer trả lời một câu hỏi duy nhất: "Nghiệp vụ này có những đối tượng gì, và mỗi đối tượng tự bảo vệ tính đúng đắn của chính nó ra sao?" — không phải "bảng SQL này có cột gì". Ba khái niệm outline yêu cầu ở bài này — Entity, Value Object, Aggregate Root — là 3 câu trả lời khác nhau cho câu hỏi đó.

> **📘 Ghi chú giảng viên:** *Tôi hay mở đầu bằng câu hỏi cho học viên: "Hai Category cùng tên 'Lập trình Backend' nhưng do 2 người tạo ở 2 thời điểm khác nhau — chúng có phải cùng một Category không?" Câu trả lời (không) chính là lý do Entity cần so sánh theo Id chứ không theo nội dung. Giữ câu hỏi này lại, dùng làm cầu nối sang mục 2.*

### **2. Entity — có danh tính (identity)**

*Lý thuyết + code · ~10 phút*

Một Entity được phân biệt bởi Id, không phải bởi giá trị các thuộc tính. Hai Category có Name giống hệt nhau nhưng Id khác nhau vẫn là 2 Category khác nhau — giống hệt 2 người trùng tên vẫn là 2 người khác nhau ngoài đời.

Vì hành vi so sánh này lặp lại ở mọi Entity trong hệ thống (Category, Course, Order, ...), ta viết một lần trong lớp cơ sở dùng chung:

```csharp
// TeduMarket.Domain/Common/Entity.cs
namespace TeduMarket.Domain.Common;
 
// Lớp cơ sở cho mọi Entity trong Domain layer.
// Entity được phân biệt bằng Id (danh tính), KHÔNG phải bằng nội dung thuộc tính.
public abstract class Entity<TId> where TId : notnull
{
    public TId Id { get; protected set; } = default!;
 
    protected Entity()
    {
        // Constructor rỗng dành cho EF Core (bài 0.6) khởi tạo bằng reflection.
    }
 
    protected Entity(TId id)
    {
        Id = id;
    }
 
    public override bool Equals(object? obj)
    {
        if (obj is not Entity<TId> other) return false;
        if (ReferenceEquals(this, other)) return true;
        if (GetType() != other.GetType()) return false;
 
        return Id.Equals(other.Id);
    }
 
    public override int GetHashCode() => Id.GetHashCode();
 
    public static bool operator ==(Entity<TId>? left, Entity<TId>? right)
    {
        if (left is null && right is null) return true;
        if (left is null || right is null) return false;
        return left.Equals(right);
    }
 
    public static bool operator !=(Entity<TId>? left, Entity<TId>? right)
        => !(left == right);
}
```

> **📘 Ghi chú giảng viên:** *Điểm hay bị hỏi: "Sao không dùng record cho Entity luôn, đỡ viết Equals tay?" — vì record sinh Equals theo GIÁ TRỊ property, ngược hoàn toàn với ngữ nghĩa Entity (phải theo Id). Dùng record cho Entity là lỗi khái niệm phổ biến nhất khi mới học DDD — nhấn mạnh chỗ này, học viên sẽ dùng sai nếu bỏ qua.*

### **3. Value Object — bất biến, so sánh theo giá trị**

*Lý thuyết + code · ~10 phút*

Ngược lại với Entity, một Value Object không có Id riêng và không quan tâm "đây có phải cùng một instance hay không" — nó chỉ quan tâm "giá trị bên trong có giống nhau không". Hai CategorySlug cùng giá trị "lap-trinh-backend" luôn được xem là bằng nhau, dù được tạo ở 2 dòng code khác nhau.

C# có sẵn record — sinh Equals/GetHashCode theo giá trị property, đúng ngay bản chất Value Object mà không phải tự viết tay như Entity ở trên:

```csharp
// TeduMarket.Domain/Categories/CategorySlug.cs
namespace TeduMarket.Domain.Categories;
 
// Value Object: không có Id riêng, bất biến (immutable),
// so sánh theo GIÁ TRỊ — record lo phần Equals/GetHashCode cho ta.
public sealed record CategorySlug
{
    public string Value { get; }
 
    private CategorySlug(string value)
    {
        Value = value;
    }
 
    public static CategorySlug FromName(string categoryName)
    {
        // Slug hoá đơn giản cho bài học: chuyển thường, thay khoảng trắng bằng "-".
        // Loại dấu tiếng Việt / chuẩn hoá Unicode sẽ hoàn thiện ở Module 7 (SEO thật) —
        // ở đây trọng tâm là khái niệm Value Object, không phải thuật toán slug.
        var normalized = categoryName.Trim().ToLowerInvariant().Replace(" ", "-");
        return new CategorySlug(normalized);
    }
 
    public override string ToString() => Value;
}
```

> **📘 Ghi chú giảng viên:** *Có 2 lỗi học viên hay mắc khi mới quen Value Object: (1) thêm setter public — phá vỡ tính bất biến, ai đó sửa Value giữa chừng thì mọi nơi đang giữ tham chiếu VO này đều bị ảnh hưởng ngoài ý muốn; (2) validate ở tầng gọi thay vì trong factory method — nếu FromName không tự kiểm tra, ai gọi trực tiếp \`new CategorySlug(...)\` (nếu constructor không private) đều có thể tạo ra VO sai. Nhấn 2 điểm này trước khi qua mục 4.*

### **4. Aggregate Root — ranh giới nhất quán, điểm vào duy nhất**

*Lý thuyết · ~7 phút*

Aggregate Root là một Entity đặc biệt: nó là cửa duy nhất để đọc/sửa mọi thứ bên trong ranh giới của nó. Ở Module 1, Course Aggregate sẽ chứa Lesson (child entity) — muốn thêm Lesson, code bên ngoài PHẢI gọi Course.AddLesson(...), không được insert thẳng vào bảng Lesson. Ở bài 0.3 này, Category chưa có child entity nào, nhưng vẫn kế thừa AggregateRoot để nhất quán ngay từ đầu — đúng tinh thần "CQRS + Clean Architecture là khung xương từ bài đầu tiên" mà khóa học theo đuổi.

Aggregate Root còn có thêm một trách nhiệm mà Entity thường không có: giữ danh sách Domain Event phát sinh trong quá trình xử lý nghiệp vụ (ví dụ CourseOrderedEvent ở Module 2). Ta chuẩn bị sẵn cơ chế này ở bài 0.3, dù Category chưa raise event nào — để không phải sửa lại base class giữa khóa:

```csharp
// TeduMarket.Domain/Common/IDomainEvent.cs
namespace TeduMarket.Domain.Common;
 
// Marker interface THUẦN Domain — không kế thừa MediatR.INotification ở đây.
// Domain layer không được phụ thuộc MediatR (giữ nguyên tắc Dependency
// Inversion đã thiết lập ở bài 0.2: Domain không phụ thuộc gì cả).
// Việc nối IDomainEvent với MediatR sẽ làm ở Infrastructure/Application
// khi cần dispatch event thật, bắt đầu từ Module 2 (Outbox Pattern).
public interface IDomainEvent
{
}
```

```csharp
// TeduMarket.Domain/Common/AggregateRoot.cs
namespace TeduMarket.Domain.Common;
 
public abstract class AggregateRoot<TId> : Entity<TId> where TId : notnull
{
    private readonly List<IDomainEvent> _domainEvents = new();
 
    // Chỉ đọc ra ngoài — không ai add trực tiếp từ bên ngoài Aggregate.
    // Đây chính là "điểm vào duy nhất để đảm bảo invariant" mà outline nhắc tới.
    public IReadOnlyCollection<IDomainEvent> DomainEvents => _domainEvents.AsReadOnly();
 
    protected AggregateRoot()
    {
    }
 
    protected AggregateRoot(TId id) : base(id)
    {
    }
 
    protected void AddDomainEvent(IDomainEvent domainEvent)
        => _domainEvents.Add(domainEvent);
 
    public void ClearDomainEvents() => _domainEvents.Clear();
}
```

> **📘 Ghi chú giảng viên:** *Nếu học viên hỏi "vậy giờ Category có raise event gì không?" — trả lời thẳng là KHÔNG, và đó là chủ ý. Đưa cơ chế Domain Event vào base class từ bài 0.3 chỉ để tránh phải sửa lại AggregateRoot\<TId> (và mọi Aggregate đã kế thừa nó) khi tới Module 2. Đừng demo AddDomainEvent ở bài này kẻo học viên tưởng phải dùng ngay — chưa cần.*

### **5. Domain Exception — invariant bị vi phạm thì báo lỗi thế nào**

*Lý thuyết ngắn + code · ~5 phút*

Outline mục 7 quy định exception nghiệp vụ đặt tên {Thực thể}{LoạiLỗi}Exception, ví dụ CourseNotFoundException. Trước khi có exception cụ thể theo từng entity, ta cần 1 lớp cơ sở dùng chung — Api layer sẽ nhận diện và map lớp này sang ProblemDetails ở bài 0.9:

```csharp
// TeduMarket.Domain/Common/DomainException.cs
namespace TeduMarket.Domain.Common;
 
// Base cho mọi exception nghiệp vụ trong Domain layer.
// Các exception cụ thể theo entity (CourseNotFoundException, ...) sẽ
// kế thừa lớp này từ Module 1 trở đi, đúng quy ước đặt tên ở mục 7.
public abstract class DomainException : Exception
{
    protected DomainException(string message) : base(message)
    {
    }
}
```

### **6. Demo/Lab — Xây dựng Category Aggregate hoàn chỉnh**

*Demo + Lab · ~25 phút*

Ghép mọi thứ vừa học vào 1 Aggregate thật. Category chỉ có 1 invariant duy nhất ở bài này: tên không được rỗng — đúng deliverable outline yêu cầu. Đặt exception theo đúng quy ước mục 7:

```csharp
// TeduMarket.Domain/Categories/CategoryNameRequiredException.cs
namespace TeduMarket.Domain.Categories;
 
using TeduMarket.Domain.Common;
 
// Đúng quy ước đặt tên mục 7 outline: {Thực thể}{LoạiLỗi}Exception.
public sealed class CategoryNameRequiredException : DomainException
{
    public CategoryNameRequiredException()
        : base("Tên Category không được để trống.")
    {
    }
}
```

```csharp
// TeduMarket.Domain/Categories/Category.cs
namespace TeduMarket.Domain.Categories;
 
using TeduMarket.Domain.Common;
 
public sealed class Category : AggregateRoot<Guid>
{
    public string Name { get; private set; } = default!;
    public CategorySlug Slug { get; private set; } = default!;
 
    // Constructor rỗng private — CHỈ EF Core dùng (bài 0.6).
    // Code nghiệp vụ không được gọi trực tiếp new Category().
    private Category()
    {
    }
 
    private Category(Guid id, string name) : base(id)
    {
        SetName(name);
    }
 
    // Factory method — điểm vào duy nhất để tạo Category mới,
    // đảm bảo invariant luôn đúng ngay từ lúc khởi tạo.
    public static Category Create(string name)
    {
        return new Category(Guid.NewGuid(), name);
    }
 
    public void Rename(string name) => SetName(name);
 
    private void SetName(string name)
    {
        if (string.IsNullOrWhiteSpace(name))
        {
            throw new CategoryNameRequiredException();
        }
 
        Name = name.Trim();
        Slug = CategorySlug.FromName(Name);
    }
}
```

> **📘 Ghi chú giảng viên:** *Chỗ hay bị hỏi nhất trong Demo: "Sao Command Handler ở bài 0.4 không tự new Category() rồi gán Name?" — vì làm vậy Handler phải tự nhớ gọi validate, còn factory method Category.Create() đảm bảo KHÔNG THỂ tồn tại một Category có tên rỗng trong hệ thống, dù ai gọi từ đâu. Đây là lý do invariant nằm trong Domain chứ không phải Validation ở Application layer, đúng như outline bài 1.1 sẽ nhắc lại với Course.*

Viết unit test xác nhận invariant hoạt động đúng — đây là deliverable của bài. Theo cấu trúc monorepo (mục 6 outline), project test cho cả Domain lẫn Application logic là TeduMarket.Application.UnitTests; ta tổ chức theo namespace con Domain/... để tách bạch với test Handler sẽ viết từ bài 0.4:

```csharp
// tests/TeduMarket.Application.UnitTests/Domain/Categories/CategoryTests.cs
namespace TeduMarket.Application.UnitTests.Domain.Categories;
 
using TeduMarket.Domain.Categories;
using Xunit;
 
public class CategoryTests
{
    [Fact]
    public void Create_WithValidName_ShouldSucceed()
    {
        var category = Category.Create("Lập trình Backend");
 
        Assert.Equal("Lập trình Backend", category.Name);
        Assert.Equal("lập-trình-backend", category.Slug.Value);
    }
 
    [Theory]
    [InlineData("")]
    [InlineData("   ")]
    [InlineData(null)]
    public void Create_WithEmptyName_ShouldThrowCategoryNameRequiredException(string? invalidName)
    {
        Assert.Throws<CategoryNameRequiredException>(() => Category.Create(invalidName!));
    }
 
    [Fact]
    public void TwoCategories_WithSameName_ShouldNotBeEqual()
    {
        // Entity so sánh theo Id — 2 Category khác Id vẫn KHÁC nhau
        // dù Name giống hệt. Đây là điểm phân biệt với Value Object bên dưới.
        var category1 = Category.Create("Backend");
        var category2 = Category.Create("Backend");
 
        Assert.NotEqual(category1, category2);
    }
 
    [Fact]
    public void TwoSlugs_WithSameValue_ShouldBeEqual()
    {
        // Value Object so sánh theo giá trị — record lo phần này tự động,
        // khác instance nhưng cùng Value vẫn được xem là bằng nhau.
        var slug1 = CategorySlug.FromName("AI cho người mới");
        var slug2 = CategorySlug.FromName("AI cho người mới");
 
        Assert.Equal(slug1, slug2);
    }
}
```

> **📘 Ghi chú giảng viên:** *Chạy \`dotnet test\` ngay trên lớp, để học viên thấy 4 test pass trong vài trăm mili-giây — không đụng DB, không đụng HttpContext. Đây chính là điểm outline bài 8.1/8.2 sẽ nhắc lại và mở rộng: Domain logic test nhanh vì không phụ thuộc hạ tầng. Gieo ấn tượng này sớm ở Module 0 sẽ giúp học viên hiểu vì sao khóa học đầu tư vào kiến trúc ngay từ đầu.*

## **Bài tập thực hành**

Tự thêm 1 invariant thứ hai cho Category, đúng tinh thần "invariant nằm trong Domain, không phải Validation ở Application":

> **✏️ Thực hành:** Category.Name không được dài quá 100 ký tự. Sửa SetName() để ném CategoryNameTooLongException (đặt tên đúng quy ước mục 7) khi vi phạm. Viết thêm ít nhất 2 unit test: 1 test với tên đúng 100 ký tự (phải pass), 1 test với tên 101 ký tự (phải throw).

**Input / Expected output:**

- Input: Category.Create(chuỗi 101 ký tự) → Expected: throw CategoryNameTooLongException.
- Input: Category.Create(chuỗi đúng 100 ký tự) → Expected: tạo thành công, không throw.

**Hint:**

- Kiểm tra length SAU khi đã Trim() — nếu check trước Trim, chuỗi có khoảng trắng thừa ở 2 đầu sẽ bị đếm sai.
- CategoryNameTooLongException nên kế thừa DomainException giống CategoryNameRequiredException — không cần sửa gì ở AggregateRoot hay Entity.

**Solution (gợi ý, đừng mở trước khi tự làm):**

```csharp
private void SetName(string name)
{
    if (string.IsNullOrWhiteSpace(name))
    {
        throw new CategoryNameRequiredException();
    }
 
    var trimmed = name.Trim();
    if (trimmed.Length > 100)
    {
        throw new CategoryNameTooLongException(trimmed.Length);
    }
 
    Name = trimmed;
    Slug = CategorySlug.FromName(Name);
}
```

> **✏️ Bonus (không bắt buộc):** Thêm thuộc tính IsActive (mặc định true) và 2 method Deactivate()/Activate(). Tự đặt invariant hợp lý: ví dụ không cho phép Rename() khi Category đang Deactivate — quyết định invariant này nằm ở đâu (trong Rename() hay SetName()) và giải thích tại sao.

## **Tổng kết**

> **✅ Tóm tắt:** Entity so sánh theo Id (danh tính) — Value Object so sánh theo giá trị property, dùng record cho gọn.Aggregate Root là Entity đặc biệt: điểm vào duy nhất để đảm bảo invariant của cả cụm entity bên trong nó.Invariant (tên không rỗng) đặt trong Domain (factory method + private setter), không phải Validation ở Application layer.Domain layer tuyệt đối không phụ thuộc EF Core hay MediatR — IDomainEvent chỉ là marker interface thuần Domain.Exception nghiệp vụ đặt tên theo mục 7 outline: {Thực thể}{LoạiLỗi}Exception, kế thừa DomainException dùng chung.

### **Entity vs Value Object vs Aggregate Root**

| **Tiêu chí** | **Entity** | **Value Object** | **Aggregate Root** |
|---|---|---|---|
| Có Id riêng? | Có | Không | Có (là 1 Entity) |
| So sánh bằng | Id | Toàn bộ giá trị property | Id (kế thừa từ Entity) |
| Bất biến (immutable)? | Không bắt buộc | Bắt buộc | Không bắt buộc |
| Implement bằng | class + Equals override theo Id | record | class kế thừa AggregateRoot\<TId> |
| Ví dụ trong bài | Category (qua AggregateRoot) | CategorySlug | Category |

**Bước tiếp theo:**

Bài 0.4 — CQRS với MediatR: Command đầu tiên sẽ dùng đúng Category.Create() vừa viết ở đây, đặt trong CreateCategoryCommandHandler. Nếu invariant ở bài 0.3 sai hoặc thiếu, bài 0.4 sẽ lộ ra ngay khi Handler gọi tới — nên đừng bỏ qua phần bài tập phía trên trước khi sang bài kế.
