## **Nội dung chính**

### **1. Vấn đề: validate rải rác thì sớm muộn cũng gãy**

*Lý thuyết · ~5 phút*

Bài 0.4 vừa cho CreateCategoryCommandHandler chạy được qua MediatR — nhưng Handler hiện tại tin tưởng tuyệt đối vào dữ liệu đầu vào. Nếu Name rỗng hoặc quá dài, request vẫn lọt vào tận Category.Create() ở Domain layer, ném ra CategoryNameRequiredException — đúng, nhưng đó là invariant bảo vệ TÍNH TOÀN VẸN dữ liệu, không phải cơ chế trả lỗi 400 thân thiện cho client. Nếu để mỗi Handler tự if-check kiểu:

```
if (string.IsNullOrWhiteSpace(request.Name))
{
    return BadRequest("Name is required");
}
if (request.Name.Length > 100)
{
    return BadRequest("Name too long");
}
// ... 20 Command khác, 20 lần if-check y hệt kiểu này
```

thì có 3 vấn đề thật: (1) code lặp lại ở mọi Handler, (2) format lỗi trả về mỗi người viết một kiểu, (3) dễ quên — Handler thứ 21 không ai nhớ thêm if-check. Đây chính là lý do outline đặt bài Validation ngay sau bài Command đầu tiên, trước cả khi có Endpoint thật (bài 0.7): validate phải là hạ tầng dùng chung ngay từ đầu, không phải thứ thêm vào sau.

### **2. MediatR Pipeline Behavior — middleware cho từng request**

*Lý thuyết · ~5 phút*

MediatR cho phép chèn các lớp "bọc quanh" Handler, gọi là Pipeline Behavior — giống hệt tinh thần Middleware của ASP.NET Core, nhưng chạy ở tầng Application, quanh từng Command/Query, không phải quanh HTTP request. Một Pipeline Behavior implement interface sau:

```csharp
public interface IPipelineBehavior<in TRequest, TResponse>
    where TRequest : notnull
{
    Task<TResponse> Handle(
        TRequest request,
        RequestHandlerDelegate<TResponse> next,
        CancellationToken cancellationToken);
}
```

request là Command/Query đang chạy (ví dụ CreateCategoryCommand), next là "đường ống tiếp theo" — gọi next(cancellationToken) tức là cho request đi tiếp (tới Behavior kế tiếp, hoặc tới Handler nếu đây là Behavior cuối cùng). Không gọi next() tức là chặn request lại ngay tại đây — đúng cơ chế ta cần cho validate: input sai thì KHÔNG cho đi tiếp tới Handler.

> **📘 Ghi chú giảng viên:** *Nếu học viên hỏi "vậy Behavior có biết được nó đang bọc Command nào không?" — trả lời: có, TRequest generic đúng bằng kiểu Command/Query thật (CreateCategoryCommand, GetCoursesQuery...) nhờ MediatR dùng generic variance của C#, không cần switch-case hay reflection thủ công.*

### **3. Viết ValidationBehavior\<TRequest, TResponse>**

*Demo · ~10 phút*

Đặt trong TeduMarket.Application/Common/Behaviors/ — đây là Behavior DÙNG CHUNG cho mọi Command/Query trong toàn hệ thống, không riêng gì Category:

```csharp
// TeduMarket.Application/Common/Behaviors/ValidationBehavior.cs
namespace TeduMarket.Application.Common.Behaviors;
 
using FluentValidation;
using MediatR;
 
public sealed class ValidationBehavior<TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;
 
    public ValidationBehavior(IEnumerable<IValidator<TRequest>> validators)
    {
        _validators = validators;
    }
 
    public async Task<TResponse> Handle(
        TRequest request,
        RequestHandlerDelegate<TResponse> next,
        CancellationToken cancellationToken)
    {
        // Command/Query nào chưa có Validator (vd GetCategoriesQuery đơn giản)
        // thì cho đi thẳng qua, không phạt tất cả vì thiếu validator.
        if (!_validators.Any())
        {
            return await next(cancellationToken);
        }
 
        var context = new ValidationContext<TRequest>(request);
 
        var validationResults = await Task.WhenAll(
            _validators.Select(v => v.ValidateAsync(context, cancellationToken)));
 
        var failures = validationResults
            .SelectMany(result => result.Errors)
            .Where(f => f is not null)
            .ToList();
 
        if (failures.Count != 0)
        {
            // Ném ValidationException của FluentValidation — Api layer sẽ bắt
            // và chuyển thành 400 ValidationProblem (xem mục 5 bên dưới).
            throw new ValidationException(failures);
        }
 
        return await next(cancellationToken);
    }
}
```

> **📘 Ghi chú giảng viên:** *Chỗ hay bị hỏi: "sao không return false/error code, lại throw exception?" — vì Handle() trả về TResponse (ví dụ Guid cho CreateCategoryCommand), không có chỗ nào để nhét "lỗi validate" vào kiểu Guid cả. Throw ValidationException là cách MediatR pipeline dùng để cắt luồng và nhường Api layer xử lý — đúng namespace exception của FluentValidation (FluentValidation.ValidationException), khác với DomainException đã học ở bài 0.3 — hai loại lỗi khác tầng, khác mục đích.*

### **4. CreateCategoryCommandValidator — validate CHO 1 Command cụ thể**

*Demo + Lab · ~10 phút*

ValidationBehavior ở trên là hạ tầng dùng chung — nó tự tìm IValidator\<TRequest> tương ứng qua DI. Giờ viết Validator thật cho CreateCategoryCommand, đặt CÙNG THƯ MỤC với Command/Handler theo mục 6 (vertical slice theo tính năng), đúng tên theo mục 7 outline ({Tên Command}Validator):

```csharp
// TeduMarket.Application/Categories/Commands/CreateCategory/CreateCategoryCommandValidator.cs
namespace TeduMarket.Application.Categories.Commands.CreateCategory;
 
using FluentValidation;
 
public sealed class CreateCategoryCommandValidator : AbstractValidator<CreateCategoryCommand>
{
    public CreateCategoryCommandValidator()
    {
        RuleFor(x => x.Name)
            .NotEmpty()
                .WithMessage("Tên Category không được để trống.")
            .MaximumLength(100)
                .WithMessage("Tên Category tối đa 100 ký tự.");
    }
}
```

(Nhắc lại CreateCategoryCommand từ bài 0.4 để đối chiếu — record đơn giản, không đổi gì:)

```csharp
// TeduMarket.Application/Categories/Commands/CreateCategory/CreateCategoryCommand.cs
namespace TeduMarket.Application.Categories.Commands.CreateCategory;
 
using MediatR;
 
public sealed record CreateCategoryCommand(string Name) : IRequest<Guid>;
```

> **📘 Ghi chú giảng viên:** *Câu hỏi chắc chắn sẽ gặp: "giới hạn 100 ký tự — sao bài 0.3 vừa bắt học viên tự thêm invariant y hệt vào Category.Create()?" — Đây KHÔNG phải trùng lặp thừa, mà là 2 lớp phòng thủ có mục đích khác nhau: CreateCategoryCommandValidator chặn ở CỬA VÀO của Application layer, trả lỗi 400 nhanh, thân thiện, đúng format cho client — trước khi tốn công dựng Category, gọi Repository. Invariant trong Category.Create() (Domain) đảm bảo KHÔNG BAO GIỜ tồn tại 1 Category tên rỗng trong hệ thống, bất kể ai gọi từ đâu — kể cả nếu sau này có Handler khác quên gắn Validator. Một bên là UX/fail-fast, một bên là data integrity tuyệt đối — thiếu 1 trong 2 đều có lỗ hổng thật.*

### **5. Đăng ký FluentValidation + Pipeline Behavior vào DI**

*Demo + Lab · ~10 phút*

Tạo (hoặc mở rộng, nếu bài 0.4 đã có) file DependencyInjection.cs ở TeduMarket.Application — đây là nơi Api layer sẽ gọi để wire toàn bộ Application layer, đúng chiều phụ thuộc đã lập ở bài 0.2 (Api phụ thuộc Application, không ngược lại):

```csharp
// TeduMarket.Application/DependencyInjection.cs
namespace TeduMarket.Application;
 
using FluentValidation;
using MediatR;
using Microsoft.Extensions.DependencyInjection;
using TeduMarket.Application.Common.Behaviors;
 
public static class DependencyInjection
{
    public static IServiceCollection AddApplicationServices(this IServiceCollection services)
    {
        var applicationAssembly = typeof(DependencyInjection).Assembly;
 
        services.AddMediatR(cfg =>
        {
            cfg.RegisterServicesFromAssembly(applicationAssembly);
 
            // Thứ tự đăng ký = thứ tự chạy. ValidationBehavior đứng TRƯỚC mọi
            // Behavior khác sẽ thêm sau (Logging, Transaction...) — input sai
            // thì chặn ngay, không tốn công chạy các Behavior phía sau.
            cfg.AddOpenBehavior(typeof(ValidationBehavior<,>));
        });
 
        // Quét toàn bộ Application assembly, tự tìm mọi class kế thừa
        // AbstractValidator<T> và đăng ký — thêm Validator mới cho Command khác
        // sau này KHÔNG cần sửa file này.
        services.AddValidatorsFromAssemblyContaining<CreateCategoryCommandValidator>(
            ServiceLifetime.Transient);
 
        return services;
    }
}
```

Gọi ở Api layer (Program.cs, bài 0.2 đã dựng khung, giờ nối thêm 1 dòng):

```csharp
// TeduMarket.Api/Program.cs
builder.Services.AddApplicationServices();
```

### **6. Test end-to-end — thấy được 400 thật**

*Lab · ~10 phút*

Module 0 chưa có Minimal API Endpoint chính thức (Endpoint Group đúng chuẩn sẽ làm ở bài 0.7). Để CHỨNG MINH ValidationBehavior hoạt động qua HTTP ngay trong bài này — đúng tinh thần "chạy được thật, không dừng ở lý thuyết suông" — thêm tạm 1 endpoint tối giản thẳng trong Program.cs:

```csharp
// TeduMarket.Api/Program.cs
// ⚠️ ENDPOINT TẠM THỜI — chỉ để demo Pipeline Behavior chạy qua HTTP.
// Bài 0.7 sẽ thay bằng Endpoint Group chuẩn (map theo mục 7: /api/v1/categories),
// bài 0.9 sẽ dọn khối try/catch này vào Exception Handling Middleware dùng chung.
app.MapPost("/api/v1/categories", async (
    CreateCategoryCommand command,
    ISender sender,
    CancellationToken cancellationToken) =>
{
    try
    {
        var categoryId = await sender.Send(command, cancellationToken);
        return Results.Created($"/api/v1/categories/{categoryId}", new { id = categoryId });
    }
    catch (ValidationException ex)
    {
        var errors = ex.Errors
            .GroupBy(e => e.PropertyName)
            .ToDictionary(g => g.Key, g => g.Select(e => e.ErrorMessage).ToArray());
 
        return Results.ValidationProblem(errors);
    }
});
```

Chạy dotnet run rồi test bằng curl — trường hợp input sai:

```bash
curl -i -X POST http://localhost:5000/api/v1/categories \
  -H "Content-Type: application/json" \
  -d '{"name": ""}'
 
# HTTP/1.1 400 Bad Request
# Content-Type: application/problem+json
# {
#   "title": "One or more validation errors occurred.",
#   "status": 400,
#   "errors": {
#     "Name": ["Tên Category không được để trống."]
#   }
# }
```

Trường hợp input đúng — request đi xuyên qua ValidationBehavior, tới thẳng CreateCategoryCommandHandler đã viết ở bài 0.4, trả về 201 Created kèm Id:

```bash
curl -i -X POST http://localhost:5000/api/v1/categories \
  -H "Content-Type: application/json" \
  -d '{"name": "Lập trình Backend"}'
 
# HTTP/1.1 201 Created
# { "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6" }
```

> **📘 Ghi chú giảng viên:** *Results.ValidationProblem() tự sinh đúng cấu trúc RFC 7807 (Problem Details) — đây là bản XEM TRƯỚC của những gì bài 0.9 (Global Error Handling & ProblemDetails) sẽ làm CHUẨN HÓA cho MỌI loại lỗi trong hệ thống (not found, exception, validation...), không chỉ validate. Nói rõ với học viên: khối try/catch ngay trong Endpoint ở bài này là bước đệm để thấy kết quả ngay, KHÔNG phải pattern cuối cùng — nếu để mỗi Endpoint tự try/catch thì lại quay về đúng vấn đề "lặp code" đã nói ở mục 1, nên bài 0.9 sẽ dọn hết vào 1 Exception Handling Middleware duy nhất.*

## **Tổng kết**

> **✅ Tóm tắt:** ValidationBehavior\<TRequest,TResponse> là Pipeline Behavior dùng CHUNG cho toàn hệ thống, tự tìm IValidator\<TRequest> tương ứng qua DI — thêm Command mới KHÔNG cần sửa lại Behavior này.

### **Recap 4 điểm chính**

- Pipeline Behavior = middleware ở tầng Application, bọc quanh Handler qua next() — không gọi next() là chặn request.
- Validator ({Tên Command}Validator) chỉ chứa rule cho 1 Command cụ thể — tách biệt hạ tầng (Behavior) khỏi nghiệp vụ (Rule).
- Validate ở Application layer (fail-fast, UX) khác vai trò với invariant ở Domain layer (bài 0.3 — bảo vệ tính toàn vẹn tuyệt đối) — cần cả hai, không phải trùng lặp.
- MediatR từ v13 là dual-license, free cho quy mô TEDU Market — đăng ký license key qua biến môi trường, không hard-code trong Application layer.

### **So sánh 2 lớp validate đã học**

| **Tiêu chí** | **CreateCategoryCommandValidator (Application)** | **Category.Create() invariant (Domain — bài 0.3)** |
|---|---|---|
| Chạy khi nào | Trước khi vào Handler (Pipeline Behavior) | Ngay khi khởi tạo Aggregate, bất kể ai gọi |
| Mục đích | Fail-fast, trả lỗi 400 thân thiện cho client | Đảm bảo dữ liệu KHÔNG BAO GIỜ sai, dù entry point nào |
| Công cụ | FluentValidation (AbstractValidator) | if-check thuần C# trong factory method |
| Có thể bỏ qua? | Có, nếu Handler nào đó không gắn Validator (rủi ro) | Không — đây là tuyến phòng thủ cuối cùng |

**Bước tiếp theo:**

Bài 0.6 — Infrastructure: EF Core DbContext (Write Model) sẽ implement ICategoryRepository thật, để CreateCategoryCommandHandler không chỉ log console mà lưu được Category xuống Postgres. ValidationBehavior vừa viết ở bài này sẽ tự động áp dụng luôn cho mọi Command mới từ giờ — kể cả Command của Order, Payment ở Module 2 — không cần viết lại.

## **Phụ lục — Cheatsheet**

### **FluentValidation — rule thường dùng**

| **Rule** | **Ý nghĩa** |
|---|---|
| NotEmpty() | Không null, không chuỗi rỗng, không chỉ toàn khoảng trắng |
| NotNull() | Không null (không check rỗng/whitespace) |
| MaximumLength(n) / MinimumLength(n) | Giới hạn độ dài chuỗi |
| GreaterThan(x) / LessThanOrEqualTo(x) | So sánh số |
| Must(predicate) | Rule tùy biến bằng Func\<T,bool> |
| MustAsync(predicate) | Rule bất đồng bộ (vd check trùng DB) — cần ValidateAsync, không dùng Validate() |
| .WithMessage(text) | Custom message tiếng Việt thay vì message mặc định tiếng Anh |

### **Ghi chú license MediatR (nhắc lại nhanh)**

- Miễn phí: cá nhân/công ty dưới 5 triệu USD doanh thu/năm, phi lợi nhuận, mục đích giáo dục, môi trường non-production.

- Không set key: vẫn chạy bình thường, chỉ log cảnh báo — không chặn tính năng.
