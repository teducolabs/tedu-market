## **Nội dung chính**

### **1. Vì sao container hóa hạ tầng dev ngay từ Module 0**

*Thời lượng: 5 phút | Loại: Lý thuyết*

Từ bài 0.6 đến 0.9, bạn đã kết nối AppDbContext tới một Postgres đang chạy sẵn trên máy — có thể là bản cài trực tiếp, có thể là container bạn tự docker run tạm. Cách này chạy được, nhưng có 3 vấn đề sẽ lộ ra ngay khi bạn làm việc nhóm hoặc chuyển máy:

- "Chạy được trên máy tôi" — version Postgres, port, username/password khác nhau giữa các máy trong team, không ai tái tạo lại đúng môi trường của người khác.
- Không có Redis sẵn — Module 4 (Rate Limiting) và các module sau cần Redis, nếu không chuẩn hóa từ bây giờ, mỗi người sẽ tự cài theo cách riêng.
- Không khớp với production — Module 9 sẽ dùng docker-compose.prod.yml với Postgres + Redis + Seq chạy container hóa hoàn toàn. Nếu dev environment không dùng Docker, bạn học 2 cách vận hành hạ tầng khác nhau cho cùng 1 dự án.

Giải pháp: một file docker-compose.yml đặt ở thư mục gốc repo (ngang hàng với backend/ và frontend/ theo đúng cấu trúc monorepo đã chốt ở mục 6 outline), định nghĩa chính xác Postgres + Redis mà cả team dùng chung. Ai clone repo về, chạy đúng 1 lệnh là có hạ tầng giống hệt nhau.

> **📘 Ghi chú giảng viên:** *Tôi hay hỏi học viên ở đây: "Nếu không có healthcheck, .NET app cố kết nối Postgres ngay khi container vừa start thì chuyện gì xảy ra?" — câu trả lời đúng là container Postgres báo "running" rất sớm nhưng Postgres bên trong có thể chưa sẵn sàng nhận connection, dẫn đến lỗi "Connection refused" ngẫu nhiên. Đây chính là lý do healthcheck + depends_on condition tồn tại, không phải chi tiết vặt vãnh.*

### **2. Viết docker-compose.yml cho Postgres + Redis**

*Thời lượng: 10 phút | Loại: Demo*

Đặt 2 file tại thư mục gốc solution: .env (không commit — chứa secret) và docker-compose.yml (commit vào git).

**File .env:**

```
POSTGRES_USER=tedumarket
POSTGRES_PASSWORD=Tedu@Market2026
POSTGRES_DB=tedumarket_dev
POSTGRES_PORT=5432
REDIS_PORT=6379
```

**File docker-compose.yml:**

```yaml
# docker-compose.yml — môi trường dev cho TEDU Market
# Compose Specification hiện tại không còn cần khai báo "version:" ở đầu file
services:
  postgres:
    image: postgres:17-alpine
    container_name: tedumarket-postgres-dev
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    ports:
      - "${POSTGRES_PORT}:5432"
    volumes:
      - tedumarket_pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 10
      start_period: 10s
 
  redis:
    image: redis:8-alpine
    container_name: tedumarket-redis-dev
    restart: unless-stopped
    ports:
      - "${REDIS_PORT}:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
 
volumes:
  tedumarket_pgdata:
```

> **📘 Ghi chú giảng viên:** *Redis chưa được code nào dùng tới ở Module 0 hay Module 1 — tôi luôn nói rõ điều này với học viên để tránh thắc mắc "sao thêm Redis mà chưa thấy dùng đâu?". Ta cấu hình sẵn ở đây vì Rate Limiting (bài 4.4) và một phần hạ tầng Hangfire/cache về sau sẽ cần, thêm ngay từ Module 0 để tránh mỗi module lại sửa docker-compose.yml một lần.*

Khởi động và kiểm tra trạng thái:

```bash
docker compose up -d
docker compose ps
# Cột STATUS phải hiện "healthy" cho cả postgres và redis, không chỉ "running"
```

### **3. Healthcheck & depends_on đúng chuẩn**

*Thời lượng: (lồng trong phần demo trên) | Loại: Demo*

Điểm hay bị bỏ qua: healthcheck chỉ có tác dụng đầy đủ khi có service khác depends_on vào nó với điều kiện service_healthy. Ở giai đoạn Module 0, backend .NET vẫn chạy trực tiếp trên máy host (chưa Dockerize — việc đó để dành Module 9.1), nên depends_on chưa áp dụng cho chính API. Nhưng cú pháp này bạn sẽ dùng lại nguyên vẹn ở bài 9.3 khi ghép API vào cùng docker-compose.prod.yml:

```bash
# Trích trước — sẽ dùng đầy đủ ở bài 9.3, không cần thêm vào file dev ở bài này
api:
  depends_on:
    postgres:
      condition: service_healthy
    redis:
      condition: service_healthy
```

Ở bài này, healthcheck phục vụ mục đích thực tế hơn: cho bạn và cả team một tín hiệu rõ ràng — "Postgres đã sẵn sàng nhận kết nối" — thay vì đoán mò hoặc chèn sleep 5 vào script như cách làm cũ.

### **4. Trỏ connection string & chạy migration**

*Thời lượng: 10 phút | Loại: Lab*

Cập nhật appsettings.Development.json trong TeduMarket.Api (kế thừa cấu hình AppDbContext đã có từ bài 0.6):

```json
{
  "ConnectionStrings": {
    "Default": "Host=localhost;Port=5432;Database=tedumarket_dev;Username=tedumarket;Password=Tedu@Market2026;Include Error Detail=true"
  }
}
```

Chạy migration từ Infrastructure, dùng Api làm startup project (cách đơn giản đủ dùng ở giai đoạn này — bài 1.5 sẽ giải thích khi nào cách này không còn đủ và cần chuyển sang IDesignTimeDbContextFactory):

```bash
dotnet ef migrations add InitialCreate \
  --project src/TeduMarket.Infrastructure \
  --startup-project src/TeduMarket.Api
 
dotnet ef database update \
  --project src/TeduMarket.Infrastructure \
  --startup-project src/TeduMarket.Api
```

> **📘 Ghi chú giảng viên:** *Nếu học viên đã tạo migration từ trước (khi còn dùng Postgres cài tay), migration cũ vẫn áp dụng được bình thường vì schema không đổi — chỉ đổi nơi Postgres chạy. Nếu có bạn nào gặp lỗi "role tedumarket does not exist", 99% là do đã có volume Postgres cũ từ lần chạy docker run thử nghiệm trước đây với user khác — hướng dẫn các bạn đó docker compose down -v để xóa sạch rồi up lại.*

### **5. Verify toàn bộ luồng CRUD Category end-to-end**

*Thời lượng: 5 phút | Loại: Lab*

Chạy API và gọi lại đúng 2 endpoint đã xây ở bài 0.7 (Command) và 0.8 (Query) — lần này dữ liệu thật sự nằm trong Postgres container:

```bash
dotnet run --project src/TeduMarket.Api
 
# Tạo Category (bài 0.7)
curl -X POST http://localhost:5000/api/v1/categories \
  -H "Content-Type: application/json" \
  -d '{"name":"Backend .NET"}'
# Kỳ vọng: 201 Created
 
# Lấy danh sách Category qua Dapper (bài 0.8)
curl http://localhost:5000/api/v1/categories
# Kỳ vọng: 200 OK, thấy đúng Category vừa tạo
```

Nếu cả 2 lệnh curl trả đúng như trên, nghĩa là toàn bộ chuỗi Endpoint → MediatR → ValidationBehavior → Handler → EF Core (ghi) / Dapper (đọc) → Postgres thật → ProblemDetails (khi lỗi) đã chạy thông suốt trên hạ tầng Docker — đúng deliverable của cả Module 0.

## **Bài tập thực hành**

> **✏️ Thực hành: Xác nhận dữ liệu bền vững qua volume**
>
> Bước 1: Tạo thêm 2-3 Category qua POST /api/v1/categories.
>
> Bước 2: Chạy docker compose down (không thêm -v) rồi docker compose up -d lại.
>
> Bước 3: Gọi lại GET /api/v1/categories — dữ liệu phải còn nguyên nhờ volume tedumarket_pgdata.
>
> Bước 4: Chạy tiếp docker compose down -v rồi up lại, gọi GET lần nữa — lần này danh sách phải rỗng.
>
> Hint: nếu bước 3 dữ liệu bị mất, kiểm tra lại volumes: trong docker-compose.yml có đúng tên và đường dẫn mount /var/lib/postgresql/data hay chưa.
>
> Mục tiêu: phân biệt rõ down (giữ volume) và down -v (xóa volume) — lỗi hay gặp nhất khi học viên tưởng down là xóa sạch dữ liệu.
