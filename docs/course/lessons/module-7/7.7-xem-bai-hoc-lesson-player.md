## **Nội dung chính**

### **1. Vì sao "ẩn nút" không phải là bảo mật**

*Thời lượng: 7 phút | Loại: Lý thuyết*

Ở bài 7.6, bạn đã dùng Enrollment để quyết định route /my-courses có hiển thị khóa học nào. Nhưng đó chỉ là UX — quyết định hiển thị cái gì trên giao diện. Route /learn/[courseId]/[lessonId] vẫn tồn tại thật trong Next.js, và bất kỳ ai biết đúng URL (kể cả người đã đăng nhập nhưng chưa mua khóa học đó) đều có thể gõ thẳng vào trình duyệt.

Nếu Next.js Server Component chỉ kiểm tra Enrollment để quyết định render hay không, mà API GET /api/v1/courses/{courseId}/lessons/{lessonId} phía sau không tự kiểm tra lại, thì ai có access token hợp lệ (chỉ cần đăng nhập, không cần đã mua) vẫn gọi thẳng API và lấy được nội dung bài học — bỏ qua hoàn toàn lớp UI.

Nguyên tắc bắt buộc: authorization phải nằm ở Resource Server, tức là ở Api layer — không phải chỉ ở client. Đây chính là lý do bài 3.9 đã cấu hình CORS cho nhiều client (React Admin, Next.js): API là điểm chặn chung cho mọi client, kể cả client không phải Next.js (ví dụ ai đó tự viết script gọi thẳng API).

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi học viên: "Nếu em test bằng UI thấy nút bị ẩn, em có dám kết luận là đã bảo mật xong chưa?" — đa số trả lời có, và đó chính là lỗi. Tôi thường ví route Next.js giống như cửa hàng khóa cửa chính nhưng cửa sau (API) vẫn để ngỏ. Đây là biến thể của lỗi kinh điển gọi là thiếu kiểm soát truy cập ở tầng đối tượng — rất phổ biến trong các hệ thống có UI 'trông có vẻ an toàn'.*

### **2. Query side: GetLessonDetailQuery kiểm tra Enrollment**

*Thời lượng: 8 phút | Loại: Demo*

Query side vẫn theo đúng khung xương từ Module 0.8 và bài 1.7: dùng Dapper raw SQL, không đụng vào Aggregate của Command side. Điểm khác ở bài này: trước khi lấy nội dung Lesson, Handler phải xác nhận UserId hiện tại có Enrollment active cho Course chứa Lesson đó.

Định nghĩa exception nghiệp vụ mới ở Domain layer, theo đúng quy ước {Thực thể}{LoạiLỗi}Exception ở mục 7 outline. Ở đây tôi đặt tên EnrollmentRequiredException thay vì EnrollmentNotFoundException — vì về ngữ nghĩa nghiệp vụ, vấn đề không phải là "Enrollment không tồn tại" (nghe như lỗi dữ liệu), mà là "cần có Enrollment mới được xem" (đúng bản chất kiểm soát truy cập). Tên exception phản ánh đúng lý do nghiệp vụ sẽ giúp Api layer map sang status code đúng hơn ở bước sau.

```csharp
// TeduMarket.Domain/Exceptions/EnrollmentRequiredException.cs
namespace TeduMarket.Domain.Exceptions;
 
public sealed class EnrollmentRequiredException : Exception
{
    public Guid CourseId { get; }
 
    public EnrollmentRequiredException(Guid courseId)
        : base($"Yêu cầu Enrollment cho CourseId={courseId} để xem nội dung bài học.")
    {
        CourseId = courseId;
    }
}
```

Query và Handler đặt trong TeduMarket.Application, đúng namespace TeduMarket.Application đã quy ước, cùng nhóm thư mục với các Query khác của Course/Lesson:

```csharp
// TeduMarket.Application/Lessons/Queries/GetLessonDetailQuery.cs
namespace TeduMarket.Application.Lessons.Queries;
 
public sealed record GetLessonDetailQuery(Guid CourseId, Guid LessonId, Guid UserId)
    : IRequest<LessonDetailDto>;
 
public sealed class GetLessonDetailQueryHandler(IDbConnection db)
    : IRequestHandler<GetLessonDetailQuery, LessonDetailDto>
{
    public async Task<LessonDetailDto> Handle(
        GetLessonDetailQuery request, CancellationToken ct)
    {
        // 1) Kiểm tra Enrollment TRƯỚC — không đụng vào bảng Lesson nếu chưa qua bước này
        const string enrollmentSql = """
            SELECT EXISTS (
                SELECT 1 FROM enrollments
                WHERE course_id = @CourseId
                  AND user_id = @UserId
                  AND status = 'Active'
            )
            """;
 
        var isEnrolled = await db.ExecuteScalarAsync<bool>(
            enrollmentSql, new { request.CourseId, request.UserId });
 
        if (!isEnrolled)
            throw new EnrollmentRequiredException(request.CourseId);
 
        // 2) Đã xác nhận quyền truy cập — lấy nội dung Lesson (multi-mapping như bài 1.7)
        const string lessonSql = """
            SELECT l.id, l.title, l.content_url, l.duration_seconds, l.\"order\",
                   c.id, c.title AS course_title
            FROM lessons l
            JOIN courses c ON c.id = l.course_id
            WHERE l.id = @LessonId AND l.course_id = @CourseId
            """;
 
        var lesson = await db.QueryAsync<LessonDetailDto, CourseSummaryDto, LessonDetailDto>(
            lessonSql,
            (l, c) => l with { Course = c },
            new { request.LessonId, request.CourseId },
            splitOn: "id");
 
        return lesson.FirstOrDefault()
            ?? throw new LessonNotFoundException(request.LessonId);
    }
}
```

So sánh nhanh với bài 3.8 (Resource-based Authorization): ở đó bạn dùng IAuthorizationHandler + CourseOwnerRequirement vì có một Aggregate .NET (Course) thật để authorize trên Command side. Ở đây, Query side đọc thẳng Dapper, không có object Aggregate nào để gắn Requirement — nên kiểm tra Enrollment ngay trong Handler là cách gọn và đúng layer hơn, dù cùng chung một tư duy: quyền truy cập phụ thuộc vào dữ liệu quan hệ cụ thể (User này có Enrollment cho Course này không), không chỉ phụ thuộc vào Role tĩnh như Policy ở bài 3.7.

> **📘 Ghi chú giảng viên:** *Điểm học viên hay hỏi: "Sao không check Enrollment bằng [Authorize(Policy=...)] cho gọn như 3.7?" — Vì Policy-based Authorization chỉ biết Role/claims tĩnh có sẵn trong token (Student, Instructor...), không biết được "User A có Enrollment cho Course B cụ thể hay không" — thông tin đó chỉ có trong database, phải query runtime. Đây là ranh giới thật giữa Policy-based và Resource-based mà bài 3.7–3.8 đã đặt nền, giờ áp dụng vào ngữ cảnh Query side.*

### **3. Api layer: map EnrollmentRequiredException sang 403, không phải 404**

*Thời lượng: 5 phút | Loại: Demo*

Mở rộng đúng middleware xử lý exception tập trung đã dựng ở bài 0.9 (IExceptionHandler, kết hợp AddProblemDetails() + UseExceptionHandler() chuẩn .NET 10) — không viết middleware mới:

```csharp
// TeduMarket.Api/Middleware/GlobalExceptionHandler.cs
public sealed class GlobalExceptionHandler : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext, Exception exception, CancellationToken ct)
    {
        var (status, title) = exception switch
        {
            CourseNotFoundException => (StatusCodes.Status404NotFound, "Không tìm thấy khóa học"),
            LessonNotFoundException => (StatusCodes.Status404NotFound, "Không tìm thấy bài học"),
            EnrollmentRequiredException => (StatusCodes.Status403Forbidden, "Yêu cầu quyền truy cập"),
            _ => (StatusCodes.Status500InternalServerError, "Đã xảy ra lỗi")
        };
 
        httpContext.Response.StatusCode = status;
 
        await httpContext.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = status,
            Title = title,
            Detail = exception.Message,
            Instance = httpContext.Request.Path,
            Type = "https://api.tedumarket.dev/errors/enrollment-required"
        }, ct);
 
        return true;
    }
}
```

Vì sao 403 Forbidden chứ không phải 404 Not Found: 404 phù hợp khi bạn muốn giấu luôn sự tồn tại của tài nguyên khỏi người không có quyền biết (ví dụ hồ sơ riêng tư). Nhưng Course ở TEDU Market là công khai — ai cũng thấy được ở trang /courses/[slug] (bài 7.3) mà không cần đăng nhập. Ở đây server hoàn toàn "biết" danh tính người gọi (đã có access token hợp lệ) và biết Course tồn tại, chỉ là từ chối quyền xem nội dung — đúng ngữ nghĩa HTTP của 403.

```csharp
// TeduMarket.Api/Endpoints/LessonEndpoints.cs
app.MapGet("/api/v1/courses/{courseId:guid}/lessons/{lessonId:guid}",
    async (Guid courseId, Guid lessonId, ClaimsPrincipal user, ISender sender) =>
    {
        var userId = Guid.Parse(user.FindFirstValue("sub")!);
        var result = await sender.Send(
            new GetLessonDetailQuery(courseId, lessonId, userId));
        return Results.Ok(result);
    })
    .RequireAuthorization()
    .WithName("GetLessonDetail")
    .Produces<LessonDetailDto>(StatusCodes.Status200OK)
    .ProducesProblem(StatusCodes.Status403Forbidden);
```

Endpoint chỉ cần .RequireAuthorization() (yêu cầu đã đăng nhập, đúng claims 'sub' đã cấu hình ở bài 3.5), không cần Policy riêng — vì việc kiểm tra "có Enrollment cụ thể hay không" đã nằm trong Handler ở bước 2, đúng phân công: Policy chặn theo Role tĩnh, Handler chặn theo dữ liệu runtime.

### **4. Next.js Server Component: trang xem bài học**

*Thời lượng: 10 phút | Loại: Demo + Lab*

Route: apps/web/app/learn/[courseId]/[lessonId]/page.tsx. Khác với trang listing /courses (bài 7.2, dùng ISR revalidate) — trang này phụ thuộc quyền truy cập theo từng User nên phải luôn dynamic, không được cache chung cho mọi người:

```tsx
// apps/web/app/learn/[courseId]/[lessonId]/page.tsx
import { cookies } from "next/headers";
import { redirect } from "next/navigation";
import { getLessonDetail } from "@tedu-market/api-client";
 
export const dynamic = "force-dynamic"; // không cache — phụ thuộc quyền theo user
 
export default async function LessonPage({
  params,
}: {
  params: Promise<{ courseId: string; lessonId: string }>;
}) {
  const { courseId, lessonId } = await params;
  const cookieStore = await cookies();
  const accessToken = cookieStore.get("tedu_session")?.value;
 
  if (!accessToken) {
    redirect(`/login?returnTo=/learn/${courseId}/${lessonId}`);
  }
 
  const { data, error } = await getLessonDetail({
    path: { courseId, lessonId },
    headers: { Authorization: `Bearer ${accessToken}` },
    cache: "no-store",
  });
 
  if (error) {
    // 403: đã đăng nhập nhưng chưa mua khóa học này
    if (error.status === 403) {
      redirect(`/courses/${courseId}?denied=true`);
    }
    // 404: bài học/khóa học không tồn tại thật
    if (error.status === 404) {
      redirect("/not-found");
    }
    throw error;
  }
 
  return <LessonPlayer lesson={data} />;
}
```

Lưu ý cách lấy session: giống bài 7.4, token nằm trong cookie HttpOnly do route handler phía server set khi đăng nhập — không đọc từ localStorage. force-dynamic bắt buộc vì mỗi request phải được đánh giá lại quyền truy cập theo đúng User hiện tại, không được tái sử dụng response đã cache cho user khác.

Khi bị 403, tôi chọn redirect về lại trang chi tiết khóa học kèm query ?denied=true (để hiển thị thông báo "Bạn cần mua khóa học này để xem bài học" + nút mua ngay) thay vì dùng notFound() — vì notFound() sẽ trả về trang 404 gây hiểu nhầm là khóa học không tồn tại, trong khi nó tồn tại thật và học viên có thể mua ngay tại đó. Đây chính là hệ quả tự nhiên của quyết định dùng 403 thay vì 404 ở Section 3 — hai lớp (Api và Next.js) phải nhất quán với nhau.

> **📘 Ghi chú giảng viên:** *Học viên mới hay quên export const dynamic = "force-dynamic" và ngạc nhiên vì sao Next.js cache mất nội dung Lesson của user khác vào response chung. Tôi thường demo trực tiếp: bỏ dòng đó đi, build production, rồi dùng 2 tài khoản khác nhau để cho học viên tự thấy lỗi trước khi giải thích lý do.*

## **Bài tập / Thực hành**

> **✏️ Thực hành:** Tự kiểm chứng rằng bạn đã chặn đúng ở API, không chỉ ở UI. Thực hiện đúng thứ tự các bước sau và ghi lại kết quả từng bước.

Input: 1 tài khoản Student CHƯA có Enrollment nào (đăng ký mới, không mua khóa học nào), 1 CourseId + LessonId bất kỳ đã có sẵn trong hệ thống.

- Bước 1: Đăng nhập bằng tài khoản Student chưa mua khóa học. Vào thẳng URL /learn/{courseId}/{lessonId} bằng cách gõ trực tiếp trên trình duyệt (không qua link trong app).
- Bước 2: Kỳ vọng — bạn phải bị redirect về /courses/{courseId}?denied=true, KHÔNG thấy nội dung bài học.
- Bước 3: Mở /scalar (bài 4.2), đăng nhập OAuth2 flow bằng đúng tài khoản Student đó để lấy access token, hoặc lấy token từ cookie tedu_session qua DevTools.
- Bước 4: Gọi thẳng GET /api/v1/courses/{courseId}/lessons/{lessonId} kèm Bearer token đó (qua Scalar hoặc curl).
- Bước 5: Kỳ vọng — response phải là 403 Forbidden với ProblemDetails đúng Type https://api.tedumarket.dev/errors/enrollment-required, KHÔNG phải 200 kèm nội dung bài học.

Expected output: Bước 2 và Bước 5 đều phải chặn thành công. Nếu Bước 5 trả về 200 kèm data — nghĩa là bạn chỉ mới chặn ở Next.js (Bước 2 pass do redirect ở tầng UI), còn API phía sau vẫn hở. Đây chính là lỗi mà Section 1 đã cảnh báo — phải quay lại kiểm tra Handler ở Section 2 có thực sự được gọi và ném EnrollmentRequiredException đúng chưa.

Hint: nếu Bước 5 vẫn trả 200, kiểm tra 2 khả năng phổ biến nhất: (1) SQL kiểm tra Enrollment dùng sai UserId — quên lấy đúng claim "sub" từ ClaimsPrincipal, lấy nhầm claim khác; (2) Endpoint quên gọi qua GetLessonDetailQuery mà gọi thẳng 1 query khác không có bước kiểm tra Enrollment (thường do copy-paste từ 1 Query cũ chưa được cập nhật).

Solution: đối chiếu đúng GetLessonDetailQueryHandler ở Section 2 — thứ tự bắt buộc là kiểm tra Enrollment TRƯỚC, ném exception ngay nếu không có, chỉ query nội dung Lesson SAU khi đã xác nhận quyền.

>
> **✅** GetLessonDetailQueryHandler kiểm tra Enrollment TRƯỚC khi truy vấn nội dung Lesson — không lấy dữ liệu rồi mới kiểm tra sau.
>
> **✅** EnrollmentRequiredException map sang 403 Forbidden (không phải 404), vì Course công khai và server đã xác định được danh tính người gọi — chỉ từ chối quyền.
>
> **✅** Trang Lesson Player trong Next.js phải force-dynamic (không cache), lấy token từ cookie server-side (bài 7.4), và xử lý 403 bằng redirect có ý nghĩa nghiệp vụ, không phải notFound().
>
> **✅** Luôn tự kiểm chứng bằng cách gọi thẳng API (curl/Scalar) — đừng bao giờ kết luận đã bảo mật xong chỉ vì UI đã ẩn được.

**So sánh 2 kiểu kiểm soát truy cập đã học:**

|  | **Policy-based (bài 3.7)** | **Resource/dữ liệu (bài 3.8 & 7.7)** |
|---|---|---|
| Dựa trên | Role/claims tĩnh trong token | Dữ liệu quan hệ cụ thể trong DB (User–Course) |
| Cơ chế | [Authorize(Policy="...")] | Kiểm tra trong Handler / IAuthorizationHandler |
| Ví dụ | InstructorOnly cho toàn bộ endpoint Course | User A có Enrollment cho Course B hay không |

**Bước tiếp theo:** Module 7 đã hoàn tất — Next.js Student Site chạy được end-to-end từ danh sách khóa học đến xem bài học có kiểm soát truy cập. Sang Module 8 (Testing), bài 8.1 sẽ viết unit test cho các Handler quan trọng, trong đó có GetLessonDetailQueryHandler vừa xây ở bài này — mock kết quả kiểm tra Enrollment để test cả 2 nhánh: có quyền và không có quyền.
