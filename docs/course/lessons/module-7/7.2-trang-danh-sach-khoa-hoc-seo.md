# Nội dung chính

## 1. ISR là gì, vì sao trang danh sách khóa học chọn ISR

*Lý thuyết · 15 phút*

Ở bài 7.1 bạn đã gọi được API từ Server Component, nhưng chưa quan tâm: dữ liệu đó được lấy mới mỗi lần load trang, hay được cache lại? Đây chính là câu hỏi route segment config trả lời. Next.js App Router (từ bản 13) thay thế hoàn toàn getServerSideProps/getStaticProps bằng 3 chế độ render, khai báo bằng cách export một biến ở đầu file page.tsx:

- force-static (SSG thuần) — trang được render 1 lần lúc build, không bao giờ tự cập nhật cho tới lần build kế tiếp. Phù hợp cho trang gần như tĩnh (về TEDU, điều khoản...).
- force-dynamic (SSR ép buộc) — mỗi request đều render lại từ đầu trên server, dữ liệu luôn mới nhất nhưng tốn tài nguyên server và chậm hơn khi traffic cao.
- revalidate = N (ISR — Incremental Static Regeneration) — trang được render và cache lại, sau N giây kể từ lần render gần nhất, request tiếp theo vẫn nhận HTML cache cũ (không phải chờ), đồng thời Next.js âm thầm render lại ở background và thay cache cho các request sau đó (stale-while-revalidate). Học viên hay hiểu nhầm N giây là "xóa cache rồi chờ render mới" — không đúng, người dùng không bao giờ phải chờ.

Danh sách khóa học đúng là ca điển hình cho ISR: giá và nội dung khóa học không đổi theo từng giây, nhưng vẫn cần cập nhật định kỳ (giảm giá, thêm khóa mới) mà không thể chấp nhận build lại toàn bộ site như SSG thuần. Khai báo đơn giản:

```tsx
// app/courses/page.tsx
export const revalidate = 300; // 5 phút — trang cache tối đa 5 phút trước khi regenerate
```

Điểm quan trọng nhất — và là điểm khác biệt lớn nhất so với các tài liệu Next.js 14 mà học viên có thể đã đọc qua: từ Next.js 15, fetch() trên server KHÔNG còn tự động được cache theo mặc định nữa (mặc định đổi từ force-cache sang no-store). Điều đó nghĩa là chỉ khai báo export const revalidate ở page là chưa đủ — nếu fetch bên trong page không tự khai báo tham gia cache, Next.js vẫn gọi lại API ở mọi request, route bị coi là dynamic hoàn toàn bất kể revalidate khai báo ở đầu file. Muốn ISR hoạt động thật, từng lệnh fetch phải khai báo rõ:

```
fetch(url, { next: { revalidate: 300 } })
// hoặc
fetch(url, { cache: "force-cache" })
```

Ở phần 2, bạn sẽ thấy cách áp dụng điều này khi gọi API không phải bằng fetch thô mà qua hàm SDK sinh từ packages/api-client.

> **📘 Ghi chú giảng viên:** *Tôi luôn dừng ở đây và hỏi cả lớp: "Nếu tôi sửa giá 1 khóa học thẳng trong Postgres, bao lâu sau trang /courses mới hiển thị giá mới?" — câu trả lời đúng là "tối đa 5 phút, và người dùng đầu tiên sau mốc đó vẫn thấy giá cũ, người dùng sau đó mới thấy giá mới" — đây là chỗ hay bị hiểu sai thành "ngay lập tức" hoặc "chỉ sau khi restart server". Nhấn mạnh: outline gọi đây là trang "render SSR" theo nghĩa rộng — server render ra HTML, không phải render ở trình duyệt như CSR — còn cơ chế cache cụ thể bên dưới chính là ISR, không phải SSR ép buộc từng request.*

## 2. Gọi lại GetCoursesListQuery qua api-client SDK trong Server Component

*Demo + Lab · 20 phút*

Ôn nhanh 2 mảnh ghép đã có từ trước khi vào code:

- Bài 1.6 (GetCoursesListQuery) — đúng theo quy ước đặt tên ở mục 7 của outline, Query trả list phải có hậu tố ListQuery. Outline ở các dòng 1.6/7.2 viết tắt thành "GetCoursesQuery" — đây là điểm chưa nhất quán trong văn bản outline so với chính bảng quy ước đặt tên; bài giảng này dùng thống nhất tên chuẩn GetCoursesListQuery, khớp ví dụ mục 7 (GetCourseDetailQuery / GetCoursesListQuery). Endpoint tương ứng: GET /api/v1/courses, hỗ trợ page, pageSize, categoryId, sort.
- Bài 5.2 (packages/api-client) — sinh sẵn 1 hàm SDK type-safe cho mỗi endpoint, đặt tên theo operationId đã khai báo lúc annotate Minimal API ở bài 4.1 (WithName). Bài này giả định operationId là GetCoursesList, nên hàm sinh ra là getCoursesList — nếu dự án của bạn đặt operationId khác, mở packages/api-client/src/client/sdk.gen.ts để lấy đúng tên hàm, đừng đoán.

Tạo route mới trong apps/web (Next.js App Router — mỗi thư mục trong app/ là 1 segment URL):

```tsx
apps/web/src/app/courses/page.tsx
```

Nội dung file, đi từng phần:

### a) Import và khai báo ISR

```typescript
import type { Metadata } from 'next';
import Link from 'next/link';
import { getCoursesList } from '@tedu-market/api-client';
 
// Route segment config — xem lại phần 1
export const revalidate = 300;
```

### b) Đọc searchParams — bắt buộc await vì là Promise trong Next.js 15

Đây là breaking change quan trọng nhất của Next.js 15 mà rất nhiều tài liệu/video cũ trên mạng chưa cập nhật: ở Next.js 14, searchParams và params là object đọc trực tiếp; từ Next.js 15, cả hai đều là Promise, page component phải là async function và phải await trước khi dùng. Không await sẽ không lỗi biên dịch ngay (TypeScript báo lỗi type nếu khai báo đúng Promise\<...>), nhưng runtime sẽ nhận object Promise thay vì giá trị thật.

```csharp
type CoursesSearchParams = Promise<{
  page?: string;
  categoryId?: string;
  sort?: 'price_asc' | 'price_desc' | 'newest';
}>;
 
type CoursesPageProps = {
  searchParams: CoursesSearchParams;
};
 
export default async function CoursesPage({ searchParams }: CoursesPageProps) {
  const { page, categoryId, sort } = await searchParams;
 
  const pageNumber = Number(page ?? '1');
  const pageSize = 12;
```

### c) Gọi GetCoursesListQuery qua SDK — nhớ khai báo cache ở đúng cấp fetch

Vì Next.js 15 không tự cache fetch, và @hey-api/client-fetch (client mà bài 5.2 dùng để tạo SDK) chỉ là lớp bọc mỏng quanh fetch chuẩn, bạn cần truyền thêm tùy chọn cache/next ngay tại lệnh gọi SDK. Hàm sinh ra bởi hey-api nhận 1 object gồm query/path/body và các field RequestInit khác, sau đó chuyển thẳng phần còn lại cho fetch() — nên next: { revalidate } đặt ngay ở cấp cao nhất của object truyền vào vẫn có tác dụng:

```csharp
  const { data, error } = await getCoursesList({
    query: {
      page: pageNumber,
      pageSize,
      categoryId,
      sort,
    },
    next: { revalidate: 300 }, // khớp với revalidate của route ở trên
  });
 
  if (error) {
    // error ở đây là ProblemDetails đã chuẩn hóa từ Module 4.5
    throw new Error('Không tải được danh sách khóa học');
  }
 
  const { items: courses, totalCount } = data;
  const totalPages = Math.ceil(totalCount / pageSize);
```

> **📘 Ghi chú giảng viên:** *Tên field items/totalCount ở trên là ví dụ minh họa cấu trúc envelope phân trang chuẩn — tên trường thật phải khớp đúng DTO đã định nghĩa khi viết GetCoursesListQuery ở bài 1.6 của dự án bạn. Nhấn mạnh với học viên: đây là lý do bài 4.5 (chuẩn hóa response) đứng trước Module 5 — nếu response shape không nhất quán, đoạn destructuring này sẽ khác nhau giữa các endpoint, TypeScript sẽ báo lỗi ngay lúc code chứ không đợi tới runtime, đúng giá trị mà bài 5.4 đã chứng minh.*

### d) Render danh sách + phân trang bằng Link, không dùng state client

Vì đây là Server Component thuần (không có "use client"), phân trang/filter không dùng useState — chuyển trang nghĩa là điều hướng sang URL khác (?page=N), Next.js render lại Server Component với searchParams mới. Đây là khác biệt cố ý so với CRUD UI ở React Admin (bài 6.3) dùng React Query + client state.

```
  return (
    <main>
      <h1>Danh sách khóa học</h1>
 
      <ul>
        {courses.map((course) => (
          <li key={course.id}>
            <Link href={`/courses/${course.slug}`}>{course.title}</Link>
            <span>{course.price.toLocaleString('vi-VN')} đ</span>
          </li>
        ))}
      </ul>
 
      <nav aria-label="Phân trang">
        {pageNumber > 1 && (
          <Link href={`/courses?page=${pageNumber - 1}`}>« Trang trước</Link>
        )}
        <span>Trang {pageNumber} / {totalPages}</span>
        {pageNumber < totalPages && (
          <Link href={`/courses?page=${pageNumber + 1}`}>Trang sau »</Link>
        )}
      </nav>
    </main>
  );
}
```

## 3. generateMetadata — SEO động theo trạng thái lọc

*Demo · 10 phút*

Metadata API của Next.js App Router thay thế hoàn toàn next/head kiểu cũ. Có 2 cách khai báo: export const metadata (tĩnh, dùng khi nội dung không đổi theo request) hoặc export async function generateMetadata (động, dùng khi title/description phụ thuộc params/searchParams hoặc dữ liệu fetch). Trang /courses cần cách thứ hai vì tiêu đề phải đổi theo trang hiện tại và bộ lọc:

```csharp
export async function generateMetadata(
  { searchParams }: CoursesPageProps
): Promise<Metadata> {
  const { page, categoryId } = await searchParams; // cũng là Promise, cũng phải await
  const pageNumber = Number(page ?? '1');
 
  const title =
    pageNumber > 1
      ? `Danh sách khóa học — Trang ${pageNumber} | TEDU Market`
      : 'Danh sách khóa học | TEDU Market';
 
  return {
    title,
    description:
      'Khám phá toàn bộ khóa học lập trình trên TEDU Market — lọc theo danh mục, sắp xếp theo giá hoặc ngày phát hành.',
    alternates: {
      canonical: `/courses${categoryId ? `?categoryId=${categoryId}` : ''}`,
    },
  };
}
```

generateMetadata và default export Page cùng nhận searchParams giống hệt nhau — nếu cả hai cùng gọi getCoursesList() với cùng tham số, Next.js sẽ dedupe (memoize) request đó trong cùng 1 lần render, không gọi API 2 lần. Bài này chưa cần fetch thêm trong generateMetadata (chỉ dùng searchParams để dựng title), nhưng nếu sau này cần tên Category thật thay vì categoryId trong title, đây chính là chỗ gọi thêm 1 query nhỏ — và Next.js sẽ tự dedupe với lần gọi trong Page nếu cùng URL/params.

> **📘 Ghi chú giảng viên:** *Câu hỏi học viên hay đặt ra: "Vậy generateMetadata có chạy 2 lần, 1 lần cho HTML 1 lần cho metadata không?" — Không, nó là 1 phần của quá trình render trang, chạy song song và được Next.js gộp vào cùng 1 response. Tôi hay demo trực tiếp: mở tab Elements trong DevTools, xem thẻ \<title> đổi theo ?page=2, để học viên thấy metadata thật sự động chứ không phải hard-code.*

# Bài tập / Thực hành

Mở rộng trang /courses vừa xây ở phần 2–3 với yêu cầu sau:

- Cho phép lọc theo danh mục qua query string: /courses?categoryId=xxx.
- Tiêu đề trang (thẻ \<title>, qua generateMetadata) phải hiển thị đúng tên Category đang lọc, ví dụ "Khóa học ReactJS | TEDU Market" — không phải hiển thị categoryId dạng GUID.
- Kiểm chứng ISR: sửa giá 1 khóa học thẳng trong Postgres (psql hoặc pgAdmin), F5 lại trang trong vòng 5 phút đầu — xác nhận giá CHƯA đổi; đợi qua mốc revalidate rồi F5 lần nữa — xác nhận giá đã đổi.

**Input / Expected output**

- Input: truy cập /courses?categoryId=\<id một Category có thật trong DB>.
- Expected: danh sách chỉ gồm khóa học thuộc Category đó; \<title> hiển thị đúng tên Category; canonical trong \<head> là /courses?categoryId=\<id>.

> **✏️ Thực hành:** Hint: GetCoursesListQuery (bài 1.6) chỉ trả categoryId trong mỗi course, không trả sẵn tên Category cho toàn trang. Bạn cần 1 trong 2 hướng: (1) gọi thêm 1 SDK function nhỏ lấy Category theo id (dựa trên CRUD Category đã có ở bài 1.9) ngay trong generateMetadata, hoặc (2) yêu cầu GetCoursesListQuery trả kèm categoryName trong response envelope nếu có categoryId lọc. Hướng (1) tái sử dụng đúng tinh thần "mỗi Query làm đúng 1 việc" của CQRS; hướng (2) nhanh hơn nhưng làm phình response cho các lần gọi không cần categoryName. TEDU khuyến nghị hướng (1) cho bài tập này.

**Solution (gợi ý code)**

```csharp
export async function generateMetadata({ searchParams }: CoursesPageProps): Promise<Metadata> {
  const { page, categoryId } = await searchParams;
  const pageNumber = Number(page ?? '1');
 
  let categoryName: string | undefined;
  if (categoryId) {
    const { data } = await getCategoryById({ path: { id: categoryId } });
    categoryName = data?.name;
  }
 
  const scope = categoryName ?? (pageNumber > 1 ? `Trang ${pageNumber}` : undefined);
  const title = scope
    ? `Khóa học ${scope} | TEDU Market`
    : 'Danh sách khóa học | TEDU Market';
 
  return {
    title,
    alternates: {
      canonical: `/courses${categoryId ? `?categoryId=${categoryId}` : ''}`,
    },
  };
}
```

# Tổng kết

- Route segment config (export const revalidate = N) khai báo ISR ở cấp trang — nhưng KHÔNG tự động cache fetch bên trong, vì Next.js 15 đổi mặc định fetch sang no-store.
- Muốn ISR hoạt động thật, từng lệnh fetch (kể cả gọi qua SDK của api-client) phải tự khai báo next: { revalidate } hoặc cache: "force-cache".
- searchParams và params trong Next.js 15 đều là Promise — page component và generateMetadata phải là async function và await trước khi đọc.
- Server Component gọi thẳng GetCoursesListQuery qua hàm SDK type-safe từ packages/api-client — không viết fetch tay, không tự đoán response shape, lỗi hiện ngay lúc biên dịch nếu backend đổi DTO (đúng giá trị đã chứng minh ở bài 5.4).
- generateMetadata trả Metadata động theo searchParams, thay thế hoàn toàn next/head kiểu cũ; Next.js tự dedupe fetch trùng URL/params giữa generateMetadata và Page.

### Bảng so sánh nhanh: SSG vs ISR vs SSR ép buộc

| **Tiêu chí** | **force-static (SSG)** | **revalidate = N (ISR)** | **force-dynamic (SSR)** |
|---|---|---|---|
| Thời điểm render | 1 lần lúc build | Lúc build/request đầu, sau đó regenerate định kỳ | Mỗi request |
| Độ mới dữ liệu | Chỉ mới sau lần build kế | Trễ tối đa N giây | Luôn mới nhất |
| Tải server | Thấp nhất | Thấp — chỉ render lại theo chu kỳ | Cao nhất |
| Dùng cho trang nào trong khóa | Trang giới thiệu, điều khoản | /courses (bài này), /courses/[slug] (bài 7.3) | /my-courses (bài 7.6) — dữ liệu theo user, không thể cache chung |

Bước tiếp theo: bài 7.3 (Trang chi tiết khóa học) áp dụng lại đúng bộ kỹ thuật này ở route động /courses/[slug] — thêm generateStaticParams, generateMetadata theo dữ liệu Course thật (không chỉ theo query string), và dùng lại GetCourseDetailQuery (bài 1.7).

# Phụ lục

### Cheatsheet — Route segment config thường dùng

| **Khai báo** | **Ý nghĩa** |
|---|---|
| export const revalidate = 300 | ISR — cache trang tối đa 300 giây trước khi regenerate ở background |
| export const dynamic = 'force-static' | Ép SSG thuần, cấm dùng dynamic API (cookies, headers, searchParams động) |
| export const dynamic = 'force-dynamic' | Ép SSR mỗi request, tương đương revalidate = 0 |
| fetch(url, { next: { revalidate: N } }) | Khai báo cache ở cấp từng fetch — bắt buộc từ Next.js 15 vì mặc định không còn cache |
| fetch(url, { cache: 'no-store' }) | Không cache request này, kéo cả route thành dynamic dù page khai báo revalidate |

### Glossary

- ISR (Incremental Static Regeneration): render tĩnh nhưng tự regenerate theo chu kỳ, không cần rebuild toàn site.
- Route Segment Config: các biến export ở đầu page.tsx/layout.tsx (revalidate, dynamic, dynamicParams...) điều khiển cách Next.js render segment đó.
- Data Cache: tầng cache riêng của Next.js cho kết quả fetch() trên server, độc lập với Full Route Cache (cache HTML của cả trang).
- generateMetadata: hàm async export từ page.tsx/layout.tsx, trả về đối tượng Metadata để Next.js dựng \<head>.
