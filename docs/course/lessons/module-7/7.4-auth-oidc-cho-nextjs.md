## 1. OIDC cho SPA và OIDC cho ứng dụng có server — khác nhau thật sự ở đâu

*Lý thuyết · ~20 phút*

Ở bài 6.2, React Admin đăng nhập bằng Authorization Code Flow + PKCE, chạy hoàn toàn trong browser qua react-oidc-context. Đó là Public Client: không có ClientSecret, vì bất kỳ thứ gì nhúng vào bundle JavaScript gửi cho browser đều có thể bị đọc ra — PKCE (code_verifier/code_challenge) chính là cơ chế thay thế ClientSecret cho loại client không giữ được bí mật. Access token sau khi lấy về được react-oidc-context giữ trong bộ nhớ JS runtime của tab đó.

Next.js Student site (apps/web) khác: nó có một tầng server Node.js chạy trước khi trả HTML về browser — Server Component, Route Handler, Middleware đều thực thi trên server, không phải trong tab của học viên. Vì vậy Next.js đăng ký với OpenIddict là Confidential Client: có ClientSecret, vì secret chỉ nằm trong biến môi trường trên server, không bao giờ được gửi xuống browser. Việc đổi authorization code lấy token (token endpoint request) cũng chạy trên server — Route Handler /api/auth/callback — chứ không chạy trong trình duyệt của học viên.

Hệ quả trực tiếp: browser của học viên không bao giờ nhìn thấy access token hay refresh token ở dạng đọc được. Thứ duy nhất browser giữ là một cookie session — được đặt httpOnly nên JavaScript phía client (kể cả script độc hại chèn qua XSS) không đọc được document.cookie ra nó — và nội dung cookie đó lại được mã hóa (JWE), nên kể cả khi ai đó đọc được giá trị cookie thô cũng không giải mã được token bên trong nếu không có khóa bí mật trên server.

### So sánh nhanh

| **Tiêu chí** | **React Admin (SPA — bài 6.2)** | **Next.js Student (bài này)** |
|---|---|---|
| **Loại Client OpenIddict** | Public — không ClientSecret | Confidential — có ClientSecret |
| **Nơi đổi code lấy token** | Trong browser (JS runtime) | Trên server (Route Handler) |
| **Nơi lưu token** | Bộ nhớ JS runtime của tab | Server — không xuống browser dạng đọc được |
| **Thư viện dùng** | react-oidc-context (chạy client-side) | openid-client + jose (chạy server-side) |
| **Đánh đổi** | Đơn giản, không cần hạ tầng server riêng cho auth | An toàn hơn, nhưng phải tự viết và vận hành logic session |

> **📘 Ghi chú giảng viên:** *Tôi hay hỏi lớp: "Nếu React Admin cũng có thể chạy được với server (ví dụ SSR), tại sao Module 6 vẫn dùng Public Client?" — câu trả lời đúng: bản thân React (Vite) build ra static file, không có server chạy song song lúc runtime, nên không có nơi nào giữ ClientSecret an toàn cả. Next.js thì luôn có server đứng sau — đó là điều kiện đủ để chuyển sang Confidential Client, không phải vì "Next.js xịn hơn React".*

## 2. Đăng ký OpenIddict Client cho Next.js Student site

*Demo · ~10 phút*

Việc đăng ký Client mới thực hiện ở project TeduMarket.Infrastructure hoặc TeduMarket.Api (cùng chỗ bạn đã seed Client cho React Admin ở bài 3.3), dùng IOpenIddictApplicationManager. Khác biệt cốt lõi so với bài 3.3: ClientType.Confidential thay vì Public, có ClientSecret, và bật thêm Endpoints.EndSession để hỗ trợ đăng xuất chuẩn OIDC (RP-Initiated Logout) ở phần 5.

***TeduMarket.Infrastructure / Identity / OpenIddictSeeder.cs (bổ sung)***

```javascript
// Client cho Next.js Student site (apps/web) — Confidential Client
if (await appManager.FindByClientIdAsync("tedumarket_web") is null)
{
    await appManager.CreateAsync(new OpenIddictApplicationDescriptor
    {
        ClientId = "tedumarket_web",
        ClientSecret = configuration["OpenIddict:WebClientSecret"], // đọc từ secret, KHÔNG hard-code
        ClientType = OpenIddictConstants.ClientTypes.Confidential,
        DisplayName = "TEDU Market — Next.js Student Site",
        RedirectUris = { new Uri("http://localhost:3000/api/auth/callback") },
        PostLogoutRedirectUris = { new Uri("http://localhost:3000/") },
        Permissions =
        {
            OpenIddictConstants.Permissions.Endpoints.Authorization,
            OpenIddictConstants.Permissions.Endpoints.Token,
            OpenIddictConstants.Permissions.Endpoints.EndSession,
            OpenIddictConstants.Permissions.GrantTypes.AuthorizationCode,
            OpenIddictConstants.Permissions.GrantTypes.RefreshToken,
            OpenIddictConstants.Permissions.ResponseTypes.Code,
            OpenIddictConstants.Permissions.Scopes.Email,
            OpenIddictConstants.Permissions.Scopes.Profile,
            OpenIddictConstants.Permissions.Scopes.Roles,
            OpenIddictConstants.Permissions.Prefixes.Scope + "tedumarket_api",
        },
        Requirements =
        {
            OpenIddictConstants.Requirements.Features.ProofKeyForCodeExchange,
        },
    });
}
```

Điểm cần để ý: dù đã là Confidential Client (có secret), bài vẫn bắt buộc PKCE qua Requirements.Features.ProofKeyForCodeExchange. Đây không phải thừa — PKCE và ClientSecret bảo vệ hai thứ khác nhau: ClientSecret xác thực danh tính client (chỉ server thật của bạn mới gọi được token endpoint), còn PKCE chống việc authorization code bị đánh cắp giữa bước redirect và bước đổi code — vẫn cần dù client có giữ được secret hay không, theo khuyến nghị hiện hành của OAuth 2.1.

> **📘 Ghi chú giảng viên:** *Nhắc lại đúng permission: GrantTypes.RefreshToken phải bật thì OpenIddict mới cấp refresh_token kèm access_token. Học viên hay quên dòng này rồi thắc mắc tại sao response không có refresh_token — đây là lỗi phổ biến nhất ở bài này.*

## 3. Setup openid-client và module session

*Demo · ~10 phút*

***Terminal — cài package trong apps/web***

```bash
cd frontend/apps/web

```

***.env.local (apps/web)***

```
AUTH_ISSUER=https://localhost:7001
AUTH_CLIENT_ID=tedumarket_web
AUTH_CLIENT_SECRET=<lấy từ OpenIddict:WebClientSecret ở backend>
AUTH_REDIRECT_URI=http://localhost:3000/api/auth/callback

SESSION_SECRET=<chuỗi base64url 32 byte ngẫu nhiên — dùng làm khóa mã hóa cookie>
```

Sinh SESSION_SECRET bằng lệnh node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))" — đây là khóa đối xứng để jose mã hóa/giải mã cookie session, khác hoàn toàn với ClientSecret của OpenIddict (một cái bảo vệ cookie phía Next.js, một cái xác thực Next.js với OpenIddict).

***lib/oidc.ts***

```typescript
import * as client from 'openid-client'
 
// Discovery gọi 1 lần, cache lại — KHÔNG gọi discovery mỗi request vì tốn round-trip
let configPromise: Promise<client.Configuration> | null = null
 
export function getOidcConfig() {
  configPromise ??= client.discovery(
    new URL(process.env.AUTH_ISSUER!),
    process.env.AUTH_CLIENT_ID!,
    process.env.AUTH_CLIENT_SECRET!,
  )
  return configPromise
}
```

***lib/session.ts***

```csharp
import { EncryptJWT, jwtDecrypt } from 'jose'
import { cookies } from 'next/headers'
 
const SESSION_COOKIE = 'tedumarket_session'
const secretKey = Buffer.from(process.env.SESSION_SECRET!, 'base64url')
 
export type SessionPayload = {
  sub: string
  name?: string
  email?: string
  accessToken: string
  refreshToken?: string
  idToken: string // giữ lại để làm id_token_hint khi logout
  expiresAt: number // epoch giây, hết hạn access token
}
 
export async function createSession(payload: SessionPayload) {
  const jwe = await new EncryptJWT(payload as any)
    .setProtectedHeader({ alg: 'dir', enc: 'A256GCM' })
    .setIssuedAt()
    .setExpirationTime('7d') // vòng đời cookie; access token hết hạn sớm hơn nhiều
    .encrypt(secretKey)
 
  const store = await cookies()
  store.set(SESSION_COOKIE, jwe, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    path: '/',
    maxAge: 60 * 60 * 24 * 7,
  })
}
 
export async function getSession(): Promise<SessionPayload | null> {
  const store = await cookies()
  const jwe = store.get(SESSION_COOKIE)?.value
  if (!jwe) return null
  try {
    const { payload } = await jwtDecrypt<SessionPayload>(jwe, secretKey)
    return payload
  } catch {
    return null // cookie hỏng hoặc hết hạn — coi như chưa đăng nhập
  }
}
 
export async function destroySession() {
  const store = await cookies()
  store.delete(SESSION_COOKIE)
}
```

> **📘 Ghi chú giảng viên:** *Vì sao dùng EncryptJWT (JWE, mã hóa) chứ không phải SignJWT (JWS, chỉ ký)? SignJWT chỉ đảm bảo cookie không bị SỬA, nhưng ai đọc được cookie vẫn đọc được access token bên trong (payload chỉ base64, không mã hóa). Session này chứa access token thật của học viên nên bắt buộc mã hóa — đây là điểm học viên dễ làm sai nhất nếu tự tra Google, vì phần lớn bài viết về "JWT session" trên mạng chỉ ký chứ không mã hóa.*

## 4. Route Handler: /api/auth/login

*Demo · ~5 phút*

***app/api/auth/login/route.ts***

```typescript
import { NextRequest, NextResponse } from 'next/server'
import * as client from 'openid-client'
import { getOidcConfig } from '@/lib/oidc'
 
const PKCE_COOKIE = 'tedumarket_pkce'
 
export async function GET(request: NextRequest) {
  const config = await getOidcConfig()
  const returnTo = request.nextUrl.searchParams.get('returnTo') ?? '/'
 
  const codeVerifier = client.randomPKCECodeVerifier()
  const codeChallenge = await client.calculatePKCECodeChallenge(codeVerifier)
  const state = client.randomState()
 
  const authorizationUrl = client.buildAuthorizationUrl(config, {
    redirect_uri: process.env.AUTH_REDIRECT_URI!,
    scope: 'openid profile email offline_access tedumarket_api',
    code_challenge: codeChallenge,
    code_challenge_method: 'S256',
    state,
  })
 
  const response = NextResponse.redirect(authorizationUrl)
  // Cookie tạm, sống rất ngắn — chỉ để sống sót qua vòng redirect tới OpenIddict và quay lại
  response.cookies.set(PKCE_COOKIE, JSON.stringify({ codeVerifier, state, returnTo }), {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    path: '/',
    maxAge: 600, // 10 phút — đủ thời gian học viên đăng nhập ở trang OpenIddict
  })
  return response
}
```

Route này không được gọi bằng fetch từ Client Component — nó phải là một điều hướng trình duyệt thật sự (thẻ \<a href="/api/auth/login"> hoặc window.location.href), vì bước tiếp theo là redirect sang trang đăng nhập của OpenIddict, nằm ngoài domain của Next.js.

## 5. Route Handler: /api/auth/callback

*Demo · ~10 phút*

***app/api/auth/callback/route.ts***

```typescript
import { NextRequest, NextResponse } from 'next/server'
import { cookies } from 'next/headers'
import * as client from 'openid-client'
import { getOidcConfig } from '@/lib/oidc'
import { createSession } from '@/lib/session'
 
const PKCE_COOKIE = 'tedumarket_pkce'
 
export async function GET(request: NextRequest) {
  const config = await getOidcConfig()
  const store = await cookies()
  const raw = store.get(PKCE_COOKIE)?.value
 
  if (!raw) {
    return NextResponse.redirect(new URL('/login?error=missing_pkce', request.url))
  }
  const { codeVerifier, state, returnTo } = JSON.parse(raw)
 
  const tokens = await client.authorizationCodeGrant(config, request.nextUrl, {
    pkceCodeVerifier: codeVerifier,
    expectedState: state,
    idTokenExpected: true,
  })
 
  const claims = tokens.claims()! // đã được openid-client verify chữ ký + iss/aud/exp
 
  await createSession({
    sub: claims.sub,
    name: typeof claims.name === 'string' ? claims.name : undefined,
    email: typeof claims.email === 'string' ? claims.email : undefined,
    accessToken: tokens.access_token,
    refreshToken: tokens.refresh_token,
    idToken: tokens.id_token!,
    expiresAt: Math.floor(Date.now() / 1000) + (tokens.expires_in ?? 3600),
  })
 
  const response = NextResponse.redirect(new URL(returnTo || '/', request.url))
  response.cookies.delete(PKCE_COOKIE)
  return response
}
```

So với bài 6.2: react-oidc-context làm đúng các bước này (buildAuthorizationUrl, authorizationCodeGrant, verify claims) nhưng ẩn hết bên trong thư viện và chạy trong browser. Ở đây bạn viết tay từng bước vì nó chạy trên server — không có thư viện SPA nào lo hộ được phần server-side này.

## 6. Route Handler: /api/auth/logout

*Demo · ~5 phút*

***app/api/auth/logout/route.ts***

```typescript
import { NextRequest, NextResponse } from 'next/server'
import { getOidcConfig } from '@/lib/oidc'
import { getSession, destroySession } from '@/lib/session'
 
export async function GET(request: NextRequest) {
  const session = await getSession()
  const config = await getOidcConfig()
  await destroySession() // xóa session phía Next.js trước
 
  const endSessionEndpoint = config.serverMetadata().end_session_endpoint
  if (session && endSessionEndpoint) {
    // RP-Initiated Logout — yêu cầu OpenIddict đóng luôn phiên đăng nhập của học viên
    const url = new URL(endSessionEndpoint)
    url.searchParams.set('id_token_hint', session.idToken)
    url.searchParams.set('post_logout_redirect_uri', process.env.AUTH_POST_LOGOUT_REDIRECT_URI!)
    return NextResponse.redirect(url)
  }
  return NextResponse.redirect(new URL('/', request.url))
}
```

> **📘 Ghi chú giảng viên:** *Chỉ xóa session cookie ở Next.js ("đăng xuất khỏi app") mà không gọi end_session_endpoint là sai một nửa — phiên đăng nhập ở OpenIddict Server vẫn còn sống. Nếu học viên bấm "Đăng nhập" lại ngay sau đó, OpenIddict có thể tự động cấp lại token mà không hỏi mật khẩu, vì Single Sign-On session ở đó chưa kết thúc. Đây là lỗi bảo mật hay bị bỏ sót nhất khi làm logout.*

## 7. Đọc session trong Server Component và middleware

*Demo · ~5 phút*

***components/Header.tsx (Server Component)***

```typescript
import { getSession } from '@/lib/session'
 
export async function Header() {
  const session = await getSession()
  return (
    <header>
      {session ? (
        <>
          <span>Xin chào, {session.name ?? session.email}</span>
          <a href="/api/auth/logout">Đăng xuất</a>
        </>
      ) : (
        <a href="/api/auth/login?returnTo=/my-courses">Đăng nhập</a>
      )}
    </header>
  )
}
```

***middleware.ts (optimistic check — bảo vệ route theo cấu trúc route Module 7.6)***

```typescript
import { NextRequest, NextResponse } from 'next/server'
 
const PROTECTED_PREFIXES = ['/my-courses', '/checkout']
 
export function middleware(request: NextRequest) {
  const isProtected = PROTECTED_PREFIXES.some(p => request.nextUrl.pathname.startsWith(p))
  if (!isProtected) return NextResponse.next()
 
  const hasSession = request.cookies.has('tedumarket_session')
  if (!hasSession) {
    const loginUrl = new URL('/api/auth/login', request.url)
    loginUrl.searchParams.set('returnTo', request.nextUrl.pathname)
    return NextResponse.redirect(loginUrl)
  }
  return NextResponse.next()
}
 
export const config = {
  matcher: ['/my-courses/:path*', '/checkout/:path*'],
}
```

Middleware chỉ kiểm tra cookie có tồn tại ("optimistic check") — nó không giải mã hay xác thực nội dung, vì middleware chạy trên Edge Runtime và nên nhẹ, nhanh. Việc giải mã thật (jwtDecrypt) và kiểm tra hết hạn diễn ra trong getSession() ở Server Component/Route Handler — đó mới là lớp kiểm tra đáng tin cậy. Đây đúng theo khuyến nghị optimistic vs secure check của Next.js: middleware chặn nhanh phần lớn truy cập trái phép, còn quyết định cuối cùng luôn ở server.

> **📘 Ghi chú giảng viên:** *Với Course/Order thật sự nhạy cảm (ví dụ endpoint xem nội dung Lesson ở bài 7.7), đừng dừng ở optimistic check này. Quyền truy cập cuối cùng vẫn phải được API backend tự kiểm tra lại qua OpenIddict Bearer token — giống nguyên tắc đã học ở Module 3.7/3.8: không bao giờ tin tưởng tuyệt đối một kiểm tra chỉ chạy phía client hay middleware.*

- Next.js Student site là Confidential Client (có ClientSecret) vì có server giữ được bí mật — khác Public Client của React Admin (SPA) ở bài 3.3/6.2.
- Toàn bộ vòng đổi code lấy token chạy trên server (Route Handler), browser chỉ nhận một cookie session httpOnly đã mã hóa bằng jose (EncryptJWT/A256GCM) — không phải chỉ ký.
- PKCE vẫn bắt buộc dù đã có ClientSecret, vì hai cơ chế bảo vệ hai rủi ro khác nhau.
- Đăng xuất đúng chuẩn phải xóa session ở Next.js VÀ gọi end_session_endpoint của OpenIddict (RP-Initiated Logout) — thiếu bước sau là lỗi phổ biến.
- Middleware chỉ làm optimistic check (cookie có tồn tại hay không); quyết định thật và mọi truy cập dữ liệu nhạy cảm vẫn phải qua kiểm tra ở server/API — không tin client.

> **✅ Tóm tắt:** Session của học viên giờ đã sống an toàn ở server Next.js, có access_token sẵn sàng dùng. Bước tiếp theo (bài 7.5 — Giỏ hàng & Checkout Flow) sẽ dùng chính access_token này trong Server Action để gọi CheckoutCommand (Module 2.2), rồi chuyển học viên sang bước thanh toán bằng chuyển khoản ngân hàng qua SePay — sinh mã QR VietQR (Module 2.4) thay vì cổng VNPay.
