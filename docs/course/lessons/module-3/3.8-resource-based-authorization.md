## **Nội dung chính**

### **1. Vì sao [Authorize] khai báo không đủ — 15 phút · Lý thuyết**

Ở bài 3.7, bạn đã gắn Policy "InstructorOnly" thẳng lên endpoint bằng .RequireAuthorization("InstructorOnly"). Cách này gọi là declarative authorization — Middleware Authorization của ASP.NET Core đọc attribute/policy này và quyết định cho qua hay chặn TRƯỚC KHI Minimal API thực hiện model binding, và tất nhiên là trước khi MediatR gửi Command đến Handler để load Course từ database.

Điều đó có nghĩa: tại thời điểm Middleware kiểm tra, hệ thống **chưa hề biết Course #123 thuộc về Instructor nào**. Policy "InstructorOnly" chỉ trả lời được câu "user này có role Instructor không" — một câu hỏi không phụ thuộc dữ liệu. Nó không thể trả lời câu "user này có phải chủ sở hữu đúng Course đang bị sửa không" — vì câu trả lời phụ thuộc vào một bản ghi cụ thể, phải load lên mới biết.

Đây chính xác là ranh giới mà tài liệu chính thức ASP.NET Core gọi tên: khi việc ra quyết định phụ thuộc vào chính resource đang truy cập, attribute khai báo không đủ — phải chuyển sang imperative authorization: tự tay gọi một service để kiểm tra, ngay sau khi resource đã nằm trong tay bạn.

### **Nối lại bài 1.2 — patch tạm giờ mới trả nợ**

Ở bài 1.2, `UpdateCourseCommand` nhận thẳng một trường `InstructorId` do client gửi lên trong request, rồi `UpdateCourseCommandHandler` so sánh trường này với `Course.InstructorId`. Đây chỉ là chỗ giữ chỗ tạm thời — outline đã nói rõ: **"Authorization đầy đủ để dành Module 3"**. Lỗ hổng của cách làm tạm này: `InstructorId` trong request body là do client tự khai, không hề được xác thực. Bất kỳ ai biết InstructorId thật của chủ Course (chỉ cần xem qua API danh sách, hoặc đoán số nguyên tăng dần) đều điền đúng giá trị đó vào body và sửa được Course của người khác — dù họ đăng nhập với tài khoản nào.

Bài này thay hoàn toàn cách check đó bằng claim instructor_id lấy từ Access Token đã được OpenIddict ký ở bài 3.2–3.5 — token này client không thể tự sửa nội dung mà không làm hỏng chữ ký, nên giá trị InstructorId trong đó đáng tin.

> **📘 Ghi chú giảng viên:** *Học viên hay hỏi: "Sao không gắn thẳng [Authorize(Policy = "CourseOwnerPolicy")] lên endpoint cho gọn, giống InstructorOnly ở bài 3.7?". Tôi thường dừng lại hỏi ngược: "Muốn biết ai là chủ Course #123, bạn cần làm gì trước?" — câu trả lời luôn là "phải query Course lên trước". Từ đó học viên tự nhận ra: attribute chạy ở tầng Middleware, không có quyền tự ý query DB trước khi endpoint thực thi — nên bắt buộc phải làm tay, sau khi đã có dữ liệu.*

### **3 khối của Resource-based Authorization**

- IAuthorizationRequirement — điều kiện cần thỏa. Thường là một class rỗng, chỉ đóng vai trò "chìa khóa" để framework tìm đúng Handler xử lý; logic thật nằm ở Handler, không nằm ở Requirement.
- AuthorizationHandler\<TRequirement, TResource> — lớp trừu tượng có 2 tham số kiểu: Requirement cần xử lý và kiểu của Resource cụ thể (ở đây là Course, không phải HttpContext chung chung như Policy-based thông thường). Override HandleRequirementAsync(context, requirement, resource) và gọi context.Succeed(requirement) khi hợp lệ.
- IAuthorizationService.AuthorizeAsync(user, resource, policyName) — entrypoint gọi tay, truyền đúng 3 thứ: ClaimsPrincipal của người dùng hiện tại, resource cụ thể vừa load, và tên Policy đã đăng ký.

> **📘 Ghi chú giảng viên:** *Nguồn tham khảo chính thức cho phần này: "Resource-based authorization in ASP.NET Core" trên Microsoft Learn (bản aspnetcore-10.0) — mẫu code DocumentAuthorizationHandler : AuthorizationHandler\<SameAuthorRequirement, Document> trong bài này chính là khuôn tôi dùng để dựng CourseOwnerAuthorizationHandler bên dưới, chỉ đổi Document thành Course.*

### **Đặt 3 khối này ở đâu trong Clean Architecture?**

Requirement và Handler ở đây thuần là logic nghiệp vụ ("so InstructorId trong claim với InstructorId của Course") — không đụng gì đến HTTP, EF Core hay bất kỳ hạ tầng nào. Theo đúng nguyên tắc Dependency Inversion đã học từ bài 0.2, chỗ hợp lý nhất là `TeduMarket.Application/Common/Authorization/`.

Có làm được không, khi Application chỉ là class library thuần, không phải Web SDK? Được — vì `Microsoft.AspNetCore.Authorization` không phải một phần "khoá cứng" vào ASP.NET Core hosting, mà được Microsoft đóng gói thành NuGet package độc lập (bản dùng cho .NET 10 target cả `net10.0` lẫn `netstandard2.0`), cài được vào bất kỳ class library nào bằng `dotnet add package Microsoft.AspNetCore.Authorization`. TeduMarket.Application vẫn giữ đúng nguyên tắc "không phụ thuộc framework hosting" — nó chỉ tham chiếu một bộ interface/abstract class thuần logic (IAuthorizationRequirement, AuthorizationHandler\<T,T>, IAuthorizationService), không kéo theo Kestrel hay HttpContext.

### **2. Demo — Dựng CourseOwnerRequirement & Handler — 15 phút · Demo**

**Bước 1 — Cài package vào đúng project:**

**Bước 2 — Requirement (rỗng, chỉ là marker):**

```csharp
// TeduMarket.Application/Common/Authorization/CourseOwnerRequirement.cs
using Microsoft.AspNetCore.Authorization;
 
namespace TeduMarket.Application.Common.Authorization;
 
public sealed class CourseOwnerRequirement : IAuthorizationRequirement
{
}
```

**Bước 3 — Handler xử lý đúng Course làm resource:**

```csharp
// TeduMarket.Application/Common/Authorization/CourseOwnerAuthorizationHandler.cs
using Microsoft.AspNetCore.Authorization;
using TeduMarket.Domain.Courses;
 
namespace TeduMarket.Application.Common.Authorization;
 
public sealed class CourseOwnerAuthorizationHandler
    : AuthorizationHandler<CourseOwnerRequirement, Course>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        CourseOwnerRequirement requirement,
        Course resource)
    {
        // "instructor_id" la claim type da cau hinh destination o bai 3.5
        var instructorIdClaim = context.User.FindFirst(TeduClaimTypes.InstructorId)?.Value;
 
        if (Guid.TryParse(instructorIdClaim, out var instructorId)
            && instructorId == resource.InstructorId)
        {
            context.Succeed(requirement);
        }
 
        return Task.CompletedTask;
    }
}
```

Lưu ý: nếu claim `instructor_id` không có hoặc không parse được thành Guid, hàm chỉ đơn giản không gọi `context.Succeed(...)` — **không throw exception ở đây**. Đây là quy ước của framework: một Handler không xác nhận được coi là "chưa đủ điều kiện", không phải "lỗi hệ thống". Kết quả cuối cùng (Succeeded = false) được xử lý ở nơi gọi AuthorizeAsync.

**Bước 4 — Đăng ký Policy + Handler ở Api/Program.cs:**

```csharp
// TeduMarket.Api/Program.cs
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("InstructorOnly", policy => policy.RequireRole("Instructor")) // da co tu bai 3.7
    .AddPolicy("CourseOwnerPolicy", policy =>
        policy.Requirements.Add(new CourseOwnerRequirement()));
 
builder.Services.AddSingleton<IAuthorizationHandler, CourseOwnerAuthorizationHandler>();
```

> **📘 Ghi chú giảng viên:** *Vì sao AddSingleton mà không phải AddScoped? Handler này không inject DbContext hay bất kỳ service theo request nào — chỉ đọc ClaimsPrincipal và so sánh 2 giá trị, hoàn toàn không giữ state. Theo đúng khuyến nghị của tài liệu "Dependency injection in requirement handlers": Singleton an toàn cho handler stateless, nhưng tuyệt đối không đăng ký Singleton cho handler nào có inject EF Core DbContext — trường hợp đó phải AddScoped, nếu không DbContext sẽ bị tái sử dụng xuyên suốt vòng đời ứng dụng, rất dễ lỗi concurrency.*

### **3. Lab — Áp dụng vào UpdateCourseCommandHandler — 15 phút · Lab**

**Bước 1 — Thêm abstraction đọc user hiện tại (Application cần ClaimsPrincipal nhưng không được biết đến HttpContext):**

// TeduMarket.Application/Common/Interfaces/ICurrentUser.cs
using System.Security.Claims;

**Bước 2 — Implement ở Api layer (nơi duy nhất được phép biết HttpContext):**

```csharp
// TeduMarket.Api/Services/CurrentUser.cs
using System.Security.Claims;
using TeduMarket.Application.Common.Interfaces;
 
namespace TeduMarket.Api.Services;
 
public sealed class CurrentUser(IHttpContextAccessor httpContextAccessor) : ICurrentUser
{
    public ClaimsPrincipal Principal =>
        httpContextAccessor.HttpContext?.User ?? new ClaimsPrincipal(new ClaimsIdentity());
}
// TeduMarket.Api/Program.cs
builder.Services.AddHttpContextAccessor();
builder.Services.AddScoped<ICurrentUser, CurrentUser>();
```

> **📘 Ghi chú giảng viên:** *CurrentUser dùng primary constructor (C# 12, .NET 8+) — cú pháp gọn, đúng phong cách xuyên suốt khóa. Đừng nhầm đây là feature C# 14: primary constructor cho class thường có từ C# 12, chỉ record mới có từ sớm hơn (C# 9). Nếu học viên hỏi "field keyword của C# 14 dùng ở đây được không" — không hợp: field keyword dùng cho property có logic trong accessor, còn Principal ở đây là expression-bodied property thuần, không cần backing field thủ công.*

**Bước 4 — Sửa Handler: load Course trước, authorize sau, throw khi không đạt:**

```csharp
// TeduMarket.Application/Courses/Commands/UpdateCourse/UpdateCourseCommandHandler.cs
using Microsoft.AspNetCore.Authorization;
using TeduMarket.Application.Common.Interfaces;
using TeduMarket.Domain.Courses;
using TeduMarket.Domain.Courses.Exceptions;
 
namespace TeduMarket.Application.Courses.Commands.UpdateCourse;
 
public sealed class UpdateCourseCommandHandler(
    ICourseRepository courseRepository,
    IAuthorizationService authorizationService,
    ICurrentUser currentUser) : IRequestHandler<UpdateCourseCommand, Unit>
{
    public async Task<Unit> Handle(
        UpdateCourseCommand request, CancellationToken cancellationToken)
    {
        var course = await courseRepository.GetByIdAsync(request.CourseId, cancellationToken)
            ?? throw new CourseNotFoundException(request.CourseId); // da co tu bai 0.9
 
        var authorizationResult = await authorizationService.AuthorizeAsync(
            currentUser.Principal, course, "CourseOwnerPolicy");
 
        if (!authorizationResult.Succeeded)
        {
            throw new CourseForbiddenException(request.CourseId);
        }
 
        course.UpdateDetails(request.Title, request.Description, request.Price);
        await courseRepository.SaveChangesAsync(cancellationToken);
 
        return Unit.Value;
    }
}
```

**Bước 5 — Exception nghiệp vụ mới, đúng quy ước mục 7 của outline:**

public sealed class CourseForbiddenException(Guid courseId)

Map exception này sang HTTP 403 trong middleware ProblemDetails đã dựng ở bài 0.9 — chỗ đó đang map `CourseNotFoundException` sang 404, giờ thêm một nhánh: `CourseForbiddenException` → `StatusCodes.Status403Forbidden`, title "Forbidden", giữ đúng format ProblemDetails đã chuẩn hóa.

### **Kiểm thử thật bằng Postman**

- Lấy Access Token cho 2 tài khoản Instructor khác nhau qua /connect/token (đã test ở bài 3.2–3.3) — decode nhanh trên jwt.io để xác nhận claim instructor_id khác nhau giữa 2 token.
- Instructor A gọi PUT /api/v1/courses/{id} lên Course do Instructor B tạo → kỳ vọng 403 Forbidden, body ProblemDetails đúng chuẩn 0.9.
- Instructor A gọi PUT /api/v1/courses/{id} lên đúng Course của mình → kỳ vọng 200 OK, dữ liệu được cập nhật thật xuống Postgres.
- Thử bỏ Access Token hoặc dùng token của Student → phải bị chặn ở tầng Policy "InstructorOnly" (bài 3.7) trước, không cần đi đến CourseOwnerPolicy — hai lớp phòng thủ độc lập, đúng nguyên tắc defense in depth.

> **📘 Ghi chú giảng viên:** *Lỗi phổ biến nhất khi học viên tự làm: quên đăng ký AddHttpContextAccessor() → ICurrentUser.Principal luôn trả về ClaimsIdentity rỗng → CourseOwnerAuthorizationHandler không bao giờ Succeed dù token đúng → mọi request đều 403. Tôi luôn để lỗi này xảy ra thật trên máy demo, cho học viên thấy log rồi mới sửa — nhớ lâu hơn nói suông.*

## **Bài tập / Thực hành**

> **✏️ Đề bài:** Áp dụng đúng pattern CourseOwnerRequirement/CourseOwnerAuthorizationHandler/CourseOwnerPolicy vừa dựng cho DeleteCourseCommand — chỉ Instructor sở hữu Course mới được xóa. Không viết lại Requirement/Handler mới — tái sử dụng nguyên bộ vừa tạo, đây chính là lợi ích của resource-based authorization: 1 Handler dùng chung cho mọi operation cùng loại resource.

Input: DELETE /api/v1/courses/{id} kèm Access Token của một Instructor bất kỳ.

Expected output: Instructor không phải chủ sở hữu → 403 Forbidden (ProblemDetails đúng chuẩn 0.9). Instructor là chủ sở hữu → xóa thành công, 204 No Content.

> **✏️ Hint:** DeleteCourseCommandHandler phải load Course lên bằng courseRepository.GetByIdAsync(...) TRƯỚC khi gọi authorizationService.AuthorizeAsync(...) — thứ tự y hệt UpdateCourseCommandHandler ở trên, vì AuthorizeAsync cần resource cụ thể mới đánh giá được.

**Solution:**

```csharp
// TeduMarket.Application/Courses/Commands/DeleteCourse/DeleteCourseCommandHandler.cs
public sealed class DeleteCourseCommandHandler(
    ICourseRepository courseRepository,
    IAuthorizationService authorizationService,
    ICurrentUser currentUser) : IRequestHandler<DeleteCourseCommand, Unit>
{
    public async Task<Unit> Handle(
        DeleteCourseCommand request, CancellationToken cancellationToken)
    {
        var course = await courseRepository.GetByIdAsync(request.CourseId, cancellationToken)
            ?? throw new CourseNotFoundException(request.CourseId);
 
        var authorizationResult = await authorizationService.AuthorizeAsync(
            currentUser.Principal, course, "CourseOwnerPolicy");
 
        if (!authorizationResult.Succeeded)
        {
            throw new CourseForbiddenException(request.CourseId);
        }
 
        await courseRepository.DeleteAsync(course, cancellationToken);
 
        return Unit.Value;
    }
}
```

## **Tổng kết**

- Declarative ([Authorize]/.RequireAuthorization) trả lời "ai được phép vào cửa" — chạy trước khi resource được load, chỉ dùng được cho điều kiện không phụ thuộc dữ liệu cụ thể (role, scope).
- Imperative (IAuthorizationService.AuthorizeAsync gọi tay, sau khi resource đã có trong tay) trả lời "user này có quyền với đúng bản ghi này không" — bắt buộc dùng khi câu trả lời phụ thuộc dữ liệu.
- CourseOwnerRequirement + CourseOwnerAuthorizationHandler đặt ở Application layer vì thuần logic, không phụ thuộc HTTP hosting — Microsoft.AspNetCore.Authorization là NuGet package độc lập, không kéo theo toàn bộ ASP.NET Core.
- Đã thay hoàn toàn check tạm InstructorId do client tự khai (bài 1.2) bằng claim instructor_id đáng tin, lấy từ Access Token đã ký (bài 3.5).
- 1 Requirement/Handler dùng lại được cho mọi Command cùng thao tác trên Course (Update, Delete, và cả các operation sau này) — không phải viết logic ownership riêng cho từng Handler.

> **✅ Tóm tắt:** Resource-based authorization = load resource trước, rồi gọi AuthorizeAsync(user, resource, policyName) — không có cách nào làm việc này chỉ bằng attribute khai báo.
