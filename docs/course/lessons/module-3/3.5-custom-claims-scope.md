## **Nội dung chính**

### **1. Vấn đề: Access Token hiện tại thiếu thông tin**

Thời lượng: 5 phút | Loại: Lý thuyết ngắn

Từ bài 3.2 đến 3.4, /connect/token của bạn đã chạy được thật, nhưng Access Token sinh ra hiện tại gần như trống rỗng — chỉ có claim "sub" (subject) là id của user hoặc client. Điều này có 2 hệ quả:

- Resource Server (chính API TeduMarket.Api) không biết user vừa gọi request là ai về mặt nghiệp vụ — không có Role, không có InstructorId.
- Ở bài 1.2, CreateCourseCommandHandler / UpdateCourseCommandHandler đang check quyền sở hữu Course bằng InstructorId truyền tay trong body request — đây là cách làm tạm, học viên có thể tự sửa payload để giả làm Instructor khác. Bài 3.8 sẽ thay bằng CourseOwnerRequirement đọc InstructorId từ token đã ký, nhưng token phải CÓ claim đó trước đã.

Bài này giải quyết đúng phần "token phải có claim đó" — chưa đụng đến Authorization Handler (đó là việc của bài 3.7, 3.8).

### **2. Vì sao OpenIddict không tự copy hết claim vào token**

Theo tài liệu chính thức của OpenIddict: khi sinh authorization code, refresh token, device/user code, OpenIddict copy toàn bộ claim của ClaimsPrincipal vào token — an toàn vì các token này luôn được mã hóa, chỉ OpenIddict tự đọc được, client hay user cuối không đọc nổi nội dung bên trong.

Nhưng với Access Token và Identity Token thì khác — hai loại token này được thiết kế để bên ngoài đọc được: Identity Token dành cho client application đọc thông tin user, Access Token dành cho Resource Server (API) đọc để authorize request. Nếu tắt mã hóa Access Token (mặc định ở nhiều cấu hình dev), user hoàn toàn có thể copy token dán vào jwt.io và đọc được nội dung. Vì lý do bảo mật đó, OpenIddict server KHÔNG tự copy claim vào Access/Identity Token — trừ đúng 1 claim bắt buộc là "sub". Muốn một claim xuất hiện trong Access Token hoặc Identity Token, bạn phải gắn rõ "đích đến" (destination) cho claim đó.

> **📘 Ghi chú giảng viên:** *Đây là điểm hay bị hỏi nhất: học viên đã quen tự ký JWT thủ công ở khóa nền tảng (đưa gì vào Claims là JWT có ngay cái đó), nên rất dễ ngạc nhiên vì sao SetClaim() xong mà token vẫn không thấy claim. Nhấn mạnh: SetClaim chỉ đưa claim vào ClaimsIdentity, còn claim đó có được SERIALIZE vào token public (Access/Identity) hay không là quyết định riêng của SetDestinations — hai bước tách biệt, đây chính là khác biệt lớn nhất so với "tự ký JWT" ở khóa nền tảng.*

### **3. Đăng ký scope: "roles" (built-in) và "tedumarket.instructor" (custom)**

OpenIddict có sẵn một vài scope chuẩn OpenID Connect: openid, profile, email, roles, offline_access. Scope "roles" chưa được đăng ký ở bài 3.2 — cần bật lên. Ngoài ra, claim InstructorId là dữ liệu nhạy cảm hơn (định danh nghiệp vụ), nên thay vì gắn cứng theo Role, ta đăng ký thêm 1 scope tùy chỉnh để client phải khai báo rõ mình cần claim này.

Mở lại cấu hình OpenIddict Server ở TeduMarket.Infrastructure (đã tạo ở bài 3.2), thêm scope "roles" vào RegisterScopes:

```csharp
// TeduMarket.Infrastructure/Identity/OpenIddictServiceExtensions.cs
using static OpenIddict.Abstractions.OpenIddictConstants;
 
services.AddOpenIddict()
    .AddServer(options =>
    {
        options.SetTokenEndpointUris("connect/token")
               .SetAuthorizationEndpointUris("connect/authorize")
               .SetUserinfoEndpointUris("connect/userinfo");
 
        // "roles" là scope chuẩn OIDC — mới bật ở bài 3.5
        // "tedumarket.instructor" là scope tự định nghĩa, gắn với claim
        // InstructorId — chỉ Resource Server dùng, không phải OIDC chuẩn.
        options.RegisterScopes(
            Scopes.Email,
            Scopes.Profile,
            Scopes.Roles,
            "tedumarket.instructor");
        // ... AllowAuthorizationCodeFlow(), AddDevelopmentSigning...
        // giữ nguyên như bài 3.2
    });
```

Tiếp theo, cấp quyền yêu cầu 2 scope mới này cho client React Admin đã đăng ký ở bài 3.3 (chỉ Admin/Instructor mới cần InstructorId, Next.js Student site ở Module 7 sẽ không xin scope "tedumarket.instructor"):

```
// Đoạn seed OpenIddictApplication cho client "tedu-admin-spa" (bài 3.3), bổ sung:
Permissions =
{
    Permissions.Endpoints.Authorization,
    Permissions.Endpoints.Token,
    Permissions.GrantTypes.AuthorizationCode,
    Permissions.GrantTypes.RefreshToken,
    Permissions.ResponseTypes.Code,
    Permissions.Scopes.Email,
    Permissions.Scopes.Profile,
    Permissions.Scopes.Roles,                 // mới thêm
    Permissions.Prefixes.Scope + "tedumarket.instructor" // mới thêm
}
```

> **📘 Ghi chú giảng viên:** *Nhấn mạnh 2 lớp cấp quyền tách biệt trong OpenIddict: (1) RegisterScopes ở server — scope này TỒN TẠI và hợp lệ trong hệ thống; (2) Permissions.Scopes trên từng OpenIddictApplication — CLIENT NÀY được phép xin scope đó. Thiếu bước 2, request /connect/authorize?scope=...roles... từ đúng client vẫn bị OpenIddict từ chối với lỗi invalid_scope dù scope đã RegisterScopes ở bước 1. Đây là lỗi học viên hay gặp nhất ở phần này.*

### **4. Mở rộng ApplicationUser và định nghĩa claim type dùng chung**

InstructorId hiện chưa có chỗ lưu ở phía Identity. Mở ApplicationUser (Infrastructure, kế thừa IdentityUser\<Guid>, tạo cùng lúc với bài 3.2) và thêm property:

```csharp
// TeduMarket.Infrastructure/Identity/ApplicationUser.cs
public sealed class ApplicationUser : IdentityUser<Guid>
{
    // Chỉ có giá trị khi user này là 1 Instructor trong bounded context Catalog.
    // Gán khi tài khoản được duyệt làm Instructor (Module 1.9 / quy trình duyệt riêng).
    public Guid? InstructorId { get; set; }
}
```

Tên claim tùy chỉnh nên khai báo 1 lần dùng chung cho cả nơi phát hành token (Api/Infrastructure) lẫn nơi đọc token sau này (bài 3.7, 3.8 ở Application). Đặt trong TeduMarket.Application để không layer nào phải phụ thuộc ngược:

```csharp
// TeduMarket.Application/Common/AppClaimTypes.cs
namespace TeduMarket.Application.Common;
 
public static class AppClaimTypes
{
    public const string InstructorId = "instructor_id";
}
```

### **5. Sửa Token Exchange Handler: đưa Role, InstructorId vào Access Token**

Thời lượng: 15 phút | Loại: Demo + Lab

Mở endpoint xử lý /connect/token đã viết ở bài 3.2 (nhánh authorization_code / refresh_token — nhánh client_credentials của bài 3.4 không đụng vào, xem Ghi chú giảng viên bên dưới). Đây là phần thay đổi chính:

```csharp
// TeduMarket.Api/Endpoints/Connect/ConnectEndpoints.cs
using static OpenIddict.Abstractions.OpenIddictConstants;
using TeduMarket.Application.Common;
 
else if (request.IsAuthorizationCodeGrantType() || request.IsRefreshTokenGrantType())
{
    var result = await context.AuthenticateAsync(
        OpenIddictServerAspNetCoreDefaults.AuthenticationScheme);
 
    var user = await userManager.GetUserAsync(result.Principal!)
        ?? throw new InvalidOperationException("Không tìm thấy user tương ứng với token.");
 
    if (!await signInManager.CanSignInAsync(user))
    {
        return Results.Forbid(
            authenticationSchemes: [OpenIddictServerAspNetCoreDefaults.AuthenticationScheme]);
    }
 
    var identity = new ClaimsIdentity(
        result.Principal!.Claims,
        authenticationType: TokenValidationParameters.DefaultAuthenticationType,
        nameType: Claims.Name,
        roleType: Claims.Role);
 
    identity.SetClaim(Claims.Subject, await userManager.GetUserIdAsync(user))
            .SetClaim(Claims.Email, await userManager.GetEmailAsync(user))
            .SetClaim(Claims.Name, await userManager.GetUserNameAsync(user))
            .SetClaims(Claims.Role, (await userManager.GetRolesAsync(user)).ToImmutableArray());
 
    // Chỉ đưa InstructorId vào nếu user thật sự là Instructor.
    if (user.InstructorId is Guid instructorId)
    {
        identity.SetClaim(AppClaimTypes.InstructorId, instructorId.ToString());
    }
 
    identity.SetScopes(result.Principal.GetScopes());
    identity.SetResources(await scopeManager.ListResourcesAsync(identity.GetScopes()).ToListAsync());
    identity.SetDestinations(claim => GetDestinations(claim, user));
 
    return Results.SignIn(
        new ClaimsPrincipal(identity),
        properties: null,
        authenticationScheme: OpenIddictServerAspNetCoreDefaults.AuthenticationScheme);
}
```

Hàm GetDestinations quyết định claim nào được đưa vào Access Token, claim nào vào cả Access lẫn Identity Token, dựa theo scope client đã được cấp:

```
static IEnumerable<string> GetDestinations(Claim claim, ApplicationUser user)
{
    return claim.Type switch
    {
        // "profile" được cấp -> Name/Email lộ ra cả Access lẫn Identity Token
        // để SPA (Module 6.2) hiển thị "Xin chào {Name}" mà không cần gọi thêm API.
        Claims.Name or Claims.Email
            when claim.Subject!.HasScope(Scopes.Profile) =>
            [Destinations.AccessToken, Destinations.IdentityToken],
 
        // "roles" được cấp -> Role vào cả 2 token, Api dùng cho
        // [Authorize(Policy = "InstructorOnly")] ở bài 3.7.
        Claims.Role when claim.Subject!.HasScope(Scopes.Roles) =>
            [Destinations.AccessToken, Destinations.IdentityToken],
 
        // InstructorId: chỉ Api (Resource Server) cần để check quyền sở hữu
        // Course ở bài 3.8 -> chỉ đưa vào Access Token, KHÔNG vào Identity Token.
        // Đồng thời bắt buộc client phải xin đúng scope "tedumarket.instructor",
        // dù user có là Instructor thật hay không.
        AppClaimTypes.InstructorId
            when claim.Subject!.HasScope("tedumarket.instructor")
                 && user.InstructorId.HasValue =>
            [Destinations.AccessToken],
 
        // Mặc định: chỉ vào Access Token, không lộ ra Identity Token.
        _ => [Destinations.AccessToken]
    };
}
```

> **📘 Ghi chú giảng viên:** *Client Credentials Flow (bài 3.4) chạy ở một nhánh code khác — identity ở đó chỉ có claim client_id làm Subject, không có user thật, nên không chạm vào Role/InstructorId. Nếu học viên hỏi "vậy Hangfire job gọi API có Role không?" — trả lời: không, và không cần, vì Hangfire không thao tác thay mặt 1 Instructor cụ thể; nó có Client Credentials riêng, được cấp quyền bằng chính client_id đó ở tầng Authorization (sẽ thấy ở bài 3.7 khi định nghĩa Policy).*
>
> **📘 Ghi chú giảng viên:** *Giải thích thêm điểm hay bị hiểu lầm: HasScope() kiểm tra scope client đã XIN VÀ ĐƯỢC CẤP trong lần đăng nhập đó — không phải Permissions.Scopes đăng ký tĩnh ở Application entry. Một React Admin login mà request không có "scope=...roles..." thì dù client được phép xin scope roles, token vẫn không có Role claim. Đây là lý do bước test ở phần 6 phải sửa đúng tham số scope trong request Postman.*

### **6. Test & decode Access Token bằng jwt.io**

Thời lượng: 5 phút | Loại: Demo

Mở lại Postman collection test luồng Authorization Code + PKCE đã dựng ở bài 3.3. Sửa request tới /connect/authorize, thêm scope mới vào tham số scope:

```
GET /connect/authorize
    ?client_id=tedu-admin-spa
    &response_type=code
    &redirect_uri=https://oauth.pstmn.io/v1/callback
    &scope=openid profile roles tedumarket.instructor
    &code_challenge=...&code_challenge_method=S256
```

- Đăng nhập bằng 1 tài khoản đã gán role Instructor + có InstructorId (tạo sẵn qua seed data hoặc Identity API).
- Đổi authorization code lấy access_token ở bước POST /connect/token như đã làm ở bài 3.3.
- Copy nguyên access_token, dán vào https://jwt.io — phần payload phải thấy đủ: sub, name, email, role, instructor_id.
- Lặp lại với 1 tài khoản Student (không có InstructorId) — payload phải KHÔNG có claim instructor_id, dù cùng client và cùng xin scope tedumarket.instructor.

Đối chiếu 2 kết quả decode chính là cách xác nhận nhanh nhất cơ chế "gate theo cả scope lẫn dữ liệu thật của user" đã hoạt động đúng.

## **Bài tập thực hành**

> **✏️ Thực hành:** Thêm 1 claim boolean "is_admin" vào Access Token: chỉ true khi user có role "Admin", chỉ đưa vào Access Token (không vào Identity Token vì SPA không cần hiển thị UI theo claim này, chỉ Api cần check). Sau đó thực hiện đăng nhập với 3 tài khoản khác nhau — Admin, Instructor, Student — decode cả 3 token bằng jwt.io và ghi lại bảng so sánh: token của mỗi loại user có đúng những claim nào, thiếu đúng những claim nào.

Input: 3 tài khoản test đã seed sẵn (Admin/Instructor/Student), Postman collection từ bài 3.3.

Expected output: 3 access token decode được ở jwt.io, đúng claim theo đúng loại user; token của Student không có instructor_id lẫn is_admin.

Hint: sửa switch expression trong GetDestinations, thêm 1 nhánh mới cho claim "is_admin" tương tự nhánh InstructorId — nhớ SetClaim("is_admin", ...) trước khi SetDestinations có tác dụng.

### **Solution**

```csharp
// Thêm trong identity.SetClaim(...) chain:
identity.SetClaim("is_admin",
    (await userManager.GetRolesAsync(user)).Contains("Admin") ? "true" : "false");
 
// Thêm nhánh trong GetDestinations:
"is_admin" => [Destinations.AccessToken],
```

## **Tổng kết**

- OpenIddict không tự copy claim vào Access/Identity Token — phải khai báo destination rõ ràng cho từng claim bằng SetDestinations().
- Access Token và Identity Token có đối tượng đọc khác nhau (Resource Server vs Client app) — gate claim theo đúng nhu cầu, đừng đưa dư dữ liệu ra ngoài.
- Scope là lớp cấp quyền đầu tiên: RegisterScopes (scope tồn tại ở server) + Permissions.Scopes trên từng client (client được phép xin scope đó) là 2 bước tách biệt, thiếu 1 trong 2 sẽ lỗi invalid_scope hoặc claim không xuất hiện.
- Claim nhạy cảm như InstructorId nên gate kép: vừa theo scope client xin, vừa theo dữ liệu thật của user — không suy diễn quyền chỉ từ 1 điều kiện.
- Client Credentials Flow (bài 3.4) không có user thật nên không mang Role/InstructorId — quyền của nó đến từ chính client_id, sẽ dùng ở Policy bài 3.7.

> **✅ Tóm tắt:** Access Token của TeduMarket giờ đã mang đủ Role và InstructorId cho Resource Server đọc trực tiếp, không cần query lại DB mỗi request. Bài 3.6 sẽ xử lý Refresh Token & Token Revocation — vòng đời của chính những token vừa tạo ra ở bài này.
