## **Nội dung chính**

### **1. Vì sao không tự ký JWT thủ công? (Lý thuyết · 15 phút)**

Ở bài 3.1 bạn đã phân biệt Authorization Server – Resource Server – Client. Câu hỏi tiếp theo: tại sao TEDU Market không tự viết một class JwtTokenGenerator như khóa nền tảng đã làm?

Tự ký JWT thủ công (cách làm ở khóa nền tảng) chỉ giải quyết đúng 1 việc: sinh ra một chuỗi JWT có chữ ký hợp lệ. Nhưng một Authorization Server đúng chuẩn OAuth2/OIDC còn phải làm nhiều hơn thế:

- Quản lý vòng đời token: access token, refresh token, authorization code — mỗi loại có thời hạn, quy tắc revoke riêng.
- Client registration: mỗi ứng dụng gọi vào (React Admin, Next.js, Hangfire job) là một "client" có client_id, redirect_uri, scope được phép — không phải ai gọi /token cũng được cấp token.
- Scope & consent: kiểm soát chính xác client nào được xin quyền gì.
- Discovery document chuẩn: /.well-known/openid-configuration để các thư viện OIDC client (react-oidc-context ở Module 6, NextAuth-style ở Module 7) tự động dò cấu hình, không cần hard-code URL.
- Revocation & introspection tập trung: logout thật sự vô hiệu hoá token, không chỉ xoá ở phía client.

*OpenIddict implement đầy đủ những phần này, lưu toàn bộ Application/Authorization/Scope/Token vào chính DbContext bạn đã có — không cần thêm hạ tầng riêng. Đây chính là quyết định kiến trúc đã chốt: "OpenIddict chạy chung trong API project", không tách thành service riêng.*

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi học viên: "Nếu không dùng OpenIddict mà tự làm đủ 5 việc trên, bạn sẽ viết bao nhiêu class?" — để họ tự nhận ra chi phí bảo trì. Điểm hay bị hiểu nhầm: học viên tưởng OpenIddict là một service ngoài (như Keycloak/Auth0), phải nhấn mạnh nó chỉ là NuGet package chạy chung trong process với Api project.*

### **2. Tích hợp ASP.NET Core Identity vào AppDbContext (Demo · 15 phút)**

AppDbContext đã tạo ở bài 0.6 hiện là DbContext thuần cho write model (Category, và từ Module 1–2 là Course, Order...). Giờ ta mở rộng nó để vừa là Identity store vừa là OpenIddict store — đúng cấu trúc monorepo đã chốt ở mục 6: mọi thứ ghi (Command side) đi qua một DbContext duy nhất trong TeduMarket.Infrastructure.

Cài package vào project TeduMarket.Infrastructure:

```bash
dotnet add TeduMarket.Infrastructure package OpenIddict.AspNetCore
dotnet add TeduMarket.Infrastructure package OpenIddict.EntityFrameworkCore
dotnet add TeduMarket.Infrastructure package Microsoft.AspNetCore.Identity.EntityFrameworkCore
```

Tạo ApplicationUser và ApplicationRole trong TeduMarket.Infrastructure/Identity/ — đây là Identity entity, không phải Domain Aggregate, nên không đặt trong TeduMarket.Domain:

```csharp
// TeduMarket.Infrastructure/Identity/ApplicationUser.cs
namespace TeduMarket.Infrastructure.Identity;
 
public class ApplicationUser : IdentityUser<Guid>
{
    // InstructorId dùng ở bài 1.2/3.8 map trực tiếp vào Id (Guid) của ApplicationUser,
    // không cần thêm property — Instructor.UserId tham chiếu về đây.
    public string DisplayName { get; set; } = string.Empty;
}
 
// TeduMarket.Infrastructure/Identity/ApplicationRole.cs
public class ApplicationRole : IdentityRole<Guid>
{
}
```

Đổi AppDbContext để kế thừa IdentityDbContext thay vì DbContext thuần, đồng thời đăng ký entity set của OpenIddict:

```csharp
// TeduMarket.Infrastructure/Persistence/AppDbContext.cs
public class AppDbContext
    : IdentityDbContext<ApplicationUser, ApplicationRole, Guid>
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }
 
    public DbSet<Category> Categories => Set<Category>();
    public DbSet<Course> Courses => Set<Course>();
    // ... các DbSet khác đã có từ Module 0–2
 
    protected override void OnModelCreating(ModelBuilder builder)
    {
        base.OnModelCreating(builder); // bắt buộc: áp Identity schema trước
        builder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);
    }
}
```

Đăng ký entity set của OpenIddict lên chính DbContextOptions — gọi UseOpenIddict() ngay khi đăng ký DbContext, không phải trong OnModelCreating:

```csharp
// TeduMarket.Infrastructure/DependencyInjection.cs
services.AddDbContext<AppDbContext>(options =>
{
    options.UseNpgsql(connectionString);
    options.UseOpenIddict(); // đăng ký entity OpenIddictApplication/Authorization/Scope/Token
});
 
services.AddIdentity<ApplicationUser, ApplicationRole>(options =>
{
    options.Password.RequiredLength = 8;
    options.User.RequireUniqueEmail = true;
})
.AddEntityFrameworkStores<AppDbContext>()
.AddDefaultTokenProviders();
```

> **⚠️ Cảnh báo:** options.UseOpenIddict() đặt trong AddDbContext(...), khác với builder.UseOpenIddict() trong OnModelCreating ở một số bản tài liệu cũ (OpenIddict 3.x). Từ OpenIddict 4.x trở đi, cách khuyến nghị là gọi trên DbContextOptionsBuilder như trên — nếu bạn thấy code mẫu cũ trên mạng gọi builder.UseOpenIddict() bên trong OnModelCreating, đó là API cũ, đừng copy.

### **3. Cấu hình OpenIddict Server: 3 endpoint (Demo + Lab · 20 phút)**

Giờ đăng ký OpenIddict Core (dùng EF Core store vừa cấu hình) và Server (bật endpoint, chứng chỉ dev, flow):

```csharp
// TeduMarket.Infrastructure/DependencyInjection.cs (tiếp)
services.AddOpenIddict()
    .AddCore(options =>
    {
        options.UseEntityFrameworkCore()
               .UseDbContext<AppDbContext>();
    })
    .AddServer(options =>
    {
        // 3 endpoint theo yêu cầu bài này — authorize và userinfo sẽ
        // dùng thật ở bài 3.3 (Authorization Code + PKCE cho React Admin)
        options.SetTokenEndpointUris("connect/token")
               .SetAuthorizationEndpointUris("connect/authorize")
               .SetUserinfoEndpointUris("connect/userinfo");
 
        // Bật tạm Client Credentials để smoke-test /connect/token ngay bài này.
        // Authorization Code + PKCE bật đầy đủ ở bài 3.3, Client Credentials
        // "thật" (cho Hangfire/BackgroundService) đăng ký lại đúng chuẩn ở bài 3.4.
        options.AllowClientCredentialsFlow();
 
        // Chứng chỉ ký & mã hoá token — bản dev, KHÔNG dùng cho production
        options.AddDevelopmentEncryptionCertificate()
               .AddDevelopmentSigningCertificate();
 
        options.UseAspNetCore()
               .EnableTokenEndpointPassthrough()
               .EnableAuthorizationEndpointPassthrough()
               .EnableUserinfoEndpointPassthrough();
    })
    .AddValidation(options =>
    {
        // Cho phép chính Api project tự validate token nó vừa phát hành
        // (Resource Server = Authorization Server, đúng quyết định kiến trúc mục 5.2)
        options.UseLocalServer();
        options.UseAspNetCore();
    });
```

Đăng ký middleware đúng thứ tự trong Program.cs — sai thứ tự là lỗi phổ biến nhất khi setup OpenIddict:

```csharp
var app = builder.Build();
 
app.UseRouting();
app.UseCors();       // phải trước UseAuthentication
app.UseAuthentication();
app.UseAuthorization();
 
app.MapControllers(); // hoặc endpoint group Minimal API tương ứng
```

> **📘 Ghi chú giảng viên:** *Điểm học viên hay bị kẹt nhất ở bài này: quên app.UseAuthentication() hoặc đặt nó sau app.MapControllers(). Khi đó gọi /connect/token trả về lỗi rất khó hiểu (thường là 404 thay vì lỗi auth rõ ràng), vì middleware OpenIddict không kịp "chặn" request trước khi vào routing. Tôi luôn demo lỗi này có chủ đích — comment tạm dòng UseAuthentication(), cho học viên thấy lỗi thật, rồi mở lại.*

Chạy migration — dùng đúng IDesignTimeDbContextFactory đã tạo ở bài 1.5:

```bash
dotnet ef migrations add AddIdentityAndOpenIddict \
  --project src/TeduMarket.Infrastructure \
  --startup-project src/TeduMarket.Api
 
dotnet ef database update \
  --project src/TeduMarket.Infrastructure \
  --startup-project src/TeduMarket.Api
```

Mở migration vừa sinh ra, bạn sẽ thấy 2 nhóm bảng mới: bảng chuẩn của ASP.NET Core Identity (AspNetUsers, AspNetRoles, AspNetUserRoles...) và bảng của OpenIddict (OpenIddictApplications, OpenIddictAuthorizations, OpenIddictScopes, OpenIddictTokens) — tất cả nằm cùng schema với Category/Course, đúng như quyết định "chạy chung trong Api project".

### **4. Seed client test & xác nhận /connect/token hoạt động (Lab · 10 phút)**

Theo cùng pattern seed data đã dùng ở bài 1.5 (Category/Course), seed 1 OpenIddict Application dùng để smoke-test — client thật, đúng chuẩn cho background job sẽ đăng ký lại ở bài 3.4:

```csharp
// Program.cs — chạy trước app.Run(), giống pattern seed ở bài 1.5
await using (var scope = app.Services.CreateAsyncScope())
{
    var manager = scope.ServiceProvider
        .GetRequiredService<IOpenIddictApplicationManager>();
 
    if (await manager.FindByClientIdAsync("smoke-test-client") is null)
    {
        await manager.CreateAsync(new OpenIddictApplicationDescriptor
        {
            ClientId = "smoke-test-client",
            ClientSecret = "smoke-test-secret-dev-only",
            Permissions =
            {
                Permissions.Endpoints.Token,
                Permissions.GrantTypes.ClientCredentials
            }
        });
    }
}
```

Chạy API, mở Postman, gọi POST tới connect/token:

```
POST https://localhost:{port}/connect/token
Content-Type: application/x-www-form-urlencoded
 
grant_type=client_credentials
client_id=smoke-test-client
client_secret=smoke-test-secret-dev-only
```

Response 200 trả về access_token — copy chuỗi đó dán vào jwt.io để decode, bạn sẽ thấy claim iss (issuer, chính là base URL API), aud, exp. Đây là bằng chứng OpenIddict Server đã chạy đúng: sinh, ký token theo chuẩn OIDC mà không cần bạn viết một dòng JWT thủ công nào.

> **✏️ Thực hành:** Mở trình duyệt, gọi GET https://localhost:{port}/.well-known/openid-configuration. Đối chiếu JSON trả về với 3 URI bạn vừa cấu hình (SetTokenEndpointUris, SetAuthorizationEndpointUris, SetUserinfoEndpointUris) — xác nhận cả 3 đều xuất hiện đúng trong discovery document. Nếu thiếu 1 endpoint, kiểm tra lại đã gọi đúng Enable...EndpointPassthrough() tương ứng chưa. Solution: so khớp field token_endpoint / authorization_endpoint / userinfo_endpoint trong JSON với URI đã set — nếu app chưa chạy được, kiểm tra lại thứ tự middleware ở mục 3 trước.

## **Tổng kết**

> **✅ Tóm tắt:** OpenIddict quản lý toàn bộ vòng đời token, client registration, scope — không phải chỉ sinh JWT như cách tự ký thủ công.
> AppDbContext (bài 0.6) giờ kế thừa IdentityDbContext và gọi options.UseOpenIddict() để chứa cả write model, Identity, OpenIddict trong cùng 1 schema — đúng quyết định "chạy chung trong Api project".
> 3 endpoint đã bật: connect/token, connect/authorize, connect/userinfo — nhưng bài này mới smoke-test được token qua Client Credentials tạm thời.
> Thứ tự middleware UseAuthentication() trước UseAuthorization(), sau UseRouting/UseCors là điểm dễ sai nhất.

### **So sánh nhanh: tự ký JWT vs OpenIddict**

| **Tiêu chí** | **Tự ký JWT thủ công** | **OpenIddict** |
|---|---|---|
| Sinh token | Tự viết class ký JWT | AddServer() xử lý sẵn |
| Client registration | Không có — ai gọi cũng được | IOpenIddictApplicationManager quản lý |
| Discovery document | Không có | Tự sinh /.well-known/openid-configuration |
| Revoke token | Tự thiết kế bảng riêng | Quản lý tập trung (bài 3.6) |
| Chuẩn OIDC | Không đảm bảo | Tuân thủ OAuth2/OIDC đầy đủ |

**Bước tiếp theo:** Bài 3.3 — Authorization Code + PKCE Flow cho SPA sẽ dùng đúng OpenIddict Server vừa dựng ở bài này để đăng ký Client thật cho React Admin, thay thế hoàn toàn client smoke-test tạm ở đây.

### **Glossary**

- Authorization Server: thành phần cấp token (chính là OpenIddict Server trong bài này).
- Resource Server: thành phần nhận token và phục vụ dữ liệu — ở TEDU Market là chính Api project đó (nhờ .AddValidation().UseLocalServer()).
- Discovery document: JSON tại /.well-known/openid-configuration mô tả toàn bộ endpoint và capability của Authorization Server.
- Client Credentials Flow: luồng lấy token bằng client_id/client_secret, không có user — dùng smoke-test ở bài này, dùng thật cho background job ở bài 3.4.
