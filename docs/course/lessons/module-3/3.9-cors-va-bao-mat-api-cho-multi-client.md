# **Nội dung chính**

## **1. Same-Origin Policy & CORS là gì**

*Thời lượng: 10 phút | Loại: Lý thuyết*

Từ Module 3.2 đến 3.8, bạn đã có một Authorization Server thật bằng OpenIddict, endpoint /connect/token hoạt động, Access Token mang đúng claims, và Policy/Resource-based Authorization chặn đúng người dùng. Nhưng có một lớp chặn khác nằm ở phía trình duyệt, xảy ra trước khi request của bạn chạm tới OpenIddict hay Authorization Handler: Same-Origin Policy.

Same-Origin Policy (SOP) là quy tắc mặc định của mọi trình duyệt: một trang web chỉ được gọi AJAX/fetch tới cùng "origin" đã phục vụ nó. Origin được xác định bởi 3 thành phần: scheme (http/https) + host + port. Với hệ thống TEDU Market, khi lên production (Module 9.4) bạn sẽ có 3 origin hoàn toàn khác nhau:

- https://api.tedumarket.dev — TeduMarket.Api (Resource Server + Authorization Server)
- https://admin.tedumarket.dev — React Admin (Module 6, build bằng Vite)
- https://www.tedumarket.dev — Next.js Student site (Module 7)

Ở môi trường dev cũng vậy: React Admin chạy ở http://localhost:5173 (Vite mặc định), Next.js chạy ở http://localhost:3000, còn Api chạy ở https://localhost:5001 (hoặc port bạn cấu hình ở launchSettings.json). Ba origin này khác cổng nhau nên đã là 3 origin khác nhau theo SOP — kể cả khi cùng là localhost.

CORS (Cross-Origin Resource Sharing) không phải là cơ chế bảo mật của server — nó là cơ chế mà server "xin phép" trình duyệt cho một số origin cụ thể được đọc response của mình. Khi JavaScript ở origin A gọi fetch/XHR sang origin B:

- Nếu là "simple request" (GET/POST/HEAD, không có custom header, Content-Type thuộc nhóm đơn giản) → trình duyệt gửi thẳng request kèm header Origin, rồi kiểm tra header Access-Control-Allow-Origin trong response để quyết định có cho JavaScript đọc response hay không.
- Nếu là "non-simple request" (có Authorization header, Content-Type: application/json, method PUT/PATCH/DELETE...) → trình duyệt tự động gửi một request OPTIONS "preflight" trước, hỏi server có đồng ý cho method + header đó không, rồi mới gửi request thật.

> **📘 Ghi chú giảng viên:** *Đây là điểm học viên hay hiểu lầm nhất: CORS KHÔNG ngăn server thực thi request. Với simple request, server vẫn xử lý và trả kết quả bình thường — trình duyệt chỉ chặn JavaScript đọc response đó thôi. Tôi hay demo bằng cách gọi 1 POST tạo Category từ origin lạ: Network tab vẫn thấy status 201 Created (Category đã được tạo thật trong Postgres), nhưng Console báo lỗi CORS và JS không lấy được response.body. Vì TeduMarket Market dùng Bearer token qua Authorization header (không dùng cookie), Authorization header không tự động bị trình duyệt đính kèm khi gọi cross-origin như cookie — nên request từ origin lạ, dù server có xử lý, cũng không có token hợp lệ để vượt qua Module 3.2–3.8. CORS ở đây là lớp phòng thủ thứ hai, không phải lớp duy nhất.*

## **2. Cấu hình CORS Policy cho 2 origin**

*Thời lượng: 8 phút | Loại: Demo*

TeduMarket.Api sẽ phục vụ đúng 2 client trình duyệt: React Admin và Next.js Student site (Hangfire ở 3.4 dùng Client Credentials, gọi server-to-server, không qua trình duyệt nên không cần CORS). Ta khai báo origin trong appsettings để dev/production khác nhau mà không sửa code.

### **appsettings.Development.json**

```json
{
  "Cors": {
    "AllowedOrigins": [
      "http://localhost:5173",
      "http://localhost:3000"
    ]
  }
}
```

### **appsettings.Production.json**

```json
{
  "Cors": {
    "AllowedOrigins": [
      "https://admin.tedumarket.dev",
      "https://www.tedumarket.dev"
    ]
  }
}
```

Trong TeduMarket.Api, tạo một extension method để đăng ký CORS — giữ Program.cs gọn, đúng phong cách các bài trước (0.7, 3.2 cũng đã tách extension tương tự cho MediatR/OpenIddict):

### **TeduMarket.Api/Extensions/CorsServiceCollectionExtensions.cs**

```csharp
namespace TeduMarket.Api.Extensions;
 
public static class CorsServiceCollectionExtensions
{
    public const string TeduMarketClientsPolicy = "TeduMarketClients";
 
    public static IServiceCollection AddTeduMarketCors(
        this IServiceCollection services, IConfiguration configuration)
    {
        var allowedOrigins = configuration
            .GetSection("Cors:AllowedOrigins")
            .Get<string[]>() ?? [];
 
        services.AddCors(options =>
        {
            options.AddPolicy(TeduMarketClientsPolicy, policy =>
            {
                policy.WithOrigins(allowedOrigins)
                      .AllowAnyHeader()
                      .WithMethods("GET", "POST", "PUT", "PATCH", "DELETE")
                      .WithExposedHeaders("X-Total-Count");
            });
        });
 
        return services;
    }
}
```

Ba lựa chọn cần giải thích rõ cho học viên, vì đây là chỗ hay bị làm sai:

- WithOrigins(allowedOrigins) thay vì AllowAnyOrigin(): whitelist đúng origin, không dùng wildcard "\*" cho một API có OAuth2 thật.
- Không gọi AllowCredentials(): Admin và Web đều gửi Access Token qua header Authorization: Bearer ..., không dùng cookie liên-origin, nên không cần trình duyệt gửi kèm credential (cookie/HTTP auth) cross-origin. AllowCredentials() chỉ cần khi bạn dùng cookie-based session cross-origin — và ASP.NET Core sẽ từ chối cấu hình AllowAnyOrigin() + AllowCredentials() cùng lúc vì đó là lỗ hổng CSRF kinh điển.
- WithExposedHeaders("X-Total-Count"): mặc định trình duyệt chỉ cho JavaScript đọc một số header "an toàn" (Content-Type, Content-Length...). Nếu GetCoursesQuery ở bài 1.6 trả tổng số bản ghi qua header tùy biến X-Total-Count để FE dựng phân trang, mà không expose header này trong CORS, React Admin sẽ nhận response 200 OK bình thường nhưng response.headers.get('X-Total-Count') luôn trả null — một lỗi rất khó đoán nếu không biết CORS chi phối cả việc đọc header, không chỉ đọc body.

Đăng ký và kích hoạt trong Program.cs — thứ tự middleware là phần dễ sai nhất của bài này:

### **TeduMarket.Api/Program.cs (phần liên quan)**

```csharp
var builder = WebApplication.CreateBuilder(args);
 
// ... AddMediatR, AddOpenIddict (3.2), AddAuthorization (3.7) như các bài trước
builder.Services.AddTeduMarketCors(builder.Configuration);
 
var app = builder.Build();
 
if (app.Environment.IsProduction())
{
    app.UseHsts();
}
app.UseHttpsRedirection();
 
app.UseSecurityHeaders(); // custom middleware — xem mục 3
 
app.UseCors(CorsServiceCollectionExtensions.TeduMarketClientsPolicy);
 
app.UseAuthentication();
app.UseAuthorization();
 
app.MapCategoryEndpoints();
app.MapCourseEndpoints();
// ... các endpoint group khác
 
app.Run();
```

> **📘 Ghi chú giảng viên:** *UseCors() bắt buộc nằm SAU UseRouting (với Minimal API, routing được thiết lập ngầm khi bạn gọi các phương thức Map\*, nên chỉ cần đặt UseCors trước UseAuthentication/UseAuthorization) và TRƯỚC UseAuthentication/UseAuthorization. Đặt sai thứ tự — ví dụ UseCors sau UseAuthorization — sẽ khiến response lỗi 401/403 không có header CORS, và học viên sẽ thấy lỗi CORS trên Console dù bản chất là lỗi Auth, gây nhầm lẫn khi debug. Tôi luôn dừng ở dòng này và hỏi học viên: "Nếu đổi UseCors xuống dưới UseAuthorization thì request bị 403 có còn header Access-Control-Allow-Origin không?" — câu trả lời là không, và đó chính là lý do lỗi CORS hay bị chẩn đoán nhầm.*

## **3. Security Headers cơ bản & HTTPS**

*Thời lượng: 5 phút | Loại: Demo*

.NET 10 không có middleware dựng sẵn để set các security header (khác với CORS hay HSTS đã có UseCors/UseHsts) — cách chuẩn và phổ biến nhất là viết một middleware inline ngắn gọn, không cần thêm package ngoài cho mức "cơ bản" mà bài học yêu cầu:

### **TeduMarket.Api/Extensions/SecurityHeadersMiddlewareExtensions.cs**

```csharp
namespace TeduMarket.Api.Extensions;
 
public static class SecurityHeadersMiddlewareExtensions
{
    public static IApplicationBuilder UseSecurityHeaders(this IApplicationBuilder app)
    {
        return app.Use(async (context, next) =>
        {
            var headers = context.Response.Headers;
            headers["X-Content-Type-Options"] = "nosniff";
            headers["X-Frame-Options"] = "DENY";
            headers["Referrer-Policy"] = "strict-origin-when-cross-origin";
            headers["Permissions-Policy"] =
                "geolocation=(), camera=(), microphone=()";
 
            await next();
        });
    }
}
```

Ý nghĩa từng header, cần giải thích ngắn cho học viên vì đây là kiến thức hay bị học vẹt:

- X-Content-Type-Options: nosniff — chặn trình duyệt tự đoán Content-Type khác với header server trả về, tránh kiểu tấn công MIME-sniffing.
- X-Frame-Options: DENY — API này không cần render trong \<iframe>, chặn luôn để tránh clickjacking (không áp dụng logic tương tự cho Next.js/React Admin vì đó là 2 app khác, tự cấu hình security header riêng ở tầng của chúng).
- Referrer-Policy: strict-origin-when-cross-origin — không rò rỉ URL đầy đủ (có thể chứa query string nhạy cảm) khi request đi từ HTTPS sang origin khác.
- Permissions-Policy — tắt các quyền trình duyệt (camera, micro, geolocation) mà một Web API thuần túy không bao giờ cần, phòng trường hợp response bị nhúng sai chỗ.

Về HTTPS: app.UseHsts() chỉ nên bật ở production (đã thấy trong Program.cs ở mục 2) — HSTS yêu cầu trình duyệt đã có ít nhất 1 lần kết nối HTTPS thành công, sau đó ép mọi request tiếp theo (kể cả gõ http://) phải đi qua HTTPS trong suốt Max-Age đã cấu hình. Bật HSTS ở dev dễ khiến trình duyệt "nhớ" localhost phải HTTPS và làm hỏng lần test http local sau này.

> **📘 Ghi chú giảng viên:** *Nếu học viên hỏi "Sao không dùng package NWebsec hay tương tự cho security header?" — trả lời thẳng: các package đó vẫn hữu ích ở dự án thật, nhưng bài học ưu tiên middleware tự viết để học viên hiểu rõ cơ chế app.Use(...) trung gian, tránh biến việc set header thành "cấu hình ma thuật" qua package ngoài. Có thể nhắc học viên tự tìm hiểu thêm nếu muốn Content-Security-Policy chi tiết hơn cho production thật — nằm ngoài phạm vi khóa này.*

## **4. Lab: Test CORS thật với 2 origin**

*Thời lượng: 7 phút | Loại: Lab*

Chưa cần chờ tới Module 6/7 mới có React Admin và Next.js thật — ta giả lập 2 origin tĩnh ngay bây giờ để kiểm chứng cấu hình CORS vừa viết.

### **Bước 1 — Giả lập 2 origin**

```bash
# Terminal 1 — giả lập origin của React Admin (port 5173)
mkdir -p /tmp/fake-admin && cd /tmp/fake-admin
npx serve -l 5173
 
# Terminal 2 — giả lập origin của Next.js Student site (port 3000)
mkdir -p /tmp/fake-web && cd /tmp/fake-web
npx serve -l 3000
```

### **Bước 2 — Test bằng preflight request thật với curl**

```bash
# Origin được allow → phải thấy Access-Control-Allow-Origin trong response
curl -i -X OPTIONS https://localhost:5001/api/v1/categories \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: authorization,content-type"
```

# Origin lạ, không nằm trong allowlist → không có header Access-Control-Allow-Origin

```bash
curl -i -X OPTIONS https://localhost:5001/api/v1/categories \
  -H "Origin: https://evil-clone.com" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: authorization,content-type"
```

Ở request thứ nhất, bạn phải thấy: Access-Control-Allow-Origin: http://localhost:5173, Access-Control-Allow-Methods có POST, Access-Control-Allow-Headers có authorization. Ở request thứ hai, response vẫn trả 200/204 (middleware CORS không trả lỗi HTTP) nhưng KHÔNG có bất kỳ header Access-Control-\* nào — đây chính là cách trình duyệt (không phải curl) sẽ tự chặn request thật ở bước tiếp theo.

### **Bước 3 — Test bằng Console của trình duyệt**

Mở http://localhost:5173 (trang giả lập admin), bấm F12 mở Console, chạy:

```
fetch('https://localhost:5001/api/v1/categories', {
  headers: { 'Authorization': 'Bearer <access_token_lấy_từ_3.2>' }
}).then(r => r.json()).then(console.log)
```

Request phải thành công, thấy dữ liệu categories trả về. Sau đó mở tab http://localhost:3000 (giả lập origin khác nhưng đã được allow) và chạy lại — cũng phải thành công. Cuối cùng, đổi tạm origin allowlist trong appsettings.Development.json bỏ port 3000 ra, restart Api, chạy lại fetch y hệt từ http://localhost:3000 — lần này Console phải hiện lỗi CORS đỏ, còn Network tab vẫn thấy request có status 200 (server vẫn xử lý) nhưng Response bị ẩn khỏi JavaScript. Nhớ thêm lại port 3000 vào allowlist trước khi qua bài tập.

# **Bài tập thực hành**

> **✏️ Thực hành:** Module 4.4 (bài kế tiếp sau OpenIddict) sẽ thêm Rate Limiting cho nhóm endpoint Payment. Chuẩn bị trước cho bài đó: expose thêm header X-RateLimit-Remaining trong CORS policy hiện tại, dù server chưa thực sự trả header này (sẽ làm thật ở 4.4). Sau đó viết 1 middleware tạm (đặt trước UseCors) set cứng header X-RateLimit-Remaining: 100 cho mọi response, và verify bằng curl rằng header này xuất hiện trong Access-Control-Expose-Headers của response preflight.

*Input: Policy CORS hiện tại (mục 2) + middleware tạm bạn tự viết.*

*Expected output: curl -i -X OPTIONS ... -H "Origin: http://localhost:5173" phải trả về header Access-Control-Expose-Headers chứa cả X-Total-Count lẫn X-RateLimit-Remaining.*

*Hint 1: WithExposedHeaders() nhận vào params string[], có thể truyền nhiều giá trị cùng lúc thay vì gọi lại nhiều lần.*

*Hint 2: Middleware tạm chỉ cần app.Use(async (ctx, next) => { ctx.Response.Headers["X-RateLimit-Remaining"] = "100"; await next(); }); đặt trước app.UseCors(...).*

### **Solution**

```
policy.WithOrigins(allowedOrigins)
      .AllowAnyHeader()
      .WithMethods("GET", "POST", "PUT", "PATCH", "DELETE")
      .WithExposedHeaders("X-Total-Count", "X-RateLimit-Remaining");
```

# **Tổng kết**

> ✅ Same-Origin Policy là quy tắc của trình duyệt (scheme+host+port); CORS là cơ chế server "xin phép" trình duyệt cho một số origin cụ thể đọc response — không phải cơ chế Authentication/Authorization.
>
> ✅ Named CORS Policy được cấu hình bằng WithOrigins() đọc từ appsettings, khác nhau giữa dev (localhost:5173/3000) và production (admin/www.tedumarket.dev) — không dùng AllowAnyOrigin() cho API có OAuth2 thật.
>
> ✅ Không cần AllowCredentials() vì TEDU Market dùng Bearer token qua Authorization header, không dùng cookie liên-origin.
>
> ✅ UseCors() phải đặt sau UseHttpsRedirection, trước UseAuthentication/UseAuthorization — sai thứ tự sẽ làm lỗi Auth (401/403) bị hiểu nhầm thành lỗi CORS.
>
> ✅ Security header cơ bản (X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Permissions-Policy) viết bằng 1 middleware inline; HSTS chỉ bật ở production để tránh cache sai trên trình duyệt khi dev.

Bước tiếp theo: Module 3 đã hoàn tất — Authorization Server bằng OpenIddict giờ đã bảo vệ đúng người dùng (Authentication/Authorization) và đúng nguồn gọi (CORS). Bài 4.1 (.NET 10 OpenAPI built-in) sẽ chuẩn hóa schema OpenAPI của toàn bộ endpoint đã xây từ Module 0 đến 3 — bước bắt buộc trước khi generate API Client dùng chung cho cả React Admin và Next.js ở Module 5.
