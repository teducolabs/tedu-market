## **Nội dung chính**

### **1. Policy là gì — vì sao Role-based cũng chỉ là Policy (Lý thuyết · 10 phút)**

Từ bài 3.5 bạn đã có Access Token chứa claim Role và InstructorId. Nhưng "có claim" và "chặn được request" là hai việc khác nhau — muốn chặn, endpoint phải khai báo yêu cầu gì đó để framework đối chiếu với claim. Trong ASP.NET Core, thứ đối chiếu đó luôn luôn là một AuthorizationPolicy, kể cả khi bạn tưởng mình đang dùng "role check" hay "claim check" riêng biệt.

Một Policy là tập hợp các Requirement. Mỗi Requirement được một Handler xử lý — Handler gọi context.Succeed(requirement) khi user thỏa điều kiện. Khi bạn gọi policy.RequireRole("Instructor"), thực chất framework âm thầm thêm một RolesAuthorizationRequirement vào policy và dùng handler dựng sẵn để xử lý nó. RequireClaim cũng vậy, chỉ khác Requirement. Đây không phải chi tiết cắc cớ — nó giải thích tại sao ở bài 3.8, khi bạn cần logic phức tạp hơn (Instructor chỉ sửa được Course của chính mình), bạn sẽ viết một Requirement + Handler của riêng mình thay vì tìm một RequireXxx() có sẵn không tồn tại.

Cú pháp đăng ký chuẩn từ .NET 7 trở đi — và vẫn là cách khuyến nghị ở .NET 10 — là AddAuthorizationBuilder(), thay cho AddAuthorization(options => ...) kiểu cũ:

```csharp
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("AdminOnly",      policy => policy.RequireRole("Admin"))
    .AddPolicy("InstructorOnly", policy => policy.RequireRole("Instructor"))
    .AddPolicy("StudentOnly",    policy => policy.RequireRole("Student"));
```

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi: "Ai đã từng viết [Authorize(Roles = \\"Admin\\")] trực tiếp trên action?" — hầu hết học viên đã dùng nhưng không biết bên dưới nó cũng tạo ra một policy vô danh (anonymous policy). Đặt tên cho policy ("AdminOnly") chỉ là gói lại logic đó một chỗ, đổi 1 nơi thì mọi endpoint dùng chung policy đổi theo — khác hẳn việc phải sửa Roles = "Admin" rải rác ở từng action.*

### **2. Đăng ký Policy Admin / Instructor / Student — và bẫy claim của OpenIddict (Demo · 10 phút)**

Ba dòng AddPolicy ở trên nhìn đơn giản, nhưng nếu bạn dán thẳng vào project và test bằng token thật lấy từ /connect/token, endpoint sẽ trả 403 Forbidden dù bạn chắc chắn user có role Instructor. Đây là lỗi phổ biến nhất khi ghép OpenIddict với Policy Role-based, và gần như học viên nào cũng gặp — cần hiểu đúng nguyên nhân thay vì đoán mò sửa.

Nguyên nhân: ở bài 3.5, claim role được set destination bằng tên ngắn (Claims.Role, tức chuỗi "role") — đây là cách chính thức OpenIddict dùng khi ghi claim vào token. Nhưng RequireRole() / User.IsInRole() bên trong không tự đọc chuỗi "role" — nó đọc theo ClaimsIdentity.RoleClaimType, mà giá trị mặc định của thuộc tính này trong .NET lại là một URI dài kiểu WS-Federation (http://schemas.microsoft.com/ws/2008/06/identity/claims/role), không khớp với "role". Kết quả: claim có trong token thật, decode ở jwt.io thấy rõ, nhưng IsInRole() vẫn trả về false vì nó đang so sánh sai claim type.

> **⚠️ Lỗi kinh điển:** RequireRole("Instructor") luôn trả 403 dù access token có claim "role": "Instructor" — vì RoleClaimType mặc định không khớp với tên claim "role" mà OpenIddict phát ra.

Cách sửa: chỉnh RoleClaimType ngay tại nơi bạn đã cấu hình Validation handler ở bài 3.2 (Api project, cùng chạy OpenIddict Server theo quyết định kiến trúc #2). Thêm đúng 1 dòng options.Configure(...) — đây là API chính thức OpenIddict cung cấp để chỉnh TokenValidationParameters của validation handler:

```csharp
using static OpenIddict.Abstractions.OpenIddictConstants;
 
builder.Services.AddOpenIddict()
    .AddValidation(options =>
    {
        // Đã có từ bài 3.2 — OpenIddict Server và Api chạy chung project
        options.UseLocalServer();
        options.UseAspNetCore();
 
        // MỚI ở bài 3.7: khớp RoleClaimType với claim "role" OpenIddict phát ra,
        // nếu không RequireRole()/IsInRole() sẽ luôn trả về false.
        options.Configure(o => o.TokenValidationParameters.RoleClaimType = Claims.Role);
    });
```

> **📘 Ghi chú giảng viên:** *Đã học ở bài 3.2 rằng UseLocalServer() + UseAspNetCore() là đủ để Validation handler chạy — giờ bổ sung đúng 1 dòng RoleClaimType, không viết lại cấu hình từ đầu. Đây là dạng lỗi tôi khuyến khích để học viên tự đụng phải trước khi đưa lời giải — bắt request 403, mở jwt.io xem claim rõ ràng có "role", rồi mới ngồi lại giải thích nguyên nhân sẽ nhớ lâu hơn nhiều so với việc dán code đúng ngay từ đầu.*

### **3. Áp Policy lên endpoint Course (Lab · 10 phút)**

Course có 2 endpoint ghi dữ liệu từ Module 1.2: CreateCourseCommand và UpdateCourseCommand, expose qua Minimal API endpoint group /api/v1/courses (pattern đã dựng từ bài 0.7). Ở bài 1.2, việc "chỉ Instructor mới được sửa" mới chỉ là check tạm bằng cách so InstructorId truyền vào — chưa có xác thực thật. Bài này thay bước đó bằng Policy thật ở tầng Api, còn phần "đúng Instructor nào" (ownership) vẫn để nguyên, dành cho bài 3.8.

```csharp
var courses = app.MapGroup("/api/v1/courses").WithTags("Courses");
 
courses.MapPost("/", async (CreateCourseCommand command, ISender sender) =>
{
    var id = await sender.Send(command);
    return Results.Created($"/api/v1/courses/{id}", new { id });
})
// Đã học ở bài 1.2: check InstructorId tạm bợ trong Handler.
// Giờ thêm lớp chặn thật ở Api layer trước khi request chạm vào Handler.
.RequireAuthorization("InstructorOnly");
 
courses.MapPut("/{id:guid}", async (Guid id, UpdateCourseCommand command, ISender sender) =>
{
    await sender.Send(command with { CourseId = id });
    return Results.NoContent();
})
.RequireAuthorization("InstructorOnly");
```

Với project dùng Controller thay vì Minimal API, cách viết tương đương chính là [Authorize(Policy = "InstructorOnly")] đặt trên action — cùng một policy, chỉ khác cú pháp khai báo do TEDU Market dùng Minimal API endpoint group theo quyết định kiến trúc đã chốt ở mục 6 của outline.

> **📘 Ghi chú giảng viên:** *Điểm hay bị hỏi: "Sao không dùng RequireRole(\\"Instructor\\") thẳng trên endpoint cho nhanh, cần gì đặt tên Policy?" — Trả lời: nếu 5 endpoint khác nhau đều cần role Instructor, và sau này Product muốn cho phép thêm Admin cũng sửa được Course, dùng RequireRole rải rác phải sửa 5 chỗ; dùng RequireAuthorization("InstructorOnly") chỉ sửa đúng 1 dòng AddPolicy.*

> **⚠️ Giới hạn cố ý của bài này:** RequireAuthorization("InstructorOnly") chỉ trả lời "user này có role Instructor không" — chưa trả lời "Instructor này có đúng là chủ Course #123 không". Course A của Instructor A vẫn có thể bị Instructor B sửa ở trạng thái hiện tại. Đây là lỗ hổng có chủ đích, để lại đúng cho bài 3.8 giải quyết bằng Resource-based Authorization (IAuthorizationHandler + CourseOwnerRequirement), thay hẳn cho check InstructorId tạm bợ từ bài 1.2.

### **4. Test bằng Scalar / Postman**

Lấy 2 access token khác role từ /connect/token (một token role Instructor, một token role Student — dùng Client Credentials hoặc Password/Authorization Code tùy setup ở bài 3.2–3.4). Gọi thử:

- PUT /api/v1/courses/{id} với token role Instructor → kỳ vọng 204 No Content (hoặc 200 tùy handler).
- PUT /api/v1/courses/{id} với token role Student → kỳ vọng 403 Forbidden.
- Dán access token vào jwt.io, kiểm tra payload có đúng claim "role": "Instructor" — đối chiếu lại với claims destination đã cấu hình ở bài 3.5.

> **✏️ Thực hành:** Trong Scalar (/scalar), dùng nút Authorize để nhập access token, gọi thử PUT /api/v1/courses/{id} với cả 2 token. Chụp lại 2 response (200/204 và 403) để đối chiếu khi làm bài tập.

## **Bài tập thực hành**

Module 1.9 đã có CRUD Category hoàn chỉnh, trong đó có endpoint xóa Category (DELETE /api/v1/categories/{id}) — hiện tại endpoint này đang mở cho mọi user đã đăng nhập, chưa có ràng buộc role.

> **✏️ Yêu cầu:** Thêm policy AdminOnly (đã đăng ký ở mục 2) vào đúng endpoint DELETE /api/v1/categories/{id}, sao cho chỉ user role Admin mới xóa được Category, còn Instructor/Student gọi vào phải nhận 403.

Input: request DELETE /api/v1/categories/{id} kèm access token.

Expected output: token role Admin → 204 No Content, xóa thành công. Token role Instructor hoặc Student → 403 Forbidden, Category không bị xóa.

Hint: endpoint DELETE Category cũng nằm trong 1 MapGroup theo đúng pattern /api/v1/{số nhiều thực thể} ở mục 7 outline — chỉ cần thêm .RequireAuthorization("AdminOnly") vào đúng dòng MapDelete, không cần đổi Command hay Handler.

### **Solution**

```csharp
categories.MapDelete("/{id:guid}", async (Guid id, ISender sender) =>
{
    await sender.Send(new DeleteCategoryCommand(id));
    return Results.NoContent();
})
.RequireAuthorization("AdminOnly");
```

## **Tổng kết**

> Role-based, Claims-based trong ASP.NET Core đều được dựng trên cùng một cơ chế Policy — Requirement + Handler — không phải 3 kỹ thuật tách rời nhau.
>
> AddAuthorizationBuilder().AddPolicy(...) là cú pháp chuẩn để đặt tên và tập trung logic authorization, thay vì rải RequireRole/RequireClaim ở từng endpoint.
>
> OpenIddict phát claim role bằng tên ngắn "role" — phải set RoleClaimType = Claims.Role trong Validation handler, nếu không RequireRole()/IsInRole() luôn trả về false dù claim có thật trong token.
>
> RequireAuthorization("InstructorOnly") đã chặn đúng theo role, nhưng chưa chặn theo ownership (đúng Instructor nào) — phần đó thuộc về bài 3.8.

| **Kiểu Authorization** | **Trả lời câu hỏi** | **Dùng ở bài** |
|---|---|---|
| Role-based (Policy) | User có role gì? | 3.7 (bài này) |
| Claims-based (Policy) | User có claim cụ thể gì (InstructorId, scope...)? | 3.5 (phát claim) → có thể mở rộng ở 3.7 |
| Resource-based | User có quyền trên đúng resource này không? | 3.8 (bài kế tiếp) |

**Bước tiếp theo:** bài 3.8 — Resource-based Authorization, thay hẳn check InstructorId tạm bợ ở bài 1.2 bằng CourseOwnerRequirement + IAuthorizationHandler đúng chuẩn.

## **Phụ lục — Cheatsheet & tham khảo**

### **Cheatsheet AddPolicy**

```csharp
// Theo 1 role
policy.RequireRole("Instructor");
 
// Theo nhiều role (OR — chỉ cần 1 trong các role)
policy.RequireRole("Admin", "Instructor");
 
// Theo claim cụ thể (vd scope)
policy.RequireClaim("scope", "courses.write");
 
// Áp trên Minimal API endpoint / group
app.MapGroup("/api/v1/courses").RequireAuthorization("InstructorOnly");
```
