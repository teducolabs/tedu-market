## **Nội dung chính**

### **1. Vì sao SPA không thể giữ client_secret? (Lý thuyết · 15 phút)**

Ở bài 3.2, client "smoke-test-client" dùng Client Credentials Flow: gửi client_id + client_secret thẳng trong request, không có user nào tham gia — hợp lý cho Hangfire background job (bài 3.4) vì secret nằm trên server, không ai xem được. React Admin thì khác hẳn: code chạy hoàn toàn trong trình duyệt của người dùng. Bất kỳ chuỗi nào bạn nhúng vào bundle JavaScript — kể cả "giấu" trong file .env.production — đều có thể xem được chỉ bằng View Source hoặc mở DevTools. Một public client (thuật ngữ chính thức của OAuth2) không có nơi nào an toàn để giữ secret.

PKCE (Proof Key for Code Exchange, đọc là "pixy") giải quyết đúng vấn đề này: thay vì 1 secret cố định đăng ký sẵn, React Admin tự sinh ra một cặp giá trị MỚI cho mỗi lần đăng nhập:

- code_verifier — một chuỗi ngẫu nhiên (43–128 ký tự), chỉ tồn tại trong bộ nhớ của trình duyệt trong phiên đăng nhập đó.
- code_challenge — kết quả SHA-256(code_verifier) rồi encode Base64URL, gửi công khai trong URL redirect sang OpenIddict.

Luồng đầy đủ — đúng những gì bạn sẽ tự tay làm ở phần Lab:

- 1. React Admin sinh code_verifier + code_challenge, redirect trình duyệt sang GET /connect/authorize kèm code_challenge và code_challenge_method=S256.
- 2. OpenIddict lưu code_challenge lại, gắn với authorization code sắp phát hành. User đăng nhập (qua cookie ASP.NET Core Identity).
- 3. OpenIddict redirect trình duyệt về redirect_uri của React Admin kèm 1 authorization code (chuỗi dùng 1 lần, sống rất ngắn).
- 4. React Admin POST /connect/token gửi kèm code + code_verifier gốc (KHÔNG gửi secret).
- 5. OpenIddict tự tính lại SHA-256(code_verifier) nhận được, so với code_challenge đã lưu ở bước 2 — khớp mới phát access token + id_token.

> **📘 Ghi chú giảng viên:** *Điểm hay bị hiểu nhầm nhất: PKCE không thay thế việc đăng nhập — nó không xác thực user. User vẫn đăng nhập thật bằng cookie Identity ở bước 2. PKCE chỉ bảo vệ RIÊNG bước 3→4 (đổi code lấy token) khỏi bị một ứng dụng độc hại khác trên cùng máy chặn được authorization code rồi tự đổi lấy token thay. Tôi hay hỏi ngược: "Nếu không có PKCE, kẻ tấn công cần gì để lợi dụng authorization code bị lộ?" — câu trả lời: chỉ cần client_id (public, không bí mật) — đó chính là lỗ hổng PKCE vá lại.*

### **2. Bật Authorization Code Flow trên OpenIddict Server (Demo · 10 phút)**

Mở lại khối AddServer() đã viết ở bài 3.2 (TeduMarket.Infrastructure/DependencyInjection.cs), thêm 2 việc: cho phép flow mới, và đăng ký các scope chuẩn OIDC React Admin sẽ cần:

```csharp
// TeduMarket.Infrastructure/DependencyInjection.cs
services.AddOpenIddict()
    .AddCore(options =>
    {
        options.UseEntityFrameworkCore()
               .UseDbContext<AppDbContext>();
    })
    .AddServer(options =>
    {
        options.SetTokenEndpointUris("connect/token")
               .SetAuthorizationEndpointUris("connect/authorize")
               .SetUserinfoEndpointUris("connect/userinfo");
 
        // Đã có từ bài 3.2 — giữ nguyên cho smoke-test-client (bài 3.4 sẽ đăng ký lại đúng chuẩn)
        options.AllowClientCredentialsFlow();
 
        // MỚI ở bài 3.3: Authorization Code + bắt buộc PKCE cho MỌI client, không tuỳ chọn theo
        // từng client — nhất quán với quyết định kiến trúc: PKCE là bắt buộc, không phải "nice to have".
        options.AllowAuthorizationCodeFlow()
               .RequireProofKeyForCodeExchange();
 
        // Scope OIDC chuẩn React Admin sẽ xin — openid/offline_access được OpenIddict
        // special-case sẵn (không cần khai ở đây), 3 scope dưới thì bắt buộc phải đăng ký
        // tại Server, nếu không request sẽ bị từ chối dù Client đã có Permission tương ứng.
        options.RegisterScopes(
            OpenIddictConstants.Scopes.Email,
            OpenIddictConstants.Scopes.Profile,
            OpenIddictConstants.Scopes.Roles);
 
        options.AddDevelopmentEncryptionCertificate()
               .AddDevelopmentSigningCertificate();
 
        options.UseAspNetCore()
               .EnableTokenEndpointPassthrough()
               .EnableAuthorizationEndpointPassthrough()
               .EnableUserinfoEndpointPassthrough();
    })
    .AddValidation(options =>
    {
        options.UseLocalServer();
        options.UseAspNetCore();
    });
```

SetAuthorizationEndpointUris và EnableAuthorizationEndpointPassthrough() đã có sẵn từ bài 3.2 (bài đó bật cả 3 endpoint cùng lúc để chuẩn bị trước) — bài này chỉ thêm dòng AllowAuthorizationCodeFlow().RequireProofKeyForCodeExchange() và RegisterScopes(...).

> **📘 Ghi chú giảng viên:** *RequireProofKeyForCodeExchange() gọi ở đây là mức GLOBAL — áp dụng cho mọi client dùng Authorization Code Flow, kể cả client Next.js sẽ đăng ký ở Module 7. Cách khác là gắn Requirements.Features.ProofKeyForCodeExchange cho từng OpenIddictApplicationDescriptor riêng lẻ — tôi vẫn giữ dòng Requirements đó ở Client bên dưới cho tường minh, dù về mặt kỹ thuật là dư khi đã bật global, phòng trường hợp sau này đổi sang enforce theo từng client.*

### **3. Đăng ký OpenIddict Client cho React Admin (Demo · 10 phút)**

Theo đúng pattern seed đã dùng ở bài 3.2 (Program.cs, chạy trước app.Run() bằng IOpenIddictApplicationManager) — thêm 1 client MỚI bên cạnh smoke-test-client, không xoá client cũ:

```csharp
// Program.cs — tiếp phần seed OpenIddict application đã có ở bài 3.2
await using (var scope = app.Services.CreateAsyncScope())
{
    var manager = scope.ServiceProvider
        .GetRequiredService<IOpenIddictApplicationManager>();
 
    // smoke-test-client (bài 3.2) giữ nguyên ở đây, không đổi
 
    if (await manager.FindByClientIdAsync("tedu-market-admin") is null)
    {
        await manager.CreateAsync(new OpenIddictApplicationDescriptor
        {
            ClientId = "tedu-market-admin",
            ClientSecret = null,               // Public client — PKCE thay thế secret
            Type = OpenIddictConstants.ClientTypes.Public,
            ConsentType = OpenIddictConstants.ConsentTypes.Implicit, // first-party app của TEDU, bỏ màn hình consent
            DisplayName = "TEDU Market — React Admin",
            RedirectUris =
            {
                new Uri("http://localhost:5173/callback")
            },
            Permissions =
            {
                OpenIddictConstants.Permissions.Endpoints.Authorization,
                OpenIddictConstants.Permissions.Endpoints.Token,
                OpenIddictConstants.Permissions.GrantTypes.AuthorizationCode,
                OpenIddictConstants.Permissions.ResponseTypes.Code,
                OpenIddictConstants.Permissions.Scopes.Email,
                OpenIddictConstants.Permissions.Scopes.Profile,
                OpenIddictConstants.Permissions.Scopes.Roles
            },
            Requirements =
            {
                OpenIddictConstants.Requirements.Features.ProofKeyForCodeExchange
            }
        });
    }
 
    // Seed 1 user thật để đăng nhập thử — bỏ qua nếu bảng AspNetUsers đã có sẵn user
    var userManager = scope.ServiceProvider
        .GetRequiredService<UserManager<ApplicationUser>>();
 
    if (await userManager.FindByEmailAsync("instructor@tedu.com.vn") is null)
    {
        var user = new ApplicationUser
        {
            UserName = "instructor@tedu.com.vn",
            Email = "instructor@tedu.com.vn",
            EmailConfirmed = true
        };
        await userManager.CreateAsync(user, "Instructor@123");
    }
}
```

http://localhost:5173/callback là placeholder khớp cổng mặc định của Vite (bài 6.1 sẽ dựng apps/admin bằng Vite) — Module 6.2 mới thật sự implement route /callback trong React. Bài này chỉ cần khai đúng redirect_uri để Postman dùng test, vì OpenIddict so khớp redirect_uri theo chuỗi chính xác — sai 1 ký tự cũng bị từ chối invalid_client.

> **⚠️ Lưu ý version:** http (không phải https) cho localhost:5173 chỉ hợp lệ ở môi trường dev. OpenIddict không tự động ép https cho redirect_uri (khác với một số IdP thương mại như Auth0 luôn yêu cầu https) — nhưng khi lên production ở Module 9 (Nginx + Let's Encrypt), redirect_uri PHẢI đổi sang https://admin.teduMarket.dev/callback, nếu không token sẽ bị chặn ở tầng trình duyệt (mixed content) trước khi tới được OpenIddict.

### **4. Endpoint /connect/authorize — cầu nối cookie Identity với OpenIddict (Demo · 10 phút)**

Quyết định kiến trúc (mục 7 outline) chỉ quy định route domain dạng /api/v1/{số nhiều}; /connect/authorize là route giao thức cố định do chuẩn OAuth2/OIDC quy định, không thuộc phạm vi đó — nhưng ta vẫn viết nó bằng Minimal API, đúng tinh thần "toàn bộ Api layer là Minimal API" đã chốt từ bài 0.2, không cần thêm MVC Controller.

```csharp
// TeduMarket.Api/Endpoints/AuthorizationEndpoints.cs
using static OpenIddict.Abstractions.OpenIddictConstants;
 
public static class AuthorizationEndpoints
{
    public static void MapAuthorizationEndpoints(this WebApplication app)
    {
        app.MapMethods("connect/authorize", ["GET", "POST"], HandleAuthorizeAsync)
           .ExcludeFromDescription(); // route hạ tầng OpenIddict, không phải endpoint domain
    }
 
    private static async Task<IResult> HandleAuthorizeAsync(
        HttpContext httpContext,
        UserManager<ApplicationUser> userManager)
    {
        var request = httpContext.GetOpenIddictServerRequest()
            ?? throw new InvalidOperationException("Không đọc được yêu cầu OpenIddict.");
 
        var result = await httpContext.AuthenticateAsync(IdentityConstants.ApplicationScheme);
        if (!result.Succeeded)
        {
            // Chưa đăng nhập — yêu cầu học viên tự POST /account/login (mục Lab) bằng Postman trước
            return Results.Challenge(authenticationSchemes: [IdentityConstants.ApplicationScheme]);
        }
 
        var user = await userManager.GetUserAsync(result.Principal)
            ?? throw new InvalidOperationException("Cookie hợp lệ nhưng không tìm thấy user tương ứng.");
 
        var identity = new ClaimsIdentity(
            authenticationType: TokenValidationParameters.DefaultAuthenticationType,
            nameType: Claims.Name,
            roleType: Claims.Role);
 
        identity.SetClaim(Claims.Subject, await userManager.GetUserIdAsync(user))
                .SetClaim(Claims.Email, await userManager.GetEmailAsync(user))
                .SetClaim(Claims.Name, user.UserName)
                .SetClaims(Claims.Role, [.. await userManager.GetRolesAsync(user)]);
 
        identity.SetScopes(request.GetScopes());
        identity.SetDestinations(claim => claim.Type switch
        {
            Claims.Name or Claims.Email or Claims.Role =>
                [Destinations.AccessToken, Destinations.IdentityToken],
            _ => [Destinations.AccessToken]
        });
 
        return Results.SignIn(
            new ClaimsPrincipal(identity),
            authenticationScheme: OpenIddictServerAspNetCoreDefaults.AuthenticationScheme);
    }
}
```

Endpoint login tạm — CHỈ để test thủ công bằng Postman trước khi React Admin có UI thật, sẽ bỏ hẳn khi bài 6.2 hoàn thành (React tự POST credentials vào 1 trang login riêng, hoặc redirect thẳng qua /connect/authorize theo đúng chuẩn OIDC):

```csharp
// TeduMarket.Api/Endpoints/AuthorizationEndpoints.cs (tiếp)
app.MapPost("account/login", async (
    LoginRequest body,
    SignInManager<ApplicationUser> signInManager) =>
{
    var result = await signInManager.PasswordSignInAsync(
        body.Email, body.Password, isPersistent: false, lockoutOnFailure: false);
 
    return result.Succeeded ? Results.Ok() : Results.Unauthorized();
})
.ExcludeFromDescription();
 
public record LoginRequest(string Email, string Password);
```

> **📘 Ghi chú giảng viên:** *Đây là điểm .NET 10 thay đổi hành vi mà bạn PHẢI biết trước khi demo: từ .NET 10, một Minimal API endpoint dùng kiểu trả về IResult/TypedResults được ASP.NET Core tự nhận diện là "known API endpoint". Khi đó, cookie authentication handler KHÔNG còn redirect sang LoginPath khi Challenge() được gọi — nó trả thẳng 401. Điều này trước đây (net9 trở xuống) sẽ redirect sang trang login mặc định (không tồn tại) và làm Postman nhận một response HTML lỗi rất khó hiểu. Ở .NET 10, bạn sẽ thấy đúng 401 sạch sẽ — chính là hành vi ta cần để test bằng Postman mà không cần dựng trang login HTML nào cả.*

> **⚠️ Lưu ý version:** Behavior trên ("known API endpoints không redirect login, trả 401/403") là thay đổi chính thức từ .NET 10, áp dụng cho controller có [ApiController], Minimal API đọc/ghi JSON, và endpoint dùng TypedResults — nguồn: learn.microsoft.com/aspnet/core/security/authentication/api-endpoint-auth. Nếu bạn from .NET 9 lên .NET 10 và thấy hành vi Challenge() đổi khác so với video/tài liệu cũ, đây chính là nguyên nhân, không phải bug.

## **Bài tập / Thực hành**

Đi hết một vòng Authorization Code + PKCE hoàn toàn bằng Postman — không cần trình duyệt, không cần React.

### **Bước 1 — Đăng nhập lấy cookie**

```
POST https://localhost:{port}/account/login
Content-Type: application/json
 
{
  "email": "instructor@tedu.com.vn",
  "password": "Instructor@123"
}
```

Postman tự lưu cookie .AspNetCore.Identity.Application vào Cookie Jar (mặc định đã bật, không cần cấu hình gì thêm).

### **Bước 2 — Sinh code_verifier / code_challenge**

Mở tab Pre-request Script của request ở Bước 3, dán:

```typescript
const CryptoJS = require('crypto-js');
 
function base64url(wordArray) {
    return CryptoJS.enc.Base64.stringify(wordArray)
        .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}
 
const verifier = base64url(CryptoJS.lib.WordArray.random(32));
const challenge = base64url(CryptoJS.SHA256(verifier));
 
pm.collectionVariables.set('code_verifier', verifier);
pm.collectionVariables.set('code_challenge', challenge);
```

### **Bước 3 — Gọi /connect/authorize (nhớ tắt Automatically follow redirects)**

```
GET https://localhost:{port}/connect/authorize
  ?client_id=tedu-market-admin
  &response_type=code
  &redirect_uri=http://localhost:5173/callback
  &scope=openid profile email roles
  &code_challenge={{code_challenge}}
  &code_challenge_method=S256
  &state=xyz123
```

Response mong đợi: 302, header Location chứa http://localhost:5173/callback?code=...&state=xyz123 — copy giá trị code (chỉ dùng được 1 lần, hết hạn rất nhanh).

### **Bước 4 — Đổi code lấy token**

```
POST https://localhost:{port}/connect/token
Content-Type: application/x-www-form-urlencoded
 
grant_type=authorization_code
client_id=tedu-market-admin
code={code vừa copy}
redirect_uri=http://localhost:5173/callback
code_verifier={{code_verifier}}
```

Response 200 trả về access_token và id_token. Dán access_token vào jwt.io — xác nhận claim sub, email, name, role xuất hiện đúng như SetDestinations đã cấu hình ở mục 4.

> **✏️ Thực hành:** Lặp lại đúng Bước 4 nhưng đổi code_verifier thành một chuỗi ngẫu nhiên khác (sai). Xác nhận response trả lỗi 400 invalid_grant — đây là bằng chứng sống PKCE thật sự chặn được, không phải lý thuyết suông. Nếu vẫn nhận được token dù sai code_verifier, kiểm tra lại RequireProofKeyForCodeExchange() ở mục 2 đã được gọi đúng vị trí (bên trong .AddServer(), sau AllowAuthorizationCodeFlow()) chưa. Solution: so lại đúng thứ tự code ở mục 2 — thiếu dòng này là nguyên nhân phổ biến nhất khiến PKCE bị bỏ qua.

## **Tổng kết**

> **✅ Tóm tắt**
>
> • SPA là public client — không có nơi an toàn để giữ client_secret, PKCE thay thế bằng cặp code_verifier/code_challenge sinh mới mỗi lần đăng nhập.
>
> • AllowAuthorizationCodeFlow().RequireProofKeyForCodeExchange() bật ở mức Server, áp dụng cho mọi client dùng flow này, không tuỳ chọn theo từng app.
>
> • Client "tedu-market-admin" đăng ký kiểu Public, không ClientSecret, redirect_uri khớp cổng Vite mặc định — sẽ dùng thật ở Module 6.2.
>
> • /connect/authorize viết bằng Minimal API (không cần MVC Controller), dựa hoàn toàn vào cookie ASP.NET Core Identity đã có từ bài 3.2.
>
> • .NET 10 đổi hành vi Challenge() trên known API endpoint: trả 401 thay vì redirect — đúng thứ ta cần để test bằng Postman, không phải bug.

### **So sánh nhanh: Client Credentials (bài 3.2) vs Authorization Code + PKCE (bài này)**

| **Tiêu chí** | **Client Credentials** | **Authorization Code + PKCE** |
|---|---|---|
| Ai gọi | Service-to-service (Hangfire, bài 3.4) | User thật qua trình duyệt (React Admin) |
| Client type | Confidential — có client_secret | Public — không secret, PKCE thay thế |
| User context | Không có | Có — token gắn với 1 user cụ thể |
| Bảo vệ bằng | client_secret giữ trên server | code_verifier sinh mới mỗi phiên |
