## Nội dung chính

### 1. Vì sao module này khó nhất khóa — và vì sao không tự ký JWT nữa

Ở khóa nền tảng "Xây dựng website học trực tuyến với ASP.NET Core", bạn đã tự ký JWT thủ công: tự viết code sinh token, tự thiết kế bảng lưu refresh token, tự viết logic revoke. Cách đó chạy được, nhưng có vấn đề: mọi lỗ hổng bảo mật liên quan đến vòng đời token — refresh token bị đánh cắp, replay attack, quên revoke khi logout — đều do bạn tự chịu trách nhiệm, tự nghĩ ra cách vá.

OpenIddict là một Authorization Server hoàn chỉnh, implement đúng chuẩn OAuth2/OpenID Connect (OIDC), đã được cộng đồng dùng thật trong production và liên tục vá lỗi bảo mật. Từ Module 3 trở đi, TEDU Market không tự ký JWT nữa — toàn bộ vòng đời token (cấp, refresh, revoke) giao cho OpenIddict quản lý.

Nhưng trước khi mở Visual Studio cấu hình OpenIddict ở bài 3.2, bạn phải hiểu đúng khái niệm nền OAuth2/OIDC. Đây là lý do bài 3.1 là bài lý thuyết thuần — nếu hiểu sai luồng ngay từ đầu, bạn có thể cấu hình đúng cú pháp OpenIddict nhưng sai luồng bảo mật mà không hề biết.

### 2. Authentication và Authorization — tách bạch rõ ràng

Hai khái niệm này thường bị gộp làm một, nhưng trả lời hai câu hỏi hoàn toàn khác nhau:

- Authentication (AuthN) — "Bạn là ai?": xác minh danh tính, thường qua bước đăng nhập (username/password, hoặc social login).
- Authorization (AuthZ) — "Bạn được làm gì?": sau khi đã biết danh tính, xác định người này có quyền truy cập tài nguyên nào.

Ví dụ ngay trong TEDU Market: Instructor đăng nhập vào React Admin (Authentication) — hệ thống xác minh đúng là Instructor đó. Nhưng khi Instructor này bấm sửa một Course, hệ thống còn phải kiểm tra thêm: Course đó có đúng do Instructor này sở hữu không (Authorization) — đây chính là nội dung bài 3.8 (Resource-based Authorization) sẽ triển khai bằng IAuthorizationHandler.

Điểm quan trọng cần nói rõ ngay: bản chất OAuth2 là một giao thức ỦY QUYỀN (Authorization) — không phải giao thức xác thực (Authentication). OAuth2 thuần chỉ định nghĩa cách một Client lấy được access token để truy cập tài nguyên thay mặt user, và không chuẩn hóa cách lấy thông tin danh tính của user đó. Đây là lý do OpenID Connect (mục 7 của bài) ra đời.

> **📘 Ghi chú giảng viên:** *Đây là lỗi hiểu sai phổ biến nhất tôi gặp: học viên nghĩ "dùng OAuth2 để login". Tôi hay dừng lại ở đây, hỏi ngược: "Nếu OAuth2 chỉ lo authorization, vậy cái gì cho hệ thống biết user vừa đăng nhập tên gì, email gì?" — câu trả lời sẽ dẫn thẳng vào phần OpenID Connect ở mục 7, giữ học viên tò mò thay vì nhồi định nghĩa ngay.*

### 3. Bốn vai trò trong OAuth2

RFC 6749 định nghĩa 4 vai trò cố định trong mọi luồng OAuth2. Nắm chắc 4 vai trò này là điều kiện để đọc hiểu bất kỳ tài liệu OAuth2/OIDC nào sau này, kể cả docs của OpenIddict.

| Vai trò (RFC 6749) | Ý nghĩa | Trong TEDU Market |
|---|---|---|
| **Resource Owner** | Chủ sở hữu tài nguyên, thường là con người. | Học viên hoặc Instructor — chủ sở hữu Order, Course của chính họ. |
| **Client** | Ứng dụng yêu cầu truy cập tài nguyên thay mặt Resource Owner. | React Admin (SPA), Next.js Student site, và Background Service xử lý Outbox (bài 2.7). |
| **Authorization Server** | Nơi xác thực Resource Owner và cấp token cho Client. | OpenIddict — chạy chung trong TeduMarket.Api (quyết định kiến trúc #2, không tách service riêng). |
| **Resource Server** | Nơi lưu trữ tài nguyên thực tế, chấp nhận access token để trả dữ liệu. | Cũng chính là TeduMarket.Api — các endpoint /api/v1/courses, /api/v1/orders... |

> **📘 Ghi chú giảng viên:** *Học viên hay bối rối vì Authorization Server và Resource Server "trùng nhau" — cùng nằm trong TeduMarket.Api. Tôi nhấn mạnh: đây vẫn là 2 vai trò logic khác nhau, chỉ là được triển khai chung 1 process để giảm độ phức tạp vận hành cho quy mô của khóa (đúng như quyết định kiến trúc đã chốt ở outline). Ở hệ thống lớn hơn, 2 vai trò này hoàn toàn có thể tách thành 2 service riêng — Module 9 có ghi chú ngắn về hướng này.*

### 4. Authorization Code Flow — luồng chuẩn cho ứng dụng có user

Đây là flow OAuth2 dùng khi có Resource Owner (user) tham gia trực tiếp — tức là gần như mọi trường hợp đăng nhập của React Admin và Next.js Student site. Các bước theo RFC 6749 §4.1:

1. Client (ví dụ React Admin) redirect trình duyệt của user sang endpoint /connect/authorize của Authorization Server, kèm client_id, redirect_uri, scope.
1. Authorization Server hiển thị trang đăng nhập (nếu user chưa có session) và trang consent (đồng ý cấp quyền cho Client).
1. Sau khi user đăng nhập và đồng ý, Authorization Server redirect trình duyệt về đúng redirect_uri đã đăng ký, kèm theo một authorization code (chuỗi ngắn hạn, dùng một lần).
1. Client gửi authorization code này lên endpoint /connect/token — lần gửi này đi qua kênh backchannel (server-to-server), không qua trình duyệt, nên an toàn hơn.
1. Authorization Server xác thực Client, kiểm tra code hợp lệ, rồi trả về access_token (và id_token, refresh_token nếu có yêu cầu).
1. Client dùng access_token để gọi API trên Resource Server — đính kèm trong header Authorization: Bearer \<access_token>.

Điểm mấu chốt: authorization code chỉ đi qua trình duyệt (kênh dễ bị lộ qua log, browser history, redirect sai), còn access_token thật sự chỉ được trao đổi qua kênh backchannel an toàn hơn. Đây là lý do Authorization Code Flow an toàn hơn hẳn Implicit Flow đời cũ (đã bị khuyến nghị bỏ, không dùng trong khóa này).

### 5. PKCE — vì sao Public Client bắt buộc dùng

Client trong OAuth2 chia làm 2 loại: Confidential Client (giữ được client_secret an toàn, ví dụ ứng dụng chạy trên server như Background Service) và Public Client (không thể giữ bí mật an toàn, vì code chạy ngay trên máy/trình duyệt của user và có thể bị đọc ngược — điển hình là Single Page Application như React Admin, hoặc ứng dụng mobile).

Với Public Client, nếu chỉ dùng Authorization Code Flow thuần, hệ thống có thể bị Authorization Code Interception Attack: kẻ tấn công chặn được authorization code ở bước redirect (qua proxy độc hại, log hệ thống, hoặc trên mobile là một app khác đăng ký trùng custom URL scheme), rồi tự mang code đó đi đổi lấy access_token — vì Public Client không có client_secret để Authorization Server phân biệt ai là Client hợp lệ.

PKCE (Proof Key for Code Exchange) giải quyết đúng lỗ hổng này:

- Trước khi redirect, Client tự sinh một chuỗi bí mật ngẫu nhiên gọi là code_verifier, và tính code_challenge = hash(code_verifier) bằng SHA-256.
- Bước redirect sang /connect/authorize gửi kèm code_challenge (không gửi code_verifier).
- Khi đổi code lấy token ở bước /connect/token, Client phải gửi kèm code_verifier gốc — Authorization Server tự hash lại và so khớp với code_challenge đã nhận trước đó.

Kết quả: kẻ tấn công có chặn được authorization code cũng không đổi được token, vì không có code_verifier (chỉ tồn tại trong bộ nhớ của Client hợp lệ, không đi qua kênh redirect). Ban đầu PKCE được thiết kế cho mobile app, nhưng hiện nay được khuyến nghị dùng cho mọi loại Client — kể cả Confidential Client — như một lớp phòng thủ bổ sung chống rò rỉ authorization code.

```
// Bài 3.2 sẽ cấu hình OpenIddict bắt buộc PKCE cho toàn bộ client:
options.RequireProofKeyForCodeExchange();
```

> **📘 Ghi chú giảng viên:** *Câu hỏi hay gặp: "Next.js Student site có server, sao vẫn cần PKCE?". Tôi trả lời: đúng là Next.js có thể đóng vai Confidential Client vì giữ được secret ở server-side (bài 7.4 sẽ làm session ở server, không lưu token ở localStorage) — nhưng OpenIddict khuyến nghị bật RequireProofKeyForCodeExchange() cho TẤT CẢ client, kể cả confidential, vì PKCE là lớp phòng thủ thêm, không thay thế cho việc giữ secret an toàn. Trong khóa này ta bật PKCE đồng loạt cho đơn giản và nhất quán, thay vì cấu hình riêng lẻ từng Client.*

### 6. Client Credentials Flow — cho service nội bộ, không có user

Không phải luồng nào cũng có user tham gia. Khi một service nội bộ cần gọi API mà không đại diện cho bất kỳ user cụ thể nào, dùng Client Credentials Flow: Client tự xác thực trực tiếp với Authorization Server bằng client_id + client_secret của chính nó, đổi thẳng lấy access_token — không có bước redirect, không có authorization code, không có Resource Owner tham gia.

Trong TEDU Market, ví dụ điển hình là Background Service xử lý Outbox đã xây ở bài 2.7: job này chạy nền, đọc bảng Outbox và tạo Enrollment sau khi Order chuyển Paid — nếu về sau job cần gọi ngược lại chính API TeduMarket.Api cho một thao tác nội bộ (thay vì thao tác thẳng vào DbContext trong cùng process), nó sẽ dùng Client Credentials Flow để tự lấy token, không thể dùng Authorization Code Flow vì không có user nào đang ngồi chờ đăng nhập. Bài 3.4 sẽ đăng ký một OpenIddict Client riêng cho đúng luồng này.

### 7. OAuth2 và OpenID Connect — đừng nhầm là một

Tên đầy đủ của thư viện là OpenIddict — ghép từ "OpenID" và "dict" (identity dictionary), vì nó implement cả hai chuẩn:

- OAuth2 (RFC 6749): chuẩn ỦY QUYỀN. Chỉ định nghĩa access_token và các flow để lấy access_token. Không định nghĩa cách lấy thông tin danh tính user một cách chuẩn hóa.
- OpenID Connect (OIDC): một lớp AUTHENTICATION xây thêm trên OAuth2. Thêm scope openid, thêm id_token (một JWT chứa các claim mô tả danh tính user: sub, name, email...), và thêm endpoint /connect/userinfo để Client lấy thông tin profile.

Nói ngắn gọn: access_token trả lời "Client này được phép làm gì trên Resource Server"; id_token trả lời "User vừa đăng nhập là ai". Khi cấu hình OpenIddict ở bài 3.2, bạn sẽ thấy cả hai token này được cấp cùng lúc trong response của /connect/token khi request có scope openid.

### 8. Áp dụng vào kiến trúc TEDU Market — sơ đồ luồng OAuth2 (deliverable)

Ghép lại toàn bộ khái niệm ở trên vào đúng 3 Client của hệ thống TEDU Market:

| Client | Loại Client | Flow sử dụng |
|---|---|---|
| **React Admin (Vite, SPA)** | Public Client | Authorization Code + PKCE bắt buộc — cấu hình Client ở bài 3.3, triển khai UI thật ở bài 6.2 bằng react-oidc-context. |
| **Next.js Student site** | Confidential Client | Authorization Code + PKCE — nhưng xử lý ở server-side (route handler), không lưu token ở trình duyệt (bài 7.4). |
| **Background Service (Outbox job)** | Confidential Client | Client Credentials Flow — không có user, tự xác thực bằng client_id/client_secret (bài 3.4). |

Sơ đồ luồng Authorization Code + PKCE áp dụng cho React Admin (đại diện cho nhóm Public Client) — dùng lại ở bài 3.3 khi cấu hình OpenIddict Client thật:

```
React Admin (Public Client)         OpenIddict (TeduMarket.Api)
        |                                       |
        | 1. Sinh code_verifier + code_challenge|
        |-------- GET /connect/authorize ------>|
        |    (client_id, redirect_uri,           |
        |     code_challenge, scope=openid)       |
        |                                       |
        |<---- Trang đăng nhập + consent --------|
        |            (Resource Owner xác nhận)   |
        |                                       |
        |<------ Redirect kèm authorization code-|
        |                                       |
        |----- POST /connect/token ------------>|
        |  (code, code_verifier, client_id)      |
        |                                       |
        |<---- access_token + id_token ----------|
        |     (+ refresh_token nếu có yêu cầu)    |
        |                                       |
        |-- Authorization: Bearer <access_token>->|
        |        GET /api/v1/courses             |
        |                                       |
        |<-------- 200 OK + dữ liệu -------------|
```

> **📘 Ghi chú giảng viên:** *Đây chính là deliverable của bài: một sơ đồ áp dụng đúng khái niệm OAuth2/OIDC vào 3 client thật của hệ thống — không phải sơ đồ SPA/Mobile chung chung trong sách. Tôi thường yêu cầu học viên tự vẽ lại sơ đồ này trên giấy hoặc Excalidraw trước khi xem bản mẫu, để chắc chắn hiểu chứ không chỉ chép lại.*

Câu hỏi tình huống (trả lời bằng 3-5 câu, không cần code): Nếu Next.js Student site lưu access_token trực tiếp ở localStorage của trình duyệt thay vì giữ ở server-side session, rủi ro bảo mật cụ thể là gì? Next.js có server (route handler) nên có thể giữ token trong session phía server, chỉ gửi cookie HttpOnly về trình duyệt — JavaScript phía client không đọc được. React Admin là SPA thuần, không có server riêng để giữ hộ, nên buộc phải chấp nhận giữ token ở phía trình duyệt (thường là bộ nhớ JS, tránh localStorage) — đây là lý do PKCE và vòng đời access_token ngắn hạn quan trọng hơn nhiều với Public Client. Bài 7.4 sẽ triển khai đúng mô hình server-side session cho Next.js.*

## Tổng kết

> **✅ Tóm tắt:** OAuth2 là giao thức ỦY QUYỀN (authorization), không phải xác thực (authentication) — OpenID Connect mới là lớp xác thực xây thêm trên OAuth2, cấp id_token.

- 4 vai trò cố định: Resource Owner, Client, Authorization Server, Resource Server — trong TEDU Market, Authorization Server và Resource Server cùng chạy trong TeduMarket.Api.
- Authorization Code Flow: dùng khi có user tham gia — authorization code đi qua trình duyệt, access_token trao đổi qua kênh backchannel an toàn hơn.
- PKCE bắt buộc với Public Client (SPA, mobile) để chống Authorization Code Interception Attack — code_verifier chỉ Client hợp lệ mới có.
- Client Credentials Flow: dùng cho service nội bộ không có user, tự xác thực bằng client_id/client_secret — áp dụng cho Background Service xử lý Outbox.

### Bảng so sánh nhanh

|  | Authorization Code + PKCE | Client Credentials |
|---|---|---|
| **Có user tham gia?** | Có — Resource Owner đăng nhập, consent. | Không — Client tự xác thực. |
| **Dùng cho Client nào trong TEDU Market** | React Admin, Next.js Student site. | Background Service xử lý Outbox. |
| **Bài cấu hình chi tiết** | Bài 3.3. | Bài 3.4. |

**Bước tiếp theo:** Bài 3.2 — Setup OpenIddict Server: cấu hình endpoint /connect/token, /connect/authorize, /connect/userinfo thật trong TeduMarket.Api, tích hợp ASP.NET Core Identity làm user store.

| **PKCE** | Proof Key for Code Exchange — cơ chế thêm code_verifier/code_challenge để bảo vệ Authorization Code Flow, bắt buộc cho Public Client. |
| **Confidential / Public Client** | Confidential: giữ được client_secret an toàn (chạy trên server). Public: không giữ được (SPA, mobile). |
| **id_token / access_token** | id_token (OIDC): JWT mô tả danh tính user. access_token (OAuth2): dùng để gọi API, không đảm bảo chứa thông tin danh tính. |

Nguồn tham khảo chính thức: RFC 6749 (The OAuth 2.0 Authorization Framework), OpenID Connect Core 1.0 (openid.net/specs), OpenIddict Documentation — mục Configuration/Proof Key for Code Exchange (documentation.openiddict.com).
