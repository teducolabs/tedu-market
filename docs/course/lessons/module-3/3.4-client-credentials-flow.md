# **Nội dung chính**

## **1. Vì sao Client Credentials, không phải Authorization Code?**

*Thời lượng: 10 phút | Loại: Lý thuyết*

Ở bài 3.3, bạn đã xây luồng Authorization Code + PKCE cho React Admin — có một User thật ngồi trước màn hình, trình duyệt redirect sang trang login, User nhập mật khẩu. Nhưng có những nơi trong hệ thống TEDU Market hoàn toàn không có User nào đứng sau request:

- Hosted Service xử lý Outbox (bài 2.7) chạy nền theo lịch, không ai đăng nhập thay cho nó.
- Về sau, nếu bạn tách Authorization Server ra một service riêng (Module 9 có ghi chú hướng này), API chính cần một cách xác thực khi gọi sang service khác mà không có phiên đăng nhập nào cả.

Đây chính là lý do OAuth 2.0 định nghĩa Client Credentials Grant (RFC 6749, mục 4.4): Client tự chứng minh danh tính bằng client_id và client_secret của chính nó, đổi thẳng lấy access token — không qua bất kỳ bước redirect hay đăng nhập nào.

Trong TEDU Market, bài này giải quyết một vấn đề cụ thể: Hosted Service ở bài 2.7, sau khi đọc Outbox và tạo Enrollment, cần lấy tên khóa học (Course.Name) để đưa vào nội dung email xác nhận. Có hai cách làm:

- Query thẳng bảng Course qua một DbContext khác trong Infrastructure — nhanh, nhưng phá vỡ ranh giới: Outbox processor giờ phải biết schema của Course, sau này đổi Read Model Course thì phải sửa luôn cả chỗ này.
- Gọi qua HTTP vào chính endpoint GetCourseDetailQuery đã xây ở bài 1.7 — giữ đúng một nguồn sự thật (Query Handler), Outbox processor chỉ cần biết "gọi GET /api/v1/courses/{id}", không cần quan tâm bên trong dùng Dapper hay công nghệ gì.

Bài này chọn cách thứ hai, đúng tinh thần CQRS: mọi nơi trong hệ thống nên đi qua Command/Query đã định nghĩa, không tự ý query tắt xuống database.

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi học viên: "Nếu Hosted Service và Api Project đang chạy chung một process, chung một database, tại sao không gọi thẳng GetCourseDetailQueryHandler qua MediatR trong process luôn, đỡ phải đi qua HTTP và OAuth cho phức tạp?" Câu trả lời đúng: hoàn toàn có thể — nhiều hệ thống thực tế inject thẳng IMediator vào Hosted Service. Bài này cố tình chọn đường HTTP + Client Credentials để dạy đúng pattern cho ngày Module 9 tách service ra riêng. Chọn cách nào cũng được, quan trọng là học viên hiểu rõ trade-off, không phải học thuộc lòng "phải làm thế này mới đúng".*

## **2. Đăng ký OpenIddict Client cho background job**

*Thời lượng: 5 phút | Loại: Demo*

Tương tự cách bạn đã đăng ký Client cho React Admin ở bài 3.3, giờ đăng ký thêm một Client loại "confidential" — có client_secret, vì Hosted Service chạy phía server nên giữ được secret an toàn, khác hẳn SPA là "public client" không thể giữ bí mật gì trong trình duyệt.

Đặt đoạn seed dưới đây trong Program.cs, cạnh khối đã seed OpenIddict Client cho React Admin ở bài 3.3:

```csharp
await using var scope = app.Services.CreateAsyncScope();
var applicationManager = scope.ServiceProvider
    .GetRequiredService<IOpenIddictApplicationManager>();
 
if (await applicationManager.FindByClientIdAsync("tedumarket-worker") is null)
{
    await applicationManager.CreateAsync(new OpenIddictApplicationDescriptor
    {
        ClientId = "tedumarket-worker",
        ClientSecret = builder.Configuration["OpenIddict:WorkerClientSecret"],
        ClientType = OpenIddictConstants.ClientTypes.Confidential,
        DisplayName = "TeduMarket Outbox Worker",
        Permissions =
        {
            OpenIddictConstants.Permissions.Endpoints.Token,
            OpenIddictConstants.Permissions.GrantTypes.ClientCredentials,
            OpenIddictConstants.Permissions.Prefixes.Scope + "internal_api"
        }
    });
}
 
var scopeManager = scope.ServiceProvider.GetRequiredService<IOpenIddictScopeManager>();
if (await scopeManager.FindByNameAsync("internal_api") is null)
{
    await scopeManager.CreateAsync(new OpenIddictScopeDescriptor
    {
        Name = "internal_api",
        DisplayName = "TeduMarket internal service-to-service API",
        Resources = { "tedumarket-api" }
    });
}
```

Vài điểm cần giải thích rõ cho học viên:

- ClientSecret lấy từ configuration (User Secrets khi dev, secret manager/Key Vault ở môi trường thật) — tuyệt đối không hard-code, không commit vào git.
- ClientType.Confidential bắt buộc phải có secret; khác với React Admin (public client) không set ClientType, mặc định là Public.
- Permissions chỉ khai đúng 2 quyền cần dùng (Endpoints.Token, GrantTypes.ClientCredentials) — không thêm thừa Endpoints.Authorization, vì Client này không bao giờ đi qua luồng redirect.
- Scope "internal_api" đánh dấu "token này chỉ dùng để gọi API nội bộ", để phân biệt với scope của user login (ví dụ scope "api" ở bài 3.3). Endpoint nào chỉ nên nhận request từ service khác sẽ kiểm scope này.

> **📘 Ghi chú giảng viên:** *Điểm hay bị hỏi: "Sao không dùng lại đúng Client id 'react-admin' cho đỡ tạo thêm?" Nhấn mạnh: mỗi Client nên là một đơn vị tin cậy tách biệt. Nếu secret của Hosted Service bị lộ, bạn chỉ cần revoke đúng Client "tedumarket-worker", không ảnh hưởng gì tới luồng đăng nhập thật của Admin.*

## **3. Xử lý grant_type=client_credentials ở /connect/token**

*Thời lượng: 5 phút | Loại: Demo*

Bài 3.2 đã dựng action Exchange() xử lý authorization_code. Giờ thêm một nhánh mới ngay trong cùng action đó:

```csharp
[HttpPost("~/connect/token"), IgnoreAntiforgeryToken, Produces("application/json")]
public async Task<IActionResult> Exchange()
{
    var request = HttpContext.GetOpenIddictServerRequest()
        ?? throw new InvalidOperationException("Khong doc duoc OpenIddict request.");
 
    if (request.IsClientCredentialsGrantType())
    {
        // Khong co User that dung sau request nay - chi co Client tu xac thuc chinh no.
        // OpenIddict da verify client_id/client_secret truoc khi vao toi day,
        // nen ClientId o request luon hop le tai diem nay.
        var identity = new ClaimsIdentity(
            TokenValidationParameters.DefaultAuthenticationType,
            OpenIddictConstants.Claims.Name,
            OpenIddictConstants.Claims.Role);
 
        identity.SetClaim(OpenIddictConstants.Claims.Subject, request.ClientId);
        identity.SetClaim(OpenIddictConstants.Claims.Name, request.ClientId);
        identity.SetScopes(request.GetScopes());
        identity.SetDestinations(static _ => [OpenIddictConstants.Destinations.AccessToken]);
 
        return SignIn(new ClaimsPrincipal(identity),
            OpenIddictServerAspNetCoreDefaults.AuthenticationScheme);
    }
 
    // Nhanh authorization_code tu bai 3.2 giu nguyen ben duoi...
    throw new InvalidOperationException("Grant type khong duoc ho tro.");
}
```

Điểm khác biệt so với nhánh authorization_code của bài 3.2:

- Subject claim ở đây là ClientId ("tedumarket-worker"), không phải UserId thật — vì không có User nào đăng nhập.
- Không có Role claim gắn với một User cụ thể trong hệ thống Identity.
- SetScopes(request.GetScopes()) copy đúng scope Client xin (đã khai ở bước đăng ký Client) vào token, để Resource Server đọc lại khi validate.

> **📘 Ghi chú giảng viên:** *Đây là chỗ học viên hay nhầm nhất trong cả Module 3: nghĩ rằng access token nào cũng đại diện cho một User, nên cố tình nhét InstructorId giả vào claim cho token này "để endpoint đỡ phải sửa". Dừng lại và nhấn mạnh: access token của Client Credentials không đại diện cho ai cả, nó đại diện cho chính cái Service đang gọi. Endpoint nào cần InstructorId thật (ví dụ check quyền sửa Course ở bài 3.8) không được chấp nhận request mang loại token này.*

## **4. Lấy token & gọi API nội bộ từ Hosted Service**

*Thời lượng: 10 phút | Loại: Lab*

### **4.1. Client lấy token — InternalApiTokenProvider**

Viết một service nhỏ chịu trách nhiệm xin token và cache lại — tránh việc mỗi lần gọi API nội bộ lại phải xin token mới, vừa chậm vừa tốn tài nguyên của Authorization Server:

```csharp
namespace TeduMarket.Infrastructure.BackgroundJobs;
 
public sealed class InternalApiTokenProvider(
    IHttpClientFactory httpClientFactory,
    IConfiguration configuration)
{
    private string? _cachedToken;
    private DateTimeOffset _expiresAt = DateTimeOffset.MinValue;
    private readonly SemaphoreSlim _lock = new(1, 1);
 
    public async Task<string> GetAccessTokenAsync(CancellationToken cancellationToken)
    {
        // Con han it nhat 30 giay thi dung lai, khong xin token moi moi lan goi.
        if (_cachedToken is not null && _expiresAt > DateTimeOffset.UtcNow.AddSeconds(30))
        {
            return _cachedToken;
        }
 
        await _lock.WaitAsync(cancellationToken);
        try
        {
            if (_cachedToken is not null && _expiresAt > DateTimeOffset.UtcNow.AddSeconds(30))
            {
                return _cachedToken;
            }
 
            using var client = httpClientFactory.CreateClient("TeduMarket.Auth");
            using var response = await client.PostAsync("connect/token",
                new FormUrlEncodedContent(new Dictionary<string, string>
                {
                    ["grant_type"] = "client_credentials",
                    ["client_id"] = "tedumarket-worker",
                    ["client_secret"] = configuration["OpenIddict:WorkerClientSecret"]!,
                    ["scope"] = "internal_api"
                }), cancellationToken);
 
            response.EnsureSuccessStatusCode();
 
            var payload = await response.Content
                .ReadFromJsonAsync<TokenResponse>(cancellationToken: cancellationToken)
                ?? throw new InvalidOperationException("Khong parse duoc token response.");
 
            _cachedToken = payload.AccessToken;
            _expiresAt = DateTimeOffset.UtcNow.AddSeconds(payload.ExpiresIn);
            return _cachedToken;
        }
        finally
        {
            _lock.Release();
        }
    }
 
    private sealed record TokenResponse(
        [property: JsonPropertyName("access_token")] string AccessToken,
        [property: JsonPropertyName("expires_in")] int ExpiresIn);
}
```

Đăng ký 2 named HttpClient trong extension DI của Infrastructure (nơi bài 0.6 đã đăng ký AppDbContext):

```
services.AddHttpClient("TeduMarket.Auth", client =>
{
    client.BaseAddress = new Uri(configuration["OpenIddict:Issuer"]!); // vd https://localhost:5001/
});
 
services.AddHttpClient("TeduMarket.InternalApi", client =>
{
    client.BaseAddress = new Uri(configuration["InternalApi:BaseUrl"]!);
});
 
services.AddSingleton<InternalApiTokenProvider>();
```

### **4.2. Gọi endpoint nội bộ từ OutboxProcessorService (bài 2.7)**

Bài 2.7 đã có OutboxProcessorService đọc Outbox và tạo Enrollment. Giờ bổ sung bước lấy tên khóa học trước khi build nội dung email xác nhận:

```csharp
public sealed class OutboxProcessorService(
    IServiceScopeFactory scopeFactory,
    InternalApiTokenProvider tokenProvider,
    IHttpClientFactory httpClientFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            // ... doc OutboxMessage, tao Enrollment nhu bai 2.7 da lam ...
 
            var token = await tokenProvider.GetAccessTokenAsync(stoppingToken);
            using var apiClient = httpClientFactory.CreateClient("TeduMarket.InternalApi");
            apiClient.DefaultRequestHeaders.Authorization =
                new AuthenticationHeaderValue("Bearer", token);
 
            var course = await apiClient.GetFromJsonAsync<CourseDetailResponse>(
                $"api/v1/courses/{courseId}", stoppingToken);
 
            // course.Name gio dung duoc de build noi dung email xac nhan.
 
            await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
        }
    }
}
```

### **4.3. Bảo vệ endpoint — kiểm tra scope thủ công**

Endpoint GET /api/v1/courses/{id} (bài 1.7) hiện đang mở cho mọi request có token hợp lệ, bất kể token đó của ai. Gắn Policy đúng chuẩn (ví dụ [Authorize(Policy = "InstructorOnly")]) chưa tới lượt — bài 3.7 mới dạy Resource-based Authorization đầy đủ. Ở đây chỉ cần chặn thô: request không mang scope "internal_api" thì không được coi là service nội bộ gọi vào:

```csharp
app.MapGet("/api/v1/courses/{id:guid}", async (
    Guid id, HttpContext httpContext, ISender sender) =>
{
    var hasInternalScope = httpContext.User
        .FindAll(OpenIddictConstants.Claims.Private.Scope)
        .Any(claim => claim.Value.Split(' ').Contains("internal_api"));
 
    // Cho phep ca 2 nguon goi: user that co quyen xem course, HOAC service noi bo co scope dung.
    // O bai 3.7 doan check tay nay se duoc thay bang IAuthorizationHandler chuan.
 
    var result = await sender.Send(new GetCourseDetailQuery(id));
    return Results.Ok(result);
})
.RequireAuthorization();
```

> **📘 Ghi chú giảng viên:** *Cố tình để đoạn check scope này "thô", không đẹp — để bài 3.7 (Resource-based Authorization) có lý do tồn tại thật khi thay nó bằng IAuthorizationHandler đúng chuẩn. Nói rõ với học viên: đoạn code này SẼ bị thay ở bài sau, đây không phải pattern cuối cùng để họ mang đi làm dự án riêng.*

# **Bài tập / Thực hành**

> **✏️ Thực hành:** Đăng ký thêm một OpenIddict Client thứ hai tên "tedumarket-report-job", dùng scope riêng "reporting_api" (không dùng chung "internal_api" với Client vừa học trong bài). Client này mô phỏng một job gọi vào GetInstructorRevenueQuery (endpoint đã xây ở bài 2.8).

### **Input**

- Sửa lại khối seed Client + Scope ở mục 2, thêm một Client Descriptor và một Scope Descriptor mới.

### **Expected output**

- POST /connect/token với client_id=tedumarket-report-job, scope=reporting_api trả về 200, response có access_token.
- Gọi GET /api/v1/instructors/{id}/revenue kèm token vừa lấy → 200.
- Dùng token của Client "tedumarket-worker" (scope internal_api) gọi vào endpoint revenue → phải bị từ chối (403), vì scope không khớp.

### **Hint**

- Endpoint revenue cần đoạn check scope tương tự mục 4.3, chỉ đổi chuỗi cần khớp thành "reporting_api" thay vì "internal_api".

### **Solution (gợi ý — tự làm trước khi xem)**

- Thêm OpenIddictApplicationDescriptor mới với ClientId "tedumarket-report-job", Permissions gồm Endpoints.Token, GrantTypes.ClientCredentials, Prefixes.Scope + "reporting_api".
- Thêm OpenIddictScopeDescriptor mới: Name = "reporting_api", Resources = { "tedumarket-api" }.
- Endpoint revenue kiểm tra claim.Value.Split(' ').Contains("reporting_api") — nếu không khớp, trả về Results.Forbid() thay vì Results.Ok().

# **Tổng kết**

> **✅ Tóm tắt**
>
> • Client Credentials Flow dùng khi không có User thật đứng sau request — Service tự chứng minh danh tính bằng client_id/client_secret.
>
> • Access token loại này không đại diện cho User nào — Subject claim là ClientId, không có InstructorId hay Role thật.
>
> • Mỗi Client nên tách riêng theo đơn vị tin cậy (Hosted Service, report job...), không dùng chung một Client cho nhiều mục đích — dễ revoke độc lập khi cần.
>
> • Scope là cách phân quyền thô ở tầng token, dùng tạm trước khi có Policy-based Authorization chuẩn ở bài 3.7.
>
> • Trong TEDU Market, flow này giải quyết bài toán thật: Hosted Service (bài 2.7) gọi lại GetCourseDetailQuery (bài 1.7) qua HTTP thay vì query tắt xuống database, giữ đúng ranh giới CQRS.

## **Bảng so sánh 2 flow đã học trong Module 3**

| **Tiêu chí** | **Authorization Code + PKCE (3.3)** | **Client Credentials (3.4)** |
|---|---|---|
| Ai đứng sau request | User thật, đăng nhập qua trình duyệt | Không ai — chính Client tự xác thực |
| Client type | Public (SPA, không giữ được secret) | Confidential (server giữ được secret) |
| Subject claim trong token | UserId thật | ClientId |
| Dùng ở đâu trong TEDU Market | React Admin (bài 6.2), Next.js Student (bài 7.4) | Hosted Service Outbox (bài 2.7) gọi API nội bộ |

**Bước tiếp theo:** Bài 3.5 — Custom Claims & Scope, đưa Role và InstructorId vào Access Token cho đúng luồng user thật (không áp dụng cho token Client Credentials vừa học trong bài này).
