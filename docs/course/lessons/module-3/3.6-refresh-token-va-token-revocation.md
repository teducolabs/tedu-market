## **Nội dung chính**

### **Phần 1 — Vì sao cần Refresh Token, và vì sao OpenIddict quản lý tốt hơn tự chế (Lý thuyết · 8 phút)**

Từ bài 3.2–3.5, access token bạn lấy được đang sống rất lâu — mặc định OpenIddict cấp access token 1 giờ nếu không cấu hình gì thêm. Với 1 giờ, nếu token bị lộ (XSS trên React Admin, log bị rò, DevTools của máy dùng chung), kẻ tấn công có nguyên 1 giờ để dùng token đó mà không cách nào chặn lại — access token JWT của OpenIddict là self-contained, verify bằng chữ ký chứ không hỏi lại DB.

Giải pháp chuẩn OAuth2: rút ngắn access token xuống còn vài phút, và cấp kèm 1 refresh token sống lâu hơn để client tự động xin access token mới mà không bắt người dùng đăng nhập lại. Đây chính là nội dung bài này.

> **📘 Ghi chú giảng viên:** *Tôi hay hỏi ngược học viên: 'Ở khóa nền tảng, các bạn tự làm refresh token thế nào?' Câu trả lời quen thuộc: tạo bảng RefreshTokens (Id, Token, UserId, ExpiresAt, IsRevoked), khi client gửi refresh token lên thì SELECT so khớp chuỗi, nếu hợp lệ thì cấp access token mới. Khi logout thì UPDATE IsRevoked = true. Cách này chạy được, nhưng có 2 lỗ hổng hay bị bỏ sót: (1) quên index cột Token nên SELECT chậm dần theo thời gian, (2) quên dọn token hết hạn nên bảng phình to vô hạn.*

**OpenIddict giải quyết cả 2 vấn đề đó bằng thiết kế sẵn có:**

- Migration ở bài 3.2 (options.UseOpenIddict() trên DbContextOptionsBuilder) đã tự tạo bảng OpenIddictTokens — mỗi token phát hành ra (kể cả access token JWT) đều có 1 dòng metadata: Subject, ApplicationId, Type, Status, CreationDate, ExpirationDate.
- Access token JWT không lưu payload trong bảng này (self-contained, verify bằng chữ ký) — nhưng authorization code và refresh token thì BẮT BUỘC lưu payload mã hóa trong DB, không có tùy chọn tắt. Đây là lý do vì sao refresh token luôn revoke được ngay lập tức: mỗi lần client gửi refresh token lên /connect/token, Server đọc thẳng bảng OpenIddictTokens để kiểm tra Status trước khi cấp access token mới — không tin vào bất kỳ thứ gì client tự gửi lên.
- Không cần tự viết job dọn token hết hạn, không cần tự thiết kế index — OpenIddict xử lý nội bộ.

Nhưng có một sự bất đối xứng quan trọng cần nhớ kỹ, sẽ demo trực tiếp ở Phần 3: revoke refresh token có hiệu lực ngay theo mặc định, còn revoke access token thì KHÔNG — vì lý do hiệu năng, OpenIddict mặc định không hỏi lại DB mỗi khi Resource Server nhận 1 API request có access token. Access token JWT vẫn được coi là hợp lệ cho tới khi hết hạn tự nhiên, dù bạn đã revoke nó ở DB.

### **Phần 2 — Demo: Bật luồng Refresh Token (10 phút)**

Bước 1 — Cấu hình Server: mở file cấu hình OpenIddict Server (đã tạo ở bài 3.2, TeduMarket.Api/Program.cs hoặc Extensions/OpenIddictServiceExtensions.cs tùy cách bạn tổ chức). Thêm AllowRefreshTokenFlow() vào cùng chuỗi flow đã có (AllowAuthorizationCodeFlow từ bài 3.3, AllowClientCredentialsFlow từ bài 3.4), và ấn định rõ thời hạn 2 loại token thay vì để mặc định (mặc định access token 1 giờ, refresh token 14 ngày — quá dài cho access token, chấp nhận được cho refresh token):

```
// TeduMarket.Api — cấu hình OpenIddict Server (bổ sung vào bài 3.2)
services.AddOpenIddict()
    .AddServer(options =>
    {
        options
            .SetAuthorizationEndpointUris("connect/authorize")
            .SetTokenEndpointUris("connect/token")
            .SetUserinfoEndpointUris("connect/userinfo");

        options
            .AllowAuthorizationCodeFlow()      // Bài 3.3
            .RequireProofKeyForCodeExchange()  // Bài 3.3 — PKCE
            .AllowClientCredentialsFlow()      // Bài 3.4
            .AllowRefreshTokenFlow();          // Mới — bài 3.6

        // Access token ngắn để giảm cửa sổ rủi ro nếu bị lộ,
        // refresh token dài để không bắt người dùng đăng nhập lại liên tục.
        options.SetAccessTokenLifetime(TimeSpan.FromMinutes(15))
               .SetRefreshTokenLifetime(TimeSpan.FromDays(14));

        // ... AddDevelopmentEncryptionCertificate/SigningCertificate, UseAspNetCore() giữ nguyên như 3.2
    });
```

> **⚠️ Lưu ý:** Không đổi AccessTokenLifetime xuống 15 phút mà không bật AllowRefreshTokenFlow() cùng lúc — học viên hay commit riêng lẻ 2 thay đổi này, kết quả React Admin bị đăng xuất liên tục sau 15 phút mà không có cách refresh. Luôn đi cùng nhau.

Bước 2 — Cập nhật quyền cho client React Admin: bài 3.3 đã seed client React Admin với Permissions cho Authorization Code + PKCE. Giờ cập nhật thêm quyền dùng Refresh Token Grant và scope offline_access — dùng UpdateAsync trên IOpenIddictApplicationManager, không tạo lại client từ đầu để giữ nguyên ClientId đã cấu hình ở React Admin (Module 6 sẽ dùng lại):

```csharp
// TeduMarket.Infrastructure — chỗ seed OpenIddict Applications (bài 3.3)
var descriptor = await _applicationManager.FindByClientIdAsync("tedu-market-admin");
if (descriptor is not null)
{
    var updated = new OpenIddictApplicationDescriptor();
    await _applicationManager.PopulateAsync(updated, descriptor);

    updated.Permissions.Add(Permissions.GrantTypes.RefreshToken);
    updated.Permissions.Add(Permissions.Prefixes.Scope + Scopes.OfflineAccess);
    updated.Permissions.Add(Permissions.Endpoints.Revocation); // dùng ở Phần 3

    await _applicationManager.UpdateAsync(descriptor, updated);
}
```

Thiếu Permissions.Prefixes.Scope + Scopes.OfflineAccess, client sẽ nhận lỗi invalid_request: "The client application is not allowed to use the 'offline_access' scope." khi request scope offline_access — đây là lỗi hầu như ai cũng gặp lần đầu làm refresh token với OpenIddict, không phải bug của bạn.

Bước 3 — Xử lý nhánh Refresh Token trong AuthorizationController.Exchange(): bài 3.5 đã tách phần build claim ra BuildUserIdentityAsync(user, scopes). Giờ thêm nhánh mới, và ĐIỂM QUAN TRỌNG NHẤT của bài: không tái sử dụng claim cũ lưu trong refresh token, mà fetch lại User từ DB rồi gọi lại BuildUserIdentityAsync — để Role và instructor_id luôn phản ánh đúng trạng thái mới nhất.

```csharp
// TeduMarket.Api/Controllers/AuthorizationController.cs
[HttpPost("~/connect/token"), IgnoreAntiforgeryToken, Produces("application/json")]
public async Task<IActionResult> Exchange()
{
    var request = HttpContext.GetOpenIddictServerRequest() ??
        throw new InvalidOperationException("The OpenID Connect request cannot be retrieved.");

    if (request.IsAuthorizationCodeGrantType())
    {
        // Giữ nguyên như bài 3.3/3.5 — không đổi.
    }
    else if (request.IsRefreshTokenGrantType())
    {
        // Lấy principal đã được OpenIddict giải mã từ chính refresh token gửi lên.
        // Middleware validation tự kiểm tra Status trong bảng OpenIddictTokens ở bước này —
        // nếu token đã bị revoke (Phần 3), AuthenticateAsync trả về Succeeded = false.
        var result = await HttpContext.AuthenticateAsync(
            OpenIddictServerAspNetCoreDefaults.AuthenticationScheme);

        var userId = result.Principal?.GetClaim(Claims.Subject);
        var user = userId is null ? null : await _userManager.FindByIdAsync(userId);

        if (user is null || await _userManager.IsLockedOutAsync(user))
        {
            return Forbid(
                authenticationSchemes: OpenIddictServerAspNetCoreDefaults.AuthenticationScheme,
                properties: new AuthenticationProperties(new Dictionary<string, string?>
                {
                    [OpenIddictServerAspNetCoreConstants.Properties.Error] = Errors.InvalidGrant,
                    [OpenIddictServerAspNetCoreConstants.Properties.ErrorDescription] =
                        "Tài khoản không còn hợp lệ để cấp access token mới."
                }));
        }

        // KHÔNG dùng lại claim cũ trong result.Principal — rebuild hoàn toàn từ DB,
        // để Role/instructor_id đổi ở Admin (VD: gỡ quyền Instructor) có hiệu lực
        // ngay lần refresh tiếp theo, không phải đợi tới khi refresh token hết hạn.
        var identity = await BuildUserIdentityAsync(user, request.GetScopes());
        return SignIn(new ClaimsPrincipal(identity), OpenIddictServerAspNetCoreDefaults.AuthenticationScheme);
    }
    else if (request.IsClientCredentialsGrantType())
    {
        // Giữ nguyên như bài 3.4 — không đổi.
    }

    throw new InvalidOperationException("The specified grant type is not supported.");
}
```

> **📘 Ghi chú giảng viên:** *Điểm hay bị hỏi: 'Sao không dùng luôn claim có sẵn trong refresh token cho nhanh, đỡ 1 query DB?' — đa số sample OpenIddict trên mạng (kể cả trong docs chính thức) làm đúng như vậy, và với app đơn giản thì ổn. Nhưng TEDU Market có instructor_id ảnh hưởng trực tiếp quyền sửa Course (bài 3.8) — nếu Admin vừa gỡ quyền Instructor của 1 user, mà refresh token của user đó còn sống 14 ngày và ta chỉ SignIn lại claim cũ, user đó vẫn giữ quyền Instructor trong access token suốt 14 ngày tới. Refresh chỉ xảy ra mỗi 15 phút/lần (bằng đúng AccessTokenLifetime) — chi phí 1 query User hoàn toàn chấp nhận được so với rủi ro đó.*

### **Phần 3 — Demo: Revocation Endpoint & Token Entry Validation (8 phút)**

Bước 1 — Bật endpoint /connect/revoke ở Server options, và cấp quyền dùng endpoint đó cho client (đã thêm Permissions.Endpoints.Revocation ở Phần 2, bước 2):

```
options.SetAuthorizationEndpointUris("connect/authorize")
       .SetTokenEndpointUris("connect/token")
       .SetRevocationEndpointUris("connect/revoke")   // Mới
       .SetUserinfoEndpointUris("connect/userinfo");
```

Không cần viết controller action riêng cho /connect/revoke — khác với /connect/token phải tự viết Exchange() từ bài 3.2, revoke endpoint được OpenIddict xử lý hoàn toàn nội bộ (vì chưa gọi EnableRevocationEndpointPassthrough()). Chỉ cần khai báo URI là chạy được ngay.

Bước 2 — Test chứng minh refresh token revoke có hiệu lực NGAY LẬP TỨC. Với Postman (client public, không cần client_secret vì React Admin dùng PKCE):

```
POST https://localhost:5443/connect/revoke
Content-Type: application/x-www-form-urlencoded

token={refresh_token_vừa_lấy}
&token_type_hint=refresh_token
&client_id=tedu-market-admin

# → 200 OK

# Thử refresh lại bằng đúng token đó:
POST /connect/token
grant_type=refresh_token&refresh_token={refresh_token_vừa_bị_revoke}&client_id=tedu-market-admin

# → 400 invalid_grant — có hiệu lực ngay, đúng như lý thuyết Phần 1 đã giải thích.
```

Bước 3 — Test access token KHÔNG bị chặn ngay theo mặc định (chỗ hay gây bất ngờ nhất bài). Sau khi vừa revoke refresh token ở trên, dùng access token vẫn còn hạn (chưa quá 15 phút) gọi thử GET /api/v1/categories (endpoint có [Authorize] từ bài 0.7):

```
GET /api/v1/categories
Authorization: Bearer {access_token_cũ_chưa_hết_hạn}

# → Vẫn 200 OK, dù refresh token của cùng phiên đã bị revoke ở Bước 2.
```

> **⚠️ Lưu ý:** Đây chính là điểm mà rất nhiều bài viết/tutorial về OpenIddict bỏ sót hoặc nói mập mờ: revoke KHÔNG đồng nghĩa access token chết ngay. Nếu demo trực tiếp cho học viên thấy request vẫn 200 sau khi đã revoke, đa số sẽ ngạc nhiên — đó là lúc dẫn vào bước tiếp theo.

Bước 4 — Bật EnableTokenEntryValidation() để access token cũng được check lại DB mỗi request. Vì TeduMarket.Api vừa là Authorization Server vừa là Resource Server (quyết định kiến trúc #2, mục 5 outline), Validation đã dùng UseLocalServer() từ bài 3.2 — có sẵn truy cập trực tiếp DB nên bật thêm option này không tốn thêm hạ tầng, chỉ tốn 1 query mỗi request:

```
// TeduMarket.Api — cấu hình OpenIddict Validation (bổ sung vào bài 3.2)
services.AddOpenIddict()
    .AddValidation(options =>
    {
        options.UseLocalServer();   // Đã có từ bài 3.2 — cùng project với Server
        options.UseAspNetCore();

        // Mới — bắt buộc để revoke access token có hiệu lực ngay,
        // đổi lại mỗi API request tốn thêm 1 round-trip tới bảng OpenIddictTokens.
        options.EnableTokenEntryValidation();
    });
```

Restart Api, lặp lại đúng Bước 2 + Bước 3: revoke refresh token, rồi gọi lại GET /api/v1/categories bằng access token cũ (vẫn còn hạn theo thời gian) — lần này nhận 401 Unauthorized ngay lập tức.

> **📘 Ghi chú giảng viên:** *Đánh đổi cần nói rõ với học viên: EnableTokenEntryValidation() thêm 1 DB round-trip cho MỌI request có access token, không riêng gì lúc revoke. Với quy mô TEDU Market (vài nghìn học viên, không phải hệ thống triệu request/giây), chi phí này chấp nhận được và đúng tinh thần 'đủ chuẩn OAuth2/OIDC để dùng thật trong production quy mô vừa' mà mục 5 outline đã chốt. Nếu sau này tách Resource Server ra khỏi Authorization Server (ghi chú mở rộng ở Module 9.4), UseLocalServer() không còn dùng được nữa — phải chuyển sang introspection (gọi HTTP sang Authorization Server mỗi request), tốn hơn nữa — đây là lý do quyết định 'OpenIddict chạy chung Api project' còn có thêm lợi ích phụ này ngoài việc giảm độ phức tạp vận hành đã nêu ở mục 5.*

### **Phần 4 — Lab: Luồng Logout hoàn chỉnh (học viên tự làm)**

Ghép các mảnh vừa học thành 1 endpoint logout thật, không dừng ở việc test rời rạc từng bước qua Postman.

> **✏️ Đề bài:** Viết endpoint POST /api/v1/auth/logout, [Authorize] (yêu cầu access token hợp lệ). Endpoint này phải revoke TẤT CẢ token — cả access token lẫn refresh token — đang gắn với user hiện tại, để logout xong thì mọi token cũ đều chết ngay, không cần đợi client tự xóa hay đợi token hết hạn tự nhiên.
> Input: access token hợp lệ trong header Authorization.
> Expected output: 204 No Content. Sau khi gọi endpoint này, access token vừa dùng để gọi logout phải bị chặn ngay ở request kế tiếp (401), và refresh token cùng phiên gọi /connect/token phải trả invalid_grant.

Gợi ý cách làm: gọi HTTP sang /connect/revoke như Postman đã làm ở Phần 3 tốn thêm 1 round-trip network dù cùng process — không cần thiết. Cách gọn hơn: dùng thẳng IOpenIddictTokenManager (đã đăng ký sẵn DI từ khi cài OpenIddict ở bài 3.2), tìm toàn bộ token theo Subject (chính là UserId) rồi revoke từng cái:

```csharp
// TeduMarket.Api/Endpoints/AuthEndpoints.cs — gợi ý, không phải lời giải đầy đủ
app.MapPost("/api/v1/auth/logout", async (
    ClaimsPrincipal user,
    IOpenIddictTokenManager tokenManager,
    CancellationToken ct) =>
{
    var userId = user.GetClaim(Claims.Subject);
    if (userId is null) return Results.Unauthorized();

    await foreach (var token in tokenManager.FindBySubjectAsync(userId, ct))
    {
        await tokenManager.TryRevokeAsync(token, ct);
    }

    return Results.NoContent();
});
```

Hint nếu bị kẹt: FindBySubjectAsync trả về toàn bộ token của user đó — kể cả token của thiết bị/phiên khác nếu user đăng nhập nhiều nơi (revoke luôn tất cả là hành vi đúng cho "đăng xuất", nhưng nếu chỉ muốn revoke phiên hiện tại, cần lọc thêm theo ApplicationId hoặc lưu thêm session identifier — nằm ngoài phạm vi bài này). Solution đầy đủ: kiểm tra Status hiện tại của từng token trước khi revoke (bỏ qua token đã Inactive) để tránh gọi thừa; TryRevokeAsync trả về false thay vì ném exception nếu token đã bị revoke từ trước, an toàn để gọi lại nhiều lần.

## **Tổng kết**

**5 điểm cốt lõi của bài:**

- Refresh token dài hạn đi kèm access token ngắn hạn (15 phút) là cách giảm cửa sổ rủi ro nếu access token bị lộ — không cần tự thiết kế bảng, OpenIddict đã tạo sẵn bảng OpenIddictTokens từ migration bài 3.2.
- Client phải có cả 2 quyền: GrantTypes.RefreshToken và scope offline_access — thiếu 1 trong 2 đều lỗi ngay ở /connect/authorize hoặc /connect/token.
- Nhánh IsRefreshTokenGrantType() nên rebuild claim từ DB (gọi lại BuildUserIdentityAsync) thay vì tin vào claim cũ đóng gói sẵn trong refresh token, để Role/instructor_id luôn cập nhật đúng.
- Revoke refresh token có hiệu lực ngay theo mặc định (Server luôn đọc DB khi redeem). Revoke access token KHÔNG có hiệu lực ngay trừ khi bật EnableTokenEntryValidation() — đánh đổi thêm 1 DB query mỗi request để lấy lại khả năng revoke tức thời.
- Logout đúng nghĩa = revoke cả access token lẫn refresh token bằng IOpenIddictTokenManager.FindBySubjectAsync + TryRevokeAsync, không chỉ xóa token ở phía client.

### **So sánh nhanh: Access Token vs Refresh Token trong TEDU Market**

| **Tiêu chí** | **Access Token** | **Refresh Token** |
|---|---|---|
| Thời hạn | 15 phút | 14 ngày |
