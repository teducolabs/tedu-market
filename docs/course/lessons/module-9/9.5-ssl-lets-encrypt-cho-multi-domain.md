## **1. ACME & HTTP-01 Challenge — hiểu trước khi làm**

**Section 1 · 5 phút · Lý thuyết**

Let’s Encrypt là một Certificate Authority (CA) miễn phí, cấp chứng chỉ TLS hoàn toàn tự động qua giao thức ACME (Automatic Certificate Management Environment). Certbot là ACME client chính thức, đóng vai trò "người đại diện" nói chuyện với server của Let’s Encrypt để xin cấp và gia hạn chứng chỉ.

Cơ chế xác minh quyền sở hữu domain phổ biến nhất — và cũng là cách bài này dùng — là HTTP-01 challenge, diễn ra theo 4 bước:

- Certbot gửi yêu cầu cấp chứng chỉ cho danh sách domain (api.tedumarket.dev, admin.tedumarket.dev, www.tedumarket.dev).
- Let’s Encrypt trả về 1 challenge token cho mỗi domain.
- Certbot đặt 1 file chứa token đó vào đường dẫn http://\<domain>/.well-known/acme-challenge/\<token> trên chính server của bạn — Nginx phải đang chạy và serve được đường dẫn này.
- Let’s Encrypt gọi HTTP GET đến đúng URL đó từ Internet. Nếu token khớp, domain được xác minh là bạn thực sự kiểm soát nó, chứng chỉ được ký và trả về.

Vì cả 3 subdomain trong bài 9.4 đều trỏ về cùng 1 server (cùng 1 IP, khác nhau ở tên miền), bài này xin 1 chứng chỉ duy nhất chứa cả 3 domain dưới dạng SAN (Subject Alternative Name) — mỗi tham số -d trong lệnh certbot là 1 SAN. Ưu điểm: chỉ 1 lệnh cấp, 1 lệnh renew, 1 cron job cần quản lý thay vì 3.

> **📘 Ghi chú giảng viên:** *Học viên hay hỏi "sao không mua wildcard \*.tedumarket.dev cho gọn?" — trả lời: wildcard bắt buộc dùng DNS-01 challenge (cần API của nhà cung cấp DNS để tự động tạo TXT record), phức tạp hơn HTTP-01 và không cần thiết khi chỉ có đúng 3 subdomain cố định biết trước. Wildcard hợp lý khi số subdomain sinh động, không biết trước (ví dụ multi-tenant \*.tedu.com.vn).*

## **2. Chuẩn bị: volume dùng chung & Nginx cho ACME challenge**

**Section 2 · 5 phút · Demo**

Certbot cần ghi file challenge vào 1 thư mục mà Nginx đang serve ở port 80. Vì Nginx và Certbot chạy trong 2 container riêng (đúng tinh thần Docker Compose multi-service của Module 9), 2 container này phải dùng chung volume. Mở docker-compose.prod.yml (bài 9.3) và thêm:

```yaml
# docker-compose.prod.yml — thêm vào services đã có (api, admin, web, nginx, postgres, redis, seq)
services:
  nginx:
    # ... giữ nguyên cấu hình routing 3 subdomain từ bài 9.4 ...
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - certbot-etc:/etc/letsencrypt          # chứa chứng chỉ đã cấp
      - certbot-www:/var/www/certbot           # webroot cho ACME challenge
 
  certbot:
    image: certbot/certbot:latest
    volumes:
      - certbot-etc:/etc/letsencrypt
      - certbot-www:/var/www/certbot
    # container này KHÔNG chạy sẵn — chỉ được gọi bằng "docker compose run"
    # ở bước cấp chứng chỉ, và bằng service renew-loop ở phần 5
 
volumes:
  certbot-etc:
  certbot-www:
```

Trong file cấu hình Nginx dùng cho HTTP (port 80) đã tạo ở bài 9.4, thêm 1 location phục vụ đúng đường dẫn ACME challenge, đặt trước rule redirect HTTPS:

```nginx
# nginx/conf.d/tedumarket.conf — server block port 80, áp dụng cho cả 3 subdomain
server {
    listen 80;
    server_name api.tedumarket.dev admin.tedumarket.dev www.tedumarket.dev;
 
    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }
 
    location / {
        return 301 https://$host$request_uri;
    }
}
```

> **📘 Ghi chú giảng viên:** *Điểm hay bị vướng nhất ở bước này: nếu bật sẵn "return 301 https://..." cho toàn bộ path (kể cả /.well-known/) thì Certbot verify sẽ luôn fail vì request bị redirect trước khi Nginx kịp trả file token. Luôn đặt location /.well-known/acme-challenge/ TRƯỚC location / trong cùng server block — Nginx match location theo độ dài prefix dài nhất trước, nhưng đặt đúng thứ tự vẫn là thói quen tốt và dễ đọc hơn khi debug.*

Ở lần chạy đầu tiên chưa có chứng chỉ nào cả nên chưa thể mở server block 443 (thiếu ssl_certificate sẽ khiến Nginx không start được). Vì vậy thứ tự bắt buộc là: start Nginx chỉ với port 80 → cấp chứng chỉ → thêm server block 443 → reload Nginx. Phần 3 và 4 dưới đây đi đúng thứ tự này.

## **3. Cấp chứng chỉ lần đầu**

**Section 3 · 8 phút · Demo**

Đảm bảo Nginx (chỉ với server block port 80 ở trên) và các service backend đang chạy, sau đó gọi Certbot dưới dạng lệnh chạy một lần (không phải service thường trực):

```yaml
docker compose -f docker-compose.prod.yml run --rm certbot certonly \
  --webroot -w /var/www/certbot \
  --email admin@tedumarket.dev \
  --agree-tos --no-eff-email \
  -d api.tedumarket.dev \
  -d admin.tedumarket.dev \
  -d www.tedumarket.dev
```

Certbot lưu chứng chỉ tại /etc/letsencrypt/live/api.tedumarket.dev/ — domain đầu tiên trong danh sách -d được dùng làm tên thư mục (lead domain), dù chứng chỉ vẫn bao phủ cả 3 domain qua SAN. Thư mục này chứa fullchain.pem (chuỗi chứng chỉ) và privkey.pem (private key) — do volume certbot-etc dùng chung, Nginx đọc được ngay 2 file này.

> **📘 Ghi chú giảng viên:** *Domain "tedumarket.dev" trong bài này viết thường theo đúng cú pháp DNS thật (tên miền không phân biệt hoa/thường). Cách viết "teduMarket.dev" ở outline chỉ để dễ đọc trong tài liệu — khi gõ lệnh hay khai báo DNS, học viên luôn dùng chữ thường.*
>
> **📘 Ghi chú giảng viên:** *Nếu học viên chưa mua domain thật để luyện tập, dùng dịch vụ domain test miễn phí trỏ thẳng về IP như sslip.io (ví dụ api.\<IP-với-dấu-gạch>.sslip.io) để có DNS resolve ngay lập tức, không cần chờ propagate.*

## **4. Bật HTTPS trên Nginx & redirect HTTP → HTTPS**

**Section 4 · 5 phút · Demo**

Chứng chỉ đã có, giờ thêm server block 443 cho từng subdomain (tách riêng để mỗi subdomain trỏ đúng container backend/admin/web như bài 9.4 đã cấu hình), trỏ đến đúng cặp fullchain.pem / privkey.pem:

```nginx
# nginx/conf.d/tedumarket.conf — thêm 3 server block 443, ví dụ cho api
server {
    listen 443 ssl;
    server_name api.tedumarket.dev;
 
    ssl_certificate     /etc/letsencrypt/live/api.tedumarket.dev/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.tedumarket.dev/privkey.pem;
 
    location / {
        proxy_pass http://api:8080;   # container backend từ bài 9.4
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
# lặp lại tương tự cho admin.tedumarket.dev -> admin container
# và www.tedumarket.dev -> web container, cùng dùng chung 1 cặp
# fullchain.pem/privkey.pem vì cả 3 domain nằm trong 1 chứng chỉ SAN
```

Reload Nginx để áp dụng cấu hình mới mà không downtime:

```yaml
docker compose -f docker-compose.prod.yml exec nginx nginx -s reload
```

Kiểm tra kết quả trên cả 3 subdomain:

```bash
curl -Iv https://api.tedumarket.dev
curl -Iv https://admin.tedumarket.dev
curl -Iv https://www.tedumarket.dev
# Kỳ vọng: HTTP/2 200 (hoặc mã tương ứng route), chứng chỉ hợp lệ,
# không có cảnh báo "self signed certificate" hay "certificate expired"
```

> **✏️ Thực hành:** Sau khi làm xong bước này, gọi thử http://api.tedumarket.dev (không có "s") và quan sát response header Location — xác nhận nó redirect 301 sang đúng https://api.tedumarket.dev với cùng path. Nếu redirect sai domain (ví dụ luôn redirect về www), kiểm tra lại chỉ thị server_name ở từng server block port 80/443 có khớp danh sách 3 subdomain hay không.

## **5. Auto-renew — không để chứng chỉ hết hạn giữa production**

**Section 5 · 7 phút · Lab**

Chứng chỉ Let’s Encrypt mặc định có hạn 90 ngày (Let’s Encrypt đang có lộ trình rút ngắn dần xuống 45 ngày vào đầu 2028 để khuyến khích tự động hóa toàn ngành — càng thêm lý do không nên renew tay). Certbot tự biết chỉ renew khi chứng chỉ còn dưới 30 ngày là hết hạn, nên gọi lệnh renew mỗi ngày là an toàn, không tốn quota.

Thêm 1 service renew-loop chạy nền trong docker-compose.prod.yml, dùng entrypoint dạng vòng lặp sleep thay vì cron — cách phổ biến khi chạy Certbot trong container vì không cần cài thêm cron daemon:

```yaml
# docker-compose.prod.yml — thêm service renew-loop, KHÁC với service
# certbot dùng "run --rm" ở phần 3 (service này chạy thường trực)
services:
  certbot-renew:
    image: certbot/certbot:latest
    restart: unless-stopped
    volumes:
      - certbot-etc:/etc/letsencrypt
      - certbot-www:/var/www/certbot
    entrypoint: >-
      /bin/sh -c "trap exit TERM;
      while :; do
        certbot renew --webroot -w /var/www/certbot --quiet;
        sleep 12h & wait $$!;
      done"
```

Renew thành công không tự reload Nginx — Nginx cần được báo để nạp lại cặp fullchain.pem/privkey.pem mới. Cách đơn giản và đủ dùng cho quy mô 1 server của khóa học: thêm 1 cron job trên host (ngoài Docker), chạy 2 lần/ngày, gọi reload sau khi renew-loop có khả năng vừa chạy xong:

```yaml
# crontab -e trên host
0 3,15 * * * cd /path/to/project && docker compose -f docker-compose.prod.yml exec nginx nginx -s reload >> /var/log/nginx-reload.log 2>&1
```

Kiểm tra toàn bộ luồng renew hoạt động đúng mà không thật sự tiêu quota chứng chỉ (Let’s Encrypt giới hạn số lần cấp thật trong 1 tuần) bằng cờ --dry-run:

```yaml
docker compose -f docker-compose.prod.yml run --rm certbot renew --dry-run
```

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây để hỏi học viên: "reload Nginx bằng cron chạy trên host, không phải trong container — có gì bất tiện?" Câu trả lời đúng hướng: host cần cài đặt sẵn Docker CLI và có quyền gọi docker compose, tức là phụ thuộc vào môi trường bên ngoài container. Cách chuẩn hơn cho hệ thống lớn là mount Docker socket vào 1 container riêng để nó tự gọi lệnh reload — nhưng đó là đánh đổi phức tạp vận hành lấy tính "đóng gói hoàn toàn", vượt quá phạm vi khóa học này (tương tự lý do Module 9.1 ghi chú ngắn về tách OpenIddict service riêng nhưng không dạy sâu).*

## **Bài tập thực hành**

Yêu cầu: Hoàn thiện HTTPS thật cho cả 3 subdomain của TEDU Market và chứng minh auto-renew hoạt động.

- Input: docker-compose.prod.yml + cấu hình Nginx từ bài 9.3/9.4 đã chạy được qua HTTP; 1 domain thật (hoặc domain test sslip.io) đã trỏ DNS đúng 3 subdomain.
- Bước 1: Thêm service certbot + certbot-renew và 2 volume như phần 2, 5 vào docker-compose.prod.yml.
- Bước 2: Sửa Nginx config theo phần 2 (location ACME challenge) và phần 4 (3 server block 443), cấp chứng chỉ theo đúng lệnh phần 3.
- Bước 3: Reload Nginx, verify cả 3 subdomain trả về HTTPS hợp lệ bằng curl -Iv như phần 4.
- Bước 4: Chạy certbot renew --dry-run thành công, không có lỗi ACME challenge.
- Expected output: 3 subdomain đều truy cập được qua https://, http:// tự động redirect sang https://, lệnh dry-run renew trả "The dry run was successful".
- Hint nếu bị kẹt: nếu certonly báo lỗi "Timeout during connect" — kiểm tra port 80 có thật sự mở ra Internet (firewall, security group cloud) và DNS đã propagate xong (dig +short api.tedumarket.dev phải trả đúng IP server) trước khi thử lại.

## **Tổng kết**

> **✅ Tóm tắt:** ACME HTTP-01 challenge xác minh quyền sở hữu domain bằng cách để Let’s Encrypt tự gọi HTTP GET vào 1 file token do Certbot đặt sẵn — Nginx bắt buộc phải serve được đường dẫn /.well-known/acme-challenge/ trước khi có HTTPS.
> 1 chứng chỉ SAN duy nhất bao phủ cả 3 subdomain (api, admin, www) đơn giản hóa việc renew: 1 lệnh, 1 cron job thay vì 3.
> Thứ tự bootstrap bắt buộc: Nginx chạy port 80 trước → cấp chứng chỉ → thêm server block 443 → reload — không thể làm ngược vì Nginx cần cert để start HTTPS.
> Auto-renew chạy như 1 service thường trực trong Docker Compose (vòng lặp sleep, không cần cron trong container), kết hợp cron trên host để reload Nginx sau khi renew.
> Chứng chỉ mặc định 90 ngày, renew khi còn dưới 30 ngày — luôn test bằng --dry-run trước khi tin tưởng quy trình chạy tự động thật.

Bước tiếp theo: Bài 9.6 — CI/CD GitHub Actions sẽ đưa toàn bộ pipeline build → test → deploy 3 service (api, admin, web) chạy tự động khi merge vào main, dùng đúng hạ tầng Docker Compose + Nginx + HTTPS vừa hoàn thiện ở bài này làm môi trường deploy đích.
