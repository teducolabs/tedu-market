## **1. Vì sao Console/ILogger mặc định không đủ cho production**

*Lý thuyết · 10 phút*

Từ bài 0.9, TeduMarket.Api đã trả về ProblemDetails có kèm trường traceId mỗi khi có lỗi. Nhưng thử hỏi: đang nửa đêm, học viên báo lỗi kèm traceId đó, bạn lấy log ra bằng cách nào? SSH vào server, chạy docker logs teduMarket-api, rồi Ctrl+F dò một chuỗi 20 ký tự giữa hàng nghìn dòng log không có cấu trúc, xen giữa log của Postgres, Redis, Nginx trộn lẫn trong cùng 1 terminal. Đó là log dạng text — chỉ đọc được, không query được.

Structured logging là ghi log kèm theo các property có tên và có kiểu, thay vì ghép sẵn thành 1 chuỗi text. So sánh trực tiếp:

```
// Log dạng text — mất hết thông tin ngay khi ghép chuỗi
_logger.LogInformation($"Order {orderId} paid by user {userId}");
 
// Structured log — orderId và userId vẫn là property độc lập,
// query được riêng từng cái trên Seq sau khi ghi
_logger.LogInformation("Order {OrderId} paid by user {UserId}", orderId, userId);
```

Chỉ khác cách viết message template (giữ nguyên {OrderId} thay vì nội suy chuỗi), nhưng khác biệt lúc query là một trời một vực: dòng dưới cho phép lọc "tất cả log có OrderId = 123" mà không cần biết trước format câu chữ.

Serilog không thay thế Microsoft.Extensions.Logging.ILogger mà TeduMarket.Api đã dùng xuyên suốt Module 0–8 — nó là một logging provider cắm phía dưới ILogger. Toàn bộ \_logger.LogInformation(...) trong CreateCategoryCommandHandler (0.4), CreateCourseCommandHandler (1.2)... không cần sửa một dòng nào. Điều thay đổi là: log giờ được route qua nhiều "sink" (đích ghi) cùng lúc — Console để xem lúc dev, Seq để lưu tập trung và query lúc production.

Seq là server lưu structured log, cho phép gõ query kiểu SQL-like (CorrelationId = '...' and @Level = 'Warning') để lọc chính xác, thay vì đọc từng dòng.

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi học viên: "traceId ở bài 0.9 dùng để làm gì nếu không có chỗ nào query theo nó?" — hầu hết trả lời được là để báo lỗi cho dev, nhưng ít ai nhận ra nếu log không tập trung thì traceId đó chỉ là một chuỗi vô dụng nằm trên màn hình học viên. Bài 9.7 chính là mảnh ghép biến traceId từ 0.9 thành công cụ debug thật.*

## **2. Cài đặt Serilog + Seq sink trong TeduMarket.Api**

*Demo · 10 phút*

Cài 2 package vào đúng project Api (không cài vào Domain/Application — hai layer đó không được biết logging framework nào đang chạy phía dưới, theo đúng nguyên tắc Dependency Inversion đã học ở bài 0.2):

*bash*

```bash
dotnet add src/TeduMarket.Api package Serilog.AspNetCore
dotnet add src/TeduMarket.Api package Serilog.Sinks.Seq
```

Serilog.AspNetCore đã kéo theo Serilog.Sinks.Console và Serilog.Settings.Configuration nên không cần cài thêm 2 gói đó.

Thêm section Serilog vào appsettings.json (file đã tồn tại từ bài 0.6, chỉ thêm section mới, không đổi ConnectionStrings hay các section khác):

*json*

```json
// appsettings.json — thêm vào file đã có
{
  "Serilog": {
    "MinimumLevel": {
      "Default": "Information",
      "Override": {
        "Microsoft.AspNetCore": "Warning",
        "Microsoft.EntityFrameworkCore": "Warning"
      }
    },
    "Properties": {
      "Application": "TeduMarket.Api"
    }
  }
}
```

appsettings.Production.json (đã có sẵn khung từ bài 9.1) thêm đúng 1 khóa — địa chỉ Seq bên trong mạng Docker nội bộ, không phải localhost:

*json*

```json
// appsettings.Production.json
{
  "Serilog": {
    "SeqServerUrl": "http://seq:5341"
  }
}
```

Trong Program.cs, thêm cấu hình theo mô hình "two-stage initialization" — Serilog khuyến nghị chính thức để không mất log nếu app crash ngay trong lúc build DI container (ví dụ sai ConnectionStrings ở bài 0.6, hoặc thiếu biến môi trường OpenIddict ở bài 3.2):

```csharp
// Program.cs — đặt TRÊN CÙNG file, trước var builder = WebApplication.CreateBuilder(args);
using Serilog;
 
// Bootstrap logger: chỉ ghi Console, dùng để bắt lỗi TRƯỚC KHI builder build xong
Log.Logger = new LoggerConfiguration()
    .WriteTo.Console()
    .CreateBootstrapLogger();
 
try
{
    Log.Information("Đang khởi động TeduMarket.Api...");
 
    var builder = WebApplication.CreateBuilder(args);
 
    builder.Host.UseSerilog((context, services, configuration) => configuration
        .ReadFrom.Configuration(context.Configuration)
        .ReadFrom.Services(services)
        .Enrich.FromLogContext()
        .WriteTo.Console()
        .WriteTo.Seq(context.Configuration["Serilog:SeqServerUrl"] ?? "http://localhost:5341"));
 
    // ... toàn bộ đăng ký service Module 0-8 giữ nguyên: MediatR, DbContext,
    //     OpenIddict, Repository, RateLimiter, CORS... không đổi gì ở đây
 
    var app = builder.Build();
 
    // Middleware pipeline — xem thứ tự đầy đủ ở Mục 3
 
    app.Run();
}
catch (Exception ex)
{
    Log.Fatal(ex, "TeduMarket.Api dừng đột ngột lúc khởi động");
}
finally
{
    await Log.CloseAndFlushAsync();
}
```

> **📘 Ghi chú giảng viên:** *Log.CloseAndFlushAsync() ở finally hay bị quên nhất. Seq nhận log qua HTTP theo batch — nếu process bị kill (docker stop, container restart lúc CI/CD deploy ở bài 9.6) mà chưa flush, đúng những dòng log cuối cùng trước sự cố — thứ quan trọng nhất — sẽ mất. Tôi hay demo bằng cách bỏ dòng finally, tắt app đột ngột, cho học viên tự thấy log cuối biến mất trên Seq.*

## **3. Middleware CorrelationId — nối log xuyên suốt 1 request**

*Demo · 7 phút*

Bài 0.9 đã cấu hình AddProblemDetails() với CustomizeProblemDetails để gán traceId = Activity.Current?.Id ?? httpContext.TraceIdentifier vào mọi response lỗi. Bài này không phát minh thêm một khái niệm "correlation ID" mới — dùng lại đúng công thức đó, chỉ đẩy thêm giá trị này vào LogContext của Serilog để MỌI dòng log (không riêng lỗi) đều mang theo nó.

```csharp
// src/TeduMarket.Api/Middleware/CorrelationIdLoggingMiddleware.cs
using System.Diagnostics;
using Serilog.Context;
 
namespace TeduMarket.Api.Middleware;
 
public sealed class CorrelationIdLoggingMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext context)
    {
        // Đúng công thức đã dùng cho traceId ở bài 0.9 — 1 giá trị duy nhất
        // xuất hiện cả trong response lỗi trả về client lẫn trong log trên Seq.
        var correlationId = Activity.Current?.Id ?? context.TraceIdentifier;
 
        using (LogContext.PushProperty("CorrelationId", correlationId))
        {
            await next(context);
        }
    }
}
```

Vị trí đăng ký trong Program.cs quyết định middleware này có tác dụng hay không. LogContext.PushProperty dùng AsyncLocal — property chỉ tồn tại bên TRONG khối using; nếu middleware này nằm SAU UseSerilogRequestLogging trong pipeline, thì đến lúc UseSerilogRequestLogging ghi dòng log "responded 200 in X ms" (được ghi SAU khi next() trả về), property CorrelationId đã bị pop ra khỏi scope — dòng log request-completion quan trọng nhất sẽ thiếu đúng cái cần tìm.

Thứ tự đúng, cập nhật lại đoạn pipeline TeduMarket.Api đã xây dần từ bài 0.9 đến giờ:

```csharp
// Program.cs — sau var app = builder.Build();
app.UseMiddleware<CorrelationIdLoggingMiddleware>();  // MỚI — phải đứng ngoài cùng
app.UseExceptionHandler();                            // đã có từ bài 0.9
app.UseSerilogRequestLogging();                       // MỚI
app.UseCors();                                        // đã có từ bài 3.9
app.UseAuthentication();                              // OpenIddict, Module 3
app.UseAuthorization();
app.UseRateLimiter();                                 // đã có từ bài 4.4
 
// ... app.MapGroup(...) của Module 0-4 giữ nguyên
```

> **📘 Ghi chú giảng viên:** *Lỗi phổ biến nhất tôi thấy học viên mắc: chèn app.UseSerilogRequestLogging() ngay dưới var app = builder.Build() theo đúng README của thư viện, mà quên README đó không biết TeduMarket.Api đã có middleware CorrelationId. Tôi hay vẽ nhanh sơ đồ lồng nhau (outer → inner) lên bảng để học viên thấy PushProperty giống như dấu ngoặc — middleware nào đăng ký trước thì ngoặc rộng hơn, bao trọn middleware log ghi SAU khi next() trả về.*

## **4. Seq chạy nội bộ & query log theo CorrelationId**

*Demo · 3 phút*

Service seq đã được thêm vào docker-compose.prod.yml từ bài 9.3, chạy cùng API/Admin/Web/Postgres/Redis. Bài này chỉ chỉnh 2 điểm mà 9.3 chưa cần đến vì lúc đó chưa có ai gọi tới Seq:

- Serilog trong TeduMarket.Api trỏ đến Seq bằng tên service nội bộ Docker network — http://seq:5341 (cổng ingestion, không phải cổng UI 80) — như appsettings.Production.json đã cấu hình ở Mục 2.
- Cổng UI của Seq (80 trong container) chỉ bind ra 127.0.0.1 trên VPS, KHÔNG thêm subdomain thứ 4 — bài 9.4 đã chốt đúng 3 subdomain công khai (api / admin / www), Seq là công cụ nội bộ của giảng viên/dev, không public ra Internet.

*yaml*

```yaml
# docker-compose.prod.yml — phần ports của service seq
seq:
  image: datalust/seq:latest
  environment:
    - ACCEPT_EULA=Y
  ports:
    - "127.0.0.1:5340:80"   # chỉ localhost VPS truy cập được, không public
  volumes:
    - seq-data:/data
```

Truy cập Seq UI từ máy cá nhân qua SSH tunnel, không mở port ra Internet:

*bash*

```
ssh -L 5340:127.0.0.1:5340 deploy@teduMarket-vps
# rồi mở trình duyệt: http://localhost:5340
```

Gọi thử 1 API bất kỳ (ví dụ POST /api/v1/orders/checkout ở bài 2.2), lấy giá trị traceId từ response lỗi (nếu có) hoặc từ chính CorrelationId đã log, rồi vào Seq gõ query:

```
CorrelationId = '0HN3K2VJ8QF3L:00000001'
```

Kết quả trả về đúng toàn bộ dòng log của request đó theo thứ tự thời gian — dòng bắt đầu request, log trong Handler (nếu có), câu EF Core query nếu bật Debug level, và dòng request-completion — không lẫn log của request khác hay của container khác.

## **Bài tập / Thực hành**

> **✏️ Thực hành:** Thêm 1 dòng log cảnh báo có structured property vào CheckoutCommandHandler (bài 2.2) ngay trước khi Handler ném CartEmptyException (giả định exception này đã có từ Module 2): \_logger.LogWarning("Checkout attempted with empty cart for {UserId}", userId). Sau đó gọi thử checkout với giỏ hàng rỗng, vào Seq lọc theo Application = 'TeduMarket.Api' and @Level = 'Warning' và xác nhận thấy đúng dòng log kèm UserId đúng, không phải chuỗi text ghép sẵn.

Input: 1 request checkout với cart rỗng (test qua Scalar, đã có từ bài 4.2). Expected output: 1 sự kiện Warning trên Seq, filter được riêng theo UserId.

Hint: đừng dùng string interpolation ($"...{userId}") — làm vậy sẽ mất property UserId, Seq chỉ thấy được 1 chuỗi text không lọc được.

## **Tổng kết**

> **✅ Tóm tắt:** Serilog là logging provider cắm phía dưới ILogger — không cần sửa lại \_logger.LogInformation(...) đã viết từ Module 0.
>
> **✅ Tóm tắt:** Two-stage initialization (bootstrap logger + Log.CloseAndFlushAsync() ở finally) đảm bảo không mất log kể cả lúc app crash lúc khởi động hoặc bị kill đột ngột.
>
> **✅ Tóm tắt:** CorrelationId không phải khái niệm mới — tái dùng đúng công thức traceId đã có từ bài 0.9, chỉ đẩy thêm vào LogContext qua middleware.
>
> **✅ Tóm tắt:** Vị trí middleware quyết định tất cả: CorrelationId middleware phải đứng NGOÀI CÙNG (đăng ký sớm nhất) để bọc được cả UseExceptionHandler lẫn UseSerilogRequestLogging.
>
> **✅ Tóm tắt:** Seq chạy nội bộ, chỉ bind localhost trên VPS, truy cập qua SSH tunnel — không phá vỡ quyết định 3 subdomain cố định của bài 9.4.
