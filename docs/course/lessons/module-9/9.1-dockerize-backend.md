## **Nội dung chính**

### **Phần 1 — Vì sao phải multi-stage build (Lý thuyết · 10 phút)**

Một sai lầm phổ biến khi mới container hóa .NET là dùng luôn image SDK (mcr.microsoft.com/dotnet/sdk) làm image chạy production. Image SDK chứa toàn bộ compiler, MSBuild, NuGet cache — nặng khoảng 800MB trở lên. Image này build được code, nhưng không nên dùng để chạy production: mang theo compiler lên production là mang theo rủi ro bảo mật không cần thiết và làm image nặng gấp nhiều lần mức cần thiết.

Multi-stage build giải quyết đúng vấn đề này bằng 2 stage tách biệt trong cùng 1 Dockerfile:

- Stage build: dùng image SDK (mcr.microsoft.com/dotnet/sdk:10.0) — đầy đủ công cụ để compile và publish
- Stage runtime: dùng image ASP.NET Core Runtime (mcr.microsoft.com/dotnet/aspnet:10.0) — chỉ chứa runtime + thư viện cần thiết để chạy DLL đã publish, không có compiler

Stage cuối chỉ COPY kết quả publish từ stage build sang, image cuối cùng không hề biết SDK từng tồn tại. Đây là pattern chính thức Microsoft khuyến nghị cho mọi ứng dụng .NET chạy trong container.

> **📘 Ghi chú giảng viên:** *Tôi hay demo trực quan bằng cách build cả 2 cách rồi chạy \`docker images\` so kích thước ngay tại chỗ — con số chênh lệch (800MB+ so với dưới 100MB) thuyết phục hơn nhiều so với giải thích suông. Học viên thường ngạc nhiên vì nghĩ Docker image .NET 'vốn dĩ phải nặng'.*

Một điểm cần lưu ý riêng cho .NET 10: kể từ .NET 10, Ubuntu (Noble Numbat 24.04) là distro Linux mặc định cho mọi image chính thức — Debian không còn được cung cấp nữa. Các tag như `10.0` và `10.0-noble-chiseled` đều dựa trên Ubuntu 24.04.

### **Phần 2 — Viết Dockerfile multi-stage cho TeduMarket.Api (Demo + Lab · 15 phút)**

Dockerfile đặt ở thư mục backend/ — cùng cấp với TeduMarket.sln, đúng cấu trúc monorepo đã chốt ở mục 6 outline (docker-compose.yml ở thư mục gốc sẽ orchestrate cả backend lẫn frontend từ bài 9.3). Trước tiên tạo file .dockerignore để loại các thư mục build cũ, tránh COPY rác vào build context:

```bash
# backend/.dockerignore
**/bin
**/obj
**/.vs
**/*.user
tests/
.git
.dockerignore
Dockerfile
```

Solution có 4 project theo đúng chiều phụ thuộc đã dựng ở bài 0.2: Domain không phụ thuộc gì, Application phụ thuộc Domain, Infrastructure implement interface của Application, Api phụ thuộc cả Application và Infrastructure. Dockerfile phải COPY đủ 4 file .csproj trước khi restore — thiếu 1 file là restore lỗi ngay vì Api project reference tới cả 3 project kia.

```bash
# syntax=docker/dockerfile:1
 
# ===== STAGE 1: BUILD =====
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
 
# Copy solution + từng .csproj riêng để tận dụng layer cache của Docker.
# Nếu code (.cs) đổi nhưng .csproj không đổi, bước restore bên dưới sẽ
# dùng lại cache, không phải tải lại NuGet package.
COPY ["TeduMarket.sln", "./"]
COPY ["src/TeduMarket.Domain/TeduMarket.Domain.csproj", "src/TeduMarket.Domain/"]
COPY ["src/TeduMarket.Application/TeduMarket.Application.csproj", "src/TeduMarket.Application/"]
COPY ["src/TeduMarket.Infrastructure/TeduMarket.Infrastructure.csproj", "src/TeduMarket.Infrastructure/"]
COPY ["src/TeduMarket.Api/TeduMarket.Api.csproj", "src/TeduMarket.Api/"]
 
RUN dotnet restore "src/TeduMarket.Api/TeduMarket.Api.csproj"
 
# Copy toàn bộ source còn lại rồi publish (Release, không debug symbol thừa)
COPY src/ src/
RUN dotnet publish "src/TeduMarket.Api/TeduMarket.Api.csproj" \
    -c Release \
    -o /app/publish \
    --no-restore
 
# ===== STAGE 2: RUNTIME =====
FROM mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled AS final
WORKDIR /app
 
COPY --from=build /app/publish .
 
USER app
EXPOSE 8080
 
ENTRYPOINT ["dotnet", "TeduMarket.Api.dll"]
```

> **📘 Ghi chú giảng viên:** *3 chi tiết học viên dễ bỏ sót, tôi luôn dừng lại nhấn mạnh: (1) EXPOSE 8080 chứ không phải 80 — từ .NET 8 trở đi, image ASP.NET Core chính thức lắng nghe ở cổng 8080 mặc định vì container chạy non-root không có quyền bind cổng dưới 1024. (2) USER app chuyển sang user không phải root trước khi chạy — đúng nguyên tắc least privilege cho production. (3) Tag -noble-chiseled là image "rút gọn": không có shell, không có package manager — bảo mật tốt hơn hẳn nhưng đổi lại là không \`docker exec -it ... bash\` vào debug được. Nếu học viên cần debug sâu trong container, đổi tạm sang tag 10.0 (đầy đủ Ubuntu, có shell) rồi quay lại chiseled khi lên production thật.*

### **Phần 3 — Build, đo kích thước và chạy thử image (Demo + Lab · 5 phút)**

Build image từ thư mục backend/ (nơi chứa Dockerfile và TeduMarket.sln):

```bash
cd backend
docker build -t tedumarket-api:1.0 .
docker images | grep tedumarket-api
```

Kết quả tham khảo (số liệu chính thức từ Microsoft cho image .NET 10, có thể lệch vài MB tùy nội dung publish thực tế):

```
mcr.microsoft.com/dotnet/aspnet:10.0                  ~92 MB
mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled    ~53 MB
mcr.microsoft.com/dotnet/sdk:10.0 (nếu dùng làm runtime, KHÔNG NÊN)  800MB+
```

Chạy thử container độc lập để xác nhận app khởi động đúng. Vì Postgres/Redis đang chạy trong network Docker Compose dựng ở bài 0.10, container test cần join chung network đó mới kết nối được connection string (cấu hình full-stack đúng chuẩn sẽ làm ở bài 9.3, ở đây chỉ verify riêng backend image):

```bash
docker network ls | grep tedumarket   # tìm tên network do docker-compose (bài 0.10) tạo ra
docker run -d --name tedumarket-api-test \
  --network tedumarket_default \
  -p 8080:8080 \
  -e ConnectionStrings__DefaultConnection="Host=postgres;Port=5432;\
Database=tedumarket;Username=postgres;Password=postgres" \
  tedumarket-api:1.0
 
docker logs -f tedumarket-api-test
curl http://localhost:8080/scalar   # Scalar UI từ bài 4.2 — 200 OK là image chạy đúng
```

> **📘 Ghi chú giảng viên:** *Tôi luôn nói rõ với học viên: connection string truyền bằng -e ở đây chỉ để test nhanh, không phải cách làm production. Bài 9.3 (Docker Compose Full-stack) sẽ chuẩn hóa việc này bằng environment section trong docker-compose.prod.yml, và checklist go-live ở bài 9.8 sẽ nhắc lại việc không hard-code secret vào image.*

## **Bài tập / Thực hành**

> **✏️ Thực hành:** Viết Dockerfile hoàn chỉnh cho backend/ (dựa theo mẫu ở Phần 2), build ra image tên tedumarket-api:1.0, sau đó chạy \`docker images\` để ghi lại kích thước thật của image bạn build được.

Yêu cầu bổ sung để hiểu rõ giá trị của multi-stage build: dựng thêm 1 Dockerfile thử nghiệm chỉ dùng 1 stage duy nhất (FROM mcr.microsoft.com/dotnet/sdk:10.0, publish và chạy luôn trên image SDK, không tách stage runtime). Build image này với tên tedumarket-api-singlestage:1.0, so sánh kích thước 2 image bằng docker images. Ghi lại chênh lệch cụ thể (số MB) — đây là con số bạn sẽ dùng để giải thích cho người khác vì sao multi-stage là bắt buộc, không phải best practice tùy chọn.

*Hint: nếu gặp lỗi "NETSDK1004: Assets file '...' not found. Run a NuGet package restore" khi RUN dotnet publish, gần như chắc chắn bạn thiếu COPY 1 trong 4 file .csproj ở bước restore, hoặc đường dẫn COPY không khớp với cấu trúc thư mục thật trong src/. Đối chiếu lại đúng 4 dòng COPY .csproj ở Phần 2.*

*Hint 2: nếu container chạy xong exit ngay (docker ps không thấy container), dùng \`docker logs tedumarket-api-test\` để xem exception — phổ biến nhất ở bước này là lỗi kết nối Postgres do sai tên network hoặc sai connection string, không phải lỗi build image.*

## **Tổng kết**

> **✅ Tóm tắt**
>
> Multi-stage build tách biệt stage SDK (build) và stage Runtime (chạy) — image production không mang theo compiler.
>
> Dockerfile của TeduMarket.Api phải COPY đủ 4 file .csproj (Domain, Application, Infrastructure, Api) trước khi restore, đúng chiều phụ thuộc đã dựng ở bài 0.2.
>
> Image runtime .NET 10 mặc định là Ubuntu Noble; tag -noble-chiseled cho image nhỏ và an toàn hơn cho production, đánh đổi bằng việc không có shell để debug trực tiếp.
>
> Container ASP.NET Core lắng nghe ở cổng 8080 mặc định (không phải 80), chạy với USER app (non-root).
>
> **Bước tiếp theo:** bài 9.2 sẽ dockerize 2 frontend app (React Admin build ra static file serve bằng Nginx, Next.js dùng standalone output) — 2 chiến lược khác nhau cho SPA và app có server. Bài 9.3 sẽ ghép cả backend lẫn 2 frontend vào 1 docker-compose.prod.yml, lúc đó connection string và biến môi trường mới được chuẩn hóa đúng cách.
