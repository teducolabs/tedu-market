# Nội dung chính

## 1. Vì sao cần Nginx reverse proxy đứng trước nhiều app (15 phút · Lý thuyết)

Ở khóa nền tảng "Xây dựng website học trực tuyến với ASP.NET Core", bạn đã cấu hình Nginx cho đúng 1 app: 1 domain, 1 upstream, xong. Bài 9.4 mở rộng sang tình huống thật của production: 1 VPS chạy cùng lúc 3 ứng dụng độc lập — API (.NET), Admin (React SPA), Web (Next.js SSR) — mỗi ứng dụng nằm trong 1 container riêng, lắng nghe 1 cổng nội bộ riêng.

Vấn đề nếu không có reverse proxy: bạn phải mở 3 port khác nhau ra Internet (ví dụ 5000 cho API, 5001 cho Admin, 3000 cho Web), học viên truy cập kiểu http://ip:5000 — không chuyên nghiệp, không cấp được SSL cho từng port riêng lẻ theo cách thông thường, và mỗi lần thêm app mới lại phải mở thêm port, khó kiểm soát bảo mật.

Giải pháp chuẩn production — mà mọi hệ thống multi-app đều dùng: chỉ mở đúng 1 cổng vào (port 80/443) ra ngoài. Một Nginx container đóng vai trò "người gác cổng" duy nhất, đọc Host header trong request (chính là tên miền học viên gõ trên trình duyệt: api.tedumarket.dev, admin.tedumarket.dev hay www.tedumarket.dev) để quyết định chuyển tiếp (proxy) request đó vào đúng container nào — đây gọi là định tuyến theo virtual host / subdomain-based routing, khác với định tuyến theo path (/api, /admin) vì mỗi app ở đây là 1 origin độc lập, có domain riêng, tránh phải xử lý base path phức tạp ở cả 3 phía frontend/backend.

### Sơ đồ luồng request

```
Trình duyệt học viên
   |  gõ: https://admin.tedumarket.dev/courses
   v
DNS: 3 subdomain (api / admin / www) cùng trỏ A record về 1 IP VPS
   v
Nginx container (port 80/443 — CỔNG VÀO DUY NHẤT ra ngoài Internet)
   |  đọc Host header --> so khớp server_name
   |--- api.tedumarket.dev   --> proxy_pass --> container api:8080
   |--- admin.tedumarket.dev --> proxy_pass --> container admin:80
   |--- www.tedumarket.dev   --> proxy_pass --> container web:3000
   (Host header lạ, không khớp cái nào)  --> default_server --> đóng kết nối (444)
 
Toàn bộ đường đi từ Nginx --> api/admin/web chỉ nằm TRONG Docker network nội bộ,
không container nghiệp vụ nào mở port ra ngoài Internet ngoại trừ Nginx.
```

> **📘 Ghi chú giảng viên:** *Học viên hay hỏi "sao không mở luôn port 8080 của API ra ngoài cho nhanh, đỡ phải cấu hình Nginx?" — Tôi thường trả lời bằng 3 lý do thật: (1) SSL chỉ cần cấp chứng chỉ và renew ở đúng 1 chỗ (Nginx) thay vì tự làm HTTPS trong Kestrel cho từng container; (2) rate limiting, log truy cập, chặn bot có thể xử lý tập trung ở Nginx (Module 4.4 đã làm rate limit ở tầng API, đây là lớp phòng thủ thứ 2 phía ngoài); (3) đổi hạ tầng phía sau (đổi cổng, thêm container mới, scale ra 2 instance API) không ảnh hưởng gì tới học viên vì họ luôn chỉ thấy đúng 1 cổng vào.*

## 2. Xác nhận lại 3 service từ bài 9.3

Bài 9.3 đã dựng docker-compose.prod.yml với các service chạy trên cùng 1 Docker network. Bài này giả định tên service đặt như bảng dưới — nếu bạn đặt tên khác ở 9.3, chỉ cần đổi lại đúng tên đó trong các file upstream bên dưới, bản chất cấu hình không đổi:

| **Service (tên trong compose)** | **Cổng nội bộ & vai trò** |
|---|---|
| api | 8080 — TeduMarket.Api (.NET 10). Từ .NET 8 trở đi, image ASP.NET Core chính thức mặc định ASPNETCORE_HTTP_PORTS=8080, không phải 80. |
| admin | 80 — bên trong chính là 1 Nginx phụ (Module 9.2) serve static file build của React Admin. Nginx ở bài này chỉ proxy thuần, không xử lý SPA fallback thay nó. |
| web | 3000 — Next.js chạy ở chế độ standalone output (node server.js), cổng mặc định 3000 trừ khi override biến môi trường PORT. |

Cả 3 container này KHÔNG publish port ra host (không có dòng ports: trong compose của chúng) — chỉ Nginx mới có ports: "80:80". Đây là điểm hay bị bỏ sót: nếu bài 9.3 của bạn đang publish sẵn port của api/admin/web ra host, hãy gỡ các dòng ports: đó đi, chỉ giữ lại cho service nginx — nếu không, học viên vẫn truy cập vòng qua được API bằng http://ip:8080, phá vỡ mục tiêu "1 cổng vào duy nhất" của bài này.

## 4. nginx.conf — main context

```nginx
# nginx/nginx.conf
user  nginx;
worker_processes  auto;
 
events {
    worker_connections  1024;
}
 
http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;
 
    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                     '$status $body_bytes_sent "$http_referer" '
                     '"$http_user_agent" "$http_x_forwarded_for"';
    access_log  /var/log/nginx/access.log  main;
 
    sendfile           on;
    tcp_nopush          on;
    keepalive_timeout   65;
    server_tokens       off;   # ẩn version Nginx trong header Server, giảm bề mặt tấn công
    client_max_body_size 5m;   # JSON payload lớn (mô tả khóa học dài) vẫn qua được, ảnh Course đi thẳng MinIO không qua đây
 
    include /etc/nginx/conf.d/*.conf;
}
```

## 5. snippets/proxy-common.conf — header dùng chung

Đây là phần quan trọng nhất bài, vì nó quyết định API và Next.js phía sau có "nhìn thấy đúng sự thật" về request gốc hay không (đúng domain, đúng scheme https/http, đúng IP client thật của học viên chứ không phải IP nội bộ của Nginx).

```nginx
# nginx/snippets/proxy-common.conf
proxy_http_version 1.1;
proxy_set_header Connection "";           # tắt keep-alive header riêng lẻ, dùng upstream keepalive chuẩn
 
proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Forwarded-Host  $host;
 
proxy_connect_timeout 5s;
proxy_send_timeout    60s;
proxy_read_timeout    60s;
```

> **📘 Ghi chú giảng viên:** *X-Forwarded-Proto là header hay bị bỏ quên nhất. Ở bài 9.5 khi bật SSL, Nginx sẽ nhận https từ trình duyệt nhưng nói chuyện http thuần với container phía sau — nếu không forward đúng $scheme, OpenIddict (Module 3) sẽ nghĩ request đang là http và sinh redirect_uri/issuer sai giao thức, PKCE flow ở Module 6.2/7.4 sẽ lỗi ngay bước redirect đầu tiên. Tôi luôn bắt học viên tự gây lỗi này 1 lần bằng cách xóa dòng X-Forwarded-Proto rồi thử login, để nhớ lâu hơn là chỉ nghe giảng.*

## 6. default.conf — chặn Host header lạ

Nếu chỉ khai báo 3 server block theo server_name, Nginx vẫn có 1 hành vi mặc định là dùng server block ĐẦU TIÊN đọc được làm nơi xử lý mọi request không khớp server_name nào — nghĩa là ai đó gõ thẳng http://\<IP VPS> hoặc trỏ 1 domain rác về IP của bạn (kỹ thuật quét bot rất phổ biến) vẫn lọt được vào 1 trong 3 app. Khai báo default_server tường minh để đóng lỗ hổng này:

```nginx
# nginx/conf.d/default.conf
server {
    listen 80 default_server;
    server_name _;
    return 444;   # đóng kết nối ngay, không trả response — chặn bot quét theo IP
}
```

## 7. api.conf — route tới TeduMarket.Api

Điểm kỹ thuật quan trọng nhất của cả bài: nếu viết proxy_pass http://api:8080; theo kiểu "ai cũng viết", Nginx sẽ resolve tên api ra IP đúng 1 lần duy nhất lúc container Nginx khởi động (hoặc lúc reload), rồi CACHE địa chỉ IP đó. Khi bạn deploy lại container api (Module 9.6 — CI/CD) và Docker cấp cho nó 1 IP nội bộ mới, Nginx vẫn giữ IP cũ trong bộ nhớ → 502 Bad Gateway dù container api đang chạy tốt. Cách đúng chuẩn: dùng biến trong proxy_pass, kết hợp resolver trỏ về DNS nội bộ của Docker (127.0.0.11) để Nginx resolve lại tên service mỗi khi TTL hết hạn, không cache vĩnh viễn.

```nginx
# nginx/conf.d/api.conf
server {
    listen 80;
    server_name api.tedumarket.dev;
 
    resolver 127.0.0.11 valid=10s;   # DNS nội bộ của Docker (Docker embedded DNS)
 
    location / {
        set $upstream_api api:8080;   # dùng biến -> Nginx re-resolve mỗi khi TTL hết hạn
        proxy_pass http://$upstream_api;
        include /etc/nginx/snippets/proxy-common.conf;
    }
}
```

> **📘 Ghi chú giảng viên:** *Đây là lỗi kinh điển tôi thấy nhiều học viên gặp nhất sau khi lên production: "chạy docker compose up lần đầu thì OK hết, nhưng cứ deploy lại API là Admin/Web báo lỗi kết nối API, phải restart cả Nginx mới hết" — 99% là do proxy_pass viết trực tiếp domain (không qua biến), thiếu resolver. Đáng nhớ vì đây chính là lý do dùng biến trong proxy_pass — không phải "để cho đúng chuẩn" chung chung.*

## 8. admin.conf — route tới React Admin

Container admin (bài 9.2) bên trong đã là 1 Nginx tĩnh serve file build React, tự lo việc try_files cho client-side routing của SPA. Nginx ở tầng ngoài này chỉ đơn thuần chuyển tiếp — không lặp lại logic SPA fallback:

```nginx
# nginx/conf.d/admin.conf
server {
    listen 80;
    server_name admin.tedumarket.dev;
 
    resolver 127.0.0.11 valid=10s;
 
    location / {
        set $upstream_admin admin:80;
        proxy_pass http://$upstream_admin;
        include /etc/nginx/snippets/proxy-common.conf;
    }
}
```

## 9. web.conf — route tới Next.js Student Site

Next.js standalone (Module 9.2) chạy server Node thật, không phải file tĩnh — proxy tương tự admin.conf nhưng cần lưu ý X-Forwarded-Host vì Next.js 15 dùng header Host để dựng URL tuyệt đối (ví dụ trong generateMetadata ở bài 7.3, hoặc redirect sau Server Action ở bài 7.5); nếu thiếu, URL sinh ra có thể trỏ nhầm về tên service nội bộ web thay vì www.tedumarket.dev.

```nginx
# nginx/conf.d/web.conf
server {
    listen 80;
    server_name www.tedumarket.dev tedumarket.dev;
 
    resolver 127.0.0.11 valid=10s;
 
    location / {
        set $upstream_web web:3000;
        proxy_pass http://$upstream_web;
        include /etc/nginx/snippets/proxy-common.conf;
    }
 
    # Chuẩn bị sẵn cho bài 9.5 (SSL Let's Encrypt) — certbot cần đường dẫn này
    # để xác thực quyền sở hữu domain qua HTTP-01 challenge, không cần sửa lại file này ở bài sau.
    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }
}
```

Áp dụng đúng khối .well-known/acme-challenge/ này cho cả api.conf và admin.conf trước khi sang bài 9.5, vì mỗi subdomain cần tự chứng minh quyền sở hữu riêng khi Certbot cấp chứng chỉ.

## 10. Thêm service nginx vào docker-compose.prod.yml

Mở rộng file compose đã có từ bài 9.3 — chỉ thêm service nginx và bỏ publish port trực tiếp của api/admin/web như đã nói ở mục 2:

```yaml
# docker-compose.prod.yml (phần thêm mới)
services:
  # ... api, admin, web, postgres, redis, seq da co tu bai 9.1-9.3 ...
  # LƯU Ý: gỡ mọi dòng 'ports:' của api/admin/web nếu đang có, chỉ giữ lại ở nginx
 
  nginx:
    image: nginx:1.27-alpine
    container_name: tedumarket-nginx
    restart: unless-stopped
    ports:
      - "80:80"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - ./nginx/snippets:/etc/nginx/snippets:ro
      - certbot-webroot:/var/www/certbot:ro
    depends_on:
      - api
      - admin
      - web
    networks:
      - tedumarket-net
 
volumes:
  certbot-webroot:   # dùng ở bài 9.5, tạo sẵn để không phải sửa lại file này
 
networks:
  tedumarket-net:
    driver: bridge
```

Nếu network hoặc tên các volume khác ở bài 9.3 của bạn, giữ nguyên tên bạn đã đặt — chỉ cần bảo đảm nginx nằm trong cùng networks: với 3 service kia, vì resolver 127.0.0.11 chỉ resolve được tên service trong cùng 1 Docker network.

## 11. Lưu ý bắt buộc trong TeduMarket.Api — ForwardedHeadersMiddleware

Nginx đã forward đúng header X-Forwarded-Proto/Host, nhưng ASP.NET Core mặc định KHÔNG tự đọc các header này — phải khai báo tường minh ForwardedHeadersMiddleware trong Program.cs. Mặc định của middleware này còn chặt hơn nữa: chỉ tin request đến từ loopback (127.0.0.1) — trong khi ở đây proxy đứng trước là 1 container Nginx riêng, có IP nội bộ Docker (không phải loopback), nên nếu không cấu hình lại, ASP.NET Core sẽ âm thầm BỎ QUA header Nginx gửi lên, và lỗi ở mục 5/7 vẫn xảy ra dù Nginx đã cấu hình đúng.

```csharp
// TeduMarket.Api/Program.cs
using Microsoft.AspNetCore.HttpOverrides;
 
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders = ForwardedHeaders.XForwardedFor
                              | ForwardedHeaders.XForwardedProto
                              | ForwardedHeaders.XForwardedHost;
 
    // Nginx chạy trong Docker network nội bộ, IP không phải loopback
    // -> phải bỏ giới hạn mặc định (chỉ tin loopback) để middleware chấp nhận header từ nó.
    // Vì Nginx là điểm vào DUY NHẤT ra Internet (không container nghiệp vụ nào lộ port),
    // chấp nhận tin toàn bộ request tới Kestrel là hợp lý trong phạm vi mạng nội bộ này.
    options.KnownNetworks.Clear();
    options.KnownProxies.Clear();
});
 
var app = builder.Build();
 
app.UseForwardedHeaders();   // PHẢI đặt trước mọi middleware đọc scheme/host,
                              // đặc biệt trước OpenIddict server middleware (Module 3.2)
// ... phần còn lại của pipeline (giữ nguyên từ Module 0-8) ...
```

> **📘 Ghi chú giảng viên:** *Đã học ở Module 3.2 — OpenIddict tự sinh issuer URL và validate redirect_uri dựa trên Request.Scheme/Request.Host của HttpContext. Đây chính là lý do dòng app.UseForwardedHeaders() phải đứng TRƯỚC bất kỳ middleware nào của OpenIddict trong pipeline: nếu đặt sau, OpenIddict đã đọc scheme/host sai (http, hoặc host nội bộ) trước khi middleware kịp sửa lại.*

### Hint khi bị kẹt

- 502 Bad Gateway ngay cả khi container đang chạy → gần như chắc chắn thiếu resolver 127.0.0.11 hoặc quên dùng biến trong proxy_pass (mục 7) — kiểm tra lại đúng 2 dòng đó trước.
- Mọi subdomain đều rơi vào cùng 1 app → thiếu default_server hoặc server_name gõ sai chính tả, không khớp Host header thật.
- Đăng nhập Admin xong bị redirect về sai domain hoặc sai http/https → thiếu X-Forwarded-Proto ở Nginx, hoặc quên gọi app.UseForwardedHeaders() trong Program.cs, hoặc gọi đúng nhưng đặt SAU middleware OpenIddict.
- curl với Host giả không bị 444 → thiếu listen 80 default_server; đang có 2 server block cùng để listen 80 mà không block nào default_server, Nginx tự chọn block đầu tiên trong conf.d (thứ tự alphabet: admin.conf) làm mặc định.

# Tổng kết

- 1 Nginx container là cổng vào duy nhất (port 80/443) cho toàn bộ 3 app — không container nghiệp vụ nào expose port ra Internet.
- Định tuyến dựa trên server_name (Host header) — mỗi subdomain một server block, có default_server catch-all để chặn Host header lạ.
- proxy_pass PHẢI dùng biến kết hợp resolver 127.0.0.11, không viết thẳng domain — nếu không, container restart sẽ gây 502 vì Nginx cache IP cũ.
- Bộ header X-Forwarded-\* là cầu nối bắt buộc giữa Nginx và ASP.NET Core/Next.js phía sau — thiếu nó, OpenIddict (Module 3) và Next.js (Module 7) sẽ sinh sai URL tuyệt đối.
- ForwardedHeadersMiddleware trong Program.cs phải Clear() KnownNetworks/KnownProxies (vì proxy không phải loopback) và đặt trước mọi middleware đọc scheme/host.

### So sánh nhanh: Reverse proxy 1 app vs Multi-app theo subdomain

| **Reverse proxy 1 app (khóa nền tảng)** | **Multi-app theo subdomain (bài này)** |
|---|---|
| 1 server block, 1 upstream cố định | N server block, mỗi cái 1 server_name + upstream riêng |
| Không cần default_server (chỉ 1 app, ai gõ IP cũng vào đúng app đó) | Bắt buộc default_server để chặn Host header không khớp |
| Ít quan tâm DNS cache vì hiếm khi container đổi IP giữa chừng | Bắt buộc resolver + biến, vì deploy lại 1 trong nhiều container là chuyện thường xuyên |
| 1 domain, ít rủi ro sai X-Forwarded-Host | Nhiều domain — sai X-Forwarded-Host/Proto ảnh hưởng trực tiếp OAuth2 redirect |
