## Nội dung chính

### Phần 1 — Vì sao pipeline phải đi đúng thứ tự Test → Build → Deploy

*Thời lượng: 15 phút | Loại: Lý thuyết*

Bài 9.6 là bài chốt hạ của Module 9: mọi thứ bạn đã dựng — Dockerfile (9.1, 9.2), docker-compose.prod.yml (9.3), Nginx multi-app + SSL (9.4, 9.5) — giờ được nối lại thành 1 pipeline chạy tự động mỗi khi có code mới merge vào main. Outline gọi đây là "build gate thật, không phải hình thức" — nghĩa là nếu test fail, image không được build, VPS không nhận bản deploy mới. Đây chính là điểm khác biệt với một pipeline chỉ chạy test cho có rồi vẫn build/deploy bất kể kết quả.

Một workflow GitHub Actions gồm nhiều job. Mặc định, các job chạy song song — muốn job B chỉ chạy sau khi job A xong, phải khai báo rõ:

```yaml
jobs:
  build-and-push:
    needs: test        # job này chỉ chạy khi job "test" pass
```

Theo mặc định, needs yêu cầu job trước phải kết thúc với trạng thái success. Nếu job test fail, GitHub Actions tự động chuyển job build-and-push (và mọi job needs nó, tức deploy) sang trạng thái skipped — không cần bạn tự viết if kiểm tra kết quả test.

Trigger cũng phải tách rõ 2 tình huống:

- pull_request vào main — chỉ cần chạy job test để review code trước khi merge, không build image, không deploy (tránh push image thử nghiệm lên registry production).
- push vào main (tức đã merge) — chạy đủ cả 3 job: test → build-and-push → deploy.

Việc gắn quyền lấy image: GHCR dùng chung với GitHub, nên không cần tạo Personal Access Token riêng cho bước đẩy image trong CI — mỗi lần workflow chạy, GitHub tự cấp một GITHUB_TOKEN tạm thời, đủ quyền push vào ghcr.io nếu bạn khai báo permissions: packages: write. Còn 3 giá trị để SSH vào VPS (host, username, private key) là thông tin thật sự nhạy cảm, phải lưu ở GitHub Secrets (Settings → Secrets and variables → Actions) — Secrets được mã hoá và tự động che trong log, khác với Variables chỉ dùng cho giá trị không nhạy cảm.

> **📘 Ghi chú giảng viên:** *Lỗi tôi thấy học viên mắc nhiều nhất ở bài này là quên khai báo needs — 3 job chạy song song, image vẫn build và deploy dù job test đang fail. Lúc demo, tôi cố tình bỏ needs, cho học viên xem cả 3 job chạy đồng thời trên tab Actions, rồi hỏi: "Pipeline này có test không?" — Có. "Vậy test có tác dụng gì không?" — Không, vì chẳng ai đợi kết quả test trước khi build. Đó chính là ý outline muốn nói khi ghi "build gate thật, không phải hình thức".*

### Phần 2 — Job test: chạy lại bộ test Module 8 trên CI

*Thời lượng: 15 phút | Loại: Demo + Lab*

Tạo file .github/workflows/ci-cd.yml ở gốc repo — thư mục .github/workflows luôn nằm ở root, ngang hàng với backend/ và frontend/ theo cấu trúc monorepo đã chốt ở mục 6 outline:

```yaml
name: TEDU Market CI/CD
 
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
 
concurrency:
  group: tedu-market-deploy
  cancel-in-progress: false
 
env:
  REGISTRY: ghcr.io
  IMAGE_PREFIX: ${{ github.repository_owner }}/tedu-market
 
jobs:
  test:
    name: Chạy bộ test Module 8 (build gate)
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
 
      - name: Setup .NET 10 SDK
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '10.0.x'
 
      - name: Restore dependencies
        run: dotnet restore backend/TeduMarket.sln
 
      - name: Unit Test (Handler + Domain — bài 8.1, 8.2)
        run: >
          dotnet test backend/tests/TeduMarket.Application.UnitTests
          --configuration Release --logger "trx"
 
      - name: Integration Test (Testcontainers — bài 8.3, 8.4)
        run: >
          dotnet test backend/tests/TeduMarket.Api.IntegrationTests
          --configuration Release --logger "trx"
```

Không cần cấu hình gì thêm cho Testcontainers: GitHub-hosted runner ubuntu-latest có sẵn Docker daemon, nên đoạn code ở bài 8.3 tự pull image Postgres và dựng container thật ngay trên CI, giống hệt cách nó chạy ở máy local — không cần "mock" hay service container riêng.

> **📘 Ghi chú giảng viên:** *Lần chạy đầu sẽ chậm hơn local vì runner phải pull image Postgres từ đầu. Từ lần thứ 2 trở đi, GitHub cache lại Docker layer nên nhanh hơn hẳn — tôi hay nhắc học viên đừng hoảng nếu lần đầu job test chạy 3–4 phút, đó là bình thường.*

### Phần 3 — Job build-and-push: build & đẩy 3 Docker image lên GHCR

*Thời lượng: 15 phút | Loại: Demo + Lab*

3 service api, admin, web dùng 3 Dockerfile khác nhau đã tạo ở bài 9.1 và 9.2. Dùng matrix strategy để build cả 3 trong cùng 1 job definition, tránh copy-paste 3 lần:

```
  build-and-push:
    name: Build & push Docker image
    needs: test
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    strategy:
      matrix:
        include:
          - service: api
            context: ./backend
            dockerfile: ./backend/src/TeduMarket.Api/Dockerfile
          - service: admin
            context: ./frontend
            dockerfile: ./frontend/apps/admin/Dockerfile
          - service: web
            context: ./frontend
            dockerfile: ./frontend/apps/web/Dockerfile
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
 
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3
 
      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
 
      - name: Build and push ${{ matrix.service }}
        uses: docker/build-push-action@v6
        with:
          context: ${{ matrix.context }}
          file: ${{ matrix.dockerfile }}
          push: true
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE_PREFIX }}-${{ matrix.service }}:${{ github.sha }}
            ${{ env.REGISTRY }}/${{ env.IMAGE_PREFIX }}-${{ matrix.service }}:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

Điểm cần chú ý: if ở job này kiểm tra github.event_name == 'push' chứ không chỉ github.ref — nếu chỉ check ref, một số cấu hình trigger khác (ví dụ workflow_dispatch) có thể vô tình lọt qua điều kiện. Mỗi image được gắn 2 tag: ${{ github.sha }} để biết chính xác image nào ứng với commit nào (phục vụ rollback), và latest để docker-compose.prod.yml trên VPS luôn kéo được bản mới nhất.

> **📘 Ghi chú giảng viên:** *cache-from/cache-to: type=gha là cache build của GitHub Actions — giúp lần build sau tái sử dụng layer Docker chưa đổi (ví dụ layer restore NuGet package), rút thời gian build từ vài phút xuống vài chục giây nếu chỉ đổi code tầng trên. Tôi hay demo trực tiếp: build lần 1 mất ~2 phút, sửa 1 dòng code rồi build lại chỉ mất ~20 giây, để học viên thấy giá trị của cache thay vì chỉ nghe lý thuyết.*

### Phần 4 — Job deploy: SSH vào VPS, chạy lại docker compose

*Thời lượng: 15 phút | Loại: Demo + Lab*

Trước khi viết job này, tạo 3 Secrets trên GitHub: repo → Settings → Secrets and variables → Actions → New repository secret: VPS_HOST (IP hoặc domain VPS), VPS_USERNAME (user Linux dùng để SSH), VPS_SSH_KEY (nội dung private key riêng cho CI — public key tương ứng đã add vào ~/.ssh/authorized_keys trên VPS).

```
  deploy:
    name: Deploy lên VPS Production
    needs: build-and-push
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - name: Deploy qua SSH
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.VPS_HOST }}
          username: ${{ secrets.VPS_USERNAME }}
          key: ${{ secrets.VPS_SSH_KEY }}
          script: |
            cd /srv/tedu-market
            docker compose -f docker-compose.prod.yml pull
            docker compose -f docker-compose.prod.yml up -d --remove-orphans
            docker image prune -f
```

docker compose ... pull kéo về đúng image :latest vừa được job trước push lên GHCR; up -d --remove-orphans khởi động lại container với image mới và dọn container thừa nếu có service nào bị xoá khỏi compose file; docker image prune -f dọn các image cũ không còn container nào dùng, tránh VPS đầy ổ đĩa sau nhiều lần deploy.

concurrency (đã khai báo ở đầu file, Phần 2) đảm bảo nếu có 2 commit liên tiếp merge vào main trong lúc job deploy trước còn đang chạy, job deploy thứ 2 sẽ đợi thay vì chạy chồng — tránh tình huống 2 lệnh docker compose up -d chạy cùng lúc trên cùng 1 VPS.

> **📘 Ghi chú giảng viên:** *VPS_SSH_KEY phải là key riêng tạo cho CI (ssh-keygen -t ed25519 -C "github-actions-deploy"), không phải key cá nhân của bạn hay của dev nào khác. Nếu key này rò rỉ, chỉ cần revoke đúng 1 key đó khỏi authorized_keys trên VPS chứ không phải đổi mật khẩu/khoá của cả team. Tôi cũng khuyên giới hạn user SSH deploy chỉ có quyền trong thư mục /srv/tedu-market, không cấp sudo toàn hệ thống.*

## Bài tập thực hành

Mục tiêu: tự tay chứng minh build gate có tác dụng thật, không chỉ đọc lý thuyết.

> **✏️ Thực hành:** Bước 1 — Tạo 1 branch mới, cố tình sửa sai 1 assertion trong bộ test TeduMarket.Application.UnitTests (ví dụ đổi Assert.Equal(expected, actual) thành so sánh sai giá trị), push lên GitHub và mở Pull Request vào main. Vào tab Actions, quan sát: job test có trạng thái Failed; job build-and-push và deploy có trạng thái gì? Ghi lại đúng trạng thái bạn thấy (Skipped hay không chạy) và giải thích vì sao dựa trên từ khóa needs.
>
> **✏️ Thực hành:** Bước 2 — Sửa lại test cho đúng, push tiếp lên cùng branch, đợi job test pass trên PR rồi merge Pull Request vào main. Vào tab Actions của lần chạy trên main, xác nhận đủ 3 job chạy tuần tự và đều Success. Sau đó SSH vào VPS, chạy docker image ls | grep tedu-market để xác nhận image vừa deploy có tag đúng bằng commit SHA của lần merge này.

Input: repo GitHub đã có file .github/workflows/ci-cd.yml từ Phần 2–4. Expected output: log Actions cho thấy rõ 2 lần chạy khác nhau — 1 lần bị chặn ở job test, 1 lần chạy trọn 3 job và VPS nhận đúng image mới.

Hint: nếu job build-and-push vẫn chạy dù job test Failed, kiểm tra lại chính tả tên job trong needs — needs phải khớp chính xác (phân biệt hoa/thường) với tên key của job đứng trước trong jobs:, không phải với trường name hiển thị trên UI.

Solution: toàn bộ nội dung file .github/workflows/ci-cd.yml hoàn chỉnh — ghép đúng thứ tự các đoạn code ở Phần 2, 3, 4 phía trên (block on/concurrency/env, sau đó 3 job test, build-and-push, deploy) là đáp án đầy đủ cho bài tập này.

## Tổng kết

- 3 job nối bằng needs (test → build-and-push → deploy) là cách hiện thực build gate thật trong GitHub Actions — job sau tự động Skipped nếu job trước Failed, không cần tự viết điều kiện kiểm tra.
- Trigger phải tách rõ: pull_request vào main chỉ chạy job test (gate review code); push vào main (đã merge) mới chạy đủ cả build và deploy.
- GHCR dùng GITHUB_TOKEN tự động cấp mỗi lần workflow chạy — không cần tạo Personal Access Token riêng, chỉ cần khai báo permissions: packages: write.
- 3 thông tin SSH vào VPS (host, username, private key) là dữ liệu nhạy cảm thật sự, luôn lưu ở GitHub Secrets, dùng 1 key riêng cho CI, không dùng chung key cá nhân.
- concurrency group ở đầu workflow tránh 2 lần deploy chạy chồng nhau khi có nhiều commit liên tiếp vào main.

| **Tình huống trigger** | **Job chạy** | **Có deploy không?** |
|---|---|---|
| Mở Pull Request vào main | Chỉ job test | Không |
| Merge / push thẳng vào main, test pass | test → build-and-push → deploy | Có |
| Merge / push thẳng vào main, test fail | Chỉ job test (Failed); 2 job sau Skipped | Không |

> **✅ Tóm tắt:** Pipeline CI/CD đã hoàn chỉnh: mỗi commit merge vào main, nếu bộ test Module 8 pass, hệ thống tự build 3 Docker image và deploy thẳng lên VPS — không còn thao tác thủ công nào ở bước đưa code lên production.

**Bước tiếp theo:** bài 9.7 — Serilog + Seq Production Logging. Khi pipeline này deploy một bản có lỗi, bạn cần công cụ để lần theo đúng request đã gây lỗi trên production — đó là lý do structured logging và CorrelationId được dạy ngay sau bài CI/CD này.
