# Nội dung chính

## 1. SPA và Next.js: hai bài toán deploy khác nhau

*Lý thuyết · 10 phút*

Ở bài 9.1, bạn đã Dockerize backend .NET 10 bằng multi-stage build: một stage để build (SDK image, nặng), một stage runner chỉ chứa artifact đã publish (ASP.NET runtime image, nhẹ). Nguyên lý đó vẫn đúng cho frontend — nhưng "artifact cuối cùng" và "runtime tối thiểu" của apps/admin và apps/web là hai thứ khác hẳn nhau, nên không thể dùng chung 1 Dockerfile.

### apps/admin (React + Vite) — SPA thuần

Sau khi chạy vite build, kết quả chỉ là các file HTML/CSS/JS tĩnh nằm trong thư mục dist/. Không có bất kỳ đoạn code Node.js nào chạy ở production — trình duyệt tải file tĩnh về và tự chạy React trên client. Vì vậy "runtime" mà image cần chỉ là một web server tĩnh, và lựa chọn kinh điển là Nginx: image cuối cùng không chứa Node.js, không chứa node_modules, chỉ có vài chục MB HTML/CSS/JS cộng với Nginx.

### apps/web (Next.js App Router) — có server thật

apps/web không phải SPA. Bạn đã dùng Server Component và ISR ở bài 7.2, Server Action ở bài 7.5, và đặc biệt là route handler xử lý session OIDC ở bài 7.4 — session được lưu phía server, không lưu ở localStorage như React Admin. Tất cả những thứ này cần một Node.js process chạy thật ở production để xử lý request, không thể "build ra rồi serve tĩnh" như Vite. Next.js hỗ trợ sẵn chế độ output: 'standalone' để đóng gói server đó gọn nhất có thể — chỉ copy đúng phần node_modules mà app thực sự dùng tới, thay vì cả node_modules gốc (có thể vài trăm MB).

### Vấn đề riêng của monorepo: cache Docker bị "toang" oan

apps/admin và apps/web nằm chung 1 pnpm workspace (Module 5.1), cùng phụ thuộc packages/api-client. Nếu Dockerfile COPY toàn bộ repo rồi chạy pnpm install cho cả workspace, Docker sẽ dùng layer cache dựa trên toàn bộ nội dung COPY — nghĩa là chỉ cần sửa 1 dòng code ở apps/admin, cache của layer install cũng bị invalidate, kéo theo build lại apps/web từ đầu dù nó không hề đổi. Turborepo giải quyết vấn đề này bằng lệnh turbo prune \<tên-app> --docker: tạo ra một bản sao monorepo đã cắt gọn, chỉ giữ lại package.json và lockfile của đúng những package mà app đó phụ thuộc, tách thành 2 thư mục con json/ (chỉ package.json, dùng để cache layer install) và full/ (toàn bộ source, dùng để build).

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi học viên: "Tại sao Turborepo lại tách json/ và full/ thành 2 bước COPY riêng thay vì COPY hết 1 lần?" — câu trả lời đúng là để tận dụng Docker layer cache: layer RUN pnpm install chỉ cần chạy lại khi package.json/lockfile đổi, còn COPY source code (hay đổi liên tục khi code) nằm ở layer sau, không làm invalidate layer install. Đây chính là lý do turbo prune --docker sinh ra 2 thư mục out/json và out/full thay vì gộp làm một.*

## 2. Dockerize apps/admin — React (Vite) + Nginx

*Demo · 10 phút*

Dockerfile của apps/admin gồm 2 stage: builder (cài dependency bằng pnpm + turbo, build ra dist/) và runner (chỉ chứa Nginx + file tĩnh, không có Node.js).

> **`frontend/apps/admin/Dockerfile`**

```dockerfile
FROM node:22-alpine AS base
 
# ---
FROM base AS pruner
WORKDIR /app
RUN npm install -g turbo
COPY . .
# Chỉ giữ lại package.json + lockfile của admin và các package nó phụ thuộc
RUN turbo prune admin --docker
 
# ---
FROM base AS builder
WORKDIR /app
RUN npm install -g pnpm
# Cài dependency trước — layer này chỉ rebuild khi package.json/lockfile đổi
COPY --from=pruner /app/out/json/ .
RUN pnpm install --frozen-lockfile
# Copy source code thật vào sau — đổi code không làm invalidate layer install ở trên
COPY --from=pruner /app/out/full/ .
RUN pnpm turbo build --filter=admin
 
# ---
FROM nginx:1.27-alpine AS runner
COPY --from=builder /app/apps/admin/dist /usr/share/nginx/html
COPY apps/admin/nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

File nginx.conf là phần dễ bị bỏ quên nhất khi Dockerize SPA. React Router (client-side routing) xử lý URL như /courses/123 hoàn toàn trên trình duyệt — server không hề có file /courses/123 thật. Nếu Nginx không được cấu hình fallback, user bấm F5 ở route đó sẽ nhận 404 thay vì trang admin.

> **`frontend/apps/admin/nginx.conf`**

```csharp
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;
 
    # Mọi route không khớp file tĩnh đều trả về index.html
    # để React Router tự xử lý routing phía client
    location / {
        try_files $uri $uri/ /index.html;
    }
 
    # Cache dài hạn cho asset đã có hash trong tên file (Vite tự thêm hash khi build)
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }
}
```

## 3. Dockerize apps/web — Next.js App Router (standalone)

*Demo · 10 phút*

Trước tiên, bật chế độ standalone trong next.config.ts. Vì apps/web nằm trong monorepo, Next.js mặc định chỉ trace file phụ thuộc trong chính thư mục apps/web — cần khai báo outputFileTracingRoot trỏ về gốc monorepo để nó trace đúng cả packages/api-client dùng chung.

> **`frontend/apps/web/next.config.ts`**

```typescript
import type { NextConfig } from "next";
import path from "node:path";
 
const nextConfig: NextConfig = {
  output: "standalone",
  // Trace file phụ thuộc từ gốc monorepo, không chỉ trong apps/web
  // để packages/api-client được copy đúng vào .next/standalone
  outputFileTracingRoot: path.join(__dirname, "../../"),
};
 
export default nextConfig;
```

Dockerfile áp dụng đúng pattern pruner → builder → runner như apps/admin, nhưng runner stage chạy Node.js thay vì Nginx.

> **`frontend/apps/web/Dockerfile`**

```dockerfile
FROM node:22-alpine AS base
 
# ---
FROM base AS pruner
WORKDIR /app
RUN npm install -g turbo
COPY . .
RUN turbo prune web --docker
 
# ---
FROM base AS builder
WORKDIR /app
RUN npm install -g pnpm
COPY --from=pruner /app/out/json/ .
RUN pnpm install --frozen-lockfile
COPY --from=pruner /app/out/full/ .
RUN pnpm turbo build --filter=web
 
# ---
FROM base AS runner
WORKDIR /app
ENV NODE_ENV=production
ENV PORT=3000
 
# Không chạy production bằng root
RUN addgroup --system --gid 1001 nodejs
RUN adduser --system --uid 1001 nextjs
 
# .next/standalone đã tự chứa node_modules cần thiết — không cần pnpm install ở đây
# Lưu ý: do build từ gốc monorepo, server.js nằm ở apps/web/server.js
# bên trong thư mục standalone, không nằm ở gốc
COPY --from=builder --chown=nextjs:nodejs /app/apps/web/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/apps/web/.next/static ./apps/web/.next/static
COPY --from=builder --chown=nextjs:nodejs /app/apps/web/public ./apps/web/public
 
USER nextjs
EXPOSE 3000
CMD ["node", "apps/web/server.js"]
```

> **📘 Ghi chú giảng viên:** *Lỗi phổ biến nhất học viên gặp ở bài này: build xong, chạy docker run báo "Cannot find module '/app/server.js'". Nguyên nhân hầu như luôn là COPY sai path — vì build từ gốc monorepo (outputFileTracingRoot trỏ về root), Next.js sinh ra .next/standalone/apps/web/server.js chứ không phải .next/standalone/server.js như khi build 1 app đơn lẻ. Tôi thường yêu cầu học viên tự ls /app/apps/web/.next/standalone sau build để nhìn thấy cấu trúc lồng này trước khi hỏi "tại sao path lại thế".*

Một điểm cần lưu ý riêng cho phần Auth OIDC (bài 7.4): session lưu phía server đọc biến môi trường lúc container khởi động (runtime), khác với biến NEXT_PUBLIC_\* — loại biến này bị Next.js "đóng băng" giá trị ngay lúc build, đổi ENV lúc docker run sẽ không có tác dụng với NEXT_PUBLIC_\*. Đây là lý do image production của Next.js không nên hard-code URL API vào biến NEXT_PUBLIC\_ nếu URL đó còn thay đổi giữa các môi trường.

# Bài tập thực hành

> **✏️ Thực hành:** Build và kiểm chứng cả 2 image frontend cho TEDU Market, chạy từ thư mục gốc frontend/ (nơi có pnpm-workspace.yaml, vì turbo prune cần thấy toàn bộ workspace).

1. Build image admin: docker build -f apps/admin/Dockerfile -t tedu-market-admin . — sau đó docker run -p 8080:80 tedu-market-admin, mở trình duyệt vào 1 route con (ví dụ /courses/1), bấm F5 để xác nhận Nginx không trả về 404.
1. Build image web: docker build -f apps/web/Dockerfile -t tedu-market-web . — sau đó docker run -p 3000:3000 tedu-market-web, curl http://localhost:3000 để xác nhận trả về 200.
1. Chạy docker images | grep tedu-market, so sánh kích thước 2 image — image admin (Nginx + static) phải nhỏ hơn đáng kể so với image web (có Node.js runtime).
1. Nâng cao: sửa 1 dòng bất kỳ chỉ trong apps/admin (ví dụ đổi text 1 button), build lại image web. Quan sát log build — layer RUN pnpm install của web phải được lấy từ cache (Docker báo CACHED), không chạy lại, chứng minh turbo prune đã cô lập đúng dependency giữa 2 app.

**Gợi ý (Hint):**

- Nếu build báo lỗi "Cannot find module 'next'" hoặc "Cannot find module '.../server.js'", gần như chắc chắn là sai path COPY ở runner stage — hãy build đến hết stage builder rồi ls thủ công /app/apps/web/.next/standalone để xem cấu trúc thật.
- Nếu turbo prune báo lỗi liên quan lockfile (ví dụ "Broken lockfile"), kiểm tra lại pnpm-lock.yaml đã được commit và không bị conflict — turbo prune parse trực tiếp file này.

Solution: 2 Dockerfile và nginx.conf hoàn chỉnh đã có đầy đủ ở phần Nội dung chính phía trên — copy đúng nguyên văn, chỉ cần đổi tên app (--filter, prune \<app>) nếu bạn thêm app thứ 3 vào monorepo sau này.

# Tổng kết

> **✅ Tóm tắt:** apps/admin (React + Vite) là SPA thuần — build ra static file, Nginx serve, image không cần Node.js runtime. apps/web (Next.js App Router) có Server Component/Server Action/session OIDC chạy thật ở server — cần output: 'standalone' + Node.js runtime tối thiểu. Cả 2 Dockerfile đều dùng chung pattern turbo prune \<app> --docker → pnpm install (cache theo lockfile) → build → runner tối giản, để sửa code ở 1 app không kéo theo rebuild oan app còn lại.

| **Tiêu chí** | **apps/admin (Vite)** | **apps/web (Next.js)** |
|---|---|---|
| Kết quả build | File tĩnh trong dist/ | Server bundle trong .next/standalone |
| Runtime production | Không cần Node.js — chỉ Nginx | Cần Node.js chạy server.js |
| Base image runner | nginx:1.27-alpine | node:22-alpine |
| Điểm dễ sai | Quên try_files → 404 khi refresh route con | Sai path COPY do server.js nằm lồng trong apps/web/ |
