## Nội dung chính

### 1. Vì sao cần checklist go-live viết ra giấy

*Thời lượng: 10 phút | Loại: Lý thuyết*

Đến bài 9.8, TEDU Market đã có đủ hạ tầng: Docker hóa cả backend lẫn 2 frontend (9.1–9.3), Nginx route đúng 3 subdomain (9.4), SSL Let's Encrypt (9.5), pipeline CI/CD chạy test trước khi deploy (9.6), và log tập trung theo CorrelationId trên Seq (9.7). Vấn đề bài này giải quyết không phải kỹ thuật mới — mà là quy trình: đưa hệ thống lên production thật lần đầu, nơi có tiền thật của học viên chảy qua webhook SePay (2.5).

Ba tình huống thực tế hay xảy ra nếu không có checklist viết sẵn:

- Webhook SePay đăng ký sai domain (vẫn trỏ về URL sandbox/dev) — Order không bao giờ chuyển sang Paid dù học viên đã chuyển khoản thật, dẫn đến tranh chấp và mất uy tín ngay lần bán đầu tiên.
- DNS TTL để mặc định 24 giờ — khi cần đổi IP để rollback hạ tầng, bản ghi cũ vẫn được cache ở nhiều resolver trong nhiều giờ, không rollback nhanh được dù code đã sẵn sàng.
- Migration cuối cùng trước go-live chạy thẳng bằng dotnet ef database update mà không xem trước SQL sinh ra — nếu migration đó khóa bảng Order/Course lớn, hệ thống đơ ngay lúc có traffic thật.

Nguyên tắc cốt lõi của bài này: checklist tồn tại để loại bỏ quyết định phải nghĩ ra lúc đang có sự cố. Rollback phải là một hành động đã viết sẵn từng bước, không phải một cuộc họp khẩn lúc 11 giờ đêm.

> **📘 Ghi chú giảng viên:** *Tôi hay nhấn mạnh với học viên một mình làm chủ dự án (giống chính TEDU lúc mới mở công ty): checklist càng quan trọng hơn khi không có ai review chéo. Ở đội nhóm lớn, đồng nghiệp có thể bắt lỗi hộ bạn lúc deploy; một mình thì checklist là người review duy nhất bạn có.*

### 2. Checklist Trước Go-live (Pre-launch)

*Thời lượng: 15 phút | Loại: Demo + Lab*

### 2.1. Database

- **Backup đầy đủ trước khi migrate:** pg_dump toàn bộ database production, và quan trọng hơn — thử restore bản backup đó lên một database rỗng khác ngay lúc đó. Backup chưa từng được restore thử không tính là backup.

```bash
# Backup
pg_dump -h <host> -U tedumarket -Fc tedumarket_prod > backup_$(date +%Y%m%d_%H%M).dump

# Test restore lên database tạm để xác nhận backup dùng được
createdb -h <host> -U tedumarket tedumarket_restore_test
pg_restore -h <host> -U tedumarket -d tedumarket_restore_test backup_20260920_2100.dump
```

- **Review SQL trước khi apply:** không chạy dotnet ef database update thẳng vào production mà không xem SQL sinh ra. Dùng dotnet ef migrations script để xuất SQL, đọc kỹ xem có lệnh khóa bảng lớn (ví dụ ALTER TABLE thêm cột NOT NULL trên bảng Order đã có dữ liệu) không.

```sql
dotnet ef migrations script --idempotent \
  --project src/TeduMarket.Infrastructure \
  --startup-project src/TeduMarket.Api \
  --output migration-review.sql

# Đọc migration-review.sql, xác nhận an toàn rồi mới apply thật:
dotnet ef database update \
  --project src/TeduMarket.Infrastructure \
  --startup-project src/TeduMarket.Api
```

### 2.2. Payment / Webhook SePay

Outline gốc của khóa ghi "kiểm tra webhook VNPay production" — nhưng TEDU Market dùng chuyển khoản ngân hàng qua QR (VietQR) và webhook SePay (bài 2.4–2.5), không dùng VNPay. Checklist dưới đây theo đúng kiến trúc thật đang dạy.

- **Domain webhook:** vào dashboard SePay, xác nhận URL nhận webhook đã trỏ đúng https://api.teduMarket.dev/api/v1/payments/webhook (domain production, không còn trỏ về URL ngrok/dev).
- **Secret production khác secret dev:** khóa dùng để xác thực chữ ký HMAC-SHA256 (X-SePay-Signature, bài 2.5) ở production phải là khóa riêng, không tái sử dụng khóa sandbox/dev.
- **Test bằng giao dịch thật, số tiền nhỏ:** quét QR VietQR thật với số tiền tối thiểu ngân hàng cho phép, xác nhận toàn bộ luồng: webhook SePay gửi tới → xác thực chữ ký đúng → Order chuyển Pending sang Paid đúng 1 lần (idempotency, bài 2.5) → Enrollment được tạo qua Outbox/Hosted Service (2.6–2.7).

### 2.3. DNS & SSL

- **Hạ TTL trước vài giờ:** giảm TTL bản ghi DNS của 3 subdomain (api, admin, www — bài 9.4) xuống khoảng 300 giây trước thời điểm go-live, để nếu cần đổi IP rollback hạ tầng thì bản ghi mới lan truyền nhanh, không phải chờ hàng giờ.
- **Xác nhận auto-renew SSL hoạt động:** chạy certbot renew --dry-run cho cả 3 subdomain, đảm bảo chứng chỉ Let's Encrypt (bài 9.5) sẽ tự gia hạn đúng hạn — hết hạn SSL giữa lúc đang bán hàng là lỗi hoàn toàn có thể tránh trước.

```bash
certbot renew --dry-run
```

### 2.4. CI/CD & Secrets

- **Build gate bắt buộc:** pipeline GitHub Actions (bài 9.6) phải chạy hết bộ test Module 8 (unit test Handler/Domain, integration test Testcontainers) và pass toàn bộ mới cho phép deploy — không tắt bước test "cho nhanh" ở lần deploy đầu tiên, vì đây là lần rủi ro cao nhất.
- **Secrets production tách biệt hoàn toàn:** connection string Postgres, signing certificate của OpenIddict (bài 3.2), API key/secret SePay — tất cả phải là giá trị riêng cho production, quản lý qua GitHub Actions Secrets hoặc biến môi trường trên server, không copy nguyên secrets từ môi trường dev.
- **Tag image theo phiên bản, không chỉ dùng latest:** ở bước build của CI/CD (9.6), gắn tag image Docker theo git SHA hoặc semantic version (ví dụ tedumarket-api:2026.09.20-a1b2c3d) bên cạnh tag latest. Đây là điều kiện bắt buộc để rollback code nhanh ở phần 3 — không có tag cũ thì không có gì để rollback về.

```bash
# Bước build trong GitHub Actions workflow (9.6), bổ sung tag theo SHA
docker build -t registry.tedumarket.dev/api:${{ github.sha }} \
             -t registry.tedumarket.dev/api:latest .
docker push registry.tedumarket.dev/api:${{ github.sha }}
docker push registry.tedumarket.dev/api:latest
```

### 2.5. Health check endpoint

Trước giờ Module 9 chưa có endpoint nào cho biết "backend còn sống và kết nối được Postgres hay không" một cách chuẩn — thứ Nginx (9.4) và người vận hành dùng để quyết định go/no-go. Thêm health check bằng gói Microsoft.Extensions.Diagnostics.HealthChecks (built-in) kết hợp AspNetCore.HealthChecks.NpgSql (gói cộng đồng, dùng phổ biến cho Postgres):

```csharp
// Program.cs — TeduMarket.Api
builder.Services.AddHealthChecks()
    .AddNpgSql(
        builder.Configuration.GetConnectionString("Postgres")!,
        name: "postgresql",
        tags: ["ready"])
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

/health/live trả lời "process còn chạy không" — dùng cho container restart policy. /health/ready trả lời "đã sẵn sàng nhận traffic thật chưa" (kết nối được Postgres) — dùng làm tín hiệu go-live và cho load balancer/Nginx biết khi nào route traffic vào container mới.

> **📘 Ghi chú giảng viên:** *Tôi hay demo lỗi kinh điển ở đây: gộp chung 1 endpoint /health cho cả live và ready. Hậu quả là lúc Postgres chậm tạm thời, orchestrator tưởng process chết và restart liên tục container — trong khi process vẫn sống bình thường, chỉ là chưa sẵn sàng nhận traffic. Tách 2 endpoint giải quyết đúng vấn đề này.*

### 3. Rollback Plan

*Thời lượng: 5 phút lý thuyết, thực hành trong phần Demo | Loại: Lý thuyết + Demo*

Rollback Code và Rollback Database là hai quyết định khác nhau, không đi chung một lệnh và không luôn đi chung với nhau.

| **Tiêu chí** | **Rollback Code (Docker image)** | **Rollback Database (EF Core migration)** |
|---|---|---|
| Tốc độ | Vài chục giây — chỉ đổi tag image và restart container | Có thể mất vài phút, phụ thuộc số bảng bị ảnh hưởng |
| Rủi ro mất dữ liệu | Không — code không giữ state | Có — nếu đã có Order/Payment ghi vào cột/bảng mới sau migration |
| Khi nào dùng | Luôn là lựa chọn đầu tiên khi phát hiện lỗi sau deploy | Chỉ khi CHƯA có giao dịch thật nào ghi đè lên schema mới |
| Điều kiện tiên quyết | Image được tag theo git SHA/version, không chỉ dùng tag latest | Đã có bản backup pg_dump trước khi migrate + migration reversible |

### 3.1. Rollback code

Nhờ image đã tag theo git SHA ở mục 2.4, rollback code chỉ là đổi container đang chạy sang image tag trước đó:

```yaml
# Rollback API về bản build trước sự cố
docker compose -f docker-compose.prod.yml pull api
docker tag registry.tedumarket.dev/api:a1b2c3d_previous tedumarket-api:current
docker compose -f docker-compose.prod.yml up -d --no-deps api

# Xác nhận rollback thành công qua health check
curl -f https://api.tedumarket.dev/health/ready
```

### 3.2. Rollback database — và khi nào TUYỆT ĐỐI không được rollback

Lệnh kỹ thuật rất đơn giản:

```bash
dotnet ef database update <TenMigrationTruocDo> \
  --project src/TeduMarket.Infrastructure \
  --startup-project src/TeduMarket.Api
```

Nhưng điều kiện để được phép chạy lệnh này mới là phần quan trọng: chỉ rollback database khi CHƯA có giao dịch thật nào (Order, Payment, Enrollment) được ghi vào schema mới sau migration. Nếu đã có dù chỉ 1 đơn hàng thật đi qua webhook SePay sau thời điểm migrate, rollback database đồng nghĩa xóa mất bản ghi thanh toán thật của học viên đó — hậu quả nặng hơn nhiều so với việc chấp nhận sống chung với lỗi trong lúc vá.

Trong tình huống đã có giao dịch thật, hướng xử lý đúng là roll-forward: giữ nguyên database, deploy nhanh một bản vá sửa đúng lỗi, thay vì lùi database về trạng thái cũ.

### 3.3. Rollback trigger — ngưỡng quyết định, không phải cảm tính

Viết sẵn con số cụ thể để không phải tranh luận lúc đang sự cố. Ví dụ áp dụng cho TEDU Market:

- Tỷ lệ lỗi 5xx trên endpoint /api/v1/orders/checkout hoặc /api/v1/payments/webhook vượt 5% trong 5 phút liên tiếp, theo dõi qua log CorrelationId trên Seq (bài 9.7) → rollback ngay, không chờ điều tra thêm.
- /health/ready trả về lỗi liên tục quá 2 phút sau khi deploy → rollback code ngay lập tức.
- Webhook SePay không xác nhận được bất kỳ giao dịch nào trong 10 phút kể từ lúc go-live dù đã có học viên bấm Checkout → dừng nhận thanh toán mới, kiểm tra cấu hình webhook trước khi quyết định rollback hay vá tại chỗ.

### 3.4. Thứ tự deploy đúng

Deploy backend trước (kèm migration), chờ /health/ready trả về khỏe mạnh, rồi mới deploy 2 frontend (9.2). Lý do: nếu đảo ngược thứ tự, frontend mới có thể gọi field/endpoint mà backend cũ chưa hỗ trợ — đúng vấn đề Module 4.5 và 5.4 đã cảnh báo về việc đổi API phải nhất quán 2 phía cùng lúc.

## Tổng kết

- Checklist go-live tồn tại để loại bỏ quyết định phải nghĩ ra lúc đang có sự cố — rollback là hành động đã viết sẵn, không phải phản xạ tức thời.
- Bốn nhóm checklist bắt buộc trước go-live: Database (backup + review migration script), Payment/Webhook SePay (domain, secret, test giao dịch thật), DNS/SSL (TTL thấp, auto-renew), CI-CD/Secrets (build gate từ Module 8, tag image theo version).
- Rollback Code (đổi tag Docker image) và Rollback Database (dotnet ef database update) là 2 quyết định khác nhau — không bao giờ rollback database nếu đã có giao dịch thật ghi vào schema mới.
- Rollback trigger phải là con số cụ thể (tỷ lệ lỗi, thời gian health check fail liên tục) viết sẵn trước, không quyết định cảm tính lúc sự cố.
- Thứ tự deploy đúng: backend (kèm migration) → chờ health check ready → frontend, tránh mismatch API giữa 2 phía.
