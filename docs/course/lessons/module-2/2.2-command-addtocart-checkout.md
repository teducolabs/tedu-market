## **Nội dung chính**

### **1. Ôn lại nhanh: Cart & Order Aggregate (5 phút — Lý thuyết)**

Ở bài 2.1 bạn đã thiết kế 2 Aggregate tách biệt trong bounded context Ordering:

- Cart — mutable, thuộc về 1 User, sống trong "phiên mua hàng". Học viên thêm/bớt khóa học thoải mái.
- Order — immutable ngay khi tạo, là bản ghi lịch sử giao dịch. Một khi Checkout xong, Order không đổi nội dung item nữa (chỉ đổi Status).

Bài này bạn viết 2 Command nối 2 Aggregate đó lại: AddToCartCommand (thêm khóa học vào Cart) và CheckoutCommand (chuyển Cart thành Order). Đây là lần đầu tiên trong khóa một Command chạm vào 2 Aggregate trong cùng 1 transaction — quy tắc quan trọng cần nhớ: mỗi Aggregate tự bảo vệ invariant của chính nó, còn quy trình "lấy dữ liệu từ Aggregate này để tạo Aggregate khác" là việc của Application Handler, không nhét vào bên trong Aggregate.

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi học viên: "Tại sao không để Cart tự sinh ra Order, kiểu cart.Checkout() trả về Order?" — Câu trả lời: Cart không có quyền biết cách Order tính TotalAmount hay áp Coupon (bài 2.3). Nhét hết vào Cart sẽ làm Cart phình to và 2 Aggregate dính chặt vào nhau. Giữ Handler làm nhạc trưởng là đúng kiến trúc.*

### **2. Command AddToCart (15 phút — Demo)**

Business rule cần enforce: không thêm trùng khóa học vào Cart, và chỉ khóa học Course.Status đã publish mới cho phép mua. Quy tắc thứ 2 là quy tắc chéo giữa 2 bounded context (Catalog và Ordering) nên đặt ở Handler, không đặt trong Cart.AddItem — Cart không được phép biết gì về khái niệm "publish" của Catalog.

**Domain layer — mở rộng Cart Aggregate đã tạo ở bài 2.1:**

```csharp
// TeduMarket.Domain/Ordering/Cart.cs
namespace TeduMarket.Domain.Ordering;
 
public sealed class Cart : AggregateRoot
{
    private readonly List<CartItem> _items = [];
 
    public Guid UserId { get; private set; }
    public IReadOnlyCollection<CartItem> Items => _items.AsReadOnly();
 
    private Cart() { } // EF Core
 
    public static Cart Create(Guid userId) => new()
    {
        Id = Guid.NewGuid(),
        UserId = userId
    };
 
    public void AddItem(Guid courseId, string courseName, decimal price)
    {
        if (_items.Any(i => i.CourseId == courseId))
            throw new CartItemDuplicateException(courseId);
 
        _items.Add(new CartItem(courseId, courseName, price));
    }
 
    public void Clear() => _items.Clear();
}
// TeduMarket.Domain/Ordering/CartItem.cs
namespace TeduMarket.Domain.Ordering;
 
public sealed class CartItem
{
    public Guid CourseId { get; private set; }
    public string CourseName { get; private set; } = default!;
    public decimal Price { get; private set; }
 
    private CartItem() { } // EF Core
 
    internal CartItem(Guid courseId, string courseName, decimal price)
    {
        CourseId = courseId;
        CourseName = courseName;
        Price = price;
    }
}
```

> **📘 Ghi chú giảng viên:** *CartItem.Price là giá chốt ngay lúc AddToCart, không re-fetch lại khi Checkout. Đây là quyết định thiết kế có đánh đổi thật: nếu Instructor đổi giá Course giữa lúc học viên AddToCart và lúc Checkout, học viên vẫn trả giá cũ đã chốt. Nói rõ điều này với học viên — đừng để họ nghĩ đây là bug, đây là business decision (nhiều sàn thương mại điện tử thật cũng làm vậy để tránh tranh chấp giá).*

**Application layer — Command, Validator, Handler:**

```csharp
// TeduMarket.Application/Ordering/Commands/AddToCartCommand.cs
namespace TeduMarket.Application.Ordering.Commands;
 
public sealed record AddToCartCommand(Guid UserId, Guid CourseId) : IRequest<Guid>;
 
public sealed class AddToCartCommandValidator : AbstractValidator<AddToCartCommand>
{
    public AddToCartCommandValidator()
    {
        RuleFor(x => x.UserId).NotEmpty();
        RuleFor(x => x.CourseId).NotEmpty();
    }
}
 
public sealed class AddToCartCommandHandler(
    ICourseRepository courseRepository,
    ICartRepository cartRepository,
    IUnitOfWork unitOfWork) : IRequestHandler<AddToCartCommand, Guid>
{
    public async Task<Guid> Handle(AddToCartCommand request, CancellationToken cancellationToken)
    {
        var course = await courseRepository.GetByIdAsync(request.CourseId, cancellationToken)
            ?? throw new CourseNotFoundException(request.CourseId);
 
        if (!course.IsPublished)
            throw new CourseNotPublishedException(request.CourseId);
 
        var cart = await cartRepository.GetByUserIdAsync(request.UserId, cancellationToken);
 
        if (cart is null)
        {
            cart = Cart.Create(request.UserId);
            await cartRepository.AddAsync(cart, cancellationToken);
        }
 
        cart.AddItem(course.Id, course.Title, course.Pricing.Amount);
 
        await unitOfWork.SaveChangesAsync(cancellationToken);
 
        return cart.Id;
    }
}
```

> **📘 Ghi chú giảng viên:** *course.Pricing.Amount — dùng lại đúng Pricing Value Object đã tạo ở bài 1.1/1.4, không tự thêm field Price rời rạc trên Course. Nếu học viên viết course.Price thẳng, dừng lại sửa ngay — đây là chỗ hay bị làm sai nhất khi ráp code 2 Module với nhau vì học viên quên cấu trúc VO.*

    {

Dùng numeric(18,2) chứ không phải decimal(18,2): Postgres gọi kiểu này là numeric, decimal chỉ là alias — dùng tên gốc cho rõ ràng khi đọc migration script sau này.*

### **3. Command Checkout (20 phút — Demo)**

Checkout là Command phức tạp nhất khóa tính đến giờ: đọc 1 Aggregate (Cart), tạo mới 1 Aggregate khác (Order), rồi xóa dữ liệu ở Aggregate đầu — tất cả phải commit atomic trong 1 transaction.

**IUnitOfWork — vì sao cần từ bài này:**

Từ Module 0/1, mỗi Repository chỉ đụng 1 Aggregate nên gọi SaveChanges ở đâu cũng không quan trọng. Checkout đụng 2 Aggregate (thêm Order, sửa Cart) trong cùng 1 nghiệp vụ — nếu để mỗi Repository tự SaveChanges riêng, một thao tác có thể thành công còn thao tác kia thất bại, dữ liệu lệch nhau. Từ bài này, Repository chỉ track thay đổi (Add/Update vào DbContext), còn Handler quyết định khi nào commit — đúng 1 lần, qua IUnitOfWork:

```csharp
// TeduMarket.Application/Common/Interfaces/IUnitOfWork.cs

namespace TeduMarket.Domain.Ordering;
 
public sealed class Order : AggregateRoot
{
    private readonly List<OrderItem> _items = [];
 
    public Guid UserId { get; private set; }
    public OrderStatus Status { get; private set; }
    public decimal TotalAmount { get; private set; }
    public DateTime CreatedAt { get; private set; }
    public IReadOnlyCollection<OrderItem> Items => _items.AsReadOnly();
 
    private Order() { } // EF Core
 
    public static Order Create(Guid userId, IReadOnlyCollection<OrderItem> items)
    {
        if (items is null || items.Count == 0)
            throw new OrderEmptyException(userId);
 
        var order = new Order
        {
            Id = Guid.NewGuid(),
            UserId = userId,
            Status = OrderStatus.Pending,
            TotalAmount = items.Sum(i => i.Price),
            CreatedAt = DateTime.UtcNow
        };
 
        order._items.AddRange(items);
 
        order.AddDomainEvent(new CourseOrderedEvent(
            order.Id,
            userId,
            items.Select(i => i.CourseId).ToList()));
 
        return order;
    }
}
```

> **📘 Ghi chú giảng viên:** *Order.Create là factory method duy nhất — không có public constructor, không có setter công khai. Học viên hay hỏi "sao không cho Order rỗng rồi AddItem từng cái như Cart?" — vì Order immutable ngay từ lúc sinh ra (đã nói ở bài 2.1): phải có đủ item ngay trong lệnh gọi factory, không có API để thêm item sau khi Order đã tồn tại. Đây chính là khác biệt cố ý so với Cart.AddItem.*

**Application layer — Command, Validator, Handler:**

```csharp
// TeduMarket.Application/Ordering/Commands/CheckoutCommand.cs
namespace TeduMarket.Application.Ordering.Commands;
 
public sealed record CheckoutCommand(Guid UserId) : IRequest<CheckoutResult>;
 
public sealed record CheckoutResult(Guid OrderId, decimal TotalAmount, string Status);
 
public sealed class CheckoutCommandValidator : AbstractValidator<CheckoutCommand>
{
    public CheckoutCommandValidator()
    {
        RuleFor(x => x.UserId).NotEmpty();
    }
}
 
public sealed class CheckoutCommandHandler(
    ICartRepository cartRepository,
    IOrderRepository orderRepository,
    IUnitOfWork unitOfWork,
    IDomainEventDispatcher domainEventDispatcher) : IRequestHandler<CheckoutCommand, CheckoutResult>
{
    public async Task<CheckoutResult> Handle(CheckoutCommand request, CancellationToken cancellationToken)
    {
        var cart = await cartRepository.GetByUserIdAsync(request.UserId, cancellationToken);
 
        if (cart is null || cart.Items.Count == 0)
            throw new CartEmptyException(request.UserId);
 
        var orderItems = cart.Items
            .Select(item => new OrderItem(item.CourseId, item.CourseName, item.Price))
            .ToList();
 
        var order = Order.Create(request.UserId, orderItems);
 
        await orderRepository.AddAsync(order, cancellationToken);
 
        cart.Clear();
 
        await unitOfWork.SaveChangesAsync(cancellationToken);
 
        await domainEventDispatcher.DispatchAndClearEventsAsync([order], cancellationToken);
 
        return new CheckoutResult(order.Id, order.TotalAmount, order.Status.ToString());
    }
}
```

> **📘 Ghi chú giảng viên:** *Thứ tự trong Handler quan trọng: Add Order + Clear Cart PHẢI nằm chung 1 lần SaveChangesAsync (transaction ngầm định của EF Core) để atomic — không thể Checkout thành công mà Cart vẫn còn item, hoặc ngược lại. Domain Event chỉ publish SAU KHI SaveChanges thành công — publish trước khi commit là lỗi kinh điển vì Handler khác có thể phản ứng với 1 Order chưa thật sự tồn tại trong DB.*

### **4. Domain Event CourseOrderedEvent (10 phút — Demo)**

Đây là Domain Event đầu tiên trong khóa. Nó chuẩn bị trực tiếp cho Outbox Pattern ở bài 2.6, nên phải cài đúng ngay từ đầu — không làm tắt rồi refactor sau.

Vấn đề kiến trúc cần giải quyết: bài 0.2 đã chốt "Domain không phụ thuộc gì cả". Nhưng cách publish event tiện nhất là dùng MediatR.INotification — mà MediatR lại là gói NuGet của Application layer. Nếu Domain Event implement thẳng INotification, Domain project buộc phải reference MediatR → phá vỡ nguyên tắc đã chốt. Cách xử lý: Domain chỉ định nghĩa 1 interface thuần, không phụ thuộc gì cả; Application layer làm cầu nối sang MediatR.

**Infrastructure — implement bằng reflection (viết 1 lần, dùng cho mọi Domain Event sau này, kể cả OrderPaidEvent ở bài 2.5):**

```csharp
// TeduMarket.Infrastructure/Events/DomainEventDispatcher.cs
namespace TeduMarket.Infrastructure.Events;
 
internal sealed class DomainEventDispatcher(IMediator mediator) : IDomainEventDispatcher
{
    public async Task DispatchAndClearEventsAsync(
        IEnumerable<AggregateRoot> aggregatesWithEvents,
        CancellationToken cancellationToken = default)
    {
        foreach (var aggregate in aggregatesWithEvents)
        {
            var events = aggregate.DomainEvents.ToArray();
            aggregate.ClearDomainEvents();
 
            foreach (var domainEvent in events)
            {
                var notificationType = typeof(DomainEventNotification<>)
                    .MakeGenericType(domainEvent.GetType());
 
                var notification = (INotification)Activator
                    .CreateInstance(notificationType, domainEvent)!;
 
                await mediator.Publish(notification, cancellationToken);
            }
        }
    }
}
```

> **📘 Ghi chú giảng viên:** *Đoạn Activator.CreateInstance dùng reflection để MediatR định danh đúng generic type lúc runtime (domainEvent lúc compile-time chỉ có kiểu IDomainEvent, nhưng Handler đăng ký theo kiểu cụ thể CourseOrderedEvent). Đây là 1 đoạn hạ tầng viết đúng 1 lần rồi không đụng lại — học viên không cần nhớ thuộc lòng cách viết, chỉ cần hiểu VÌ SAO cần nó.*

**Handler để chứng minh event chạy thật (demo, sẽ được thay bằng Enrollment ở bài 2.7):**

```csharp
// TeduMarket.Application/Ordering/EventHandlers/CourseOrderedEventLoggingHandler.cs
namespace TeduMarket.Application.Ordering.EventHandlers;
 
public sealed class CourseOrderedEventLoggingHandler(
    ILogger<CourseOrderedEventLoggingHandler> logger)
    : INotificationHandler<DomainEventNotification<CourseOrderedEvent>>
{
    public Task Handle(
        DomainEventNotification<CourseOrderedEvent> notification,
        CancellationToken cancellationToken)
    {
        var e = notification.DomainEvent;
        logger.LogInformation(
            "Order {OrderId} vua duoc tao boi User {UserId} voi {Count} khoa hoc",
            e.OrderId, e.UserId, e.CourseIds.Count);
 
        return Task.CompletedTask;
    }
}
```

> **📘 Ghi chú giảng viên:** *Đây chính là chỗ nối sang bài 2.6. Nếu server crash NGAY SAU dòng unitOfWork.SaveChangesAsync() nhưng TRƯỚC dòng domainEventDispatcher.DispatchAndClearEventsAsync(), Order vẫn nằm trong DB ở trạng thái Pending — nhưng CourseOrderedEvent bị mất vĩnh viễn, không Handler nào chạy, sau này Enrollment (bài 2.7) sẽ không bao giờ được tạo dù học viên đã checkout thành công. Đây là vấn đề "dual write" kinh điển. Outbox Pattern ở bài 2.6 giải quyết đúng vấn đề này bằng cách ghi event vào bảng cùng transaction với Order, không publish trực tiếp qua MediatR như cách làm tạm ở bài này. Nói rõ với học viên: code hôm nay CHẠY ĐƯỢC nhưng CHƯA AN TOÀN 100% — đó là lý do bài sau tồn tại, không phải vì bài này sai.*

## **Bài tập thực hành**

> **✏️ Bài 1 — RemoveFromCartCommand:** Viết Command đối xứng với AddToCart: RemoveFromCartCommand(Guid UserId, Guid CourseId) xóa 1 CourseId khỏi Cart hiện tại của user. Input: UserId + CourseId đang có trong Cart. Expected output: gọi lại GET Cart (viết tạm 1 query nhỏ nếu chưa có) thấy Cart không còn item đó; nếu CourseId không tồn tại trong Cart, trả lỗi 404 dạng ProblemDetails, không trả 200 im lặng.

Hint: thêm method Cart.RemoveItem(Guid courseId) trong Aggregate (ném CartItemNotFoundException nếu không tìm thấy — đặt tên exception đúng quy ước mục 7). Repository chỉ cần thêm 1 method UpdateAsync hoặc tận dụng EF Core change tracking sẵn có (vì cart đã được Include(c => c.Items) và đang tracked).

Solution (rút gọn): Handler load Cart qua ICartRepository.GetByUserIdAsync, gọi cart.RemoveItem(request.CourseId), gọi unitOfWork.SaveChangesAsync() — không cần gọi lại AddAsync vì entity đã được EF Core track từ lúc load. Endpoint: DELETE /api/v1/cart/items/{courseId}.

> **✏️ Bài 2 (nâng cao) — Idempotency check cho AddToCart:** Hiện tại AddToCart ném CartItemDuplicateException nếu học viên bấm 2 lần liên tiếp (double-click). Hãy đổi behavior: nếu CourseId đã có trong Cart, trả về 200 OK với cartId hiện tại thay vì lỗi 409 — an toàn hơn cho UX, và chuẩn bị tư duy cho Idempotency key sẽ học kỹ ở bài 2.9. Input/Expected output: gọi AddToCart 2 lần liên tiếp với cùng CourseId → cả 2 lần đều trả 200/201, Cart chỉ có đúng 1 item của CourseId đó (không nhân đôi).

Hint: sửa Cart.AddItem thành no-op có kiểm tra thay vì throw, hoặc thêm method TryAddItem trả về bool. Cân nhắc: đây có phải lúc nào cũng đúng? Nếu học viên đổi ý muốn mua với giá khác (giảm giá vừa cập nhật) thì sao? Không có solution tuyệt đối — đúng tinh thần thảo luận best practice, khuyến khích học viên tự quyết định và giải thích lý do.

## **Tổng kết**

> **✅** AddToCartCommand ghi vào Cart Aggregate, business rule chéo bounded context (Course phải publish) nằm ở Handler, không nằm trong Cart.
>
> **✅** CheckoutCommand đọc Cart, tạo Order qua factory method Order.Create (immutable, không có setter công khai), rồi Clear Cart — tất cả commit atomic qua 1 lần IUnitOfWork.SaveChangesAsync().
>
> **✅** Domain Event (CourseOrderedEvent) giữ Domain layer sạch — không reference MediatR — bằng cách tách IDomainEvent thuần và để Application layer làm cầu nối qua DomainEventNotification\<T>.
>
> **✅** Publish domain event luôn SAU KHI SaveChanges thành công, không publish trước. Cách publish trực tiếp qua MediatR hiện tại CHƯA an toàn tuyệt đối trước crash — đó là lý do Outbox Pattern tồn tại ở bài 2.6.
>
> **✅** Order tạo ra ở Status = Pending, chưa phải Paid — bài 2.4/2.5 sẽ tích hợp VNPay và xử lý webhook để chuyển Order sang Paid.

| **Tiêu chí** | **Cart** | **Order** |
|---|---|---|
| Vòng đời | Mutable, sống trong phiên mua hàng | Immutable ngay khi tạo, bản ghi lịch sử |
| Cách khởi tạo | Cart.Create(userId) rồi AddItem nhiều lần | Order.Create(userId, items) — 1 lần duy nhất, đủ item ngay từ đầu |
| Domain Event | Không phát event | Phát CourseOrderedEvent ngay khi tạo |
| Xóa dữ liệu | Clear() sau khi Checkout thành công | Không có method xóa item — chỉ đổi Status |

*Bước tiếp theo: Bài 2.3 — Coupon & Pricing Rule sẽ chèn thêm bước tính giá có áp dụng giảm giá vào giữa AddToCart và Checkout, dùng Specification pattern để tránh if/else rải rác khi có nhiều loại rule giảm giá.*

## **Phụ lục — Cheatsheet & Glossary**

### **Naming cheatsheet áp dụng trong bài này**

- Command: AddToCartCommand, CheckoutCommand — đúng mẫu {Động từ}{Thực thể}Command
- Handler: AddToCartCommandHandler, CheckoutCommandHandler — đúng mẫu {Tên Command}Handler
- Domain Event: CourseOrderedEvent — đúng mẫu {Thực thể}{Động từ quá khứ}Event
- Exception: CartEmptyException, CartItemDuplicateException, OrderEmptyException, CourseNotPublishedException — đúng mẫu {Thực thể}{LoạiLỗi}Exception
- Repository: ICartRepository, IOrderRepository — định nghĩa ở Application, implement ở Infrastructure

### **Glossary**

- Aggregate Root — điểm vào duy nhất để đảm bảo invariant của 1 nhóm entity liên quan (đã học bài 0.3).
- Domain Event — sự kiện phát ra từ Aggregate khi có thay đổi nghiệp vụ quan trọng, cho phép các phần khác của hệ thống phản ứng mà không cần Aggregate biết về chúng.
- Dual write problem — vấn đề khi 1 nghiệp vụ cần ghi vào 2 nơi khác nhau (DB + message/event) không atomic, dẫn tới dữ liệu lệch nếu crash giữa chừng. Outbox Pattern (bài 2.6) là lời giải chuẩn.
- Idempotency — gọi API nhiều lần với cùng input cho ra cùng kết quả, không tạo dữ liệu trùng. Sẽ học sâu ở bài 2.9.
