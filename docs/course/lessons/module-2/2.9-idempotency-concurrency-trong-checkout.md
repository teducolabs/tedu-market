## **Phần 1 — Vì sao Checkout cần Idempotency và Concurrency riêng**

*Lý thuyết · 15 phút*

### **1.1. Hai loại "idempotency" khác nhau trong cùng 1 luồng mua hàng**

Ở bài 2.5, bạn đã cài idempotency cho webhook: SePay có thể gọi lại endpoint xác nhận thanh toán nhiều lần (do timeout, do retry ở phía SePay), và bạn đã đảm bảo Order chỉ chuyển sang Paid đúng 1 lần bằng cách chống trùng theo id giao dịch mà SePay cấp.

Bài này giải quyết một vấn đề khác, xảy ra sớm hơn trong luồng: chính hành động Checkout — bước tạo Order từ Cart — cũng có thể bị gọi trùng. Không phải do bên thứ ba retry, mà do:

- Học viên bấm nút "Thanh toán" 2 lần liên tiếp vì UI phản hồi chậm (double-click).
- Học viên mất kết nối ngay sau khi bấm, không thấy phản hồi, bấm lại — trong khi request đầu tiên vẫn đang xử lý ở server.
- Client tự động retry khi gặp lỗi mạng tạm thời (timeout, 502) mà không biết request trước đã tới server hay chưa.

Hai vấn đề tưởng giống nhau ("đừng xử lý trùng") nhưng khác nhau ở nguồn phát sinh trùng lặp và nơi cần chặn:

| **Tiêu chí** | **Idempotency ở Webhook (bài 2.5)** | **Idempotency ở Checkout (bài 2.9)** |
|---|---|---|
| Ai gây ra trùng lặp | SePay (bên thứ ba) gọi lại webhook | Chính client của TEDU Market (double-click, retry) |
| Key chống trùng | id giao dịch do SePay cấp, nằm sẵn trong payload webhook | IdempotencyKey do client tự sinh (GUID), gửi kèm mỗi lần Checkout |
| Vị trí chặn | Endpoint nhận webhook, so khớp theo id giao dịch trước khi UPDATE | CheckoutCommandHandler, so khớp theo IdempotencyKey trước khi INSERT Order |
| Hệ quả nếu không chặn | Order bị trừ tiền / cộng Enrollment 2 lần từ 1 giao dịch | Học viên bị tạo 2 Order (có thể dẫn tới thanh toán 2 lần) từ 1 lần mua |

### **1.2. Vì sao "check rồi mới ghi" (check-then-act) không đủ**

Cách trực giác nhất mà nhiều bạn thử đầu tiên: trong CheckoutCommandHandler, query xem Cart này đã có Order chưa, nếu chưa thì tạo mới. Nhìn thì hợp lý, nhưng đây là kinh điển check-then-act race condition — lỗi khiến 2.9 tồn tại như 1 bài học riêng thay vì chỉ là 1 dòng ghi chú trong bài 2.2.

Xét timeline khi 2 request Checkout đến gần như đồng thời, dùng cùng 1 IdempotencyKey (vì client giữ nguyên key khi đang loading và user bấm lại):

- t=0ms — Request A: Handler query "đã có Order với key này chưa?" → chưa có.
- t=2ms — Request B: Handler cũng query y hệt, trong transaction riêng, tại thời điểm transaction A vẫn CHƯA commit → cũng thấy "chưa có".
- t=10ms — Request A tạo Order, commit thành công.
- t=12ms — Request B, vì đã "check" xong từ t=2ms, vẫn tiếp tục tạo Order thứ 2, commit thành công.

Kết quả: 2 Order từ 1 Cart, dù logic "check rồi mới ghi" nhìn hoàn toàn đúng khi đọc code tuần tự. Vấn đề nằm ở khoảng hở giữa lúc đọc (SELECT) và lúc ghi (INSERT) — trong khoảng hở đó, một transaction khác có thể chen vào. Đây là điểm hầu hết học viên làm sai nhất khi mới tiếp cận concurrency: nghĩ rằng if (chưa tồn tại) { tạo mới } là đủ an toàn vì "đọc code thấy đúng thứ tự".

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi thẳng: "Nếu mình chỉ thêm if kiểm tra Cart đã Checkout chưa trong Handler, có chặn được double-click không?". Đa số sẽ trả lời có, vì tư duy tuần tự. Sau đó tôi vẽ 2 timeline chồng lên nhau như trên bảng để chỉ ra transaction B hoàn toàn có thể đọc xong trước khi transaction A commit. Chỉ khi thấy timeline chồng lấn cụ thể, học viên mới thực sự tin — nói suông "race condition có thể xảy ra" không đủ thuyết phục.*

Kết luận cho toàn bài: application-layer check chỉ là fast-path tối ưu (tránh phải insert rồi mới biết lỗi trong trường hợp phổ biến — request retry sau khi request trước đã xong hẳn), không phải cơ chế chống trùng chính. Cơ chế chống trùng thật sự phải nằm ở database, dưới dạng ràng buộc mà PostgreSQL tự đảm bảo tại thời điểm commit, bất kể có bao nhiêu transaction chạy song song. Với concurrency (2 request cùng SỬA 1 Order đã tồn tại), nguyên lý tương tự: cần 1 token mà PostgreSQL tự cập nhật, không phải cờ do ứng dụng tự quản.

## **Phần 2 — Idempotency Key cho CheckoutCommand**

*Demo · 15 phút*

### **2.1. Mở rộng Order Aggregate (bài 2.1)**

Thêm IdempotencyKey vào Order — đây là dữ liệu bất biến, gán đúng 1 lần khi Order được tạo từ Cart:

```csharp
// TeduMarket.Domain/Orders/Order.cs
namespace TeduMarket.Domain.Orders;
 
public class Order
{
    public Guid Id { get; private set; }
    public Guid CustomerId { get; private set; }
    public Guid IdempotencyKey { get; private set; }
    public OrderStatus Status { get; private set; }
    public decimal TotalAmount { get; private set; }
    public string? PaymentCode { get; private set; } // gán ở bài 2.4
 
    private readonly List<OrderItem> _items = new();
    public IReadOnlyCollection<OrderItem> Items => _items.AsReadOnly();
 
    private Order() { } // EF Core
 
    public static Order CreateFromCart(Cart cart, Guid idempotencyKey)
    {
        if (cart.Items.Count == 0)
            throw new EmptyCartException(cart.Id);
 
        var order = new Order
        {
            Id = Guid.NewGuid(),
            CustomerId = cart.CustomerId,
            IdempotencyKey = idempotencyKey,
            Status = OrderStatus.Pending,
            TotalAmount = cart.CalculateTotal()
        };
 
        foreach (var cartItem in cart.Items)
            order._items.Add(OrderItem.FromCartItem(cartItem));
 
        return order;
    }
}
```

### **2.2. Ràng buộc unique ở tầng database — nguồn sự thật cuối cùng**

Đây là dòng quan trọng nhất của cả bài. Unique index trên IdempotencyKey là thứ thật sự chặn được race condition ở mục 1.2, vì PostgreSQL kiểm tra ràng buộc này tại thời điểm COMMIT, không phụ thuộc vào việc 2 transaction đọc dữ liệu ở thời điểm nào:

```csharp
// TeduMarket.Infrastructure/Persistence/Configurations/OrderConfiguration.cs
public class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> builder)
    {
        builder.ToTable("Orders");
        builder.HasKey(o => o.Id);
 
        // 1 IdempotencyKey chỉ được phép tạo ra đúng 1 Order.
        // Đây là ràng buộc ở DB — không phải if trong C#.
        builder.HasIndex(o => o.IdempotencyKey)
            .IsUnique()
            .HasDatabaseName("IX_Orders_IdempotencyKey");
    }
}
```

### **2.3. CheckoutCommandHandler — 2 lớp phòng vệ**

Handler dùng 2 lớp: fast-path check để tối ưu trường hợp phổ biến (retry sau khi request trước đã xử lý xong), và catch lỗi từ unique constraint làm lớp phòng vệ cuối cùng cho đúng trường hợp race condition thật sự ở mục 1.2:

```csharp
// TeduMarket.Application/Orders/Commands/CheckoutCommandHandler.cs
public class CheckoutCommandHandler(
    IOrderRepository orderRepository,
    ICartRepository cartRepository,
    IUnitOfWork unitOfWork)
    : IRequestHandler<CheckoutCommand, CheckoutResult>
{
    public async Task<CheckoutResult> Handle(CheckoutCommand request, CancellationToken ct)
    {
        // Lớp 1 (fast-path): request retry SAU KHI request trước đã commit xong
        // sẽ dừng ở đây, không cần chạm tới ràng buộc DB.
        var existing = await orderRepository.GetByIdempotencyKeyAsync(request.IdempotencyKey, ct);
        if (existing is not null)
            return CheckoutResult.FromExisting(existing);
 
        var cart = await cartRepository.GetByIdAsync(request.CartId, ct)
            ?? throw new CartNotFoundException(request.CartId);
 
        var order = Order.CreateFromCart(cart, request.IdempotencyKey);
        orderRepository.Add(order);
 
        try
        {
            await unitOfWork.SaveChangesAsync(ct);
        }
        catch (DbUpdateException ex) when (IsDuplicateIdempotencyKey(ex))
        {
            // Lớp 2 (bắt buộc): 2 request đọc xong TRƯỚC KHI request kia commit —
            // đúng kịch bản timeline ở Phần 1. PostgreSQL từ chối INSERT thứ 2
            // ngay tại COMMIT nhờ unique index. Đọc lại Order mà request kia vừa tạo.
            var raceOrder = await orderRepository.GetByIdempotencyKeyAsync(request.IdempotencyKey, ct)
                ?? throw new InvalidOperationException(
                    "Unique violation xảy ra nhưng không tìm thấy Order tương ứng — kiểm tra lại logic.");
            return CheckoutResult.FromExisting(raceOrder);
        }
 
        return CheckoutResult.FromNew(order);
    }
 
    private static bool IsDuplicateIdempotencyKey(DbUpdateException ex) =>
        ex.InnerException is PostgresException { SqlState: PostgresErrorCodes.UniqueViolation } pgEx
        && pgEx.ConstraintName == "IX_Orders_IdempotencyKey";
}
```

> **📘 Ghi chú giảng viên:** *Nhấn mạnh: lớp 1 (fast-path SELECT) KHÔNG chặn được race condition — nó chỉ tránh việc phải insert-rồi-catch-lỗi trong trường hợp phổ biến nhất (double-click nhưng request đầu đã xử lý xong từ lâu). Lớp 2 (catch DbUpdateException theo SqlState) mới là cơ chế chống trùng thật. Nếu học viên hỏi "vậy bỏ lớp 1 có sao không?" — không sai về mặt đúng/sai, chỉ là tốn 1 round-trip DB không cần thiết cho case phổ biến.*

### **2.4. Endpoint — nhận Idempotency Key qua HTTP header**

Theo convention phổ biến của các API thanh toán (Stripe là ví dụ được biết đến nhiều nhất), Idempotency Key đặt ở header riêng thay vì trong body — tách bạch khỏi dữ liệu nghiệp vụ, và dễ áp dụng thống nhất cho nhiều Command khác nhau sau này nếu cần (ví dụ qua 1 MediatR Pipeline Behavior tương tự ValidationBehavior ở bài 0.5):

```csharp
// TeduMarket.Api/Endpoints/OrderEndpoints.cs — mở rộng endpoint checkout từ bài 2.2
group.MapPost("/checkout", async (
    CheckoutRequest request,
    HttpRequest httpRequest,
    ISender sender,
    CancellationToken ct) =>
{
    if (!httpRequest.Headers.TryGetValue("Idempotency-Key", out var keyHeader)
        || !Guid.TryParse(keyHeader, out var idempotencyKey))
    {
        return Results.Problem(
            title: "Thiếu hoặc sai định dạng header Idempotency-Key",
            statusCode: StatusCodes.Status400BadRequest);
    }
 
    var command = new CheckoutCommand(request.CartId, idempotencyKey);
    var result = await sender.Send(command, ct);
 
    // Order đã tồn tại (request trùng) -> 200, không phải lỗi.
    // Order mới tạo -> 201, đúng convention REST cho hành động tạo mới.
    return result.IsNewOrder
        ? Results.Created($"/api/v1/orders/{result.OrderId}", result)
        : Results.Ok(result);
})
.WithName("Checkout")
.Produces<CheckoutResult>(StatusCodes.Status201Created)
.Produces<CheckoutResult>(StatusCodes.Status200OK);
```

> **⚠️ Lưu ý phiên bản:** Client (React Admin / Next.js ở Module 6, 7) phải sinh IdempotencyKey MỘT LẦN khi user bắt đầu thao tác Checkout (ví dụ lúc mở trang thanh toán) và giữ nguyên giá trị đó cho mọi lần retry của cùng 1 lượt thanh toán — không sinh GUID mới mỗi lần gọi API, vì như vậy sẽ triệt tiêu hoàn toàn tác dụng chống trùng.

## **Phần 3 — Optimistic Concurrency với xmin**

*Demo · 10 phút*

### **3.1. PostgreSQL đã có sẵn version cho mọi dòng dữ liệu**

PostgreSQL dùng MVCC (Multi-Version Concurrency Control): mỗi lần UPDATE tạo ra 1 phiên bản vật lý mới của dòng dữ liệu thay vì ghi đè tại chỗ. Mỗi phiên bản mang theo cột hệ thống ẩn tên xmin — id của transaction đã tạo ra phiên bản đó. Giá trị này tự động đổi mỗi lần dòng dữ liệu bị UPDATE, nên dùng được thẳng làm concurrency token mà không cần tự thêm cột Version và tự quản lý việc tăng giá trị như cách làm truyền thống (ví dụ rowversion của SQL Server).

EF Core, thông qua Npgsql provider, hỗ trợ mapping trực tiếp: thêm 1 property kiểu uint vào entity, cấu hình bằng IsRowVersion() — Npgsql sẽ map property đó vào cột hệ thống xmin thay vì tạo cột thật. Migration sinh ra sẽ rỗng, vì không có thay đổi schema nào cả — cột xmin vốn đã tồn tại sẵn trên mọi bảng PostgreSQL.

### **3.2. Cấu hình Version cho Order**

```csharp
// TeduMarket.Domain/Orders/Order.cs — thêm vào class Order đã có
public uint Version { get; private set; } // concurrency token, map vào xmin
// TeduMarket.Infrastructure/Persistence/Configurations/OrderConfiguration.cs
public void Configure(EntityTypeBuilder<Order> builder)
{
    // ... cấu hình đã có ở mục 2.2 ...
 
    builder.Property(o => o.Version)
        .IsRowVersion();
}
dotnet ef migrations add MapOrderXminConcurrencyToken
```

Mở file migration vừa sinh ra: phần Up()/Down() rỗng, đúng như lý thuyết — không có cột nào được tạo.

> **⚠️ Lưu ý phiên bản:** Một số phiên bản Npgsql.EntityFrameworkCore.PostgreSQL 10.0.x có bug đã ghi nhận (npgsql/efcore.pg#3854): migration generator đôi khi tạo nhầm 1 lệnh AddColumn cho xmin, khiến migration fail với lỗi "column \\"xmin\\" conflicts with a system column name". Nếu gặp đúng lỗi này: mở file migration vừa sinh, xóa thủ công đoạn migrationBuilder.AddColumn liên quan tới xmin (migration đúng phải rỗng), rồi chạy lại dotnet ef database update. Kiểm tra version Npgsql.EntityFrameworkCore.PostgreSQL đang dùng trong .csproj trước khi debug hướng khác.

### **3.3. Tình huống xung đột thật: webhook thanh toán vs job hết hạn đơn hàng**

Concurrency token chỉ có ý nghĩa khi có ít nhất 2 luồng cùng SỬA 1 Order gần như đồng thời. Trong TEDU Market, tình huống thật xảy ra giữa 2 thành phần đã xây ở các bài trước:

- Webhook SePay (bài 2.5) — cập nhật Order từ Pending sang Paid khi có tiền chuyển vào.
- 1 BackgroundService mới (theo đúng pattern BackgroundService thuần đã dùng ở bài 2.7, không Hangfire) — định kỳ quét các Order ở trạng thái Pending quá lâu và tự động chuyển sang Expired.

Nếu học viên thanh toán đúng lúc job hết hạn đang quét tới Order của họ, cả 2 đều cố UPDATE cùng 1 dòng gần như đồng thời. Không có concurrency token, kết quả phụ thuộc thứ tự COMMIT ngẫu nhiên — có thể Order bị đánh dấu Expired dù học viên đã trả tiền.

```csharp
// TeduMarket.Infrastructure/BackgroundJobs/ExpireStaleOrdersJob.cs
public class ExpireStaleOrdersJob(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = scopeFactory.CreateScope();
            var dbContext = scope.ServiceProvider.GetRequiredService<AppDbContext>();
 
            var staleOrders = await dbContext.Orders
                .Where(o => o.Status == OrderStatus.Pending
                         && o.CreatedAt < DateTime.UtcNow.AddMinutes(-15))
                .ToListAsync(stoppingToken);
 
            foreach (var order in staleOrders)
            {
                order.MarkAsExpired(); // no-op nếu Status không còn là Pending
 
                try
                {
                    await dbContext.SaveChangesAsync(stoppingToken);
                }
                catch (DbUpdateConcurrencyException)
                {
                    // Webhook SePay vừa cập nhật Order này thành Paid đúng lúc
                    // job đọc xong -> xmin đã đổi -> EF Core phát hiện conflict.
                    // KHÔNG retry ghi đè: reload rồi để MarkAsExpired() tự no-op
                    // vì Status lúc này đã là Paid.
                    dbContext.Entry(order).Reload();
                }
            }
 
            await Task.Delay(TimeSpan.FromMinutes(1), stoppingToken);
        }
    }
}
```

MarkAsExpired() trên Order Aggregate phải tự bảo vệ invariant, không tin tưởng job gọi đúng lúc:

```csharp
// TeduMarket.Domain/Orders/Order.cs
public void MarkAsExpired()
{
    // Chỉ Pending mới được phép Expired. Nếu đã Paid, đây là no-op
    // có chủ đích - không phải lỗi cần throw.
    if (Status != OrderStatus.Pending)
        return;
 
    Status = OrderStatus.Expired;
}
```

> **📘 Ghi chú giảng viên:** *Điểm hay bị hiểu nhầm: DbUpdateConcurrencyException không có nghĩa là phải retry để ghi đè cho bằng được. Cách xử lý đúng phụ thuộc business rule — ở đây, reload rồi để domain method tự quyết định (no-op vì đã Paid) là đúng. Nếu học viên viết catch (DbUpdateConcurrencyException) { retry SaveChanges với data cũ } thì coi như đã tự tay ghi đè lên đúng dữ liệu mà concurrency token sinh ra để bảo vệ — hỏi ngược lại: "Retry để làm gì nếu ý định ban đầu (Expire) không còn đúng nữa?"*

## **Phần 4 — Lab: Test case race condition**

*Lab · 5 phút*

Module 8 sẽ formal hóa integration test bằng WebApplicationFactory + Testcontainers (bài 8.3). Ở đây làm phiên bản đơn giản, chạy trực tiếp trên Postgres của Docker Compose (bài 0.10), đủ để chứng minh Deliverable của bài: Checkout an toàn khi gọi trùng.

> **⚠️ Lưu ý phiên bản:** DbContext không thread-safe — không được dùng chung 1 instance DbContext/handler cho 2 request "song song" trong cùng test, việc đó sẽ ném exception không liên quan đến race condition đang muốn test. Cách đúng: dựng HttpClient thật qua WebApplicationFactory và gọi API qua HTTP, để mỗi request có scope DI và DbContext riêng — đúng như 2 request thật từ 2 trình duyệt.

```csharp
// TeduMarket.Application.UnitTests/... → thực chất đây là integration test nhẹ,
// đặt tạm trong project test hiện có; Module 8 sẽ tách project riêng cho đúng chuẩn.
public class CheckoutIdempotencyTests(TeduMarketWebApplicationFactory factory)
    : IClassFixture<TeduMarketWebApplicationFactory>
{
    [Fact]
    public async Task Checkout_GoiTrungCungIdempotencyKey_ChiTaoDuocMotOrder()
    {
        // Arrange
        var client = factory.CreateClient();
        var cartId = await factory.SeedCartWithOneItemAsync();
        var idempotencyKey = Guid.NewGuid();
 
        HttpRequestMessage BuildRequest() => new(HttpMethod.Post, "/api/v1/checkout")
        {
            Headers = { { "Idempotency-Key", idempotencyKey.ToString() } },
            Content = JsonContent.Create(new { CartId = cartId })
        };
 
        // Act: 2 request độc lập, gửi gần như đồng thời qua HTTP thật
        var responses = await Task.WhenAll(
            client.SendAsync(BuildRequest()),
            client.SendAsync(BuildRequest()));
 
        var results = await Task.WhenAll(
            responses[0].Content.ReadFromJsonAsync<CheckoutResult>(),
            responses[1].Content.ReadFromJsonAsync<CheckoutResult>());
 
        // Assert: cả 2 response trỏ về CÙNG 1 OrderId
        Assert.Equal(results[0]!.OrderId, results[1]!.OrderId);
 
        // Assert: DB chỉ có đúng 1 Order với key này
        var orderCount = await factory.CountOrdersByIdempotencyKeyAsync(idempotencyKey);
        Assert.Equal(1, orderCount);
    }
}
```

## **Bài tập thực hành**

> **✏️ Bài tập 1 — Retry 3 lần liên tiếp:** Mở rộng test ở Phần 4: thay vì gửi 2 request song song, mô phỏng đúng kịch bản double-click — gửi 3 request với cùng IdempotencyKey trong khoảng cách vài mili-giây (không cần song song tuyệt đối, chỉ cần liên tiếp thật nhanh). Assert: đúng 1 Order được tạo, và cả 3 response đều trả về cùng OrderId, mã HTTP hợp lý (1 response 201, các response còn lại 200).

*Hint: dùng vòng for gửi 3 request tuần tự không await ngay (gom Task vào List\<Task\<HttpResponseMessage>>), rồi Task.WhenAll ở cuối để tối đa hóa khả năng chồng lấn thời gian xử lý.*

> **✏️ Bài tập 2 — Concurrency token cho Cart:** Cart (bài 2.1) hiện chưa có concurrency token. Tình huống lỗi thật: học viên mở 2 tab trình duyệt, cùng AddToCart gần như đồng thời ở cả 2 tab — nếu AddToCartCommandHandler đọc Cart, thêm item vào list trong bộ nhớ rồi save, request commit sau sẽ ghi đè mất item mà request commit trước đã thêm (lost update). Thêm property Version (uint) vào Cart Aggregate, cấu hình IsRowVersion() giống Order, và viết 1 test xác nhận: 2 lần AddToCart đồng thời vào cùng Cart phải giữ được cả 2 item, không bị mất item nào.

*Hint: với Cart, xử lý DbUpdateConcurrencyException không nên là no-op như Order.MarkAsExpired() — mà nên retry có kiểm soát: reload Cart, add lại item bị lỡ, save lại (tối đa 2-3 lần retry). Đây là điểm khác biệt quan trọng so với ví dụ Order ở Phần 3: chọn no-op hay retry phụ thuộc ý nghĩa nghiệp vụ của thao tác, không có công thức chung cho mọi Aggregate.*

## **Tổng kết**

> Race condition ở Checkout không phải lỗi hiếm gặp — nó xảy ra bất cứ khi nào UI cho phép double-click hoặc client tự retry. "Check rồi mới ghi" trong Handler không đủ, vì khoảng hở giữa SELECT và INSERT cho phép 2 transaction chồng lấn.
>
> Idempotency Key + unique index là 2 lớp bổ trợ nhau: application-layer check tối ưu case phổ biến, unique constraint ở DB là cơ chế chống trùng thật sự, hoạt động đúng bất kể độ trễ giữa các transaction.
>
> PostgreSQL cho concurrency token miễn phí qua cột hệ thống xmin — chỉ cần 1 property uint + IsRowVersion(), không cần migration thật, không cần tự quản lý việc tăng version.
>
> Xử lý DbUpdateConcurrencyException phải dựa vào business rule của từng Aggregate: Order.MarkAsExpired() chọn no-op (đã Paid thì bỏ qua), trong khi Cart ở bài tập 2 cần retry có kiểm soát — không có cách xử lý mặc định đúng cho mọi trường hợp.

### **So sánh nhanh: 2 khái niệm dễ nhầm trong bài**

|  | **Idempotency Key** | **Optimistic Concurrency (xmin)** |
|---|---|---|
| Chặn vấn đề gì | Tạo trùng bản ghi (2 INSERT từ 1 hành động) | Ghi đè mất dữ liệu (2 UPDATE cùng 1 bản ghi) |
| Cơ chế | Unique index trên key do client cung cấp | So khớp xmin tại thời điểm UPDATE |
| Áp dụng ở bài này cho | Order (khi tạo từ Cart, bài 2.2) | Order (khi chuyển trạng thái Pending → Paid/Expired) |
| Lỗi khi vi phạm | DbUpdateException (PostgresException 23505) | DbUpdateConcurrencyException |

**Bước tiếp theo:** Module 2 kết thúc ở đây — Order & Payment đã có đầy đủ: tạo đơn, thanh toán qua SePay, Outbox, và giờ là an toàn trước race condition. Bài 3.1 chuyển sang Module 3, module khó nhất khóa: xây Authorization Server thật bằng OpenIddict, bắt đầu từ khái niệm OAuth2/OIDC đúng chuẩn.
