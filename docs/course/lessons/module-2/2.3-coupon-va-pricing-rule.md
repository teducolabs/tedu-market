## **Nội dung chính**

### **1. Vì sao dùng Specification Pattern thay vì if/else**

*Thời lượng: 10 phút | Loại: Lý thuyết*

Ở bài 2.1, bạn đã tạo Coupon như một entity nằm trong bounded context Ordering, đi kèm Cart và Order. Nhưng một Coupon chỉ có "code" và "% giảm" thì chưa đủ để dùng thật — nó còn phải trả lời được 3 câu hỏi trước khi cho áp dụng:

- Coupon này còn hiệu lực tại thời điểm khách bấm "Áp dụng" không?
- Coupon này có giới hạn chỉ áp dụng cho một số Course cụ thể không?
- (Bài tập cuối giờ) Coupon này có yêu cầu giá trị đơn hàng tối thiểu không?

Cách viết nhanh nhất — và cũng là cách dễ hỏng nhất — là nhét cả 3 điều kiện đó vào trong ApplyCouponCommandHandler bằng một chuỗi if lồng nhau. Vấn đề không phải là code chạy sai ngay từ đầu, mà là 6 tháng sau khi Sale cần thêm rule thứ 4 (ví dụ: giới hạn số lần dùng mỗi User), bạn sẽ phải sửa lại đúng cái Handler đó, và rủi ro sửa nhầm logic rule cũ đã chạy ổn định là có thật.

Specification Pattern giải quyết đúng vấn đề này: mỗi rule là một class độc lập, implement chung 1 interface, chỉ trả lời đúng 1 câu hỏi boolean. Muốn thêm rule mới → thêm class mới, không đụng vào rule cũ. Đây chính là ví dụ thực tế của Open/Closed Principle mà không cần giải thích lý thuyết dài dòng.

> **📘 Ghi chú giảng viên:** *Tôi hay hỏi ngược lớp ở đây: "Nếu dùng if/else, review code Pull Request thêm rule mới sẽ khó hơn hay dễ hơn so với thêm 1 class Specification mới?" — đa số học viên tự nhận ra diff của PR thêm class mới nhỏ gọn hơn hẳn, dễ review hơn, đó mới là lý do thật để chọn pattern này chứ không phải vì nó "nghe pro".*

### **2. Value Object Discount**

*Thời lượng: 10 phút | Loại: Demo*

Discount là Value Object — bất biến (immutable) và tự bảo vệ invariant của chính nó: phần trăm giảm giá phải nằm trong khoảng (0, 100]. Đặt validate này bên trong Discount thay vì bên trong Handler, để không ai trong hệ thống có thể tạo ra một Discount vô lý (âm, bằng 0, hoặc trên 100%), dù gọi từ đâu.

```csharp
namespace TeduMarket.Domain.Ordering;
 
public sealed record Discount
{
    public decimal Percentage { get; }
 
    private Discount(decimal percentage) => Percentage = percentage;
 
    public static Discount FromPercentage(decimal percentage)
    {
        if (percentage <= 0 || percentage > 100)
        {
            throw new CouponDiscountInvalidException(percentage);
        }
 
        return new Discount(percentage);
    }
 
    // Làm tròn 2 chữ số thập phân, tránh lệch tiền do sai số
    public decimal ApplyTo(decimal amount) =>
        Math.Round(
            amount * (1 - Percentage / 100m), 2,
            MidpointRounding.AwayFromZero);
}
```

Vì đây là record, hai Discount có cùng Percentage sẽ so sánh bằng nhau theo giá trị (value equality) — đúng ngữ nghĩa Value Object đã học ở bài 0.3, không phải so sánh theo reference như Entity.

> **📘 Ghi chú giảng viên:** *Điểm hay bị hỏi: "Sao không để Percentage là int cho đơn giản?" — trả lời: tiền và tỉ lệ phần trăm áp lên tiền phải dùng decimal, tránh sai số nhị phân của double/float. Đây là quy ước đã thống nhất từ đầu khóa cho mọi giá trị tiền tệ (Pricing Value Object ở bài 1.1 cũng làm vậy).*

### **3. Specification Pattern áp rule cho Coupon**

*Thời lượng: 15 phút | Loại: Demo*

Định nghĩa 1 interface chung cho mọi rule, và 1 context object chứa toàn bộ dữ kiện cần thiết để rule tự kiểm tra — rule không tự đi lấy dữ liệu từ DB, dữ liệu được truyền vào (giữ Domain layer thuần, không phụ thuộc hạ tầng, đúng nguyên tắc Dependency Inversion đã học ở bài 0.2).

```csharp
namespace TeduMarket.Domain.Ordering.Specifications;
 
public sealed record CouponApplicationContext(
    DateTime NowUtc,
    IReadOnlyCollection<Guid> CourseIdsInCart);
 
public interface ICouponSpecification
{
    string FailureReason { get; }
    bool IsSatisfiedBy(CouponApplicationContext context);
}
```

Rule 1 — kiểm tra thời hạn hiệu lực:

```csharp
public sealed class CouponWithinValidPeriodSpecification
    : ICouponSpecification
{
    private readonly DateTime _validFrom;
    private readonly DateTime _validTo;
 
    public CouponWithinValidPeriodSpecification(
        DateTime validFrom, DateTime validTo)
    {
        _validFrom = validFrom;
        _validTo = validTo;
    }
 
    public string FailureReason =>
        "Mã giảm giá đã hết hạn hoặc chưa tới ngày áp dụng.";
 
    public bool IsSatisfiedBy(CouponApplicationContext context) =>
        context.NowUtc >= _validFrom && context.NowUtc <= _validTo;
}
```

Rule 2 — kiểm tra giới hạn Course áp dụng (danh sách rỗng nghĩa là áp dụng cho toàn bộ Course):

```csharp
public sealed class CouponAppliesToCourseSpecification
    : ICouponSpecification
{
    private readonly IReadOnlyCollection<Guid> _applicableCourseIds;
 
    public CouponAppliesToCourseSpecification(
        IReadOnlyCollection<Guid> applicableCourseIds)
        => _applicableCourseIds = applicableCourseIds;
 
    public string FailureReason =>
        "Mã giảm giá không áp dụng cho khóa học trong giỏ hàng.";
 
    public bool IsSatisfiedBy(CouponApplicationContext context)
    {
        if (_applicableCourseIds.Count == 0)
        {
            return true; // không giới hạn Course cụ thể
        }
 
        return context.CourseIdsInCart.Any(_applicableCourseIds.Contains);
    }
}
```

Composite — gộp nhiều rule lại, dừng ngay ở rule đầu tiên không thỏa (fail-fast), giữ lại lý do để trả lỗi rõ ràng cho người dùng:

```csharp
public sealed class CompositeCouponSpecification : ICouponSpecification
{
    private readonly IReadOnlyList<ICouponSpecification> _specifications;
    private string _failureReason = string.Empty;
 
    public CompositeCouponSpecification(
        IReadOnlyList<ICouponSpecification> specifications)
        => _specifications = specifications;
 
    public string FailureReason => _failureReason;
 
    public bool IsSatisfiedBy(CouponApplicationContext context)
    {
        foreach (var spec in _specifications)
        {
            if (!spec.IsSatisfiedBy(context))
            {
                _failureReason = spec.FailureReason;
                return false;
            }
        }
 
        return true;
    }
}
```

Ráp lại trong chính Coupon Aggregate (bổ sung vào entity Coupon đã tạo khung ở bài 2.1 — giờ thêm Discount và method dựng Specification):

```csharp
namespace TeduMarket.Domain.Ordering;
 
public sealed class Coupon
{
    public Guid Id { get; private set; }
    public string Code { get; private set; } = default!;
    public Discount Discount { get; private set; } = default!;
    public DateTime ValidFrom { get; private set; }
    public DateTime ValidTo { get; private set; }
 
    private readonly List<Guid> _applicableCourseIds = new();
    public IReadOnlyCollection<Guid> ApplicableCourseIds =>
        _applicableCourseIds.AsReadOnly();
 
    private Coupon() { } // dành cho EF Core
 
    public static Coupon Create(
        string code, Discount discount,
        DateTime validFrom, DateTime validTo,
        IEnumerable<Guid>? applicableCourseIds = null)
    {
        if (string.IsNullOrWhiteSpace(code))
        {
            throw new CouponCodeInvalidException(code);
        }
 
        if (validTo <= validFrom)
        {
            throw new CouponDateRangeInvalidException(validFrom, validTo);
        }
 
        var coupon = new Coupon
        {
            Id = Guid.NewGuid(),
            Code = code.Trim().ToUpperInvariant(),
            Discount = discount,
            ValidFrom = validFrom,
            ValidTo = validTo
        };
 
        if (applicableCourseIds is not null)
        {
            coupon._applicableCourseIds.AddRange(applicableCourseIds);
        }
 
        return coupon;
    }
 
    public ICouponSpecification BuildSpecification() =>
        new CompositeCouponSpecification(new ICouponSpecification[]
        {
            new CouponWithinValidPeriodSpecification(ValidFrom, ValidTo),
            new CouponAppliesToCourseSpecification(ApplicableCourseIds)
        });
}
```

> **📘 Ghi chú giảng viên:** *Đây là điểm hay nhầm nhất của Specification Pattern khi mới học: đừng để Cart hoặc Handler tự viết logic kiểm tra rule. Coupon phải là nơi duy nhất biết "tôi được áp dụng khi nào" — nếu để chỗ khác tự suy luận, invariant sẽ dễ rơi rớt khi có thêm luồng gọi mới (ví dụ Admin duyệt tay 1 đơn hàng).*

### **4. Command ApplyCoupon end-to-end**

*Thời lượng: 10 phút | Loại: Demo*

Cart Aggregate (khung đã có từ bài 2.1–2.2) nhận thêm method ApplyCoupon — nơi thật sự gọi Specification và cập nhật giá cuối cùng:

```csharp
namespace TeduMarket.Domain.Ordering;
 
public sealed class Cart
{
    // Id, UserId, danh sách _items đã có từ bài 2.1-2.2
    // (mỗi item gồm CourseId, UnitPrice)
 
    public Guid? AppliedCouponId { get; private set; }
    public decimal DiscountAmount { get; private set; }
 
    public decimal SubTotal => _items.Sum(i => i.UnitPrice);
    public decimal FinalTotal => SubTotal - DiscountAmount;
 
    public void ApplyCoupon(Coupon coupon, DateTime nowUtc)
    {
        if (_items.Count == 0)
        {
            throw new CartEmptyException(Id);
        }
 
        var context = new CouponApplicationContext(
            nowUtc, _items.Select(i => i.CourseId).ToArray());
 
        var specification = coupon.BuildSpecification();
        if (!specification.IsSatisfiedBy(context))
        {
            throw new CouponNotApplicableException(
                coupon.Code, specification.FailureReason);
        }
 
        AppliedCouponId = coupon.Id;
        DiscountAmount = SubTotal - coupon.Discount.ApplyTo(SubTotal);
    }
}
```

Command, Validator và Handler — đúng bộ ba pattern đã lặp lại từ Module 0 (lần lặp thứ N, nên phần này đi nhanh):

```csharp
namespace TeduMarket.Application.Ordering.Commands.ApplyCoupon;
 
public sealed record ApplyCouponCommand(Guid CartId, string CouponCode)
    : IRequest<ApplyCouponResult>;
 
public sealed record ApplyCouponResult(
    decimal SubTotal, decimal DiscountAmount, decimal FinalTotal);
 
public sealed class ApplyCouponCommandValidator
    : AbstractValidator<ApplyCouponCommand>
{
    public ApplyCouponCommandValidator()
    {
        RuleFor(x => x.CartId).NotEmpty();
        RuleFor(x => x.CouponCode).NotEmpty().MaximumLength(50);
    }
}
public sealed class ApplyCouponCommandHandler
    : IRequestHandler<ApplyCouponCommand, ApplyCouponResult>
{
    private readonly ICartRepository _cartRepository;
    private readonly ICouponRepository _couponRepository;
    private readonly TimeProvider _timeProvider;
 
    public ApplyCouponCommandHandler(
        ICartRepository cartRepository,
        ICouponRepository couponRepository,
        TimeProvider timeProvider)
    {
        _cartRepository = cartRepository;
        _couponRepository = couponRepository;
        _timeProvider = timeProvider;
    }
 
    public async Task<ApplyCouponResult> Handle(
        ApplyCouponCommand request, CancellationToken cancellationToken)
    {
        var cart = await _cartRepository.GetByIdAsync(
            request.CartId, cancellationToken)
            ?? throw new CartNotFoundException(request.CartId);
 
        var coupon = await _couponRepository.GetByCodeAsync(
            request.CouponCode, cancellationToken)
            ?? throw new CouponNotFoundException(request.CouponCode);
 
        cart.ApplyCoupon(coupon, _timeProvider.GetUtcNow().UtcDateTime);
 
        await _cartRepository.SaveChangesAsync(cancellationToken);
 
        return new ApplyCouponResult(
            cart.SubTotal, cart.DiscountAmount, cart.FinalTotal);
    }
}
```

Endpoint theo đúng route convention /api/v1/{số nhiều thực thể}, đặt trong nhóm carts:

```csharp
namespace TeduMarket.Api.Endpoints.Carts;
 
public sealed record ApplyCouponRequest(string CouponCode);
 
public static class ApplyCouponEndpoint
{
    public static RouteGroupBuilder MapApplyCoupon(
        this RouteGroupBuilder group)
    {
        group.MapPost("/{cartId:guid}/coupon", async (
            Guid cartId,
            ApplyCouponRequest request,
            ISender sender,
            CancellationToken cancellationToken) =>
        {
            var command = new ApplyCouponCommand(
                cartId, request.CouponCode);
            var result = await sender.Send(command, cancellationToken);
            return Results.Ok(result);
        })
        .WithName("ApplyCoupon")
        .WithTags("Carts")
        .Produces<ApplyCouponResult>(StatusCodes.Status200OK)
        .ProducesProblem(StatusCodes.Status400BadRequest);
 
        return group;
    }
}
```

Test thử trên Scalar (/scalar) với body { "couponCode": "SUMMER10" }, Cart có 2 khóa học 500.000đ và 300.000đ, coupon giảm 10% không giới hạn Course: SubTotal = 800.000, DiscountAmount = 80.000, FinalTotal = 720.000. Đổi CourseIdsInCart để không khớp ApplicableCourseIds của một coupon bị giới hạn → xác nhận API trả lỗi ProblemDetails đúng theo chuẩn đã làm ở bài 0.9, không phải exception thô 500.

## **Bài tập thực hành**

> **✏️ Yêu cầu:** Thêm 1 rule mới: MinimumOrderAmountSpecification — Coupon chỉ áp dụng khi SubTotal của Cart đạt tối thiểu 1 mức tiền định trước (ví dụ 500.000đ), mà KHÔNG được sửa lại 2 class Specification đã viết ở trên.

Input: Coupon có thêm property MinimumOrderAmount (decimal, mặc định 0 = không giới hạn). Cart có SubTotal = 400.000đ, Coupon yêu cầu tối thiểu 500.000đ.

Expected output: ApplyCouponCommand ném CouponNotApplicableException với FailureReason rõ ràng kiểu "Đơn hàng chưa đạt giá trị tối thiểu 500.000đ để áp dụng mã giảm giá.", không làm thay đổi AppliedCouponId hay DiscountAmount của Cart.

Hint 1: Context object CouponApplicationContext hiện chưa có SubTotal — cần thêm 1 property mới vào record này (record hỗ trợ thêm property bình thường, không phá vỡ 2 spec cũ vì chúng không dùng property đó).

Hint 2: Thêm class mới vào mảng specifications trong Coupon.BuildSpecification() — đây chính là phần "Open" của Open/Closed: mở rộng bằng cách thêm, không sửa 2 class đã có.

Solution gợi ý: MinimumOrderAmountSpecification.IsSatisfiedBy(context) => context.CartSubTotal >= \_minimumAmount, với \_minimumAmount lấy từ Coupon.MinimumOrderAmount truyền vào constructor lúc Coupon.BuildSpecification() dựng composite.

## **Tổng kết**

> **✅ Tóm tắt:**
>
> • Discount là Value Object bất biến, tự validate invariant % giảm giá — không để Handler hay Cart tự kiểm tra.
>
> • Specification Pattern tách mỗi điều kiện áp Coupon thành 1 class riêng, ráp lại bằng Composite — thêm rule mới không sửa code cũ.
>
> • Coupon Aggregate là nơi duy nhất biết cách dựng ra bộ Specification của chính nó (BuildSpecification), Cart chỉ gọi và xử lý kết quả.
>
> • ApplyCouponCommand hoàn chỉnh theo đúng bộ Command/Validator/Handler/Endpoint đã lặp lại từ Module 0, dùng TimeProvider để Handler test được (chuẩn bị cho Module 8).
>
> • Deliverable bài này: ApplyCouponCommand tính đúng FinalTotal, sẵn sàng cho bài 2.4 dùng FinalTotal này để tạo URL thanh toán VNPay.

Bước tiếp theo: Bài 2.4 — Tích hợp Cổng thanh toán VNPay Sandbox, sẽ dùng đúng FinalTotal vừa tính được ở đây để tạo InitiatePaymentCommand.
