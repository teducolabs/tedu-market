## **Nội dung chính**

### **Phần 1 — Vấn đề Dual Write & Outbox Pattern**

*Thời lượng: 20 phút | Loại: Lý thuyết*

### **1.1. Nhắc lại lỗ hổng đã gieo từ bài 2.2**

Ở bài 2.2, CheckoutCommandHandler làm 2 việc tách rời: gọi unitOfWork.SaveChangesAsync() để lưu Order xuống Postgres, rồi gọi riêng domainEventDispatcher.DispatchAndClearEventsAsync() để publish CourseOrderedEvent qua MediatR. Bài đó đã cảnh báo rõ: nếu server crash NGAY SAU dòng SaveChangesAsync() nhưng TRƯỚC dòng Dispatch, Order vẫn nằm trong DB nhưng domain event bị mất vĩnh viễn — không Handler nào chạy.

Với CourseOrderedEvent, hậu quả ở mức chấp nhận được (bài 2.2 chỉ log ra console để demo). Nhưng với OrderPaidEvent — sự kiện sẽ xuất hiện ngay trong bài này — hậu quả nghiêm trọng hơn nhiều: nếu event bị mất, Enrollment (bài 2.7) không bao giờ được tạo, học viên đã chuyển khoản thành công nhưng KHÔNG nhận được quyền truy cập khóa học. Đây chính xác là lý do Outbox Pattern tồn tại — không phải một kỹ thuật tùy chọn, mà là điều kiện bắt buộc cho luồng thanh toán.

> **📘 Ghi chú giảng viên:** *Tôi hay hỏi ngược lại học viên ở đây: "Tại sao không đơn giản là gọi Dispatch TRƯỚC SaveChangesAsync?" — câu trả lời: nếu Dispatch trước, Handler của CourseOrderedEvent/OrderPaidEvent có thể chạy dựa trên dữ liệu CHƯA thực sự được lưu (Order có thể fail lúc SaveChanges vì lỗi concurrency, unique constraint...), dẫn đến publish event cho một thay đổi chưa từng xảy ra. Đảo thứ tự không giải quyết được gì, chỉ đổi loại lỗi.*

### **1.2. Outbox Pattern giải quyết dual write như thế nào**

Ý tưởng cốt lõi: đừng cố publish event ngay lập tức. Thay vào đó, khi lưu thay đổi Order, ghi luôn một bản ghi mô tả event đó vào một bảng riêng trong CHÍNH transaction đang lưu Order — gọi là bảng Outbox. Vì EF Core đã gom mọi Insert/Update/Delete của SaveChangesAsync vào một transaction database duy nhất, chỉ cần thêm OutboxMessage vào cùng ChangeTracker trước khi gọi SaveChangesAsync là tự động có tính atomic, không cần 2-phase commit hay transaction phân tán.

Sau đó, một tiến trình nền tách biệt (Hangfire — bài 2.7) đọc các dòng Outbox chưa xử lý, publish event thật (tạo Enrollment, gửi email...), rồi đánh dấu đã xử lý. Nếu server crash giữa chừng, dòng Outbox vẫn còn nguyên trong DB — tiến trình nền sẽ đọc lại và xử lý tiếp ở lần chạy sau, không mất event.

### **1.3. So sánh trước / sau**

- Trước (bài 2.2): SaveChangesAsync() lưu Order → (điểm hở, có thể crash ở đây) → Dispatch publish event qua MediatR ngay lập tức, trong bộ nhớ, không có gì đảm bảo nếu tiến trình chết giữa chừng.
- Sau (bài 2.6): SaveChangesAsync() lưu Order VÀ ghi OutboxMessage TRONG CÙNG một transaction → luôn nhất quán, không có điểm hở. Việc publish event thật (đọc Outbox, xử lý, đánh dấu đã xong) chuyển sang Hangfire, chạy độc lập, có thể retry an toàn nếu lỗi.
- Đánh đổi: event không còn được xử lý NGAY LẬP TỨC mà có độ trễ nhỏ (đến khi Hangfire chạy job tiếp theo — bài 2.7 sẽ cấu hình chạy mỗi vài giây). Đây gọi là eventual consistency — chấp nhận được cho Enrollment và gửi email, không chấp nhận được cho thứ cần đồng bộ tức thời.

### **Bước 1 — Nhắc lại OrderPaidEvent & Order.MarkAsPaid() (bài 2.5)**

Bài 2.5 xử lý webhook SePay: sau khi xác thực chữ ký HMAC-SHA256 và khớp mã thanh toán + số tiền, Handler gọi order.MarkAsPaid() để chuyển Order từ Pending sang Paid. Nhắc lại nhanh 2 phần liên quan trực tiếp đến Outbox — chi tiết đầy đủ về xử lý webhook xem lại bài 2.5:

```csharp
// TeduMarket.Domain/Ordering/Events/OrderPaidEvent.cs
namespace TeduMarket.Domain.Ordering.Events;
 
public sealed record OrderPaidEvent(
    Guid OrderId,
    Guid UserId,
    IReadOnlyCollection<Guid> CourseIds,
    decimal Amount) : IDomainEvent
{
    public DateTime OccurredOn { get; } = DateTime.UtcNow;
}
```

Đặt tên OrderPaidEvent đúng quy ước {Thực thể}{Động từ quá khứ}Event ở mục 7 outline — đúng ví dụ đã nêu sẵn trong bảng quy ước.

```csharp
// TeduMarket.Domain/Orders/Order.cs (bổ sung, nối tiếp bài 2.4)
public sealed class Order
{
    // ... các thành viên khác giữ nguyên từ bài 2.1-2.4
 
    public void MarkAsPaid()
    {
        if (Status != OrderStatus.Pending)
        {
            throw new OrderInvalidStatusException(
                $"Order {Id} đang ở trạng thái {Status}, " +
                "không thể đánh dấu đã thanh toán.");
        }
 
        Status = OrderStatus.Paid;
 
        var courseIds = Items
            .Select(item => item.CourseId)
            .ToArray();
 
        AddDomainEvent(new OrderPaidEvent(
            Id, UserId, courseIds, FinalAmount));
    }
}
```

> **📘 Ghi chú giảng viên:** *Cùng một pattern invariant-check-rồi-đổi-trạng-thái như InitiatePayment() ở bài 2.4 — Status chỉ được đổi thông qua method của Aggregate, không update thẳng cột status ngoài luồng. AddDomainEvent() là method protected đã có sẵn trên AggregateRoot từ bài 0.3, dùng lại y hệt cách CourseOrderedEvent được raise ở bài 2.2.*

### **Bước 2 — OutboxMessage entity**

OutboxMessage không phải một khái niệm nghiệp vụ (không có invariant, không thuộc Bounded Context nào) — đây là một chi tiết hạ tầng để đảm bảo giao hàng an toàn cho domain event, nên đặt ở Infrastructure, không đặt trong Domain layer:

```csharp
// TeduMarket.Infrastructure/Outbox/OutboxMessage.cs
using System.Text.Json;
using TeduMarket.Application.Common.Interfaces;
 
namespace TeduMarket.Infrastructure.Outbox;
 
public sealed class OutboxMessage
{
    public Guid Id { get; private init; }
    public string Type { get; private init; } = default!;
    public string Content { get; private init; } = default!;
    public DateTime OccurredOnUtc { get; private init; }
    public DateTime? ProcessedOnUtc { get; private set; }
    public string? Error { get; private set; }
 
    private OutboxMessage()
    {
    }
 
    public static OutboxMessage FromDomainEvent(
        IDomainEvent domainEvent)
    {
        var eventType = domainEvent.GetType();
 
        return new OutboxMessage
        {
            Id = Guid.NewGuid(),
            Type = eventType.Name,
            Content = JsonSerializer.Serialize(
                domainEvent, eventType),
            OccurredOnUtc = domainEvent.OccurredOn,
        };
    }
 
    public void MarkAsProcessed(DateTime processedOnUtc)
    {
        ProcessedOnUtc = processedOnUtc;
    }
 
    public void MarkAsFailed(string error)
    {
        Error = error;
    }
}
```

> **📘 Ghi chú giảng viên:** *Type chỉ lưu tên class ngắn ("OrderPaidEvent"), KHÔNG lưu AssemblyQualifiedName đầy đủ — lưu full assembly-qualified name sẽ vỡ nếu sau này đổi tên assembly hoặc di chuyển namespace, vì chuỗi đó bị hard-code luôn cả version assembly vào từng dòng dữ liệu cũ trong DB. Bài 2.7 sẽ dùng switch expression để map chuỗi Type sang class C# cụ thể — đơn giản và không giòn (brittle) như reflection load-by-name.*

### **Bước 3 — EF Core Fluent Configuration & Migration**

```csharp
// TeduMarket.Infrastructure/Outbox/OutboxMessageConfiguration.cs
namespace TeduMarket.Infrastructure.Outbox;
 
public sealed class OutboxMessageConfiguration
    : IEntityTypeConfiguration<OutboxMessage>
{
    public void Configure(
        EntityTypeBuilder<OutboxMessage> builder)
    {
        builder.ToTable("outbox_messages");
        builder.HasKey(x => x.Id);
 
        builder.Property(x => x.Type)
            .HasMaxLength(200)
            .IsRequired();
 
        builder.Property(x => x.Content)
            .IsRequired();
 
        builder.Property(x => x.OccurredOnUtc)
            .IsRequired();
    }
}
```

### **Bước 4 — Trái tim của bài học: sửa AppDbContext.SaveChangesAsync**

Đây là chỗ duy nhất cần sửa để có Outbox Pattern hoạt động — không cần sửa bất kỳ Handler nào đang gọi unitOfWork.SaveChangesAsync():

```csharp
// TeduMarket.Infrastructure/Persistence/AppDbContext.cs
// (sửa lại, nối tiếp bài 0.6)
public sealed class AppDbContext : DbContext
{
    // ... constructor, DbSet khác giữ nguyên từ bài 0.6
 
    public override async Task<int> SaveChangesAsync(
        CancellationToken cancellationToken = default)
    {
        ConvertDomainEventsToOutboxMessages();
 
        return await base.SaveChangesAsync(cancellationToken);
    }
 
    private void ConvertDomainEventsToOutboxMessages()
    {
        var aggregatesWithEvents = ChangeTracker
            .Entries<AggregateRoot>()
            .Select(entry => entry.Entity)
            .Where(a => a.DomainEvents.Count > 0)
            .ToArray();
 
        foreach (var aggregate in aggregatesWithEvents)
        {
            foreach (var domainEvent in aggregate.DomainEvents)
            {
                OutboxMessages.Add(
                    OutboxMessage.FromDomainEvent(domainEvent));
            }
 
            aggregate.ClearDomainEvents();
        }
    }
}
```

> **📘 Ghi chú giảng viên:** *Điểm mấu chốt: ConvertDomainEventsToOutboxMessages() chạy TRƯỚC dòng base.SaveChangesAsync(cancellationToken) — nghĩa là các OutboxMessage vừa Add() sẽ được EF Core track và đưa vào ĐÚNG CÙNG lệnh SaveChanges với việc Update Order.Status. EF Core gom toàn bộ thay đổi được track thành 1 transaction SQL duy nhất khi gọi SaveChanges — đây chính là lý do Outbox atomic được với thay đổi nghiệp vụ mà không cần thêm bất kỳ transaction thủ công nào. Tôi hay demo trực tiếp bằng cách đặt breakpoint ngay trước base.SaveChangesAsync và cho học viên xem ChangeTracker.Entries() đã có cả Order (Modified) lẫn OutboxMessage (Added) cùng lúc.*

### **Bước 5 — Đơn giản hóa lại Handler đã viết ở bài 2.2**

Vì AppDbContext tự động lo phần Outbox, dòng gọi domainEventDispatcher.DispatchAndClearEventsAsync() thủ công trong CheckoutCommandHandler (bài 2.2) không còn cần thiết — đã học ở bài 2.2, giờ thay bằng cách làm đúng chuẩn:

```csharp
// Trước (bài 2.2):
await unitOfWork.SaveChangesAsync(cancellationToken);
await domainEventDispatcher.DispatchAndClearEventsAsync(
    new AggregateRoot[] { cart, order }, cancellationToken);
 
// Sau (bài 2.6):
await unitOfWork.SaveChangesAsync(cancellationToken);
// Không cần gọi dispatcher thủ công nữa — AppDbContext đã
// tự chuyển domain event thành OutboxMessage ngay trong
// SaveChangesAsync ở trên, cùng transaction với Order/Cart.
```

IDomainEventDispatcher và DomainEventDispatcher (bài 2.2) KHÔNG bị xóa — vẫn còn nguyên trong Infrastructure. Bài 2.7 sẽ inject lại chính class này vào Hangfire job, để deserialize OutboxMessage.Content về đúng kiểu domain event rồi publish qua MediatR — chỉ đổi CHỖ gọi (từ trong Handler sang trong background job), không đổi CƠ CHẾ dispatch đã xây từ bài 2.2.

### **Bước 6 — Kiểm tra tính atomic**

Chạy lại luồng Checkout (bài 2.2) hoặc gọi trực tiếp order.MarkAsPaid() trong một test nhỏ, rồi truy vấn Postgres:

```sql
SELECT id, type, occurred_on_utc, processed_on_utc
FROM outbox_messages
ORDER BY occurred_on_utc DESC
LIMIT 5;
```

- Xác nhận có đúng 1 dòng OutboxMessage mới với type = "OrderPaidEvent", processed_on_utc = NULL (chưa ai xử lý — đúng vì bài 2.7 chưa viết job đọc Outbox).
- Thử throw một exception giả ngay SAU order.MarkAsPaid() nhưng TRƯỚC khi Handler gọi SaveChangesAsync — xác nhận KHÔNG có dòng Outbox nào được ghi (vì transaction chưa từng commit). Đây là bằng chứng trực quan nhất cho tính atomic, nên demo trực tiếp trên máy chứ không chỉ giải thích bằng lời.

## **Bài tập thực hành**

> **✏️ Thực hành:** Thêm cơ chế đếm số lần retry cho OutboxMessage, chuẩn bị cho bài 2.7 khi Hangfire cần biết lúc nào nên dừng thử lại (dead-letter).

Input: thêm property RetryCount (int, mặc định 0, private set) vào OutboxMessage.

Expected output: MarkAsFailed(string error) mỗi lần gọi sẽ tăng RetryCount lên 1 và ghi đè Error; thêm 1 câu SQL đếm số OutboxMessage đang tồn đọng (processed_on_utc IS NULL) để dùng làm chỉ số giám sát hàng đợi Outbox.

Hint: đừng reset RetryCount về 0 khi MarkAsFailed được gọi lần thứ 2, 3... — RetryCount phải cộng dồn thì bài 2.7 mới so sánh được với một ngưỡng tối đa (ví dụ 5 lần) để quyết định dừng thử.

Solution (tham khảo sau khi tự làm):

```csharp
public int RetryCount { get; private set; }
 
public void MarkAsFailed(string error)
{
    Error = error;
    RetryCount++;
}
 
// SQL đếm hàng đợi tồn đọng:
// SELECT COUNT(*) FROM outbox_messages
// WHERE processed_on_utc IS NULL;
```

## **Tổng kết**

> **✅ Tóm tắt:** Outbox Pattern giải quyết đúng vấn đề dual write đã gieo sẵn từ bài 2.2: thay vì publish domain event ngay lập tức sau SaveChangesAsync (có điểm hở nếu crash), event được serialize thành OutboxMessage và ghi vào CÙNG transaction với thay đổi nghiệp vụ, nhờ EF Core gom mọi thay đổi được track vào một lệnh SaveChanges duy nhất. Việc phát event thật được tách sang một tiến trình nền xử lý sau (eventual consistency). Toàn bộ thay đổi chỉ nằm ở một chỗ — AppDbContext.SaveChangesAsync — Handler ở bài 2.2 thậm chí còn đơn giản đi vì không cần gọi dispatcher thủ công nữa.
