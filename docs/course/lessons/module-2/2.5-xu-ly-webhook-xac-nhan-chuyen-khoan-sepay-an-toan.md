## Nội dung chính

### Bước 1 — Ôn lại bối cảnh từ bài 2.4

Ở bài 2.4, InitiatePaymentCommand đã tạo mã thanh toán (PaymentCode) gắn vào Order, sinh mã QR VietQR để học viên chuyển khoản, và Order đang ở trạng thái Pending. Bài này xử lý bước cuối cùng của luồng thanh toán: khi tiền thực sự về tài khoản ngân hàng, SePay gọi webhook (server-to-server, không phải người dùng bấm nút) báo cho hệ thống biết — và đây mới là nguồn sự thật duy nhất để xác nhận đơn hàng đã thanh toán, không phải một API do frontend gọi.

> **📘 Ghi chú giảng viên:** *Tôi hay nhấn mạnh điểm này ngay đầu bài: khác với OAuth callback hay Return URL của cổng thanh toán (chỉ để hiển thị cho người dùng), webhook không đi qua trình duyệt của học viên — nó là request từ server SePay gọi thẳng vào server TEDU Market. Vì vậy không thể tin tưởng nó chỉ vì request tới đúng endpoint; phải xác thực chữ ký.*

### Bước 2 — Payload thật của SePay Webhook

SePay POST một JSON body tới endpoint đã đăng ký mỗi khi có giao dịch khớp tài khoản, đúng cấu trúc theo tài liệu chính thức:

```
// Payload thật SePay gửi (POST JSON)
{
  "id": 92704,
  "gateway": "Vietcombank",
  "transactionDate": "2026-09-17 11:08:33",
  "accountNumber": "1017588888",
  "code": "SEVN63DC8E5C",
  "content": "SEVN63DC8E5C chuyen tien",
  "transferType": "in",
  "transferAmount": 5000000,
  "referenceCode": "FT24012345678"

```

Map sang record trong Application layer — đây là DTO nhận từ bên ngoài, không phải Entity của Domain:

```csharp
// TeduMarket.Application/Payments/ConfirmPayment/SePayWebhookPayload.cs
namespace TeduMarket.Application.Payments.ConfirmPayment;

    long Id,
```

3 trường quan trọng nhất với TEDU Market: id (định danh duy nhất của giao dịch — dùng cho idempotency), code (chính là PaymentCode đã gắn vào Order ở bài 2.4), transferAmount (đối chiếu với FinalAmount của Order). transferType phải là "in" (tiền vào) — SePay cũng báo cả giao dịch tiền ra nếu tài khoản có phát sinh, không lọc sẵn theo chiều.

### Bước 3 — Xác thực chữ ký HMAC-SHA256

Theo tài liệu SePay, cách ký request: lấy timestamp Unix hiện tại, nối chuỗi {timestamp}.{raw_body}, tính HMAC-SHA256 với Secret Key, gửi 2 header: X-SePay-Signature: sha256={hex_hash} và X-SePay-Timestamp: {timestamp}. Điểm quan trọng nhất: SePay ký trên raw body — nếu đọc qua model binding JSON rồi serialize lại để so sánh, chữ ký sẽ lệch (khác thứ tự key, khác cách escape Unicode). Vì vậy endpoint phải tự đọc raw bytes trước khi parse JSON.

```csharp
// TeduMarket.Infrastructure/Payments/SePaySignatureVerifier.cs
namespace TeduMarket.Infrastructure.Payments;
 
public sealed class SePaySignatureVerifier(
    IOptions<SePayOptions> options,
    TimeProvider timeProvider)
{
    private const int MaxClockDriftSeconds = 300; // 5 phut, dung SePay khuyen nghi
 
    public bool IsValid(string rawBody, string? signatureHeader, string? timestampHeader)
    {
        if (string.IsNullOrEmpty(signatureHeader) || string.IsNullOrEmpty(timestampHeader))
            return false;
 
        if (!long.TryParse(timestampHeader, out var timestamp))
            return false;
 
        // Chong replay attack: tu choi neu timestamp lech qua 5 phut
        var nowUnix = timeProvider.GetUtcNow().ToUnixTimeSeconds();
        if (Math.Abs(nowUnix - timestamp) > MaxClockDriftSeconds)
            return false;
 
        var dataToSign = $"{timestamp}.{rawBody}";
        var keyBytes = Encoding.UTF8.GetBytes(options.Value.WebhookSecret);
        var dataBytes = Encoding.UTF8.GetBytes(dataToSign);
        var computedHash = HMACSHA256.HashData(keyBytes, dataBytes);
        var expectedSignature = $"sha256={Convert.ToHexStringLower(computedHash)}";
 
        // So sanh constant-time, khong dung == hay SequenceEqual
        return CryptographicOperations.FixedTimeEquals(
            Encoding.UTF8.GetBytes(expectedSignature),
            Encoding.UTF8.GetBytes(signatureHeader));
    }
}
```

> **📘 Ghi chú giảng viên:** *HMACSHA256.HashData(key, data) và HMACSHA512.HashData đã dùng ở bài 2.4 là cùng 1 họ API static "one-shot" của .NET — không cần new HMACSHA256(key).ComputeHash(...) rồi Dispose kiểu cũ. CryptographicOperations.FixedTimeEquals là điểm hay bị bỏ qua nhất: so sánh chuỗi bằng == hoặc SequenceEqual bị short-circuit ngay ký tự đầu sai, kẻ tấn công có thể đo thời gian phản hồi để dò từng byte chữ ký (timing attack). Tôi hay hỏi ngược lớp: 'Tại sao không so sánh 2 chuỗi bằng dấu == như bình thường?' để học viên tự bật ra lý do.*

> **⚠️ Lưu ý:** Anti-replay 5 phút chỉ có tác dụng nếu đồng hồ server đồng bộ NTP. Nếu server lệch giờ, mọi webhook hợp lệ sẽ bị từ chối oan — đây là lỗi thực tế học viên hay gặp khi mới deploy, cần nhắc trong bài Go-live (9.8).

### Bước 4 — Idempotency theo transaction id

SePay có cơ chế retry: nếu endpoint không phản hồi 200 với {"success": true} trong 30 giây, SePay sẽ gọi lại — nghĩa là cùng 1 giao dịch (cùng id) có thể đến endpoint nhiều lần. Nếu xử lý lại từ đầu mỗi lần, rủi ro lớn nhất là double-processing khi bài 2.7 (Hangfire) tạo Enrollment — học viên trả tiền 1 lần nhưng hệ thống ghi nhận 2 lần. Cách chặn triệt để nhất: dùng chính id của SePay làm khóa duy nhất trong 1 bảng log riêng, insert trước khi xử lý.

```csharp
// TeduMarket.Domain/Payments/SePayTransactionLog.cs
namespace TeduMarket.Domain.Payments;
 
public sealed class SePayTransactionLog
{
    public long SePayTransactionId { get; private set; } // = payload.Id, la Primary Key
    public string PaymentCode { get; private set; } = default!;
    public DateTimeOffset ReceivedAtUtc { get; private set; }
 
    private SePayTransactionLog() { }
 
    public static SePayTransactionLog Create(
        long sePayTransactionId, string paymentCode, DateTimeOffset receivedAtUtc)
        => new()
        {
            SePayTransactionId = sePayTransactionId,
            PaymentCode = paymentCode,
            ReceivedAtUtc = receivedAtUtc,
        };
}
```

Handler cố gắng insert bản ghi này trước tiên. PostgreSQL sẽ từ chối insert thứ 2 với cùng khóa chính (lỗi 23505 — unique_violation) nếu 2 request trùng id đến gần như đồng thời — đây là cách chặn idempotency đúng ở tầng DB, không phải kiểm tra tồn tại rồi mới insert (cách đó vẫn có khe hở race condition giữa 2 bước).

```csharp
// ConfirmPaymentCommandHandler.cs — phần idempotency
try
{
    dbContext.Add(SePayTransactionLog.Create(
        request.SePayTransactionId, request.Code, timeProvider.GetUtcNow()));
    await dbContext.SaveChangesAsync(cancellationToken);
}
catch (DbUpdateException ex) when (
    ex.InnerException is PostgresException pgEx
    && pgEx.SqlState == PostgresErrorCodes.UniqueViolation)
{
    // Da xu ly giao dich nay roi (SePay goi lai do retry) -> coi nhu thanh cong, khong lam gi them
    logger.LogInformation(
        "SePay webhook {TransactionId} da duoc xu ly truoc do, bo qua",
        request.SePayTransactionId);
    return new ConfirmPaymentResult(ConfirmPaymentOutcome.AlreadyProcessed);
}
```

> **📘 Ghi chú giảng viên:** *Chỗ này học viên hay hỏi: 'Sao không SELECT kiểm tra Id đã tồn tại chưa trước, đỡ phải bắt exception?' — tôi trả lời bằng đúng kịch bản: SePay retry rất nhanh (vài giây), 2 worker/instance của Api có thể nhận đúng lúc 2 request gần như song song. Nếu check-rồi-insert, cả 2 đều SELECT ra 'chưa có' trước khi cái nào insert xong — race condition kinh điển. Bắt lỗi unique constraint là cách duy nhất đảm bảo đúng ở mức DB, không phụ thuộc thứ tự luồng.*

### Bước 5 — UPDATE atomic Pending → Paid

Sau khi chắc chắn đây là lần xử lý đầu tiên cho giao dịch này, bước tiếp theo là chuyển Order sang Paid — nhưng phải khớp đúng cả PaymentCode lẫn số tiền, và chỉ chuyển nếu Order đang ở Pending. Thay vì load Order qua Repository rồi gọi method trên Aggregate như các Command trước giờ, bài này dùng ExecuteUpdateAsync của EF Core: gửi thẳng 1 câu UPDATE có điều kiện xuống Postgres, không qua Change Tracker.

```csharp
// TeduMarket.Infrastructure/Orders/OrderPaymentRepository.cs
namespace TeduMarket.Infrastructure.Orders;
 
public sealed class OrderPaymentRepository(AppDbContext dbContext) : IOrderPaymentRepository
{
    public async Task<bool> TryMarkAsPaidAsync(
        string paymentCode, decimal amount, DateTimeOffset paidAtUtc,
        CancellationToken cancellationToken)
    {
        var affectedRows = await dbContext.Orders
            .Where(o => o.PaymentCode == paymentCode
                     && o.Status == OrderStatus.Pending
                     && o.FinalAmount == amount)
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(o => o.Status, OrderStatus.Paid)
                .SetProperty(o => o.PaidAtUtc, paidAtUtc),
                cancellationToken);
 
        return affectedRows == 1;
    }
}
```

WHERE PaymentCode == code && Status == Pending && FinalAmount == amount chính là invariant "chỉ chuyển Paid từ Pending, đúng đơn, đúng tiền" — nhưng thay vì nằm trong method Order.MarkAsPaid() của Aggregate như thường lệ, nó được đẩy xuống câu SQL. PostgreSQL đảm bảo UPDATE này atomic: 2 request chạy song song, chỉ 1 request thấy affectedRows == 1, request còn lại thấy 0 (vì dòng đã không còn ở Status = Pending nữa).

> **⚠️ Lưu ý:** ExecuteUpdateAsync bỏ qua hoàn toàn Change Tracker và mọi Domain Event gắn trên Aggregate — đây là đánh đổi có chủ đích, không phải sơ suất. Order.MarkAsPaid() (định nghĩa bên dưới) vẫn tồn tại đúng chuẩn Aggregate đã dạy từ bài 1.3, nhưng KHÔNG được gọi trong Handler này.

```csharp
// TeduMarket.Domain/Orders/Order.cs (bo sung method, chua goi trong bai nay)
public void MarkAsPaid(DateTimeOffset paidAtUtc)
{
    if (Status != OrderStatus.Pending)
        throw new OrderInvalidStatusException(Id, Status, OrderStatus.Paid);
 
    Status = OrderStatus.Paid;
    PaidAtUtc = paidAtUtc;
    AddDomainEvent(new OrderPaidEvent(Id, FinalAmount, paidAtUtc));
}
```

> **📘 Ghi chú giảng viên:** *Đây là chỗ tôi luôn dừng lại giải thích kỹ nhất bài, vì nó trái ngược với mọi Command trước giờ trong khóa (Module 0 tới giờ luôn đi Load Aggregate → gọi method → Save). Câu hỏi đặt ra cho lớp: nếu đi qua đường Aggregate bình thường (load Order, gọi order.MarkAsPaid(), SaveChangesAsync), 2 webhook trùng lúc có an toàn không? Câu trả lời: KHÔNG — cả 2 request đều load cùng giá trị Status = Pending trước khi request nào Save xong, đây là race condition read-modify-write kinh điển. Muốn an toàn theo đường Aggregate, phải có RowVersion (optimistic concurrency) — và đó chính xác là nội dung bài 2.9. Ở bài 2.5 này, ta chọn giải pháp atomic UPDATE ở tầng DB để không phải đợi tới 2.9 mới có transition an toàn. Hệ quả: OrderPaidEvent định nghĩa sẵn trên Aggregate nhưng CHƯA được raise ở bài này — bài 2.6 (Outbox Pattern) sẽ giải quyết chính xác vấn đề 'sau khi atomic UPDATE xác nhận affectedRows == 1, làm sao ghi Outbox message trong cùng transaction để không mất sự kiện nếu server crash'.*

### Bước 6 — ConfirmPaymentCommand & Handler

```csharp
// TeduMarket.Application/Payments/ConfirmPayment/ConfirmPaymentCommand.cs
public sealed record ConfirmPaymentCommand(
    long SePayTransactionId,
    string Code,
    decimal Amount,
    string TransferType)
    : IRequest<ConfirmPaymentResult>;
 
public enum ConfirmPaymentOutcome { Processed, AlreadyProcessed, NoMatchingOrder }
public sealed record ConfirmPaymentResult(ConfirmPaymentOutcome Outcome);
```

```csharp
// ConfirmPaymentCommandValidator.cs — dat ten dung quy uoc muc 7 outline
public sealed class ConfirmPaymentCommandValidator : AbstractValidator<ConfirmPaymentCommand>
{
    public ConfirmPaymentCommandValidator()
    {
        RuleFor(x => x.SePayTransactionId).GreaterThan(0);
        RuleFor(x => x.Code).NotEmpty();
        RuleFor(x => x.Amount).GreaterThan(0);
        RuleFor(x => x.TransferType).Equal("in");
    }
}
```

```csharp
// ConfirmPaymentCommandHandler.cs
public sealed class ConfirmPaymentCommandHandler(
    AppDbContext dbContext,
    IOrderPaymentRepository orderPaymentRepository,
    TimeProvider timeProvider,
    ILogger<ConfirmPaymentCommandHandler> logger)
    : IRequestHandler<ConfirmPaymentCommand, ConfirmPaymentResult>
{
    public async Task<ConfirmPaymentResult> Handle(
        ConfirmPaymentCommand request, CancellationToken cancellationToken)
    {
        var receivedAt = timeProvider.GetUtcNow();
 
        // Buoc 1: idempotency - insert log truoc, bat loi unique neu trung
        try
        {
            dbContext.Add(SePayTransactionLog.Create(
                request.SePayTransactionId, request.Code, receivedAt));
            await dbContext.SaveChangesAsync(cancellationToken);
        }
        catch (DbUpdateException ex) when (
            ex.InnerException is PostgresException pgEx
            && pgEx.SqlState == PostgresErrorCodes.UniqueViolation)
        {
            logger.LogInformation(
                "SePay webhook {TransactionId} da xu ly truoc do, bo qua",
                request.SePayTransactionId);
            return new ConfirmPaymentResult(ConfirmPaymentOutcome.AlreadyProcessed);
        }
 
        // Buoc 2: UPDATE atomic Pending -> Paid, khop ca code lan so tien
        var paid = await orderPaymentRepository.TryMarkAsPaidAsync(
            request.Code, request.Amount, receivedAt, cancellationToken);
 
        if (!paid)
        {
            // Khong khop Order Pending nao - co the sai ma, sai tien, hoac da Paid tu truoc
            logger.LogWarning(
                "Webhook {TransactionId}: khong khop Order Pending nao (code {Code})",
                request.SePayTransactionId, request.Code, request.Amount);
            return new ConfirmPaymentResult(ConfirmPaymentOutcome.NoMatchingOrder);
        }
 
        logger.LogInformation(
            "Order voi PaymentCode {Code} da chuyen sang Paid tu webhook {TransactionId}",
            request.Code, request.SePayTransactionId);
        return new ConfirmPaymentResult(ConfirmPaymentOutcome.Processed);
    }
}
```

> **📘 Ghi chú giảng viên:** *Handler trả về Processed / AlreadyProcessed / NoMatchingOrder thay vì throw exception cho 2 trường hợp sau — vì đây không phải lỗi hệ thống, mà là kết quả nghiệp vụ hợp lệ. Điểm mấu chốt tôi nhấn ở bước 7: dù kết quả là gì trong 3 trường hợp trên, endpoint vẫn trả HTTP 200 {"success": true} — kể cả khi NoMatchingOrder, vì retry của SePay sẽ không tự sửa được một lệch dữ liệu, trả lỗi 4xx/5xx chỉ khiến SePay tiếp tục gọi lại vô ích trong khi ta đã ghi log để tự điều tra.*

### Bước 7 — Minimal API Endpoint: đọc raw body, verify, dispatch

Endpoint không dùng model binding JSON tự động như các Command khác trong khóa, vì cần raw body nguyên vẹn để verify chữ ký trước khi parse:

```csharp
// TeduMarket.Api/Endpoints/PaymentWebhookEndpoints.cs
app.MapPost("/api/v1/webhooks/sepay", async (
    HttpContext httpContext,
    ISender sender,
    SePaySignatureVerifier signatureVerifier,
    CancellationToken cancellationToken) =>
{
    using var reader = new StreamReader(httpContext.Request.Body);
    var rawBody = await reader.ReadToEndAsync(cancellationToken);
 
    var signature = httpContext.Request.Headers["X-SePay-Signature"].ToString();
    var timestamp = httpContext.Request.Headers["X-SePay-Timestamp"].ToString();
 
    if (!signatureVerifier.IsValid(rawBody, signature, timestamp))
    {
        return Results.Unauthorized();
    }
 
    var payload = JsonSerializer.Deserialize<SePayWebhookPayload>(
        rawBody, SePayJsonOptions.Default);
 
    if (payload is null || payload.TransferType != "in")
    {
        return Results.Ok(new { success = true }); // bo qua giao dich khong lien quan
    }
 
    await sender.Send(new ConfirmPaymentCommand(
        payload.Id, payload.Code, payload.TransferAmount, payload.TransferType),
        cancellationToken);
 
    // Luon tra 200 + success:true de SePay khong retry vo han
    return Results.Ok(new { success = true });
})
.WithName("ConfirmSePayWebhook")
.ExcludeFromDescription(); // webhook noi bo, khong len Scalar/OpenAPI cong khai
```

> **⚠️ Lưu ý:** Chữ ký sai (Unauthorized) là trường hợp DUY NHẤT không trả success:true — vì đó là dấu hiệu request giả mạo, không phải giao dịch hợp lệ cần dừng retry. Mọi kết quả nghiệp vụ khác (kể cả không khớp Order) đều trả 200 theo đúng khuyến nghị của SePay, để tránh vòng lặp retry vô nghĩa.

### Bước 8 — Test webhook khi chưa có SePay thật

Trước khi cắm SePay sandbox thật, giả lập request bằng script tự ký để kiểm tra logic verify hoạt động đúng — tự tính chữ ký giống hệt cách SePay tính, gửi bằng curl:

```bash
# Giả lập webhook SePay bằng curl (thay SECRET và BODY cho đúng)
TIMESTAMP=$(date +%s)
BODY='{"id":92704,"gateway":"Vietcombank","transactionDate":"2026-09-17 11:08:33",\
"accountNumber":"1017588888","code":"SEVN63DC8E5C","content":"SEVN63DC8E5C chuyen tien",\
"transferType":"in","transferAmount":500000,"referenceCode":"FT24012345678"}'
SIGNATURE=$(echo -n "${TIMESTAMP}.${BODY}" | openssl dgst -sha256 -hmac "$SECRET" | cut -d" " -f2)
 
curl -X POST http://localhost:5000/api/v1/webhooks/sepay \
  -H "Content-Type: application/json" \
  -H "X-SePay-Signature: sha256=${SIGNATURE}" \
  -H "X-SePay-Timestamp: ${TIMESTAMP}" \
  -d "$BODY"
```

Gọi lại đúng request này lần thứ 2 (copy nguyên lệnh curl, chạy lại) để chứng minh idempotency: lần 1 Order chuyển Paid, lần 2 log ra AlreadyProcessed, Order không bị xử lý lại. Khi ráp với SePay thật, dùng ngrok để lộ endpoint local ra Internet và trỏ Webhook URL trong cấu hình SePay về địa chỉ ngrok.

## Tổng kết

> **✅ Tóm tắt:** Webhook SePay được xác thực bằng HMAC-SHA256 trên raw body (không phải body đã parse lại), theo công thức {timestamp}.{raw_body}, so sánh bằng CryptographicOperations.FixedTimeEquals để chống timing attack, và từ chối nếu timestamp lệch quá 5 phút để chống replay. Idempotency chặn ở tầng DB bằng unique constraint trên chính id giao dịch của SePay — bắt lỗi 23505 thay vì check-rồi-insert. Order chuyển Pending → Paid bằng 1 UPDATE atomic (ExecuteUpdateAsync) khớp đúng PaymentCode và số tiền, đánh đổi có chủ đích: bỏ qua đường Aggregate thông thường để đảm bảo an toàn concurrency ngay từ bây giờ, thay vì đợi RowVersion ở bài 2.9.

| **Khía cạnh** | **Cách làm ở bài 2.5** | **Vì sao** |
|---|---|---|
| Xác thực nguồn gửi | HMAC-SHA256 trên raw body | Chống giả mạo, đảm bảo body không bị sửa trên đường truyền |
| Chặn xử lý trùng | Unique constraint + bắt lỗi 23505 | An toàn dưới concurrency thật, không có khe hở race condition |
| Chuyển trạng thái Order | ExecuteUpdateAsync có điều kiện WHERE | Atomic ở tầng DB, chưa cần RowVersion (dành cho bài 2.9) |
| OrderPaidEvent | Đã định nghĩa, CHƯA raise trong Handler | Cần ghi Outbox cùng transaction — nội dung bài 2.6 |

### Bước tiếp theo

Bài 2.6 — Outbox Pattern: giải quyết đúng vấn đề vừa đặt ra — làm sao ghi OrderPaidEvent vào bảng Outbox trong CÙNG transaction với UPDATE atomic vừa viết, để nếu server crash ngay sau khi Order chuyển Paid thì sự kiện vẫn không bị mất, chuẩn bị cho bài 2.7 (Hangfire) tạo Enrollment tự động.
