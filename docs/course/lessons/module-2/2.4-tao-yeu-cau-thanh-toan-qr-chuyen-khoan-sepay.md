## **Nội dung chính**

### **Phần 1 — Vì sao chuyển khoản ngân hàng + webhook, không dùng cổng thanh toán online**

*Thời lượng: 20 phút | Loại: Lý thuyết*

TEDU Market cần một cách để chuyển khách hàng từ "đã có Order ở trạng thái Pending" (bài 2.2, sau khi áp coupon ở bài 2.3) sang "đã thanh toán thành công". Thay vì tích hợp một cổng thanh toán online (VNPay, Momo, ZaloPay...) — vốn mất phí % trên mỗi giao dịch và quy trình đăng ký merchant khá lâu — khóa học này chọn hướng đơn giản và phổ biến với các nền tảng quy mô vừa và nhỏ tại Việt Nam: khách hàng chuyển khoản trực tiếp vào tài khoản ngân hàng của TEDU, một dịch vụ trung gian (SePay) theo dõi biến động số dư và báo lại cho hệ thống qua webhook.

### **1.1. Mô hình hoạt động**

- Bước 1: Khách hàng bấm "Thanh toán" cho Order đang Pending. Backend sinh 1 mã thanh toán (payment code) duy nhất gắn với Order, trả về kèm ảnh QR chuyển khoản.
- Bước 2: Khách hàng mở app ngân hàng bất kỳ, quét mã QR — thông tin số tài khoản, ngân hàng, số tiền, nội dung chuyển khoản được điền sẵn theo chuẩn VietQR, khách chỉ cần xác nhận.
- Bước 3: Tiền về thẳng tài khoản ngân hàng thật của TEDU (không qua trung gian giữ tiền).
- Bước 4: SePay phát hiện giao dịch mới trên tài khoản đã liên kết, đối chiếu nội dung chuyển khoản với mẫu mã thanh toán đã cấu hình, rồi gửi HTTP POST (webhook) đến server TEDU Market.
- Bước 5: Server TEDU Market xác thực webhook, khớp mã thanh toán với Order, cập nhật Order sang Paid — học chi tiết ở bài 2.5.

> **📘 Ghi chú giảng viên:** *Tôi hay so sánh trực tiếp với luồng VNPay để học viên thấy khác biệt: VNPay có bước redirect trình duyệt khách hàng sang trang thanh toán riêng và 2 kênh Return URL/IPN song song. Ở đây không có redirect — khách hàng chuyển khoản ngay trong app ngân hàng của họ, và chỉ có MỘT kênh xác nhận duy nhất: webhook SePay. Đơn giản hơn, nhưng đổi lại TEDU phải tự làm UI hiển thị QR và tự poll trạng thái, thay vì được cổng thanh toán lo phần giao diện thanh toán.*

### **1.2. Mã thanh toán (payment code) — cách hệ thống nhận diện đúng đơn hàng**

SePay không biết gì về khái niệm "Order" của TEDU Market. Nó chỉ đọc nội dung chuyển khoản do khách hàng gõ hoặc do QR điền sẵn, rồi so khớp với các mẫu tiền tố đã cấu hình tại my.sepay.vn (Công ty → Cấu hình chung → Cấu trúc mã thanh toán). Ví dụ: tiền tố TEDU, hậu tố 8–12 ký tự Số và chữ → nội dung "TEDU3F9A21B7C4 thanh toan khoa hoc" sẽ được SePay tách ra field code = "TEDU3F9A21B7C4" và gắn vào payload webhook.

- Mã thanh toán phải duy nhất và khó đoán — sinh từ OrderId, không dùng số tăng dần (tránh khách hàng đoán được mã đơn khác, hoặc bên thứ ba giả mạo nội dung chuyển khoản để "claim" đơn của người khác).
- Mã thanh toán được lưu lại trên chính Order để bài 2.5 tra cứu ngược khi webhook gọi về.

### **1.3. VietQR — chuẩn QR ngân hàng dùng chung**

VietQR là chuẩn QR liên ngân hàng tại Việt Nam: một mã QR mã hoá sẵn số tài khoản, ngân hàng thụ hưởng, số tiền và nội dung chuyển khoản, quét được bằng app của hầu hết ngân hàng và ví điện tử mà không cần khách hàng gõ tay. TEDU Market dùng endpoint ảnh QR công khai:

```
https://vietqr.app/img?acc={SO_TAI_KHOAN}&bank={NGAN_HANG}&amount={SO_TIEN}&des={NOI_DUNG}
 
// Ví dụ:
https://vietqr.app/img?acc=0010000000355&bank=Vietcombank&amount=199000&des=TEDU3F9A21B7C4
```

des (nội dung chuyển khoản) chính là mã thanh toán ở mục 1.2 — đây là mắt xích nối giữa QR khách hàng quét và webhook SePay sẽ nhận ở bài 2.5.

> **📘 Ghi chú giảng viên:** *Nhấn mạnh với học viên: bài này CHỈ tạo yêu cầu thanh toán (Order vẫn ở trạng thái Pending) và hiển thị QR. Chưa có bước nào ở bài này khiến Order tự chuyển sang Paid — kể cả khi học viên chuyển khoản thật, hệ thống chỉ nhận ra khi đã xử lý webhook ở bài 2.5. Tránh gây hiểu lầm là bài 2.4 đã hoàn chỉnh luồng thanh toán.*

### **Bước 3 — IPaymentQrService: tách interface ở Application, cài đặt ở Infrastructure**

Đúng nguyên tắc Dependency Inversion đã học ở bài 0.2/0.6: Application chỉ biết "tôi cần build được URL ảnh QR chuyển khoản", không biết gì về VietQR cụ thể.

```csharp
// TeduMarket.Application/Common/Interfaces/IPaymentQrService.cs
namespace TeduMarket.Application.Common.Interfaces;
 
public interface IPaymentQrService
{
    string BuildQrImageUrl(PaymentQrRequest request);
}
 
public sealed record PaymentQrRequest(
    string PaymentCode,
    decimal Amount,
    string OrderInfo);
```

VietQrService.cs (TeduMarket.Infrastructure/Payments/):

```csharp
using Microsoft.Extensions.Options;
 
namespace TeduMarket.Infrastructure.Payments;
 
public sealed class VietQrService(IOptions<SePayOptions> options) : IPaymentQrService
{
    private readonly SePayOptions _options = options.Value;
 
    public string BuildQrImageUrl(PaymentQrRequest request)
    {
        var query = new Dictionary<string, string>
        {
            ["acc"] = _options.BankAccountNumber,
            ["bank"] = _options.BankShortName,
            // vietqr.app không nhận phần thập phân cho VND
            ["amount"] = ((long)request.Amount).ToString(),
            ["des"] = request.PaymentCode,
        };
 
        var queryString = string.Join('&',
            query.Select(kv => $"{kv.Key}={Uri.EscapeDataString(kv.Value)}"));
 
        return $"https://vietqr.app/img?{queryString}";
    }
}
```

### **Bước 4 — Mở rộng Order Aggregate**

Order đã có ở bài 2.1/2.2 với OrderStatus (Pending/Paid/Cancelled) và FinalAmount (bài 2.3 sau khi áp coupon). Thêm khả năng ghi nhận mã thanh toán — đi qua Aggregate, không update thẳng cột PaymentCode ngoài luồng, đúng nguyên tắc đã nhấn mạnh từ bài 1.3:

```csharp
// TeduMarket.Domain/Orders/Order.cs (bổ sung)
public sealed class Order // ... phần khai báo đã có từ bài 2.1/2.2
{
    public string? PaymentCode { get; private set; }
 
    public void InitiatePayment(string paymentCode)
    {
        if (Status != OrderStatus.Pending)
        {
            throw new OrderInvalidStatusException(
                $"Order {Id} đang ở trạng thái {Status}, không thể khởi tạo thanh toán.");
        }
 
        PaymentCode = paymentCode;
    }
}
// TeduMarket.Domain/Orders/OrderInvalidStatusException.cs
public sealed class OrderInvalidStatusException(string message) : Exception(message);
```

EF Core Fluent Configuration — thêm cấu hình cột PaymentCode và index UNIQUE (mã thanh toán không được trùng, vì đây chính là khoá để webhook bài 2.5 tra ngược Order) vào OrderConfiguration.cs đã có từ bài 2.1:

```csharp
builder.Property(o => o.PaymentCode).HasMaxLength(20);
builder.HasIndex(o => o.PaymentCode).IsUnique().HasFilter("[PaymentCode] IS NOT NULL");
```

> **📘 Ghi chú giảng viên:** *Index UNIQUE có điều kiện lọc IS NOT NULL vì phần lớn Order (trước khi khởi tạo thanh toán) có PaymentCode = null — Postgres cho phép nhiều dòng NULL cùng tồn tại trong unique index, nhưng học viên hay quên thêm filter này khi mới học, dẫn đến migration lỗi khi test với SQL Server thay vì Postgres.*

Handler — dùng lại IOrderRepository đã có từ bài 2.1/2.2, gọi vào IPaymentQrService vừa viết ở Bước 3. Mã thanh toán sinh từ tiền tố cấu hình + phần hex của chính OrderId (không tăng dần, không đoán được), đúng khuyến nghị bảo mật của SePay ở mục 1.2:

```csharp
// InitiatePaymentCommandHandler.cs
public sealed class InitiatePaymentCommandHandler(
    IOrderRepository orderRepository,
    IPaymentQrService paymentQrService,
    IOptions<SePayOptions> sePayOptions)
    : IRequestHandler<InitiatePaymentCommand, InitiatePaymentResult>
{
    public async Task<InitiatePaymentResult> Handle(
        InitiatePaymentCommand request, CancellationToken cancellationToken)
    {
        var order = await orderRepository.GetByIdAsync(request.OrderId, cancellationToken)
            ?? throw new OrderNotFoundException(request.OrderId);
 
        var prefix = sePayOptions.Value.PaymentCodePrefix;
        var paymentCode = $"{prefix}{order.Id:N}"[..(prefix.Length + 12)].ToUpperInvariant();
 
        order.InitiatePayment(paymentCode);
        await orderRepository.UpdateAsync(order, cancellationToken);
 
        var qrImageUrl = paymentQrService.BuildQrImageUrl(new PaymentQrRequest(
            PaymentCode: paymentCode,
            Amount: order.FinalAmount,
            OrderInfo: $"Thanh toan khoa hoc - Order {order.Id:N}"));
 
        return new InitiatePaymentResult(
            paymentCode, qrImageUrl,
            sePayOptions.Value.BankAccountNumber,
            sePayOptions.Value.BankShortName,
            order.FinalAmount);
    }
}
```

> **📘 Ghi chú giảng viên:** *OrderNotFoundException đặt tên đúng quy ước mục 7 outline, tương tự CourseNotFoundException đã viết ở Module 1. Nếu học viên chưa có exception này cho Order thì đây là lúc thêm, dùng lại đúng mẫu ProblemDetails mapping đã dạy ở bài 0.9.*

### **Bước 6 — Query trạng thái đơn hàng cho FE polling**

Không có "Return URL" ở hướng này — FE cần một endpoint để tự hỏi "đơn này đã Paid chưa" mỗi vài giây trong lúc khách hàng đang chuyển khoản. Theo đúng CQRS đã học: đây là thao tác đọc, dùng Dapper ở Query side (bài 0.8), không tái sử dụng Aggregate của Command side:

```csharp
// TeduMarket.Application/Payments/GetOrderPaymentStatus/GetOrderPaymentStatusQuery.cs
public sealed record GetOrderPaymentStatusQuery(Guid OrderId)
    : IRequest<OrderPaymentStatusDto>;
 
public sealed record OrderPaymentStatusDto(string Status, string? PaymentCode);
// GetOrderPaymentStatusQueryHandler.cs
public sealed class GetOrderPaymentStatusQueryHandler(IDbConnection db)
    : IRequestHandler<GetOrderPaymentStatusQuery, OrderPaymentStatusDto>
{
    public Task<OrderPaymentStatusDto> Handle(
        GetOrderPaymentStatusQuery request, CancellationToken cancellationToken)
    {
        const string sql = """
            SELECT status AS "Status", payment_code AS "PaymentCode"
            FROM orders
            WHERE id = @OrderId
            """;
 
        return db.QuerySingleAsync<OrderPaymentStatusDto>(sql, new { request.OrderId });
    }
}
```

### **Bước 7 — Endpoint**

```csharp
// TeduMarket.Api/Endpoints/PaymentEndpoints.cs
public static class PaymentEndpoints
{
    public static IEndpointRouteBuilder MapPaymentEndpoints(this IEndpointRouteBuilder app)
    {
        var group = app.MapGroup("/api/v1/payments").WithTags("Payments");
 
        group.MapPost("/initiate", async (
            InitiatePaymentRequest body, ISender sender, CancellationToken ct) =>
        {
            var result = await sender.Send(new InitiatePaymentCommand(body.OrderId), ct);
            return Results.Ok(result);
        })
        .WithName("InitiatePayment")
        .Produces<InitiatePaymentResult>(StatusCodes.Status200OK);
 
        group.MapGet("/{orderId:guid}/status", async (
            Guid orderId, ISender sender, CancellationToken ct) =>
        {
            var result = await sender.Send(new GetOrderPaymentStatusQuery(orderId), ct);
            return Results.Ok(result);
        })
        .WithName("GetOrderPaymentStatus");
 
        return app;
    }
}
 
public sealed record InitiatePaymentRequest(Guid OrderId);
```

> **📘 Ghi chú giảng viên:** *Ở bài 7.5 (Next.js Student site), FE sẽ gọi 2 endpoint này y hệt: POST /initiate để lấy QR, rồi setInterval gọi GET /status mỗi 3 giây — đúng mẫu polling mà SePay khuyến nghị cho UX thanh toán đơn giản. Nói trước với học viên để họ hiểu tại sao endpoint status tách riêng khỏi initiate.*

## **Bài tập thực hành**

> **✏️ Thực hành:** Thêm cơ chế hết hạn cho yêu cầu thanh toán: một Order chỉ được phép giữ mã thanh toán trong 15 phút, quá hạn thì FE phải gọi lại /initiate để lấy mã QR mới.

Input: thêm property PaymentRequestedAt (DateTimeOffset?) vào Order, set trong InitiatePayment(). OrderPaymentStatusDto thêm field ExpiresAt (tính từ PaymentRequestedAt + 15 phút).

Expected output: GetOrderPaymentStatusQuery trả thêm ExpiresAt; FE (giả lập bằng Postman) có thể tự tính còn bao nhiêu giây trước khi hết hạn, giống ví dụ đếm ngược trong tài liệu SePay.

Hint: đừng chặn việc gọi lại /initiate nhiều lần cho cùng 1 Order Pending — mỗi lần gọi lại nên sinh cùng 1 paymentCode (không đổi mã giữa chừng, tránh SePay nhận về 2 mã khác nhau cho cùng đơn) nhưng cập nhật lại PaymentRequestedAt để gia hạn.

Solution (tham khảo sau khi tự làm):

```
// Order.InitiatePayment: nếu đã có PaymentCode từ trước, giữ nguyên
// paymentCode cũ, chỉ cập nhật PaymentRequestedAt = DateTimeOffset.UtcNow
// để gia hạn — không sinh mã mới cho cùng 1 Order.
```
