## **Nội dung chính**

### **1. Ôn lại nhanh: Entity — Value Object — Aggregate Root**

*10 phút · Lý thuyết*

Ở bài 0.3, bạn đã dựng Category Aggregate — aggregate đơn giản nhất có thể, chỉ để làm quen 3 khái niệm DDD tactical pattern:

- Entity: có identity (Id), hai entity trùng hết property vẫn là hai đối tượng khác nhau nếu Id khác nhau.
- Value Object: không có identity, bất biến (immutable), so sánh bằng theo giá trị — đổi 1 property là tạo ra Value Object mới, không sửa cái cũ.
- Aggregate Root: điểm vào duy nhất của một cụm entity liên quan, chịu trách nhiệm đảm bảo mọi invariant nghiệp vụ luôn đúng sau mỗi thao tác.

Category ở bài 0.3 chỉ có 1 invariant nhỏ: "tên không rỗng". Bài này bạn sẽ dựng Course Aggregate — phức tạp hơn hẳn vì có child entity thật (Lesson) và một invariant xuyên suốt nhiều entity con (không thể publish nếu Lesson rỗng). Đây mới là lúc Aggregate Root phát huy tác dụng thật, không còn là ví dụ minh họa cho có.

### **2. Vẽ Aggregate boundary cho Course**

*10 phút · Lý thuyết*

Ba khối trong domain Catalog của TEDU Market:

- Course — Aggregate Root. Có Id riêng, là đối tượng duy nhất bên ngoài (Application layer, Command Handler) được phép tham chiếu trực tiếp.
- Lesson — child entity. Có Id riêng (vẫn là Entity, không phải Value Object, vì Lesson 1 và Lesson 2 cùng tiêu đề vẫn là hai bài học khác nhau), nhưng KHÔNG có repository riêng, KHÔNG được sửa trực tiếp — mọi thao tác phải đi qua Course.AddLesson(...).
- Pricing — Value Object. Không có Id, gồm Amount + Currency, bất biến. Đổi giá là tạo Pricing mới rồi gán lại vào Course, không sửa property bên trong Pricing.

**Quy tắc nhớ:** nếu ngoài Course không có lý do nghiệp vụ nào cần tồn tại độc lập của Lesson (không có "xem chi tiết 1 Lesson mà không biết nó thuộc Course nào", không có "xóa Lesson mà Course không hay biết"), thì Lesson thuộc boundary của Course — đúng như trường hợp ở đây.

> **📘 Ghi chú giảng viên:** *Học viên mới học DDD hay hỏi: "Sao Lesson không tự có LessonRepository cho tiện, cần gì thì query thẳng?" — Tôi thường trả lời bằng câu hỏi ngược: "Nếu xóa thẳng 1 Lesson qua LessonRepository, ai đảm bảo Course không bị publish với 0 Lesson còn lại?" Không ai đảm bảo cả — vì logic đó nằm trong Course, không nằm trong Lesson. Đây chính là lý do Aggregate Root tồn tại. Bài 1.3 sẽ quay lại điểm này sâu hơn khi làm đầy đủ CRUD Lesson.*

### **3. Business invariant thật đầu tiên: Course phải có ít nhất 1 Lesson mới được publish**

*10-15 phút · Lý thuyết*

Đây là quy tắc nghiệp vụ luôn luôn đúng, bất kể ai gọi, gọi từ đâu, gọi bao nhiêu lần — khác hẳn với validation input (VD: "Title không được để trống" — chỉ là kiểm tra định dạng dữ liệu đầu vào).

Câu hỏi quan trọng: invariant này nên đặt ở đâu?

- KHÔNG đặt ở CreateCourseCommandValidator (FluentValidation, Application layer, sẽ học lại pattern này ở bài 1.2) — vì Validator chỉ chạy đúng 1 lần, tại thời điểm Command được gửi lên. Nếu sau này có đoạn code khác (ví dụ 1 background job) gọi thẳng vào Course.Publish() mà không qua Command, Validator sẽ không có cơ hội chạy.
- PHẢI đặt trong chính method Course.Publish() — vì đây là nơi duy nhất đảm bảo invariant đúng ở MỌI đường gọi, không phụ thuộc ai là người gọi.

> **📘 Ghi chú giảng viên:** *Đây là điểm phân biệt Validation vs Invariant mà tôi luôn nhấn mạnh ở module đầu tiên có invariant thật: Validation trả lời câu hỏi "Input có đúng định dạng không?" — chạy 1 lần ở tầng biên (Application). Invariant trả lời câu hỏi "Trạng thái đối tượng có luôn hợp lệ không?" — phải được Aggregate Root tự bảo vệ ở MỌI thời điểm. Nhầm 2 khái niệm này là lỗi kinh điển khi mới học CQRS + DDD, và sẽ gặp lại liên tục ở Module 2 (Cart/Order, Coupon).*

### **4. Demo: dựng Pricing (Value Object)**

*5 phút · Demo*

Pricing gồm Amount (decimal — bắt buộc dùng decimal cho tiền, không dùng double/float) và Currency. Dùng sealed record để có sẵn value equality, đồng thời ẩn constructor để bắt buộc đi qua factory method có validate:

```csharp
namespace TeduMarket.Domain.Courses;
 
// record cho value equality miễn phí (2 Pricing cùng Amount + Currency là "bằng nhau"),
// nhưng constructor private nên bên ngoài chỉ tạo được qua Pricing.Create(...) đã validate.
public sealed record Pricing
{
    public decimal Amount { get; }
    public string Currency { get; }
 
    private Pricing(decimal amount, string currency)
    {
        Amount = amount;
        Currency = currency;
    }
 
    public static Pricing Create(decimal amount, string currency = "VND")
    {
        if (amount < 0)
            throw new ArgumentOutOfRangeException(
                nameof(amount), "Giá khóa học không được âm.");
 
        if (string.IsNullOrWhiteSpace(currency))
            throw new ArgumentException(
                "Currency không được để trống.", nameof(currency));
 
        return new Pricing(amount, currency);
    }
 
    public static Pricing Free => new(0m, "VND");
}
```

> **📘 Ghi chú giảng viên:** *Chú ý hậu tố "m" ở 0m — thiếu hậu tố này, literal số thập phân mặc định là double, gán vào tham số decimal sẽ lỗi biên dịch. Đây là lỗi học viên mới hay dính nhất khi lần đầu viết Value Object cho tiền.*

### **5. Demo: dựng Lesson (child entity)**

*5 phút · Demo*

Lesson có Id riêng (là Entity thật) nhưng constructor là internal — chỉ code trong cùng assembly Domain (tức là chỉ Course) gọi được, bên ngoài (Application, Api) không thể new Lesson(...) trực tiếp:

```csharp
namespace TeduMarket.Domain.Courses;
 
public sealed class Lesson
{
    public Guid Id { get; private set; }
    public Guid CourseId { get; private set; }
    public string Title { get; private set; }
    public int Order { get; private set; }
 
    // internal: ép buộc mọi Lesson phải được tạo từ bên trong Course,
    // đúng nguyên tắc Aggregate boundary đã nói ở mục 2.
    // Quản lý đầy đủ (sửa/xóa/reorder) sẽ làm ở bài 1.3 — ở đây chỉ đủ để test invariant.
    internal Lesson(Guid courseId, string title, int order)
    {
        if (string.IsNullOrWhiteSpace(title))
            throw new ArgumentException(
                "Tên bài học không được để trống.", nameof(title));
 
        Id = Guid.CreateVersion7();
        CourseId = courseId;
        Title = title;
        Order = order;
    }
}
```

> **📘 Ghi chú giảng viên:** *Guid.CreateVersion7() là API mới từ .NET 9, sinh UUID v7 — GUID có nhúng timestamp nên sort được theo thời gian tạo, tốt hơn Guid.NewGuid() (UUID v4, random hoàn toàn) khi dùng làm khóa chính có index trên Postgres. Sẽ dùng nhất quán cho mọi Id trong Domain layer xuyên suốt khóa.*

### **6. Demo: dựng Course (Aggregate Root) + invariant Publish()**

*10 phút · Demo*

Course quản lý danh sách Lesson qua field private, chỉ expose ra ngoài dạng IReadOnlyCollection — bên ngoài đọc được nhưng không thêm/xóa trực tiếp được:

```csharp
namespace TeduMarket.Domain.Courses;
 
public enum CourseStatus
{
    Draft = 0,
    Published = 1
}
 
public sealed class Course
{
    private readonly List<Lesson> _lessons = [];
 
    public Guid Id { get; private set; }
    public string Title { get; private set; }
    public Guid CategoryId { get; private set; }
    public Guid InstructorId { get; private set; }
    public Pricing Pricing { get; private set; }
    public CourseStatus Status { get; private set; }
    public IReadOnlyCollection<Lesson> Lessons => _lessons.AsReadOnly();
 
    private Course(Guid categoryId, Guid instructorId, string title, Pricing pricing)
    {
        Id = Guid.CreateVersion7();
        CategoryId = categoryId;
        InstructorId = instructorId;
        Title = title;
        Pricing = pricing;
        Status = CourseStatus.Draft;
    }
 
    public static Course Create(
        Guid categoryId, Guid instructorId, string title, Pricing pricing)
    {
        if (string.IsNullOrWhiteSpace(title))
            throw new ArgumentException(
                "Tên khóa học không được để trống.", nameof(title));
 
        return new Course(categoryId, instructorId, title, pricing);
    }
 
    // Bản tối thiểu — chỉ đủ để test invariant Publish().
    // Bài 1.3 sẽ thay bằng bản đầy đủ có sửa/xóa/reorder.
    public void AddLesson(string title)
    {
        var order = _lessons.Count + 1;
        _lessons.Add(new Lesson(Id, title, order));
    }
 
    public void Publish()
    {
        if (_lessons.Count == 0)
            throw new CourseCannotPublishException(
                Id, "Course phải có ít nhất 1 Lesson mới được publish.");
 
        Status = CourseStatus.Published;
    }
}
```

Domain exception dùng lại pattern DomainException đã đặt nền ở bài 0.9 (Global Error Handling), để Api layer map đúng sang ProblemDetails về sau:

```csharp
namespace TeduMarket.Domain.Courses;
 
public sealed class CourseCannotPublishException(Guid courseId, string message)
    : DomainException(message)
{
    public Guid CourseId { get; } = courseId;
}
```

> **📘 Ghi chú giảng viên:** *CourseCannotPublishException(...) : DomainException(message) là primary constructor cho class (C# 12) — cú pháp gọn, không cần viết tay constructor + gán field. Tôi hay dừng ở đây hỏi học viên: "Nếu sau này Application layer bắt exception này để trả về 409 Conflict thay vì 400, code Api layer cần biết gì?" — câu trả lời là chỉ cần match theo type CourseCannotPublishException, không cần biết chi tiết bên trong Domain.*

### **7. Demo: unit test invariant bằng xUnit**

*10 phút · Demo*

Vì outline (mục 6) chỉ định nghĩa một project test cho toàn bộ logic .NET là TeduMarket.Application.UnitTests, ta đặt luôn test cho Domain logic ở đây — giống hệt cách đã làm với Category ở bài 0.3 — dưới thư mục con Courses/. Test này không đụng DB, không mock gì, chạy trong mili-giây vì Course là plain object:

```csharp
namespace TeduMarket.Application.UnitTests.Courses;
 
public class CoursePublishTests
{
    private static Course CreateDraftCourse() =>
        Course.Create(
            categoryId: Guid.CreateVersion7(),
            instructorId: Guid.CreateVersion7(),
            title: "ASP.NET Core Zero to Hero",
            pricing: Pricing.Create(499000m));
 
    [Fact]
    public void Publish_KhiChuaCoLesson_PhaiThrowException()
    {
        // Arrange
        var course = CreateDraftCourse();
 
        // Act
        var publish = () => course.Publish();
 
        // Assert
        Assert.Throws<CourseCannotPublishException>(publish);
        Assert.Equal(CourseStatus.Draft, course.Status);
    }
 
    [Fact]
    public void Publish_KhiDaCoItNhat1Lesson_PhaiChuyenSangPublished()
    {
        // Arrange
        var course = CreateDraftCourse();
        course.AddLesson("Bài 1: Giới thiệu");
 
        // Act
        course.Publish();
 
        // Assert
        Assert.Equal(CourseStatus.Published, course.Status);
    }
}
```

## **Bài tập thực hành**

> **✏️ Thực hành:** Course.Create(...) hiện tại nhận Pricing bất kỳ, kể cả Pricing.Free (Amount = 0). Hãy thêm invariant thứ 2 cho Publish(): "Course chỉ publish được khi Pricing.Amount > 0 HOẶC Pricing chính là Pricing.Free" — nói cách khác, chặn trường hợp Amount = 0 nhưng Currency khác rỗng do nhập sai tay (không đi qua Pricing.Free). Viết thêm exception CoursePricingInvalidException và ít nhất 2 test case (1 case throw, 1 case pass) theo đúng mẫu ở mục 7.

Input: Course đã có ≥ 1 Lesson nhưng Pricing tạo tay bằng Pricing.Create(0m, "VND") (không qua Pricing.Free).

Expected output: gọi course.Publish() phải throw CoursePricingInvalidException; nếu Pricing là Pricing.Free hoặc Amount > 0 thì Publish() chạy bình thường.

> **📘 Ghi chú giảng viên:** *Hint cho học viên bị kẹt: so sánh 2 record Pricing bằng == là hợp lệ và đúng ngữ nghĩa value equality — course.Pricing == Pricing.Free trả về true nếu Amount và Currency giống hệt Free, không cần so sánh reference. Đây cũng là dịp ôn lại vì sao dùng record thay vì class thường cho Value Object.*

## **Tổng kết**

> **✅** Course là Aggregate Root, Lesson là child entity sống trong boundary của Course, Pricing là Value Object bất biến — áp đúng 3 khái niệm DDD đã học ở bài 0.3 cho một domain có invariant thật.
>
> **✅** Invariant nghiệp vụ ("phải có ≥1 Lesson mới publish") luôn nằm trong method của Aggregate Root, không nằm ở Validator của Application layer — vì Validator chỉ bảo vệ 1 đường vào (Command), còn Aggregate Root bảo vệ MỌI đường vào.

> **✅** Lesson chỉ được tạo qua Course.AddLesson(...) — constructor internal, không có LessonRepository riêng. Đây là bản tối thiểu; bài 1.3 sẽ mở rộng đầy đủ (sửa/xóa/reorder).

> **✅** Unit test cho Domain logic không cần DB, không cần mock — đặt trong TeduMarket.Application.UnitTests, chạy cực nhanh, chạy được ngay từ bài đầu Module 1.
