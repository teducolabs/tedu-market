# **Nội dung chính**

## **1. Vì sao Query side không tái sử dụng Course Aggregate**

*Thời lượng: 15 phút | Loại: Lý thuyết*

Ở bài 0.8, bạn đã viết GetCategoriesQuery bằng Dapper thay vì EF Core — đó là lần đầu tiên khóa học chứng minh CQRS có lý do tồn tại thật: Command side dùng EF Core + Aggregate để bảo vệ business invariant, Query side dùng Dapper raw SQL vì mục tiêu hoàn toàn khác — tốc độ đọc, không phải tính toàn vẹn ghi.

Với danh sách Course, sự khác biệt này còn rõ hơn Category rất nhiều. Nếu bạn viết Query side bằng EF Core LINQ kiểu này:

```csharp
var courses = await dbContext.Courses
    .Include(c => c.Lessons)
    .Include(c => c.Instructor)
    .Where(c => c.IsPublished)
    .ToListAsync();
```

Bạn sẽ kéo theo toàn bộ Aggregate: từng Lesson con với Content dài, Pricing Value Object, các field chỉ Command side cần — trong khi trang danh sách chỉ cần Title, ảnh thumbnail, giá, tên danh mục, tên giảng viên, số lượng bài học. Include(c => c.Lessons) trên một danh sách nhiều Course còn tạo ra vấn đề cartesian explosion (mỗi Course nhân với số Lesson) nếu EF Core join thay vì split query — đây chính là mầm mống của bài toán N+1 mà bạn sẽ xử lý triệt để ở bài 1.7.

Với Dapper, bạn viết đúng 1 câu SQL SELECT đúng cột cần cho danh sách, JOIN tối thiểu, không đụng đến Aggregate. Đây không phải "Dapper luôn nhanh hơn EF Core" một cách tuyệt đối — mà là Query side được thiết kế đúng mục đích đọc, tách hẳn khỏi ràng buộc của write model.

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi học viên: "Nếu Query side dùng chung Entity với Command side, khi Instructor thêm 1 field mới vào Course chỉ phục vụ nghiệp vụ ghi (ví dụ ApprovalNote nội bộ), điều gì xảy ra với API danh sách course công khai?" — câu trả lời đúng là field đó vô tình lộ ra ngoài nếu không kiểm soát DTO. Đây là lý do thực sự khiến CQRS tách bạch có giá trị, không phải chỉ để "tách class cho đúng pattern".*

## **3. Viết Handler — Dapper, LIMIT/OFFSET và COUNT(\*) OVER()**

*Thời lượng: 20 phút | Loại: Demo*

PostgreSQL hỗ trợ 2 cú pháp phân trang: LIMIT n OFFSET m (đặc trưng Postgres/MySQL, ngắn gọn) và OFFSET m ROWS FETCH NEXT n ROWS ONLY (chuẩn SQL, Postgres hỗ trợ từ bản 13 trở đi). TEDU Market dùng LIMIT/OFFSET vì đây là cách viết phổ biến nhất trong hệ sinh thái Postgres và khớp tự nhiên với DynamicParameters của Dapper.

Điểm kỹ thuật quan trọng nhất của bài này là COUNT(\*) OVER() — window function trả về tổng số dòng khớp điều kiện lọc, tính trên toàn bộ tập kết quả trước khi LIMIT/OFFSET cắt trang, nhưng chỉ tốn đúng 1 round-trip DB thay vì phải chạy thêm 1 câu SELECT COUNT(\*) riêng để hiển thị tổng số trang.

```sql
SELECT
    c."Id",
    c."Title",
    c."Slug",
    c."ThumbnailUrl",
    c."Price",
    c."DiscountPrice",
    cat."Name"   AS "CategoryName",
    ins."FullName" AS "InstructorName",
    COUNT(l."Id") AS "LessonCount",
    c."CreatedAt",
    COUNT(*) OVER() AS "TotalCount"
FROM "Courses" c
INNER JOIN "Categories" cat ON cat."Id" = c."CategoryId"
INNER JOIN "Instructors" ins ON ins."Id" = c."InstructorId"
LEFT JOIN "Lessons" l ON l."CourseId" = c."Id"
WHERE c."IsPublished" = TRUE
  AND (@CategoryId::uuid IS NULL OR c."CategoryId" = @CategoryId)
GROUP BY c."Id", cat."Name", ins."FullName"
ORDER BY {orderByClause}
LIMIT @PageSize OFFSET @Offset;
```

Vì Postgres cho phép bỏ qua các cột không phải aggregate trong SELECT khi chúng thuộc cùng bảng với cột Primary Key đã có trong GROUP BY (functional dependency), câu SQL chỉ cần GROUP BY c."Id" — các cột khác của Courses (Title, Slug, Price...) không cần liệt kê lại. Nhưng cat."Name" và ins."FullName" đến từ bảng JOIN khác nên bắt buộc phải có mặt trong GROUP BY, nếu thiếu Postgres sẽ báo lỗi biên dịch câu SQL ngay lập tức, không chạy được.

> **📘 Ghi chú giảng viên:** *Tham số @CategoryId::uuid — tôi luôn ép kiểu tường minh khi tham số có thể NULL và cột đích là uuid, vì Npgsql đôi khi không suy luận đúng kiểu tham số khi giá trị truyền vào là null, dẫn đến lỗi "could not determine data type of parameter". Đây là lỗi học viên hay gặp nhất khi mới viết Dapper + Postgres với filter optional.*

### **3.1. Whitelist ORDER BY — không bao giờ nối chuỗi trực tiếp từ input**

ORDER BY không nhận tham số hóa (parameterized) như WHERE — Postgres không cho phép bind @SortColumn vào vị trí ORDER BY. Cách sai phổ biến là nối chuỗi tên cột người dùng gửi lên thẳng vào SQL, mở đường cho SQL injection. Cách đúng: map CourseSortBy (enum đã định nghĩa trong Application, không phải input tự do) sang đúng 1 chuỗi cố định.

```csharp
private static string BuildOrderByClause(CourseSortBy sortBy) => sortBy switch
{
    CourseSortBy.PriceAsc  => "c.\"Price\" ASC",
    CourseSortBy.PriceDesc => "c.\"Price\" DESC",
    CourseSortBy.Newest    => "c.\"CreatedAt\" DESC",
    _                      => "c.\"CreatedAt\" DESC"
};
```

### **3.2. GetCoursesListQueryHandler**

Handler dùng lại IDapperConnectionFactory đã tạo ở bài 0.8 — không tạo interface mới. Application layer chỉ biết interface này, không biết Npgsql hay connection string thật (implement nằm ở Infrastructure, đúng Dependency Inversion Principle đã học ở bài 0.2).

```csharp
using Dapper;
using MediatR;
using TeduMarket.Application.Common.Interfaces;
using TeduMarket.Application.Common.Models;
 
namespace TeduMarket.Application.Courses.Queries.GetCoursesList;
 
public sealed class GetCoursesListQueryHandler(IDapperConnectionFactory connectionFactory)
    : IRequestHandler<GetCoursesListQuery, PagedResult<CourseListItemDto>>
{
    public async Task<PagedResult<CourseListItemDto>> Handle(
        GetCoursesListQuery request, CancellationToken cancellationToken)
    {
        var offset = (request.Page - 1) * request.PageSize;
        var orderBy = BuildOrderByClause(request.SortBy);
 
        var sql = $"""
            SELECT
                c."Id", c."Title", c."Slug", c."ThumbnailUrl",
                c."Price", c."DiscountPrice",
                cat."Name" AS "CategoryName",
                ins."FullName" AS "InstructorName",
                COUNT(l."Id") AS "LessonCount",
                c."CreatedAt",
                COUNT(*) OVER() AS "TotalCount"
            FROM "Courses" c
            INNER JOIN "Categories" cat ON cat."Id" = c."CategoryId"
            INNER JOIN "Instructors" ins ON ins."Id" = c."InstructorId"
            LEFT JOIN "Lessons" l ON l."CourseId" = c."Id"
            WHERE c."IsPublished" = TRUE
              AND (@CategoryId::uuid IS NULL OR c."CategoryId" = @CategoryId)
            GROUP BY c."Id", cat."Name", ins."FullName"
            ORDER BY {orderBy}
            LIMIT @PageSize OFFSET @Offset;
            """;
 
        var parameters = new DynamicParameters();
        parameters.Add("CategoryId", request.CategoryId);
        parameters.Add("PageSize", request.PageSize);
        parameters.Add("Offset", offset);
 
        using var connection = connectionFactory.CreateConnection();
        var rows = (await connection.QueryAsync<CourseListItemRow>(sql, parameters))
            .ToList();
 
        var totalCount = rows.Count > 0 ? rows[0].TotalCount : 0;
        var items = rows.Select(r => r.ToDto()).ToList();
 
        return new PagedResult<CourseListItemDto>(items, totalCount, request.Page, request.PageSize);
    }
 
    private static string BuildOrderByClause(CourseSortBy sortBy) => sortBy switch
    {
        CourseSortBy.PriceAsc  => "c.\"Price\" ASC",
        CourseSortBy.PriceDesc => "c.\"Price\" DESC",
        CourseSortBy.Newest    => "c.\"CreatedAt\" DESC",
        _                      => "c.\"CreatedAt\" DESC"
    };
 
    private sealed record CourseListItemRow(
        Guid Id, string Title, string Slug, string? ThumbnailUrl,
        decimal Price, decimal? DiscountPrice,
        string CategoryName, string InstructorName,
        int LessonCount, DateTime CreatedAt, int TotalCount)
    {
        public CourseListItemDto ToDto() => new(
            Id, Title, Slug, ThumbnailUrl, Price, DiscountPrice,
            CategoryName, InstructorName, LessonCount, CreatedAt);
    }
}
```

> **📘 Ghi chú giảng viên:** *CourseListItemRow là record private lồng trong Handler — mục đích để Dapper map trực tiếp cột TotalCount (chỉ có ý nghĩa kỹ thuật phân trang) mà không làm bẩn CourseListItemDto trả ra ngoài API. Tôi hay nhấn mạnh: DTO trả ra Api layer phải sạch, không lộ chi tiết triển khai phân trang kiểu này.*

## **4. Lab — Filter theo Category và Sort theo giá/ngày tạo**

*Thời lượng: 15 phút | Loại: Lab — học viên tự làm*

Phần SQL và Handler ở mục 3 đã có sẵn khung filter + sort. Nhiệm vụ của bạn trong phần Lab là hoàn thiện endpoint để expose đúng 2 tính năng đó ra ngoài, và tự kiểm tra bằng dữ liệu seed thật.

> **✏️ Thực hành:** Viết endpoint GET /api/v1/courses nhận query string: page, pageSize, categoryId (optional), sortBy (optional, giá trị: Newest | PriceAsc | PriceDesc). Yêu cầu: (1) endpoint đặt trong route group /api/v1/courses đã tạo ở bài 1.2; (2) map query string sang GetCoursesListQuery bằng [AsParameters]; (3) gọi ISender.Send và trả về Results.Ok(result); (4) test bằng Scalar với ít nhất 3 case: không filter, filter theo 1 CategoryId có thật trong seed data, sort PriceAsc rồi kiểm tra thủ công thứ tự giá trả về có tăng dần không.

### **Hint**

- [AsParameters] cho phép Minimal API bind nhiều query string vào 1 record cùng lúc, thay vì khai báo từng tham số rời — đã ổn định từ .NET 7, dùng bình thường trên .NET 10.
- CourseSortBy là enum — Minimal API tự bind enum từ query string theo tên (ví dụ ?sortBy=PriceAsc) mà không cần converter thêm.
- Nếu categoryId gửi lên là chuỗi rỗng thay vì bỏ trống hẳn, model binding sẽ báo lỗi 400 trước khi tới Handler — đây là hành vi đúng, không phải bug.

### **Solution**

```csharp
using MediatR;
using TeduMarket.Application.Courses.Queries.GetCoursesList;
 
namespace TeduMarket.Api.Endpoints.Courses;
 
public sealed record GetCoursesListRequest(
    int Page = 1,
    int PageSize = 12,
    Guid? CategoryId = null,
    CourseSortBy SortBy = CourseSortBy.Newest);
 
public static class GetCoursesListEndpoint
{
    public static void MapGetCoursesList(this RouteGroupBuilder group)
    {
        group.MapGet("/", async (
            [AsParameters] GetCoursesListRequest request,
            ISender sender,
            CancellationToken cancellationToken) =>
        {
            var query = new GetCoursesListQuery(
                request.Page, request.PageSize, request.CategoryId, request.SortBy);
 
            var result = await sender.Send(query, cancellationToken);
            return Results.Ok(result);
        })
        .WithName("GetCoursesList")
        .Produces<PagedResult<CourseListItemDto>>(StatusCodes.Status200OK);
    }
}
```

## **5. Benchmark — Dapper raw SQL vs EF Core LINQ bằng EXPLAIN ANALYZE**

*Thời lượng: 10 phút | Loại: Demo + Lab*

Viết tạm 1 method EF Core LINQ tương đương ngay trong 1 unit test hoặc console tạm, không đặt trong Query side chính thức:

Chạy method này, copy chính xác câu SQL EF Core in ra console (kèm tham số thật). Đây là câu bạn sẽ đưa vào EXPLAIN ANALYZE ở bước sau — không tự đoán SQL EF Core sinh ra, vì cách EF Core dịch Include cho collection navigation có thể khác trực giác (mặc định JOIN phẳng, trừ khi bật AsSplitQuery).

### **5.2. Chạy EXPLAIN ANALYZE cho cả 2 câu SQL trong psql**

```sql
EXPLAIN ANALYZE
SELECT c."Id", c."Title", ... -- dán nguyên câu SQL Dapper ở mục 3
ORDER BY c."CreatedAt" DESC
LIMIT 12 OFFSET 0;
```

So sánh 2 kết quả EXPLAIN ANALYZE theo 3 chỉ số: Planning Time, Execution Time, và loại scan (Seq Scan vs Index Scan trên cột CreatedAt/CategoryId). Với seed data ở quy mô bài học, chênh lệch tuyệt đối có thể nhỏ — điều quan trọng học viên cần thấy là số lượng dòng dữ liệu thật sự được Postgres xử lý ("rows=") của câu EF Core (kéo theo Lesson join) thường lớn hơn hẳn câu Dapper, vì EF Core JOIN cả Lesson con vào cùng 1 query.

> **📘 Ghi chú giảng viên:** *Nếu lớp học chưa có index trên Courses.CreatedAt hoặc Courses.CategoryId, đây là thời điểm tốt để cho học viên thấy Seq Scan trên bảng lớn và đặt câu hỏi mở: "Query side tối ưu bằng SQL tay rồi — vậy còn thiếu gì để nhanh hơn nữa?" dẫn tới khái niệm index, nhưng không đi sâu index tuning trong bài này vì nằm ngoài phạm vi Module 1.*

# **Bài tập tổng hợp cuối bài**

> **✏️ Thực hành:** Mở rộng GetCoursesListQuery thêm tham số Keyword (string?, optional) để tìm theo tên Course (ILIKE, không phân biệt hoa thường). Yêu cầu: (1) thêm điều kiện WHERE (@Keyword IS NULL OR c."Title" ILIKE @Keyword) với @Keyword truyền vào dạng "%từ khóa%" — build ở Handler, không build ở SQL; (2) giữ nguyên COUNT(\*) OVER() vẫn đúng khi có thêm điều kiện Keyword; (3) test qua Scalar với ít nhất 1 từ khóa có dấu tiếng Việt (ví dụ "lập trình") để chắc chắn collation Postgres không làm sai kết quả.

Input: GET /api/v1/courses?keyword=react&sortBy=PriceAsc&page=1&pageSize=12

Expected output: JSON PagedResult\<CourseListItemDto> — Items chỉ gồm Course có Title chứa "react" (không phân biệt hoa thường), sắp xếp Price tăng dần, TotalCount đúng bằng số Course khớp điều kiện (không phải tổng toàn bộ Course trong DB).

### **Hint**

- ILIKE là toán tử case-insensitive riêng của Postgres, thay cho LIKE (case-sensitive theo mặc định).
- Build chuỗi "%" + keyword + "%" ở tầng C#, KHÔNG nối chuỗi "%" ngay trong văn bản SQL — để tránh nhầm lẫn với cú pháp string interpolation $""" đang dùng cho câu SQL.

### **Solution gợi ý (rút gọn)**

```
            AND (@Keyword IS NULL OR c."Title" ILIKE @Keyword)

        parameters.Add("Keyword",
            request.Keyword is null ? null : $"%{request.Keyword}%");
```

# **Tổng kết**

> **✅ Tóm tắt:** GetCoursesListQuery + Handler hoàn chỉnh: phân trang bằng LIMIT/OFFSET, filter theo Category, sort theo giá/ngày tạo qua whitelist enum, tổng số bản ghi lấy bằng COUNT(\*) OVER() trong đúng 1 round-trip — không cần câu COUNT(\*) riêng.

5 điểm chính cần nhớ:

- Query side viết SQL đúng mục đích đọc (chỉ SELECT cột danh sách cần), không tái sử dụng Aggregate của Command side — đây là CQRS có lý do thật, không phải tách tên class hình thức.
- ORDER BY không tham số hóa được — luôn map qua enum whitelist ở tầng C#, không bao giờ nối chuỗi trực tiếp từ input người dùng.
- COUNT(\*) OVER() thay thế cho 1 câu SELECT COUNT(\*) riêng, giảm 1 round-trip DB cho mọi API danh sách có phân trang.
- Tham số optional kiểu Guid? khi bind Postgres cần ép kiểu tường minh (::uuid) để tránh lỗi Npgsql không suy luận được kiểu tham số null.
- EXPLAIN ANALYZE là công cụ đối chiếu khách quan — đừng chỉ tin cảm tính "Dapper chắc nhanh hơn", hãy đo bằng Planning/Execution Time và số dòng (rows=) thật sự được xử lý.

### **Dapper vs EF Core cho Query side — bảng so sánh nhanh**

| **Tiêu chí** | **Dapper raw SQL** | **EF Core LINQ** |
|---|---|---|
| Cột trả về | Chỉ đúng cột DTO cần, tự kiểm soát 100% | Mặc định kéo cả entity, phải Select() thủ công để giới hạn |
| Danh sách + quan hệ 1-nhiều | JOIN + GROUP BY tay, kiểm soát được cartesian explosion | Include() dễ gây cartesian explosion hoặc cần AsSplitQuery |
| Tổng số bản ghi để phân trang | COUNT(\*) OVER() — 1 round-trip | Thường cần thêm 1 câu CountAsync() — 2 round-trip |
| Rủi ro chính | Tự viết SQL tay — phải tự canh injection, tự canh đúng kiểu tham số | Dễ vô tình N+1 hoặc query nặng hơn cần thiết nếu không review SQL sinh ra |
