## **Nội dung chính**

### **1. Ôn lại: vì sao Lesson không có Repository riêng**

*5 phút · Lý thuyết*

Từ bài 1.1: Lesson là child entity, constructor đánh dấu internal — chỉ code trong cùng assembly Domain (tức là chỉ chính Course) mới new Lesson(...) được. Không có ILessonRepository, không có DbSet\<Lesson> nào để Application query trực tiếp.

Lý do nằm ở Aggregate boundary: Course là "cổng vào" duy nhất bảo vệ invariant nghiệp vụ — ví dụ Publish() ở bài 1.1 yêu cầu Course phải có ít nhất 1 Lesson. Nếu Application được phép gọi thẳng một câu UPDATE lên bảng Lessons, hoặc context.Set\<Lesson>().Remove(...) mà không đi qua Course, sẽ không có ai đứng ra đảm bảo invariant đó còn đúng sau thao tác — đây chính là lỗi học viên mới học DDD hay mắc nhất.

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi lớp: "Nếu Application code viết course.Lessons.ToList()... rồi thao tác trực tiếp lên List vừa tạo ra thì sao?" — Câu trả lời: không thay đổi được gì thật. Lessons trả về kiểu IReadOnlyCollection\<Lesson> (đã học ở bài 1.1), không có Add/Remove. .ToList() chỉ tạo ra một bản sao rời rạc, sửa trên bản sao đó không ảnh hưởng gì tới \_lessons thật bên trong Course. Aggregate boundary ở đây được compiler cưỡng bức, không chỉ dừng ở quy ước.*

### **2. Demo: mở rộng Course Aggregate — 4 method quản lý Lesson**

2.1. Nâng cấp AddLesson — trả về LessonId

Đã học ở bài 1.1: AddLesson(string title) là void, chỉ đủ để test invariant Publish(). Giờ Handler cần trả LessonId về cho client (đúng tinh thần CreateCourseCommand trả CourseId ở bài 1.2), nên đổi return type từ void sang Guid:

```csharp
// TeduMarket.Domain/Courses/Course.cs — nâng cấp so với bài 1.1
public Guid AddLesson(string title)
{

    var lesson = new Lesson(Id, title, order);

    return lesson.Id;
```

2.2. UpdateLesson — sửa Title phải đi qua Course, không set thẳng lên Lesson

Lesson.Title vẫn private set (từ bài 1.1). Course tìm đúng Lesson trong \_lessons rồi gọi 1 method internal mới trên chính Lesson đó — nguyên tắc giống hệt UpdateDetails(...) của Course ở bài 1.2:

2.3. RemoveLesson — xoá xong phải reindex lại Order

Nếu chỉ Remove khỏi \_lessons mà không làm gì thêm, xoá Lesson ở giữa danh sách sẽ để lại "lỗ hổng" thứ tự — ví dụ Order còn lại 1, 2, 4, 5. Không sai về dữ liệu, nhưng phá vỡ giả định "Order liên tục từ 1" mà giao diện quản lý bài học ở Module 6/7 sẽ dựa vào để sort:

```csharp
// TeduMarket.Domain/Courses/Course.cs — method mới
public void RemoveLesson(Guid lessonId)
{
    var lesson = _lessons.FirstOrDefault(l => l.Id == lessonId)
        ?? throw new LessonNotFoundException(lessonId);
 
    _lessons.Remove(lesson);
    ReindexLessons();
}
 
private void ReindexLessons()
{
    var ordered = _lessons.OrderBy(l => l.Order).ToList();
    for (var i = 0; i < ordered.Count; i++)
        ordered[i].UpdateOrder(i + 1);
}
// TeduMarket.Domain/Courses/Lesson.cs — method internal mới
internal void UpdateOrder(int order) => Order = order;
```

> **📘 Ghi chú giảng viên:** *ReindexLessons() là private — chỉ Course tự gọi nội bộ, Application không có lý do gì cần biết cơ chế đánh lại số thứ tự. Đây là ví dụ tốt để phân biệt public method (AddLesson, UpdateLesson, RemoveLesson, ReorderLessons — Application gọi qua Command) với private method hỗ trợ nội bộ (ReindexLessons — chỉ Course tự dùng để giữ invariant "Order liên tục", Application không bao giờ gọi trực tiếp).*

2.4. ReorderLessons — đổi thứ tự bằng cách gửi danh sách LessonId mới

Học viên (qua UI kéo-thả ở Module 6) sẽ gửi lên đúng danh sách LessonId theo thứ tự mới. Course phải validate danh sách gửi lên khớp 100% với danh sách Lesson thật — không thiếu, không thừa, không lẫn Id lạ — trước khi gán lại Order:

```csharp
// TeduMarket.Domain/Courses/Course.cs — method mới
public void ReorderLessons(IReadOnlyList<Guid> orderedLessonIds)
{
    var currentIds = _lessons.Select(l => l.Id).ToHashSet();
 
    if (orderedLessonIds.Count != currentIds.Count
        || !currentIds.SetEquals(orderedLessonIds))
    {
        throw new CourseLessonOrderInvalidException(Id);
    }
 
    for (var i = 0; i < orderedLessonIds.Count; i++)
    {
        var lesson = _lessons.First(l => l.Id == orderedLessonIds[i]);
        lesson.UpdateOrder(i + 1);
    }
}
```

### **3. Repository & EF Core: lần đầu Course thật sự "biết" Lesson**

*8 phút · Demo*

3.1. Cập nhật CourseRepository.GetByIdAsync — thêm Include

Ở bài 1.2, GetByIdAsync không Include gì cả vì Lessons đang bị Ignore ở EF Core — collection rỗng cũng không sao vì không dùng tới. Giờ Lessons đã map thật xuống Postgres, quên dòng Include là lỗi phổ biến nhất của bài này: Course load lên vẫn thành công, nhưng course.Lessons luôn rỗng dù bảng Lessons có dữ liệu thật — mọi Command UpdateLesson/RemoveLesson/ReorderLessons sẽ báo LessonNotFoundException dù Lesson tồn tại, khiến học viên đi tìm sai chỗ (nghi ngờ Command/Handler) trong khi lỗi nằm ở Repository:

```csharp
// TeduMarket.Infrastructure/Persistence/Repositories/CourseRepository.cs
// — cập nhật so với bài 1.2
public Task<Course?> GetByIdAsync(Guid id, CancellationToken cancellationToken = default)
    => context.Courses
        .Include(c => c.Lessons)
        .FirstOrDefaultAsync(c => c.Id == id, cancellationToken);
```

> **⚠️ Cảnh báo:** Interface ICourseRepository ở Application layer KHÔNG đổi gì — .Include(...) là chi tiết triển khai EF Core, thuộc về Infrastructure. Application chỉ biết "GetByIdAsync trả về Course kèm đủ Lesson", không cần biết bằng cách nào. Đúng tinh thần Dependency Inversion đã học từ bài 0.2.

3.2. Gỡ Ignore(Lessons), thêm quan hệ Course–Lesson thật

Course.Lessons expose kiểu IReadOnlyCollection\<Lesson> chứ không phải ICollection, và không có setter — đây chính xác là pattern "backing field" mà Microsoft Learn khuyến nghị cho navigation collection kiểu này. Theo mặc định, EF Core tự tìm field khớp tên (property Lessons ↔ field \_lessons) và đọc/ghi thẳng qua field đó, ứng dụng chỉ nhìn thấy bản sao chỉ-đọc qua property — không cần gọi .HasField("_lessons") tường minh:

```csharp
// TeduMarket.Infrastructure/Persistence/AppDbContext.cs
// — cập nhật entity Course so với bài 1.2
modelBuilder.Entity<Course>(builder =>
{
    builder.ToTable("Courses");
    builder.HasKey(c => c.Id);
    builder.Property(c => c.Title).IsRequired().HasMaxLength(200);
    builder.OwnsOne(c => c.Pricing);
 
    // ĐÃ GỠ: builder.Ignore(c => c.Lessons) — bài 1.3 bắt đầu thao tác thật
    // với Lesson nên không thể Ignore nữa. EF tự tìm field _lessons khớp
    // tên với property Lessons theo convention mặc định (Microsoft Learn,
    // "Relationship navigations": EF truy cập collection qua backing field).
    builder.HasMany(c => c.Lessons)
        .WithOne()
        .HasForeignKey(l => l.CourseId)
        .OnDelete(DeleteBehavior.Cascade);
});
 
// Entity mới — Lesson không có DbSet<Lesson> riêng (đúng tinh thần Aggregate:
// chỉ truy cập được qua navigation từ Course), nhưng vẫn cần khai báo Fluent
// Configuration vì EF cần biết cách map Lesson xuống bảng.
modelBuilder.Entity<Lesson>(builder =>
{
    builder.ToTable("Lessons");
    builder.HasKey(l => l.Id);
    builder.Property(l => l.Title).IsRequired().HasMaxLength(200);
});
```

> **⚠️ Cảnh báo:** Đây vẫn là cấu hình TỐI THIỂU, có chủ đích — đủ để 4 Command của bài này chạy đúng. Pricing (OwnsOne) vẫn dùng mặc định chưa có precision/tên cột, cascade delete ở trên viết tường minh nhưng chưa bàn kỹ trade-off. "Fluent Configuration cho Aggregate phức tạp" đầy đủ là nội dung chính thức của bài 1.4 — làm hết ngay bây giờ sẽ giẫm chân lên bài đó.

OnDelete(DeleteBehavior.Cascade) ở đây thật ra đã là hành vi mặc định của EF Core cho quan hệ bắt buộc (Lesson.CourseId là Guid, không phải Guid? — FK không thể null), viết tường minh chỉ để code tự giải thích chứ không đổi hành vi. Hệ quả cụ thể: khi RemoveLesson() gọi \_lessons.Remove(lesson), EF Core coi đây là "cắt đứt quan hệ bắt buộc" — vì FK không thể null, EF tự đánh dấu Lesson đó ở trạng thái Deleted và sinh câu DELETE thật khi SaveChangesAsync() chạy, không cần gọi gì thêm.

### **4. Command, Handler, Validator, Endpoint cho cả 4 thao tác**

*13 phút · Demo + Lab*

Cả 4 Command lặp lại đúng chuỗi Command/Validator/ValidationBehavior/Handler đã học từ Module 0 (bài 0.4, 0.5) và áp dụng lần thứ 3 ở bài 1.2 — điểm chung: load Course qua GetByIdAsync, kiểm tra ownership tạm bằng InstructorId (như bài 1.2, đợi bài 3.8 thay bằng IAuthorizationHandler thật), gọi đúng method Aggregate, SaveChangesAsync.

AddLessonCommand — trả về LessonId, giống tinh thần CreateCourseCommand:

```csharp
// TeduMarket.Application/Courses/Commands/AddLesson/AddLessonCommand.cs
namespace TeduMarket.Application.Courses.Commands.AddLesson;
 
public sealed record AddLessonCommand(
    Guid CourseId,
    Guid InstructorId,
    string Title) : IRequest<Guid>;
// TeduMarket.Application/Courses/Commands/AddLesson/AddLessonCommandHandler.cs
using TeduMarket.Application.Courses.Repositories;
using TeduMarket.Domain.Exceptions;
 
namespace TeduMarket.Application.Courses.Commands.AddLesson;
 
public sealed class AddLessonCommandHandler(ICourseRepository courseRepository)
    : IRequestHandler<AddLessonCommand, Guid>
{
    public async Task<Guid> Handle(
        AddLessonCommand request, CancellationToken cancellationToken)
    {
        var course = await courseRepository.GetByIdAsync(
            request.CourseId, cancellationToken)
            ?? throw new CourseNotFoundException(request.CourseId);
 
        if (course.InstructorId != request.InstructorId)
            throw new CourseNotOwnedException(course.Id, request.InstructorId);
 
        var lessonId = course.AddLesson(request.Title);
 
        await courseRepository.SaveChangesAsync(cancellationToken);
 
        return lessonId;
    }
}
// TeduMarket.Application/Courses/Commands/AddLesson/AddLessonCommandValidator.cs
namespace TeduMarket.Application.Courses.Commands.AddLesson;
 
public sealed class AddLessonCommandValidator : AbstractValidator<AddLessonCommand>
{
    public AddLessonCommandValidator()
    {
        RuleFor(x => x.CourseId).NotEmpty();
        RuleFor(x => x.InstructorId).NotEmpty();
        RuleFor(x => x.Title).NotEmpty().MaximumLength(200);
    }
}
```

```csharp
// TeduMarket.Api/Endpoints/CourseEndpoints.cs — bổ sung so với bài 1.2
using TeduMarket.Application.Courses.Commands.AddLesson;
using TeduMarket.Application.Courses.Commands.UpdateLesson;
using TeduMarket.Application.Courses.Commands.RemoveLesson;
using TeduMarket.Application.Courses.Commands.ReorderLessons;
 
// Trong MapCourseEndpoints(), sau group.MapPut("/{id:guid}", UpdateCourse):
group.MapPost("/{courseId:guid}/lessons", AddLesson);
group.MapPut("/{courseId:guid}/lessons/{lessonId:guid}", UpdateLesson);

// TeduMarket.Api/Endpoints/CourseEndpoints.cs — 4 handler method mới
private static async Task<Created<AddLessonResponse>> AddLesson(
    Guid courseId, AddLessonRequest request,
    ISender sender, CancellationToken cancellationToken)
{
    var command = new AddLessonCommand(
        courseId, request.InstructorId, request.Title);
 
    var lessonId = await sender.Send(command, cancellationToken);
 
    return TypedResults.Created(
        $"/api/v1/courses/{courseId}/lessons/{lessonId}",
        new AddLessonResponse(lessonId));
}
 
private static async Task<NoContent> UpdateLesson(
    Guid courseId, Guid lessonId, UpdateLessonRequest request,
```

Kiểm chứng nhanh 4 tình huống qua curl/Postman sau khi chạy dotnet run:

- 201 — POST .../courses/{courseId}/lessons → trả { "id": "..." }, Location trỏ đúng URL Lesson vừa tạo.
- 204 — PUT .../lessons/{lessonId} với Title mới → GET lại Course thấy đúng Title đã đổi, Order không đổi.
- 204 — DELETE .../lessons/{lessonId} ở giữa danh sách 3 Lesson → GET lại Course, 2 Lesson còn lại có Order là 1 và 2 (không phải 1 và 3) — chứng minh ReindexLessons() chạy đúng.
- 409 — PUT .../lessons/reorder với danh sách thiếu 1 LessonId → ProblemDetails 409, detail nêu đúng Course nào bị lỗi (CourseLessonOrderInvalidException).

## **Bài tập thực hành**

> **✏️ Thực hành:** Thêm invariant mới cho RemoveLesson: "Course đã Published thì không được xoá Lesson cuối cùng" — tái khẳng định invariant Publish() đã viết ở bài 1.1 (Course phải có ≥1 Lesson mới publish), lần này bảo vệ theo chiều ngược lại. Tạo exception CourseCannotRemoveLastLessonException : DomainException theo đúng convention (giống CourseCannotPublishException ở bài 1.1), rồi sửa RemoveLesson để kiểm tra điều kiện này TRƯỚC khi xoá.

Input: Course đã Publish(), chỉ còn đúng 1 Lesson, gọi course.RemoveLesson(lessonId) đúng LessonId đó.

Expected output: ném CourseCannotRemoveLastLessonException; nếu Course còn Draft, hoặc Published nhưng còn ≥2 Lesson, RemoveLesson() phải chạy bình thường như cũ.

> **📘 Ghi chú giảng viên:** *Hint cho học viên bị kẹt: điều kiện chặn phải đặt trước dòng \_lessons.Remove(lesson) — nếu đặt sau, Lesson đã bị xoá khỏi \_lessons rồi mới throw, exception có ném ra thì dữ liệu trong bộ nhớ course đã sai (mất tính "tất cả hoặc không gì cả" của một invariant). Đây cũng là dịp nhắc lại: SaveChangesAsync() chỉ chạy ở Handler, nên nếu exception ném ra ngay trong Course.RemoveLesson(), không có gì được ghi xuống Postgres — an toàn.*

```csharp
// TeduMarket.Domain/Exceptions/CourseCannotRemoveLastLessonException.cs
namespace TeduMarket.Domain.Exceptions;
 
public sealed class CourseCannotRemoveLastLessonException(Guid courseId)
    : DomainException(
        $"Course {courseId} đã Published, không thể xoá Lesson cuối cùng " +
        "— invariant yêu cầu Course đã publish phải có ít nhất 1 Lesson.")
{
    public Guid CourseId { get; } = courseId;
}
// TeduMarket.Application.UnitTests/Courses/CourseTests.cs — 2 test case bổ sung
[Fact]
public void RemoveLesson_WhenPublishedAndOnlyOneLessonLeft_ShouldThrow()

    var lessonId = course.AddLesson("Bài 1 — Giới thiệu");
```
