## Ôn lại nhanh trước khi vào bài

Bài 1.1 đã xây Course Aggregate với 2 phần đáng chú ý: Lesson là child entity sống bên trong Course, và Pricing là Value Object — không có định danh riêng, so sánh bằng giá trị. Bài 1.3 đã khóa chặt aggregate consistency boundary: mọi thay đổi Lesson đều đi qua Course.AddLesson(...), không có Command nào update thẳng bảng Lesson.

Vấn đề là: 2 quyết định thiết kế domain đó chưa có nghĩa gì với EF Core cho tới khi bạn cấu hình Fluent API tường minh. Đây là nội dung chính của bài 1.4 — biến 2 quyết định domain thành schema PostgreSQL đúng ý đồ.

## 1. Vì sao Aggregate phức tạp cần Fluent Configuration riêng (10 phút)

Convention mặc định của EF Core xử lý tốt entity đơn giản (property kiểu nguyên thủy, quan hệ 1-nhiều thông thường qua navigation property công khai). Nhưng Course Aggregate có 2 điểm convention mặc định không tự suy ra được:

- Pricing là một class thông thường, không có Id — nếu không cấu hình gì, EF Core sẽ cố coi Pricing như một Entity Type độc lập và ném lỗi lúc build model (không tìm được khóa chính cho Pricing). EF Core không tự suy luận "đây là Value Object" — bạn phải khai báo tường minh bằng OwnsOne() hoặc attribute [Owned].
- Course.Lessons là IReadOnlyCollection\<Lesson> không có setter công khai, dữ liệu thật nằm ở field private \_lessons. EF Core vẫn map được quan hệ này (vì field đặt tên đúng convention), nhưng delete behavior giữa Course và Lesson cần được nói rõ ý đồ nghiệp vụ, không thể phó mặc hoàn toàn cho suy luận ngầm.

> **📘 Ghi chú giảng viên:** *Tôi hay dừng ở đây và hỏi học viên: "Nếu không cấu hình gì cả, chạy dotnet ef migrations add ngay bây giờ thì chuyện gì xảy ra?" — câu trả lời đúng là build model sẽ lỗi ngay ở Pricing, chưa kịp đụng tới Lessons. Đây là lỗi rất hay gặp khi học viên tự thêm Value Object mới ở bài tập cuối chương mà quên OwnsOne.*

## 2. Owned Type cho Pricing — Value Object không có bảng riêng (10 phút)

Nhắc lại Pricing đã viết ở bài 1.1 (rút gọn, chỉ để tham chiếu — không viết lại):

```csharp
// TeduMarket.Domain/Courses/Pricing.cs — đã tạo ở bài 1.1
public sealed record Pricing
{
    public decimal Amount { get; }
    public decimal? DiscountAmount { get; }
    public string Currency { get; }
 
    private Pricing(decimal amount, decimal? discountAmount, string currency)
    {
        Amount = amount;
        DiscountAmount = discountAmount;
        Currency = currency;
    }
 
    public static Pricing Create(decimal amount, string currency = "VND", decimal? discountAmount = null)
    {
        if (amount < 0m)
            throw new ArgumentOutOfRangeException(nameof(amount), "Giá khóa học không được âm.");
 
        return new Pricing(amount, discountAmount, currency);
    }
 
    public decimal FinalPrice => Amount - (DiscountAmount ?? 0m);
}
```

Cấu hình Owned Type trong CourseConfiguration.cs — đây là phần mới của bài này:

```csharp
// TeduMarket.Infrastructure/Persistence/Configurations/CourseConfiguration.cs
builder.OwnsOne(c => c.Pricing, pricing =>
{
    pricing.Property(p => p.Amount)
        .HasColumnName("Price_Amount")
        .HasColumnType("numeric(18,2)")   // kiểu PostgreSQL, không phải "decimal" kiểu SQL Server
        .IsRequired();
 
    pricing.Property(p => p.DiscountAmount)
        .HasColumnName("Price_DiscountAmount")
        .HasColumnType("numeric(18,2)");
 
    pricing.Property(p => p.Currency)
        .HasColumnName("Price_Currency")
        .HasMaxLength(3)
        .IsRequired();
});
 
// Course luôn phải có Pricing — không có trạng thái "chưa định giá"
builder.Navigation(c => c.Pricing).IsRequired();
```

OwnsOne dùng table splitting: 3 cột Price_Amount, Price_DiscountAmount, Price_Currency nằm chung bảng Courses, không sinh bảng riêng — đúng yêu cầu "Value Object không có bảng riêng" trong outline. EF Core tạo cho Pricing một shadow key ẩn (giá trị trùng với Id của Course) chỉ để tracking nội bộ, bạn không thấy cột này và cũng không cần quan tâm tới nó.

> **📘 Ghi chú giảng viên:** *PostgreSQL không có kiểu "decimal" như SQL Server hay dùng trong ví dụ mẫu trên mạng — decimal chỉ là alias của numeric trong Postgres, nhưng tôi luôn viết numeric(18,2) cho đúng "giọng" Postgres, tránh học viên quen tay copy "decimal(18,2)" từ tài liệu SQL Server rồi thắc mắc sao script sinh ra khác.*
>
> **📘 Ghi chú giảng viên:** *Câu hỏi hay gặp: "Sao không dùng Complex Type mới của EF Core 8 cho gọn?" Tài liệu chính thức của Microsoft thật ra khuyến nghị Complex Type cho value object không có identity, vì nó không có shadow key, đúng ngữ nghĩa value semantics hơn Owned Type. Khóa học vẫn chọn Owned Type vì đây là pattern phổ biến, nhiều tài liệu tham khảo, và đủ đáp ứng yêu cầu của TEDU Market. Tôi có ghi lại bảng so sánh ở phần Tổng kết — học viên nào muốn thử Complex Type cho project riêng thì đọc thêm phần đó.*

## 3. Quan hệ Course – Lesson qua backing field (10 phút)

Nhắc lại phần khai báo collection trong Course (bài 1.1, 1.3) — field private, navigation chỉ đọc:

```csharp
// TeduMarket.Domain/Courses/Course.cs — đã tạo ở bài 1.1, dùng lại ở 1.3
public sealed class Course : AggregateRoot<Guid>
{
    private readonly List<Lesson> _lessons = new();
 
    public IReadOnlyCollection<Lesson> Lessons => _lessons.AsReadOnly();
 
    public void AddLesson(string title, int durationInSeconds, string videoUrl)
    {
        var orderIndex = _lessons.Count == 0 ? 1 : _lessons.Max(l => l.OrderIndex) + 1;
        _lessons.Add(new Lesson(Id, title, orderIndex, durationInSeconds, videoUrl));
    }
}
```

EF Core dò tìm backing field theo quy ước đặt tên: với property Lessons, nó tìm lần lượt lessons, \_lessons, \_Lessons, m_lessons, m_Lessons — field \_lessons trong Course khớp ngay quy ước đầu tiên nên không cần khai báo gì thêm cho riêng việc "tìm field". Nhưng quan hệ FK và delete behavior thì vẫn phải khai báo tường minh:

```csharp
// CourseConfiguration.cs (tiếp)
builder.HasMany(c => c.Lessons)
    .WithOne()                          // Lesson KHÔNG có navigation property trỏ ngược về Course
    .HasForeignKey(l => l.CourseId)
    .OnDelete(DeleteBehavior.Cascade);
```

Chú ý .WithOne() không truyền tham số: Lesson cố tình không có property Course để tham chiếu ngược — chỉ có CourseId. Đây là quyết định giữ đúng aggregate boundary từ bài 1.3: nếu Lesson có navigation Course, code ứng dụng rất dễ viết kiểu lesson.Course.SomeMethod() đi vòng qua Course.AddLesson(...), phá vỡ invariant mà bài 1.3 vừa dựng.

> **📘 Ghi chú giảng viên:** *Điểm hay bị hỏi: "Không có backing field \_lessons thì có map được quan hệ này không?" — Vẫn được, nhưng EF Core sẽ không thể ghi dữ liệu vào collection khi query từ DB (vì Lessons chỉ có getter). Muốn không dùng backing field convention, phải tự gọi .Navigation(c => c.Lessons).UsePropertyAccessMode(PropertyAccessMode.Field) và .HasField("tenFieldKhac") nếu tên field không theo quy ước — nhưng trong Course chúng ta đặt tên đúng chuẩn ngay từ đầu nên không cần bước này.*

### Cấu hình phụ trợ cho Lesson

Lesson cũng cần một Configuration riêng để giới hạn độ dài chuỗi và đảm bảo không có 2 Lesson trùng thứ tự trong cùng 1 Course:

```csharp
// TeduMarket.Infrastructure/Persistence/Configurations/LessonConfiguration.cs
public sealed class LessonConfiguration : IEntityTypeConfiguration<Lesson>
{
    public void Configure(EntityTypeBuilder<Lesson> builder)
    {
        builder.ToTable("Lessons");
        builder.HasKey(l => l.Id);
 
        builder.Property(l => l.Title).HasMaxLength(200).IsRequired();
        builder.Property(l => l.VideoUrl).HasMaxLength(500).IsRequired();
 
        builder.HasIndex(l => new { l.CourseId, l.OrderIndex }).IsUnique();
    }
}
```

## 4. Cascade delete — vì sao chọn Cascade, không phải Restrict hay SetNull (10 phút)

CourseId trên Lesson là FK bắt buộc (không nullable). Với quan hệ required, EF Core mặc định (theo convention) đã áp dụng Cascade khi sinh migration — nghĩa là dù bạn không viết .OnDelete(DeleteBehavior.Cascade), hành vi cascade vẫn xảy ra. Vậy tại sao outline vẫn yêu cầu viết tường minh?

- Code tự document ý đồ nghiệp vụ: người đọc CourseConfiguration.cs không cần đoán "đây là convention hay cố ý" — đọc thấy .OnDelete(Cascade) là biết ngay đây là quyết định có chủ đích.
- An toàn khi refactor: nếu sau này có ai đổi CourseId thành nullable (ví dụ cho phép Lesson "mồ côi" tạm thời), convention mặc định sẽ tự đổi sang ClientSetNull — im lặng thay đổi hành vi mà không ai để ý. Khai báo tường minh giữ hành vi Cascade dù FK có đổi nullable hay không.

Bảng các DeleteBehavior thường dùng:

| **Giá trị** | **Hành vi** | **Khi nào dùng** |
|---|---|---|
| **Cascade** | Xóa Course → tự động xóa toàn bộ Lesson liên quan | Aggregate boundary chặt: Lesson không có lý do tồn tại ngoài Course — đúng trường hợp TEDU Market |
| **Restrict** | Chặn xóa Course nếu còn Lesson tham chiếu, DB ném lỗi FK | Muốn buộc nghiệp vụ xóa/di chuyển Lesson trước, tránh xóa nhầm dây chuyền |
| **SetNull / ClientSetNull** | Set CourseId = null trên Lesson khi xóa Course | Chỉ dùng được nếu CourseId nullable — không hợp thiết kế hiện tại (CourseId required) |
| **NoAction / ClientNoAction** | EF/DB không tự làm gì, ứng dụng tự xử lý logic xóa | Cần kiểm soát thủ công hoàn toàn — ít dùng trong CRUD thông thường |

## 5. Demo: đăng ký Configuration và chạy migration

Đảm bảo AppDbContext (bài 0.6) đã áp dụng toàn bộ Configuration trong assembly Infrastructure:

```csharp
// TeduMarket.Infrastructure/Persistence/AppDbContext.cs
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.ApplyConfigurationsFromAssembly(typeof(CourseConfiguration).Assembly);
    base.OnModelCreating(modelBuilder);
}
```

Chạy migration (cách chạy đầy đủ với IDesignTimeDbContextFactory sẽ học kỹ ở bài 1.5 — ở đây chỉ cần đủ để verify Configuration đúng):

```bash
cd backend/src/TeduMarket.Infrastructure
dotnet ef migrations add AddCourseAggregateConfiguration --startup-project ../TeduMarket.Api
dotnet ef database update --startup-project ../TeduMarket.Api
```

Migration sinh ra sẽ có dạng rút gọn minh họa như sau (phần chính cần kiểm tra):

```
migrationBuilder.CreateTable(
    name: "Courses",
    columns: table => new
    {
        Id = table.Column<Guid>(nullable: false),
        // ... các cột khác của Course ...
        Price_Amount = table.Column<decimal>(type: "numeric(18,2)", nullable: false),
        Price_DiscountAmount = table.Column<decimal>(type: "numeric(18,2)", nullable: true),
        Price_Currency = table.Column<string>(type: "character varying(3)", maxLength: 3, nullable: false)
    });
 
migrationBuilder.CreateTable(
    name: "Lessons",
    columns: table => new { /* ... */ CourseId = table.Column<Guid>(nullable: false) },
    constraints: table =>
    {
        table.ForeignKey(
            name: "FK_Lessons_Courses_CourseId",
            column: x => x.CourseId,
            principalTable: "Courses",
            principalColumn: "Id",
            onDelete: ReferentialAction.Cascade);   // <- xác nhận đúng Cascade
    });
 
migrationBuilder.CreateIndex(
    name: "IX_Lessons_CourseId_OrderIndex",
    table: "Lessons",
    columns: new[] { "CourseId", "OrderIndex" },
    unique: true);
```

Checklist verify sau khi chạy migration: (1) bảng Courses không có bảng Pricing riêng, 3 cột Price_\* nằm ngay trong Courses; (2) bảng Lessons có FK_Lessons_Courses_CourseId với onDelete: Cascade; (3) index unique trên (CourseId, OrderIndex); (4) chạy dotnet build sạch, không warning liên quan tới model EF Core.

## Bài tập thực hành

> **✏️ Thực hành:** Thêm thuộc tính OriginalPrice (giá gốc trước khuyến mãi, decimal? — có thể null nếu Course chưa từng giảm giá) vào Pricing Value Object, cấu hình Owned Type đúng cho property mới, sinh migration mới và verify script SQL.

Input: Pricing hiện tại chỉ có Amount, DiscountAmount, Currency.

Expected output: build thành công; lệnh dotnet ef migrations add AddPricingOriginalPrice chỉ sinh ra đúng 1 cột mới Price_OriginalPrice kiểu numeric(18,2), không đụng tới cột khác; dotnet ef database update chạy không lỗi.

Hint 1: OriginalPrice khai báo tương tự DiscountAmount — decimal?, không IsRequired().

Hint 2: đừng quên khai báo bên trong khối builder.OwnsOne(c => c.Pricing, pricing => { ... }) đã viết ở mục 2, không tạo OwnsOne thứ hai.

### Solution

```
pricing.Property(p => p.OriginalPrice)
    .HasColumnName("Price_OriginalPrice")
    .HasColumnType("numeric(18,2)");
```

## Tổng kết

> **✅ Tóm tắt bài học**
>
> 1. Value Object không có identity (Pricing) phải khai báo tường minh bằng OwnsOne() — EF Core không tự suy luận được, convention mặc định sẽ ném lỗi build model nếu bỏ qua bước này.
>
> 2. OwnsOne mặc định dùng table splitting: value object nằm chung bảng với owner, đúng yêu cầu "không có bảng riêng" — đặt tên cột rõ ràng bằng HasColumnName để tránh tên cột Navigation_Property mặc định khó đọc.
>
> 3. Collection encapsulated qua backing field (_lessons) được EF Core tự dò theo convention đặt tên, nhưng quan hệ FK và delete behavior vẫn phải khai báo Fluent API tường minh.
>
> 4. DeleteBehavior.Cascade khai báo tường minh dù đôi khi trùng với convention mặc định của quan hệ required — mục đích là code tự document ý đồ nghiệp vụ và giữ hành vi ổn định khi model thay đổi.
>
> 5. PostgreSQL dùng numeric(p,s), không phải decimal(p,s) kiểu SQL Server — tuy decimal là alias hợp lệ của numeric trong Postgres, bài giảng dùng numeric cho đúng chuẩn Postgres xuyên suốt khóa.

### Owned Entity Type vs Complex Type — tham khảo thêm

| **Owned Entity Type (OwnsOne) — dùng trong bài này** | **Complex Type (ComplexProperty, EF Core 8+)** |
|---|---|
| Có shadow key ẩn, EF Core theo dõi như một entity con của owner | Không có key, value semantics thuần túy — đúng bản chất DDD value object hơn |
| Có thể lưu bảng riêng (ToTable), hỗ trợ nested owned type, navigation có thể null | Luôn thuộc bảng của owner (không tách bảng riêng), một số ràng buộc còn đang hoàn thiện qua các bản EF Core gần đây |
| Pattern phổ biến từ EF Core 2.x, nhiều tài liệu và ví dụ DDD tham khảo | Mới hơn, được Microsoft khuyến nghị cho value object không identity, nhưng ít pattern tham khảo hơn |

Khóa học chọn Owned Type cho Pricing vì đây là pattern chủ đạo hiện tại trong cộng đồng .NET và đủ đáp ứng yêu cầu TEDU Market. Complex Type là hướng đáng cân nhắc khi bạn tự thiết kế value object cho project riêng ở bản EF Core mới hơn.
