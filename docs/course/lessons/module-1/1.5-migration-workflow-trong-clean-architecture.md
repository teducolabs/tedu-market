# **Nội dung chính**

## **1. Vì sao "chạy migration ở đâu" là vấn đề thật**

*Thời lượng: 10 phút | Loại: Lý thuyết*

Nhắc lại cấu trúc 4 layer đã dựng từ Module 0 (mục 6 trong outline): TeduMarket.Domain, TeduMarket.Application, TeduMarket.Infrastructure, TeduMarket.Api. AppDbContext và toàn bộ file Migrations nằm ở Infrastructure — nhưng Infrastructure là class library thuần, không có Program.cs, không có Main(). Nó không tự "chạy" được.

Ở bài 0.6, lệnh dotnet ef migrations add đã chạy được dù bạn chưa viết thêm gì đặc biệt cho việc này. Lý do: EF Core Tools tìm DbContext tại design-time theo thứ tự ưu tiên sau:

1. Tìm class implement IDesignTimeDbContextFactory\<TContext> trong assembly khởi động hoặc assembly chứa DbContext. Nếu có — dùng ngay, bỏ qua các cách còn lại.
1. Nếu không có, với project dùng ASP.NET Core Generic Host (chính là Api của chúng ta), Tools sẽ build toàn bộ ứng dụng thông qua host builder — dựng gần như y hệt DI container thật lúc runtime — rồi lấy AppDbContext ra từ đó.

Cách 2 hoạt động ổn khi Api còn đơn giản như ở Module 0 và 1.1–1.4. Nhưng nhìn lại lộ trình khóa học: Module 1.8 (chỉ 3 bài trước bài này) đã thêm MinIO client; Module 2 sẽ cần VNPay sandbox và Hangfire storage; Module 3 cần OpenIddict với signing key. Design-time host build sẽ cố resolve TẤT CẢ service đã đăng ký trong Program.cs — kể cả những service chẳng liên quan gì tới AppDbContext. Chỉ cần thiếu một biến môi trường, một container chưa lên, lệnh migrations add đơn giản sẽ văng ra một exception dài dằng dặc không nói gì về migration cả.

> **📘 Ghi chú giảng viên:** *Tôi hay để dành đúng câu chuyện này cho bài 1.5: kể lỗi kiểu "Unable to resolve service for type IHangfireBackgroundJobClient" khi chỉ muốn thêm một cột vào bảng Course. Học viên nào từng bị dính pattern "cách 2" trong dự án thật sẽ gật đầu ngay. Đây là lúc đúng để giới thiệu IDesignTimeDbContextFactory — làm sớm trước khi Api phình to, không phải vá khi đã bị lỗi.*

Giải pháp: implement IDesignTimeDbContextFactory\<AppDbContext> ngay trong Infrastructure. EF Core Tools ưu tiên nó tuyệt đối — bỏ qua hoàn toàn bước dựng Generic Host của Api. Migration workflow từ đây tách biệt 100% khỏi việc Api có chạy được hay không.

## **2. Demo — Viết AppDbContextFactory**

*Thời lượng: 10 phút | Loại: Demo*

### **Bước 1 — Khai báo package đúng cách**

Microsoft.EntityFrameworkCore.Design là một DevelopmentDependency package — mặc định KHÔNG flow transitively sang project khác, kể cả khi Api đã cài nó gián tiếp qua Microsoft.EntityFrameworkCore.Tools. Muốn compile được với type IDesignTimeDbContextFactory trong Infrastructure, phải khai báo tường minh và bỏ IncludeAssets rút gọn:

```xml
<!-- TeduMarket.Infrastructure.csproj -->
<ItemGroup>
  <PackageReference Include="Microsoft.EntityFrameworkCore.Design" Version="10.0.0">
    <PrivateAssets>all</PrivateAssets>
    <!-- Không đặt IncludeAssets rút gọn -> mới compile được against assembly này -->
  </PackageReference>
</ItemGroup>
```

### **Bước 2 — Class AppDbContextFactory**

```csharp
// src/TeduMarket.Infrastructure/Persistence/AppDbContextFactory.cs
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Design;
 
namespace TeduMarket.Infrastructure.Persistence;
 
public sealed class AppDbContextFactory : IDesignTimeDbContextFactory<AppDbContext>
{
    public AppDbContext CreateDbContext(string[] args)
    {
        var connectionString = Environment.GetEnvironmentVariable("ConnectionStrings__Postgres")
            ?? "Host=localhost;Port=5432;Database=tedumarket;Username=postgres;Password=postgres";
 
        var optionsBuilder = new DbContextOptionsBuilder<AppDbContext>();
        optionsBuilder.UseNpgsql(connectionString, npgsql =>
            npgsql.MigrationsAssembly(typeof(AppDbContext).Assembly.FullName));
 
        return new AppDbContext(optionsBuilder.Options);
    }
}
```

Đọc connection string từ biến môi trường ConnectionStrings__Postgres trước (khớp key với docker-compose.yml đã dựng ở bài 0.10), có fallback local để chạy ngay cả khi chưa set biến môi trường. MigrationsAssembly trỏ tường minh về assembly chứa AppDbContext — tránh EF Core Tools đoán nhầm project khi solution có nhiều assembly tham chiếu chéo nhau.

> **📘 Ghi chú giảng viên:** *Điểm hay bị hỏi: "Sao không đọc thẳng appsettings.json cho giống Api?" — Infrastructure là class library, không có appsettings.json, và cố tình copy file cấu hình sang đây sẽ tạo ra một nguồn sự thật thứ hai, dễ lệch với connection string thật của Api theo thời gian. Biến môi trường là điểm trung lập nhất giữa hai project.*

### **Bước 3 — Chạy migration**

```bash
dotnet ef migrations add AddCourseAggregateConfiguration \
  --project src/TeduMarket.Infrastructure \
  --startup-project src/TeduMarket.Api \
  --output-dir Persistence/Migrations
```

--project chỉ định project chứa AppDbContext — nơi file migration thực sự được sinh ra. --startup-project chỉ định project Tools sẽ build để lấy design-time service — nhưng giờ với AppDbContextFactory sẵn có, Tools chỉ cần Api build thành công, KHÔNG cần chạy được, không cần resolve bất kỳ service runtime nào của Api nữa.

Verify ngay: kể cả khi appsettings.json của Api còn thiếu cấu hình OpenIddict hay VNPay (bình thường, vì chưa học tới), lệnh migrations add vẫn chạy sạch — vì AppDbContextFactory không đụng gì tới các service đó. Áp dụng thật lên Postgres bằng:

```bash
dotnet ef database update --project src/TeduMarket.Infrastructure --startup-project src/TeduMarket.Api
```

## **3. Demo + Lab — Seed Category & Course đúng chuẩn Aggregate**

*Thời lượng: 10 phút | Loại: Demo + Lab*

Tra nhanh trên mạng "EF Core seed data", phần lớn ví dụ đều dùng modelBuilder.Entity\<T>().HasData(...). Cách này có vấn đề thật với TEDU Market: HasData yêu cầu cung cấp toàn bộ property với khóa chính cố định, được EF Core serialize thẳng thành InsertData operation bên trong migration bằng reflection — nó KHÔNG gọi được constructor riêng tư hay factory method static như Category.Create(...) / Course.Create(...) đã thiết kế ở bài 1.1. Seed theo kiểu này thực chất đang lách qua đúng lớp encapsulation domain mà khóa học đang cố dạy cho đúng.

Giải pháp: EF Core 9 trở lên có UseSeeding (đồng bộ) và UseAsyncSeeding (bất đồng bộ), cấu hình ngay trên DbContextOptionsBuilder. Cả hai chạy tự động mỗi khi EnsureCreated, Migrate hoặc dotnet ef database update được gọi, và được bảo vệ bởi cơ chế migration lock để tránh chạy trùng khi có nhiều instance cùng migrate. Khác biệt cốt lõi so với HasData: code bên trong chạy như code nghiệp vụ bình thường — gọi được factory method, query kiểm tra tồn tại trước khi insert, dùng được async/await.

### **Cấu hình trong Infrastructure/DependencyInjection.cs**

Mở rộng đúng đoạn UseNpgsql đã có sẵn từ bài 0.6, trong hàm AddInfrastructure():

```csharp
services.AddDbContext<AppDbContext>(options =>
    options.UseNpgsql(connectionString)
           .UseAsyncSeeding(async (context, _, cancellationToken) =>
           {
               if (!await context.Set<Category>().AnyAsync(cancellationToken))
               {
                   var webDev = Category.Create("Lập trình Web");
                   var mobileDev = Category.Create("Lập trình Mobile");
                   context.Set<Category>().AddRange(webDev, mobileDev);
 
                   var course = Course.Create(
                       title: "ASP.NET Core 10 từ Zero đến Production",
                       categoryId: webDev.Id,
                       instructorId: SeedData.DefaultInstructorId,
                       pricing: Pricing.Create(1_990_000m, "VND"));
 
                   course.AddLesson("Giới thiệu Clean Architecture", order: 1);
                   context.Set<Course>().Add(course);
 
                   await context.SaveChangesAsync(cancellationToken);
               }
           }));
```

AnyAsync trên Category là điều kiện bắt buộc — vì UseAsyncSeeding chạy lại mỗi lần Migrate được gọi. Không check trước, mỗi lần container Postgres bị \`docker compose down -v && up\` lại, bạn sẽ insert trùng dữ liệu.

Instructor thật chưa tồn tại tới Module 3 (Identity/OpenIddict), nên seed tạm bằng SeedData.DefaultInstructorId — một hằng số Guid cố định, có ghi chú TODO nối với User thật khi học tới Module 3. Đúng tinh thần đã nêu ở bài 1.2: dùng giá trị tạm được kiểm soát, không phải giá trị bịa vô căn cứ.

Kết nối lại bài 0.10: khi chạy docker compose up, Program.cs của Api gọi await app.Services.GetRequiredService\<AppDbContext>().Database.MigrateAsync() lúc khởi động (đã viết ở bài 0.10) — dòng này tự động trigger UseAsyncSeeding, không cần thêm bước thủ công nào.

> **📘 Ghi chú giảng viên:** *Hay bị hỏi: "Sao không viết hẳn 1 file SeedData.cs, gọi tay trong Program.cs cho dễ đọc?" — Trả lời: cả hai cách đều hợp lệ, nhưng UseAsyncSeeding có cơ chế lock chống race condition khi có nhiều instance Api khởi động song song (chuyện bình thường khi scale ngang ở Module 9), còn gọi tay ngoài Program.cs dễ bị double-seed nếu hai instance cùng chạy MigrateAsync() một lúc.*

Chạy thử toàn bộ luồng:

```bash
docker compose down -v
docker compose up
```

Mở DBeaver hoặc psql, kiểm tra bảng Categories có 2 dòng, Courses có 1 dòng, Lessons có 1 dòng — đúng dữ liệu vừa seed.

# **Bài tập thực hành**

> **✏️ Thực hành:** Thêm Category "Lập trình AI/Data" và một Course thứ hai thuộc category này, có ít nhất 2 Lesson — dùng đúng Category.Create / Course.Create / course.AddLesson đã học, không new trực tiếp entity.

Input: sửa đoạn UseAsyncSeeding trong TeduMarket.Infrastructure/DependencyInjection.cs.

Expected output: sau khi chạy lại docker compose down -v && docker compose up, bảng Categories có 3 dòng, Courses có 2 dòng, Lessons có ít nhất 3 dòng.

Hint 1: điều kiện AnyAsync hiện tại chỉ check theo Category — nếu bạn thêm logic if lồng nhau cho Course thứ hai mà không cẩn thận, dễ bị bỏ sót seed khi Category đã tồn tại nhưng Course mới thì chưa. Kiểm tra riêng từng entity trước khi insert.

Hint 2: instructorId của Course thứ hai cứ dùng tạm SeedData.DefaultInstructorId giống Course đầu — đừng bịa Guid mới, giữ nhất quán để không tạo thêm dữ liệu rác.

Gợi ý solution: cấu trúc lại thân UseAsyncSeeding thành 2 khối if độc lập — một khối seed Category, một khối seed Course — mỗi khối tự kiểm tra điều kiện tồn tại riêng của chính nó, tránh phụ thuộc chéo giữa hai điều kiện.

# **Tổng kết**

> **✅ Tóm tắt:** EF Core Tools tìm DbContext design-time theo 2 cách: IDesignTimeDbContextFactory (ưu tiên tuyệt đối) hoặc dựng Generic Host của project khởi chạy (rủi ro khi Api phình to).
>
> AppDbContextFactory tách hoàn toàn migration tooling khỏi DI container runtime của Api — chạy được dù Api chưa cấu hình xong OpenIddict, VNPay hay Hangfire.
>
> Microsoft.EntityFrameworkCore.Design là DevelopmentDependency — phải khai báo PackageReference tường minh với PrivateAssets=all trong project thư viện mới compile được.
>
> HasData không gọi được factory method của Aggregate — dùng UseSeeding/UseAsyncSeeding (EF Core 9+) để seed đúng qua Category.Create()/Course.Create(), có lock chống race condition tự động.
>
> Seed data phải idempotent (check AnyAsync trước khi insert) vì UseAsyncSeeding chạy lại mỗi lần Migrate được gọi.

## **So sánh HasData vs UseSeeding / UseAsyncSeeding**

| **Tiêu chí** | **HasData** | **UseSeeding / UseAsyncSeeding** |
|---|---|---|
| Chạy khi nào | Bake sẵn thành InsertData operation trong migration | Chạy lúc EnsureCreated / Migrate / dotnet ef database update |
| Gọi được factory method? | Không — serialize object graph bằng reflection | Có — chạy như code nghiệp vụ bình thường |
| Idempotent tự động? | Có (do nằm trong migration, chỉ chạy 1 lần) | Không — phải tự check (AnyAsync) trong code |
| Phù hợp dữ liệu nào | Bảng tra cứu tĩnh, PK cố định (vd. Role, Status) | Dữ liệu có invariant, quan hệ, cần domain logic (Category, Course) |

*Bước tiếp theo: bài 1.6 — Query Side: Danh sách Course có phân trang/filter/sort bằng Dapper, query trực tiếp trên đúng dữ liệu vừa seed ở bài này để đo hiệu năng thật.*

# **Phụ lục — Cheatsheet lệnh dotnet ef**

```bash
# Thêm migration mới
dotnet ef migrations add <TenMigration> \
  --project src/TeduMarket.Infrastructure --startup-project src/TeduMarket.Api
 
# Áp dụng migration lên database
dotnet ef database update \
  --project src/TeduMarket.Infrastructure --startup-project src/TeduMarket.Api
 
# Gỡ migration mới nhất (chưa apply)
dotnet ef migrations remove \
  --project src/TeduMarket.Infrastructure --startup-project src/TeduMarket.Api
 
# Xuất SQL script idempotent (dùng cho CI/CD ở Module 9)
dotnet ef migrations script --idempotent -o migrations.sql \
  --project src/TeduMarket.Infrastructure --startup-project src/TeduMarket.Api
```
