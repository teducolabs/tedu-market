# **Nội dung chính**

## **1. Vấn đề N+1 nằm ở đâu khi lấy Course Detail**

*Thời lượng: 8 phút | Loại: Lý thuyết*

Trang chi tiết 1 Course (bạn sẽ dùng lại Query này ở bài 7.3 cho Next.js) cần đủ 4 nhóm dữ liệu trong 1 lần load: thông tin Course, tên Category, tên Instructor, và toàn bộ danh sách Lesson để hiển thị mục lục khóa học. Đây chính xác là kiểu dữ liệu "1 cha nhiều con" mà bài 1.6 đã nhắc tới khi giải thích vì sao Include(c => c.Lessons) trên danh sách nhiều Course gây cartesian explosion. Với Course Detail chỉ có đúng 1 Course, cartesian explosion không còn là vấn đề chính — vấn đề chính ở đây là N+1: nếu bạn viết Handler theo phản xạ tự nhiên (query từng phần một cách tuần tự) thay vì gộp lại, bạn vô tình tạo ra N+1 round-trip.

Cách viết sai phổ biến nhất — trông rất hợp lý nhưng sai — là thế này:

// ❌ Cách viết gây N+1 — KHÔNG dùng trong Handler

```csharp
var course = await connection.QuerySingleAsync<CourseRow>(
    "SELECT * FROM \"Courses\" WHERE \"Slug\" = @Slug", new { Slug = slug });
 
var lessons = await connection.QueryAsync<LessonRow>(
    "SELECT * FROM \"Lessons\" WHERE \"CourseId\" = @CourseId",
    new { CourseId = course.Id });   // round-trip thứ 2
 
var category = await connection.QuerySingleAsync<CategoryRow>(
    "SELECT * FROM \"Categories\" WHERE \"Id\" = @Id",
    new { Id = course.CategoryId }); // round-trip thứ 3
 
var instructor = await connection.QuerySingleAsync<InstructorRow>(
    "SELECT * FROM \"Instructors\" WHERE \"Id\" = @Id",
    new { Id = course.InstructorId }); // round-trip thứ 4
```

4 round-trip cho đúng 1 Course. Với danh sách nhiều Course (ví dụ trang "Khóa học của tôi" ở bài 7.6 lặp qua từng Enrollment để lấy chi tiết Course), số round-trip nhân lên theo N — đúng nghĩa đen của tên gọi "N+1": 1 query lấy danh sách cha, cộng thêm N query lấy dữ liệu con cho từng phần tử. Vấn đề không nằm ở việc dùng Dapper hay EF Core — N+1 là lỗi thiết kế query, xảy ra ở bất kỳ ORM/data access nào nếu bạn tách các bước fetch dữ liệu quan hệ thành nhiều round-trip tuần tự thay vì gộp bằng JOIN.

Giải pháp đúng: viết đúng 1 câu SQL JOIN đủ 4 bảng, rồi dùng Dapper multi-mapping để tách 1 dòng kết quả phẳng (flat row) trở lại thành object đồ thị lồng nhau (Course chứa Category, Instructor, danh sách Lesson) — không cần round-trip thứ 2.

> **📘 Ghi chú giảng viên:** *Tôi hay hỏi học viên: "Nếu chỉ có 1 Course, N+1 gây chậm cỡ nào?" — với 1 Course thì chỉ chậm hơn khoảng 3 round-trip network, có thể không cảm nhận được trên máy dev. Nhưng thói quen viết Handler kiểu tuần tự này rất dễ bị copy sang chỗ khác (ví dụ Handler duyệt danh sách Order rồi query rời Course cho từng OrderItem) — lúc đó N+1 mới thật sự gây chậm rõ rệt trên production. Sửa thói quen từ bài nhỏ như thế này quan trọng hơn bản thân con số benchmark.*

## **2. Thiết kế DTO cho Course Detail**

*Thời lượng: 5 phút | Loại: Demo*

Giữ đúng tinh thần bài 1.6: DTO trả ra ngoài API chỉ chứa dữ liệu sạch, không lộ chi tiết kỹ thuật của câu query. CourseDetailDto và LessonSummaryDto đặt cùng namespace với Query, theo đúng cấu trúc thư mục Application layer đã dùng cho GetCoursesList ở bài 1.6.

namespace TeduMarket.Application.Courses.Queries.GetCourseDetail;
 
public sealed record CourseDetailDto(

> **📘 Ghi chú giảng viên:** *LessonSummaryDto cố tình KHÔNG có VideoUrl. Nhắc trước điểm này ở đây để học viên không tiện tay thêm VideoUrl vào DTO chỉ vì "đằng nào cũng có sẵn cột trong bảng Lessons".*

## **3. GetCourseDetailQuery — Dapper multi-mapping**

*Thời lượng: 15 phút | Loại: Demo*

Theo đúng quy ước đặt tên mục 7 outline, Query lấy 1 bản ghi theo tham số dùng mẫu Get{Thực thể}Query — khớp GetCourseDetailQuery đã được nhắc tới làm ví dụ ngay từ bài 1.6.

```csharp
using MediatR;
 
namespace TeduMarket.Application.Courses.Queries.GetCourseDetail;
 
public sealed record GetCourseDetailQuery(string Slug)
    : IRequest<CourseDetailDto?>;
```

Câu SQL JOIN đủ 4 bảng trong 1 lần, LEFT JOIN Lessons vì Course mới tạo (Draft) có thể chưa có Lesson nào — INNER JOIN ở đây sẽ làm biến mất luôn cả Course khỏi kết quả, sai hoàn toàn với ý định của Query:

```sql
SELECT
    c."Id", c."Title", c."Slug", c."ThumbnailUrl",
    c."Price", c."DiscountPrice", c."CreatedAt",
    cat."Id" AS "CategoryId", cat."Name" AS "CategoryName",
    ins."Id" AS "InstructorId", ins."FullName" AS "InstructorName",
    l."Id" AS "LessonId", l."Title" AS "LessonTitle",
    l."OrderIndex", l."DurationInSeconds"
FROM "Courses" c
INNER JOIN "Categories" cat ON cat."Id" = c."CategoryId"
INNER JOIN "Instructors" ins ON ins."Id" = c."InstructorId"
LEFT JOIN "Lessons" l ON l."CourseId" = c."Id"
WHERE c."Slug" = @Slug AND c."IsPublished" = TRUE
ORDER BY l."OrderIndex" ASC;
```

Category và Instructor dùng INNER JOIN vì bài 1.2 đã bắt buộc CategoryId và InstructorId khi CreateCourse — 2 quan hệ này không bao giờ NULL. Lesson dùng LEFT JOIN vì quan hệ Course–Lesson là optional ở thời điểm Draft (invariant Publish() ở bài 1.1 chỉ chặn publish khi 0 Lesson, không chặn việc tạo Course trước rồi thêm Lesson sau).

### **3.1. Row type cho từng phần multi-mapping**

Dapper multi-mapping cắt 1 dòng kết quả phẳng thành nhiều object dựa trên tham số splitOn — vị trí cột đầu tiên của mỗi "phần" tiếp theo. Cần 1 record ứng với mỗi phần, đặt private lồng trong Handler để không lộ ra ngoài Application layer:

```csharp
private sealed record CourseRow(
    Guid Id, string Title, string Slug, string? ThumbnailUrl,
    decimal Price, decimal? DiscountPrice, DateTime CreatedAt);
 
private sealed record CategoryRow(Guid CategoryId, string CategoryName);
 
private sealed record InstructorRow(Guid InstructorId, string InstructorName);
 
// Guid? / int? vì LEFT JOIN có thể trả NULL khi Course chưa có Lesson
private sealed record LessonRow(
    Guid? LessonId, string? LessonTitle,
    int? OrderIndex, int? DurationInSeconds);
```

> **📘 Ghi chú giảng viên:** *Điểm hay bị bỏ sót nhất bài này: nếu LessonRow khai báo Guid LessonId (không nullable) thay vì Guid?, Dapper sẽ map cột NULL thành default(Guid) = Guid.Empty thay vì báo lỗi — Handler chạy "được" nhưng âm thầm tạo ra 1 Lesson rác có Id toàn số 0 cho mọi Course chưa có bài học nào. Đây là lỗi im lặng, rất khó phát hiện nếu không viết test cho đúng trường hợp Course 0 Lesson.*

### **3.2. GetCourseDetailQueryHandler**

```csharp
using Dapper;
using MediatR;
using TeduMarket.Application.Common.Interfaces;
 
namespace TeduMarket.Application.Courses.Queries.GetCourseDetail;
 
public sealed class GetCourseDetailQueryHandler(IDapperConnectionFactory connectionFactory)
    : IRequestHandler<GetCourseDetailQuery, CourseDetailDto?>
{
    public async Task<CourseDetailDto?> Handle(
        GetCourseDetailQuery request, CancellationToken cancellationToken)
    {
        const string sql = """
            SELECT
                c."Id", c."Title", c."Slug", c."ThumbnailUrl",
                c."Price", c."DiscountPrice", c."CreatedAt",
                cat."Id" AS "CategoryId", cat."Name" AS "CategoryName",
                ins."Id" AS "InstructorId", ins."FullName" AS "InstructorName",
                l."Id" AS "LessonId", l."Title" AS "LessonTitle",
                l."OrderIndex", l."DurationInSeconds"
            FROM "Courses" c
            INNER JOIN "Categories" cat ON cat."Id" = c."CategoryId"
            INNER JOIN "Instructors" ins ON ins."Id" = c."InstructorId"
            LEFT JOIN "Lessons" l ON l."CourseId" = c."Id"
            WHERE c."Slug" = @Slug AND c."IsPublished" = TRUE
            ORDER BY l."OrderIndex" ASC;
            """;
 
        var lookup = new Dictionary<Guid, CourseAccumulator>();
 
        using var connection = connectionFactory.CreateConnection();
        await connection.QueryAsync<CourseRow, CategoryRow, InstructorRow, LessonRow, CourseAccumulator>(
            sql,
            (course, category, instructor, lesson) =>
            {
                if (!lookup.TryGetValue(course.Id, out var accumulator))
                {
                    accumulator = new CourseAccumulator(course, category, instructor);
                    lookup.Add(course.Id, accumulator);
                }
 
                if (lesson.LessonId is Guid lessonId)
                {
                    accumulator.Lessons.Add(new LessonSummaryDto(
                        lessonId, lesson.LessonTitle!,
                        lesson.OrderIndex!.Value, lesson.DurationInSeconds!.Value));
                }
 
                return accumulator;
            },
            param: new { request.Slug },
            splitOn: "CategoryId,InstructorId,LessonId");
 
        return lookup.Values.SingleOrDefault()?.ToDto();
    }
 
    private sealed class CourseAccumulator(
        CourseRow course, CategoryRow category, InstructorRow instructor)
    {
        public Guid Id { get; } = course.Id;
        public List<LessonSummaryDto> Lessons { get; } = [];
 
        public CourseDetailDto ToDto() => new(
            course.Id, course.Title, course.Slug, course.ThumbnailUrl,
            course.Price, course.DiscountPrice,
            category.CategoryId, category.CategoryName,
            instructor.InstructorId, instructor.InstructorName,
            course.CreatedAt, Lessons);
    }
}
```

Cơ chế cốt lõi: Dapper gọi hàm map 1 lần cho MỖI DÒNG kết quả trả về — tức là gọi N lần nếu Course có N Lesson (ít nhất 1 lần nếu 0 Lesson, do LEFT JOIN vẫn trả 1 dòng với phần Lesson toàn NULL). lookup.TryGetValue đảm bảo CourseAccumulator chỉ được tạo đúng 1 lần ở dòng đầu tiên; các dòng sau chỉ có tác dụng thêm 1 Lesson vào Lessons của accumulator đã có sẵn. Đây chính là kỹ thuật "gộp dòng phẳng về lại object cha-con" — thay thế hoàn toàn cho round-trip thứ 2 ở mục 1.

> **📘 Ghi chú giảng viên:** *param: new { request.Slug } dùng cú pháp target-typed new kết hợp shorthand property tên trùng field (implicit named argument từ C# 6, không phải feature mới) — Dapper tự soi property Slug trên object ẩn danh này để bind vào @Slug. Tôi hay nhắc học viên: object tham số không cần match tên class, chỉ cần match tên property với tên @tham_so trong SQL.*

## **4. Hoàn thiện endpoint GET /api/v1/courses/{slug}**

*Thời lượng: 7 phút | Loại: Demo*

Route dùng slug (không dùng Guid id) vì đây là endpoint công khai phục vụ trang Course Detail — slug thân thiện SEO, đúng với cách bài 7.3 (Next.js) sẽ gọi qua route /courses/[slug]. Đặt endpoint trong cùng route group /api/v1/courses đã tạo ở bài 1.2, cùng file với GetCoursesList (bài 1.6) hoặc file endpoint riêng đều được, miễn cùng group.

```csharp
using MediatR;
using TeduMarket.Application.Courses.Queries.GetCourseDetail;
 
namespace TeduMarket.Api.Endpoints.Courses;
 
public static class GetCourseDetailEndpoint
{
    public static void MapGetCourseDetail(this RouteGroupBuilder group)
    {
        group.MapGet("/{slug}", async (
            string slug,
            ISender sender,
            CancellationToken cancellationToken) =>
        {
            var result = await sender.Send(
                new GetCourseDetailQuery(slug), cancellationToken);
 
            return result is not null
                ? Results.Ok(result)
                : Results.NotFound();
        })
        .WithName("GetCourseDetail")
        .Produces<CourseDetailDto>(StatusCodes.Status200OK)
        .Produces(StatusCodes.Status404NotFound);
    }
}
```

Test bằng Scalar với slug thật từ seed data (bài 1.5): kiểm tra response có đủ CategoryName, InstructorName, và mảng Lessons đúng thứ tự OrderIndex tăng dần. Thử thêm 1 slug không tồn tại để xác nhận trả về 404 thay vì lỗi 500 — vì SingleOrDefault() ở Handler trả null khi Dictionary rỗng (Slug không khớp WHERE), không throw exception.

# **Bài tập thực hành**

> **✏️ Thực hành:** Viết 1 unit test (hoặc integration test tạm bằng console) xác nhận GetCourseDetailQueryHandler xử lý đúng Course có 0 Lesson: gọi Handler với slug của 1 Course vừa CreateCourse xong (chưa AddLesson lần nào), assert kết quả trả về Lessons.Count == 0 — KHÔNG phải Lessons chứa 1 phần tử có Id = Guid.Empty.

Input: slug của 1 Course mới tạo, chưa gọi AddLesson.

Expected output: CourseDetailDto khác null, Lessons là danh sách rỗng (Count = 0).

### **Hint**

- Nếu test fail với Lessons.Count == 1, quay lại kiểm tra LessonRow có đang khai báo Guid? LessonId (nullable) hay không — đây chính là lỗi đã nhắc ở mục 3.1.
- Có thể viết integration test thật bằng WebApplicationFactory + Testcontainers (sẽ học kỹ ở bài 8.3), hoặc tạm thời gọi trực tiếp qua mediator.Send trong 1 test thủ công như đã làm ở bài 0.4 nếu hạ tầng test chưa sẵn sàng.

# **Tổng kết**

> **✅ Tóm tắt:** GetCourseDetailQuery hoàn chỉnh: 1 câu SQL JOIN 4 bảng (Course, Category, Instructor, Lesson), dùng Dapper multi-mapping với Dictionary tích lũy để gộp N dòng phẳng thành 1 object cha chứa danh sách con — giải quyết triệt để N+1 đã nêu ở đầu bài, endpoint GET /api/v1/courses/{slug} trả 404 đúng chuẩn khi không tìm thấy.

5 điểm chính cần nhớ:

- N+1 là lỗi thiết kế query (tách round-trip lấy dữ liệu quan hệ thành nhiều bước tuần tự), không phải lỗi riêng của EF Core hay riêng của Dapper.
- Dapper multi-mapping cắt 1 dòng phẳng thành nhiều object bằng tham số splitOn — thứ tự splitOn phải khớp đúng thứ tự cột trong SELECT.
- LEFT JOIN cho quan hệ optional (Course có thể 0 Lesson) — row type tương ứng phải khai báo kiểu nullable, nếu không Dapper âm thầm tạo dữ liệu rác thay vì báo lỗi.
- Dictionary\<Guid, TAccumulator> là kỹ thuật chuẩn để gộp N dòng cùng 1 Course (do JOIN 1-nhiều với Lesson) về lại đúng 1 object kết quả.
- DTO trả ra API phải kiểm soát đúng phạm vi công khai — Course Detail công khai không lộ VideoUrl, dữ liệu bảo mật đó chỉ trả ở Query riêng cho trang Lesson Player sau khi xác thực Enrollment (bài 7.7).

### **N+1 round-trip: cách sai vs cách đúng**

| **Tiêu chí** | **❌ Query rời rạc (N+1)** | **✅ Multi-mapping (bài này)** |
|---|---|---|
| Số round-trip DB | 4 (Course, Lesson, Category, Instructor tách riêng) | 1 (JOIN sẵn trong SQL, tách lại bằng Dapper) |
| Với danh sách N Course | Round-trip nhân lên theo N — đây là nguồn gốc tên gọi N+1 | Vẫn giữ nguyên số round-trip cố định, không phụ thuộc N |
| Rủi ro chính | Dễ viết, dễ đọc lúc mới code, nhưng chậm dần khi dữ liệu lớn | Phải cẩn thận splitOn và kiểu nullable cho quan hệ optional |
