## 1. Vì sao đây là bài "trình diễn", không phải bài "xây"

Sau bài 5.1–5.3, chuỗi công cụ đã có đủ: openapi.json chuẩn hoá từ Module 4, 1 package api-client dùng chung qua workspace:\*, và 1 lệnh pnpm generate:client gộp mọi bước thủ công. Nhưng chưa ai thật sự thấy nó hoạt động trên cả 2 frontend app cùng lúc — bài này không thêm code sản phẩm nào mới, chỉ đưa ra bằng chứng chạy được trước khi đặt cả Module 6 (React Admin) và Module 7 (Next.js) lên nền móng đó.

Nói rõ 1 điểm quan trọng trước khi vào demo, để tránh học viên hiểu quá tay: có 2 loại thay đổi API khác hẳn nhau về mức độ nguy hiểm.

- Breaking change: đổi tên field, đổi kiểu dữ liệu, xoá field cũ — luôn bị TypeScript chặn ngay lúc biên dịch ở mọi consumer đang dùng đúng field đó.
- Additive change: thêm field mới (đặc biệt là optional) — không phá consumer cũ, vì TypeScript không bắt buộc phải biết field chưa từng khai báo.

Bài demo dựng cả 2 tình huống để học viên tự thấy sự khác biệt bằng mắt, không chỉ nghe định nghĩa.

> **⚠️ Lưu ý kỹ thuật:** Cả admin và web cùng báo lỗi trong demo này vì cả 2 hiện đang gọi CHUNG đúng 1 hàm SDK trong 1 file cảm biến tối giản — đây là set up demo, không phải vì kiến trúc đảm bảo mọi thay đổi luôn phá cả 2 app cùng lúc. Khi Module 6 và 7 viết UI thật, admin và web có thể dùng những field khác nhau của cùng 1 DTO — đổi 1 field lúc đó chỉ phá đúng app nào thật sự dùng field đó, giống bất kỳ hệ thống type-safe nào, không phải phép màu riêng của khóa học này.

## 2. Dựng "cảm biến" type-check ở apps/admin và apps/web

apps/admin, apps/web hiện vẫn là khung rỗng — script build/dev còn là placeholder echo từ bài 5.1, React (Vite) và Next.js thật sự dựng ở bài 6.1 và 7.1. Nhưng dependency workspace:\* tới @tedu-market/api-client đã khai từ bài 5.1, nên pnpm đã symlink package này vào node_modules của cả 2 app — chỉ cần thêm vừa đủ cấu hình để tsc kiểm tra kiểu, không cần chờ có UI thật.

Thêm vào MỖI app (admin và web) 3 thứ, sẽ bị thay bằng component thật ở Module 6.3 / 7.3:

### apps/admin/package.json — thêm devDependency và script typecheck

```json
{
  "name": "admin",
  "private": true,
  "version": "0.0.0",
  "scripts": {
    "build": "echo 'admin build placeholder — setup thật ở bài 6.1'",
    "dev": "echo 'admin dev placeholder'",
    "lint": "echo 'admin lint placeholder'",
    "typecheck": "tsc --noEmit"
  },
  "dependencies": {
    "@tedu-market/api-client": "workspace:*"
  },
  "devDependencies": {
    "typescript": "^5.7.0"
  }
}
```

apps/web/package.json giống hệt cấu trúc trên, chỉ đổi name thành "web". Không lặp lại toàn bộ ở đây — làm y hệt bằng cách copy khối scripts/dependencies/devDependencies.

### tsconfig.json tối giản cho cả 2 app

```json
// apps/admin/tsconfig.json và apps/web/tsconfig.json — nội dung giống hệt nhau
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "lib": ["ES2022", "DOM"],
    "strict": true,
    "noEmit": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

> **📘 Ghi chú giảng viên:** *moduleResolution: "bundler" khớp với cách packages/api-client đã build ở bài 5.2 (module: ESNext, cùng chiến lược resolve). Nếu 2 bên lệch moduleResolution, tsc ở admin/web có thể không tìm thấy đúng dist/index.d.ts dù package đã build đúng — một lỗi rất khó đoán nếu không biết nguyên nhân.*

### Cảm biến thật: src/smoke-test.ts

Gọi thử đúng 1 hàm SDK thật — getCourseDetail, sinh ra từ GetCourseDetailQuery (bài 1.7) — và log field title trong response:

```typescript
// apps/admin/src/smoke-test.ts
// "Cảm biến" type-safety tạm thời — Module 6.3 sẽ thay bằng component React thật
import { getCourseDetail } from '@tedu-market/api-client';
 
async function logCourseTitle(courseId: string) {
  const { data, error } = await getCourseDetail({ path: { id: courseId } });
  if (error) {
    console.error('[admin] Lỗi gọi API:', error);
    return;
  }
  console.log(`[admin] Course title: ${data?.title}`);
}
```

apps/web/src/smoke-test.ts viết y hệt, chỉ đổi prefix log thành [web] — mục đích là có 2 điểm gọi độc lập ở 2 app khác nhau, cùng tiêu thụ chung 1 field từ chung 1 package.

> **📘 Ghi chú giảng viên:** *data?.title viết thường (camelCase), không phải data?.Title — .NET 10 mặc định serialize JSON theo JsonNamingPolicy.CamelCase cho Minimal API, nên field C# Title trong CourseDto trở thành title trong response JSON, và types.gen.ts sinh ra interface cũng theo đúng casing đó. Đây là điểm học viên hay gõ nhầm nếu quen tư duy PascalCase của C#.*

### Đăng ký task typecheck trong turbo.json

Thêm task typecheck vào frontend/turbo.json, bên cạnh các task generate:client (bài 5.3) và build (bài 5.1–5.2) đã có:

```json
// frontend/turbo.json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**"]
    },
    "generate:client": {
      "cache": false,
      "outputs": ["src/**", "openapi.json"]
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "cache": false
    }
  }
}
```

> **📘 Ghi chú giảng viên:** *dependsOn: ["^build"] ở task typecheck là chốt kỹ thuật quan trọng nhất của bài này: nó buộc Turborepo build lại @tedu-market/api-client (sinh dist/ mới) TRƯỚC KHI chạy typecheck ở admin và web — dựa đúng vào chiều phụ thuộc workspace:\* đã khai từ bài 5.1. Nếu thiếu dòng này, pnpm generate:client (bài 5.3) chỉ cập nhật packages/api-client/src, còn dist/index.d.ts mà admin/web thật sự import vẫn là bản cũ — tsc sẽ không báo lỗi gì cả, tạo cảm giác sai rằng mọi thứ vẫn ổn.*

Cài lại dependency vừa thêm:

```bash
cd frontend
pnpm install
```

## 3. Baseline: xác nhận cả 2 app compile sạch trước khi đổi gì

```bash
pnpm exec turbo run typecheck
```

Kỳ vọng: admin#typecheck và web#typecheck đều PASS — field data?.title hiện khớp đúng CourseDto đang có. Đây là mốc "trước" để so sánh, bắt buộc phải chạy qua bước này trước khi đổi bất cứ gì ở backend, tránh học viên nhầm lẫn lỗi cấu hình môi trường với lỗi cố ý tạo ra ở bước sau.

## 4. Breaking change: đổi field Title ở backend

Vào TeduMarket.Application, tìm CourseDto dùng cho GetCourseDetailQuery (bài 1.7, Dapper multi-mapping). Đổi tên property Title thành CourseTitle — đúng thao tác học viên đã tự làm ở bài tập bài 5.3, lần này làm chính thức và đi hết chuỗi tới tận 2 frontend app thay vì dừng ở xem types.gen.ts:

```csharp
// TeduMarket.Application/Courses/Queries/GetCourseDetail/CourseDto.cs
public sealed record CourseDto(
    Guid Id,
    string CourseTitle,   // đổi từ Title
    decimal Price,
    string InstructorName);
```

Sửa alias trong câu SQL Dapper tương ứng — nếu quên bước này, property CourseTitle sẽ luôn null vì Dapper map theo tên cột trả về, không phải theo tên property C#:

```sql
-- trước
SELECT c."Title" AS "Title", c."Price", i."Name" AS "InstructorName"
FROM courses c JOIN instructors i ON i.id = c.instructor_id
WHERE c.id = @CourseId;
 
-- sau
SELECT c."Title" AS "CourseTitle", c."Price", i."Name" AS "InstructorName"
FROM courses c JOIN instructors i ON i.id = c.instructor_id
WHERE c.id = @CourseId;
```

## 6. Sửa lỗi, so sánh additive change, đưa hệ thống về baseline

Sửa cả 2 file smoke-test.ts, đổi data?.title thành data?.courseTitle, chạy lại pnpm exec turbo run typecheck — cả 2 app pass trở lại.

So sánh ngược lại bằng 1 additive change: thêm field Language (string, có default trong SQL, không NOT NULL) vào CourseDto, generate lại, typecheck lại:

```csharp
public sealed record CourseDto(
    Guid Id,
    string CourseTitle,
    decimal Price,
    string InstructorName,
    string Language = "vi");   // field mới, optional, có default
```

Chạy lại pnpm generate:client rồi pnpm exec turbo run typecheck — cả 2 app vẫn PASS, vì smoke-test.ts hiện tại không hề tham chiếu field Language. TypeScript chỉ chặn khi consumer thật sự dùng đúng field bị đổi/xoá, không chặn khi có field mới xuất hiện mà không ai dùng tới.

Đưa hệ thống về đúng baseline trước khi kết thúc bài, để bài 6.1/7.1 khởi động trên nền dữ liệu quen thuộc: revert CourseTitle về lại Title (cả C# record lẫn alias SQL), bỏ field Language vừa thêm demo, sửa 2 file smoke-test.ts dùng lại data?.title, generate lại lần cuối và xác nhận turbo run typecheck pass sạch.

> **⚠️ Lưu ý kỹ thuật:** Việc revert này là chủ ý sư phạm, không phải học viên tự tiện đổi ý — mọi bài giảng sau (đặc biệt 6.3, 7.3 dùng lại GetCourseDetailQuery) đều giả định CourseDto.Title giữ nguyên tên như bài 1.7 đã đặt. Nếu để CourseTitle tồn tại sau bài này, học viên chạy các bài sau theo đúng nội dung sách sẽ bị lệch code, khó dò nguyên nhân.

## Bài tập thực hành

> **✏️ Thực hành:** Chọn 1 DTO khác — ví dụ CourseDto dùng trong danh sách của GetCoursesListQuery (bài 1.6, khác record với CourseDto ở bài 1.7) — đổi tên 1 field bất kỳ, tự lặp lại đúng quy trình: đổi field ở backend → pnpm generate:client → pnpm exec turbo run typecheck. Quan sát: lần này chỉ app nào có smoke-test thật sự import và dùng field đó mới báo lỗi — không phải cứ đổi API là cả admin và web luôn cùng lỗi như ở phần demo chính. Ghi lại 1 câu giải thích vì sao khác nhau.

Hint: nếu cả 2 app vẫn cùng lỗi dù bạn chỉ sửa 1 file smoke-test, kiểm tra lại xem file kia có vô tình cũng import đúng field đó không — đây là lỗi thường gặp khi copy nguyên si code giữa 2 app mà không đọc lại.

Solution: chỉ sửa smoke-test.ts của app đang dùng field bị đổi → chỉ app đó fail ở turbo run typecheck, app còn lại vẫn PASS và không bị chạy lại (Turborepo cache task typecheck của app không đổi). Sau khi xác nhận đúng, revert lại field về tên ban đầu, generate lại, đảm bảo cả 2 app pass sạch trước khi rời bài.

## Tổng kết

- Lời hứa "đổi API backend → generate lại 1 lệnh → N app nhận type mới cùng lúc" chỉ thành hiện thực khi 3 điều kiện cùng đúng: OpenAPI schema chuẩn hoá (Module 4), 1 package api-client dùng chung qua workspace:\* (bài 5.1), và 1 lệnh generate rút gọn (bài 5.2–5.3) — bài này là bằng chứng chạy được, không phải khẳng định suông.
- turbo.json task typecheck với dependsOn: ["^build"] là chốt kỹ thuật bắt buộc — thiếu dòng này, generate:client chỉ cập nhật src/ của api-client mà không rebuild dist/, khiến tsc ở admin/web vẫn đọc type cũ và không báo lỗi gì, tạo cảm giác sai lệch rằng hệ thống an toàn.
- Breaking change (đổi/xoá field) luôn bị TypeScript chặn compile-time ở đúng consumer đang dùng field đó; additive change (thêm field optional) không phá consumer cũ — 2 hành vi khác nhau rõ ràng, không phải "đổi gì cũng báo lỗi cả 2 app".
- Hệ thống đã được đưa về đúng baseline (CourseDto.Title, không có Language) trước khi kết thúc bài — Module 6 và 7 khởi động đúng trên nền dữ liệu bài 1.7 đã thiết lập, không bị lệch do phần demo của bài này.

**Bước tiếp theo:** Module 5 khép lại ở đây. Bài 6.1 sẽ thay apps/admin/src/smoke-test.ts bằng project React (Vite) thật đầu tiên, và bắt đầu dùng thật getCategories, getCourseDetail cùng các hàm SDK khác trong UI, không còn gọi tay để kiểm tra như bài này nữa.
