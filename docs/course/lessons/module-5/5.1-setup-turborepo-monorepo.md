## 1. Vì sao TEDU Market dùng Turborepo thay vì multi-repo

Từ Module 5 trở đi, dự án có 2 ứng dụng frontend sống song song: apps/admin (React/Vite, dạy ở Module 6) và apps/web (Next.js App Router, dạy ở Module 7). Cả hai đều gọi chung 1 backend API, và quan trọng hơn — cả hai đều cần dùng chung 1 bộ type TypeScript được generate từ OpenAPI schema (packages/api-client, dạy ở bài 5.2). Đây chính là lý do outline khóa học chốt kiến trúc "tách API client thành package riêng" ở mục 5, quyết định 3.

Nếu tách admin và web thành 2 repo độc lập, mỗi lần backend đổi API, bạn phải: generate lại client, publish lên npm (hoặc registry riêng), rồi vào từng repo admin/web để bump version — 3 bước thủ công, dễ quên, và 2 app dễ bị lệch version client với nhau. Monorepo giải quyết đúng vấn đề này: 1 lệnh generate, cả 2 app dùng ngay bản mới nhất qua workspace dependency (workspace:\*), không qua registry, không qua version bump thủ công.

Turborepo không phải là package manager — nó là task runner/orchestrator chạy trên nền workspace của package manager (ở đây là pnpm). Turborepo giải quyết 2 vấn đề mà npm/pnpm workspace thuần không có sẵn:

- Task graph theo thứ tự phụ thuộc: build packages/api-client phải xong trước khi build apps/admin, vì admin import type từ api-client. Turborepo tự suy ra thứ tự này từ dependency trong package.json, bạn không cần viết script điều phối tay.
- Cache: nếu packages/api-client không đổi, lần build sau Turborepo trả kết quả từ cache ngay lập tức thay vì build lại — quan trọng khi khóa học sang Module 9 làm CI/CD, vì pipeline build 2 app + 1 package mỗi lần push code sẽ rất chậm nếu build lại từ đầu.

> **📘 Ghi chú giảng viên:** *Tôi hay bị học viên hỏi "sao không dùng Nx, nó mạnh hơn?". Câu trả lời thật lòng: Nx đúng là có nhiều plugin và generator hơn, nhưng đi kèm độ phức tạp cấu hình cao hơn hẳn. Với quy mô 2 app + 1 package của TEDU Market, Turborepo đủ dùng và học trong 45 phút là nắm được toàn bộ, còn Nx cần nguyên 1 buổi riêng chỉ để hiểu executor/generator. Chọn công cụ đúng độ phức tạp của bài toán, không phải công cụ mạnh nhất trên giấy.*

## 2. Cấu trúc monorepo tedu-market-frontend

Đúng theo mục 6 của outline chuẩn, cấu trúc thư mục frontend/ nằm ngang hàng với backend/ trong repo gốc TEDU Market (repo gốc còn có docker-compose.yml orchestrate cả hai — sẽ dùng tới ở Module 9). Trong bài này, ta chỉ làm việc bên trong frontend/:

```
frontend/
├── apps/
│   ├── admin/          # React (Vite) — dựng đầy đủ ở Module 6
│   └── web/            # Next.js (App Router) — dựng đầy đủ ở Module 7
├── packages/
│   └── api-client/     # Generate bằng @hey-api/openapi-ts — bài 5.2
├── turbo.json
├── pnpm-workspace.yaml
└── package.json
```

Ở bài này, apps/admin, apps/web và packages/api-client chỉ là khung rỗng (placeholder) — Vite/Next.js thật sự sẽ setup ở 6.1 và 7.1, code generate client thật sẽ có ở 5.2. Mục tiêu duy nhất của 5.1 là: pnpm nhận diện đúng 3 package con này là thành viên workspace, và Turborepo chạy task theo đúng thứ tự phụ thuộc giữa chúng.

### Bước 1 — Khởi tạo package.json gốc và pnpm-workspace.yaml

Tạo thư mục frontend/ trong repo gốc, sau đó:

```bash
cd frontend
pnpm init
 
# Bật Corepack để pin đúng version pnpm cho cả team — tránh lệch
# version pnpm giữa các máy dẫn đến lockfile không nhất quán.
corepack enable
corepack use pnpm@10
```

Khai báo workspace — đây là file pnpm đọc để biết những thư mục nào là package con:

```yaml
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"
```

> **📘 Ghi chú giảng viên:** *Điểm hay bị nhầm: pnpm-workspace.yaml chỉ khai báo "những thư mục nào được coi là package", nó không tự tạo ra các thư mục đó. Bạn vẫn phải mkdir apps/admin, apps/web, packages/api-client và mỗi thư mục phải có package.json riêng thì pnpm mới nhận diện được — thư mục rỗng không có package.json sẽ bị bỏ qua.*

### Bước 2 — Tạo khung 3 package con

Mỗi package con cần tối thiểu 1 package.json có field name và scripts (kể cả khi chưa có code thật, để turbo có target để chạy):

```bash
mkdir -p apps/admin apps/web packages/api-client
// apps/admin/package.json
{
  "name": "admin",
  "private": true,
  "version": "0.0.0",
  "scripts": {
    "build": "echo 'admin build placeholder — setup thật ở bài 6.1'",
    "dev": "echo 'admin dev placeholder'",
    "lint": "echo 'admin lint placeholder'"
  }
}
// apps/web/package.json
{
  "name": "web",
  "private": true,
  "version": "0.0.0",
  "scripts": {
    "build": "echo 'web build placeholder — setup thật ở bài 7.1'",
    "dev": "echo 'web dev placeholder'",
    "lint": "echo 'web lint placeholder'"
  }
}
// packages/api-client/package.json
{
  "name": "@tedu-market/api-client",
  "private": true,
  "version": "0.0.0",
  "main": "./dist/index.js",
  "scripts": {
    "build": "echo 'generate client thật ở bài 5.2'"
  }
}
```

Để mô phỏng đúng quan hệ phụ thuộc thật (admin và web sẽ import type từ api-client ở bài 5.2), khai báo workspace dependency ngay từ bây giờ trong apps/admin/package.json và apps/web/package.json:

```json
// thêm vào "dependencies" của apps/admin/package.json và apps/web/package.json
"dependencies": {
  "@tedu-market/api-client": "workspace:*"
}
```

> **📘 Ghi chú giảng viên:** *workspace:\* là protocol riêng của pnpm (và Yarn/npm workspace): nó nói "lấy đúng bản package-này-đang-nằm-trong-repo, không lên npm registry tìm". Đây chính là cơ chế kỹ thuật đứng sau lời hứa ở outline: "đổi API ở backend → generate lại 1 lệnh → cả 2 app nhận type mới cùng lúc" — vì admin và web không resolve api-client qua registry, mà trỏ thẳng vào thư mục packages/api-client trên đĩa.*

## 3. Cấu hình turbo.json — khai báo task graph

Cài turbo làm dev dependency ở workspace root (không cài riêng trong từng app):

```bash
pnpm add -D -w turbo
```

Tạo turbo.json ở thư mục gốc frontend/:

```json
// turbo.json
{
  "$schema": "https://turborepo.dev/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "lint": {
      "outputs": []
    }
  }
}
```

> **📘 Ghi chú giảng viên:** *Outline gốc ghi "turbo.json pipeline (build, dev, lint...)" — chữ "pipeline" ở đây là cách gọi khái niệm chung (task pipeline), không phải tên field JSON. Từ Turborepo v2 trở lên (bản hiện hành khi soạn bài này), field JSON đúng là "tasks", còn "pipeline" là tên cũ của Turborepo v1 và đã bị loại bỏ. Nếu học viên tra tài liệu cũ hoặc video cũ trên mạng thấy "pipeline": {...}, phải nói rõ đó là cú pháp lỗi thời, dùng sẽ báo lỗi ở version hiện tại.*

Giải thích từng phần:

- dependsOn: ["^build"] trên task build: dấu ^ nghĩa là "chờ task build của mọi package mà package-này phụ thuộc, hoàn thành trước". Vì apps/admin và apps/web có dependency workspace:\* tới @tedu-market/api-client, Turborepo tự suy ra: phải build api-client xong trước, rồi mới build admin/web. Không cần bạn viết thứ tự tay.
- outputs: ["dist/\*\*", ".next/\*\*"] khai báo thư mục nào là kết quả build cần cache lại — dist cho Vite/api-client, .next cho Next.js. Turborepo hash input (source code + dependency), nếu hash không đổi thì trả outputs từ cache thay vì chạy lại script.
- dev có cache: false và persistent: true vì dev server chạy vô tận (watch mode), không có "kết quả cuối" để cache, và Turborepo cần biết task này không tự thoát để không coi là bị treo.
- lint có outputs: [] — không sinh ra file nào, nhưng vẫn được cache theo log/exit code, hữu ích khi Module 9 chạy trong CI.

### Bổ sung script điều phối ở package.json gốc

```json
// package.json (thư mục gốc frontend/)
{
  "name": "tedu-market-frontend",
  "private": true,
  "packageManager": "pnpm@10.0.0",
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev",
    "lint": "turbo run lint"
  },
  "devDependencies": {
    "turbo": "^2.5.0"
  }
}
```

> **📘 Ghi chú giảng viên:** *Trường packageManager là bắt buộc nên có, không phải tùy chọn: nó khóa đúng version pnpm cho toàn bộ team và CI (Module 9 sẽ dựa vào field này để cài đúng pnpm trong GitHub Actions). Thiếu field này, một bạn trong team lỡ dùng pnpm 8 có thể tạo ra lockfile không tương thích với người dùng pnpm 10.*

## 4. Cài đặt và verify task graph

Chạy cài đặt từ thư mục gốc frontend/:

```bash
pnpm install
```

Kết quả mong đợi: pnpm nhận diện đúng 3 workspace package (admin, web, @tedu-market/api-client), tạo 1 pnpm-lock.yaml duy nhất ở gốc, và symlink @tedu-market/api-client vào node_modules của admin/web (đây là cách workspace:\* hoạt động — symlink trên đĩa, không copy code).

Verify thứ tự thực thi task bằng --dry-run trước khi tin vào kết quả thật — thói quen nên có trước khi chạy build thật trên monorepo lớn dần theo khóa học:

```bash
pnpm exec turbo run build --dry-run
```

Đọc phần "Tasks to Run" trong output: @tedu-market/api-client#build phải đứng trước admin#build và web#build. Nếu thứ tự ngược lại hoặc api-client không xuất hiện trong graph, nghĩa là dependency workspace:\* ở bước 2 khai báo sai (kiểm tra lại đúng tên package trong dependencies có khớp field name của api-client/package.json không — pnpm resolve theo tên, không theo đường dẫn thư mục).

Chạy thật để chắc chắn không có lỗi cấu hình:

```bash
pnpm build
```

> **📘 Ghi chú giảng viên:** *Lần build đầu luôn là cache MISS cho cả 3 package (chưa có gì để cache). Chạy lại pnpm build lần 2 ngay sau đó, bạn sẽ thấy log ghi FULL TURBO hoặc cache hit — vì input (chỉ có 3 dòng echo placeholder) không đổi. Đây là lúc tốt để cho học viên thấy giá trị cache bằng mắt, dù nội dung build chưa có gì thật — cảm nhận về tốc độ quan trọng hơn giải thích lý thuyết suông ở bước này.*

## Bài tập thực hành

Đề bài: Thêm 1 package con mới tên packages/config chứa file tsconfig.base.json dùng chung (chưa cần nội dung phức tạp, chỉ cần compilerOptions cơ bản). Khai báo workspace dependency từ apps/admin và apps/web tới package này, thêm task "typecheck" vào turbo.json với dependsOn phù hợp, rồi verify bằng --dry-run rằng packages/config#build (nếu có) hoặc chính bản thân config đứng đúng vị trí trong task graph trước khi admin/web chạy typecheck.

- Input: monorepo tedu-market-frontend đã có sau phần Demo ở trên.
- Expected output: pnpm exec turbo run typecheck --dry-run hiển thị đúng 2 task (admin#typecheck, web#typecheck), không báo lỗi "could not find package".
- Hint 1: packages/config không nhất thiết cần script "build" nếu nó chỉ export file cấu hình tĩnh (tsconfig, eslint config) — task dependsOn có thể trỏ vào task "typecheck" phụ thuộc trực tiếp dependency đó qua workspace:\*, Turborepo vẫn suy ra đúng thứ tự cài đặt dù không có task build tương ứng.
- Hint 2: nếu turbo báo "Cannot find module" khi resolve workspace:\*, 90% là do quên chạy lại pnpm install sau khi thêm dependency mới — pnpm không tự động symlink lại khi bạn chỉ sửa tay package.json.

> **✏️ Thực hành:** Làm xong, so với repo mẫu: 4 package con (admin, web, api-client, config), 4 task trong turbo.json (build, dev, lint, typecheck), pnpm install và pnpm exec turbo run build lint typecheck --dry-run chạy sạch không lỗi.

## Tổng kết

- Turborepo là task orchestrator chạy trên nền pnpm workspace, giải quyết đúng 2 vấn đề: thứ tự build theo dependency graph, và cache kết quả build.
- Cấu trúc tedu-market-frontend gồm apps/admin, apps/web, packages/api-client — đúng mục 6 outline, hiện tại mới là khung rỗng.
- workspace:\* là cơ chế kỹ thuật cho phép "generate lại 1 lệnh, cả 2 app nhận type mới cùng lúc" — không qua npm registry.
- turbo.json dùng field "tasks" (không phải "pipeline" — tên cũ của Turborepo v1), dependsOn: ["^build"] là cách khai báo thứ tự topological.

> **✅ Tóm tắt:** Monorepo đã có khung, task graph đã đúng thứ tự — nhưng packages/api-client vẫn đang rỗng. Bài 5.2 sẽ dùng @hey-api/openapi-ts đọc openapi.json từ Module 4 để generate type-safe client thật vào đúng package này, và bạn sẽ thấy dependsOn: ["^build"] vừa cấu hình ở bài này phát huy tác dụng ngay khi build admin/web.
