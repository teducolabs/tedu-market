## **Nội dung chính**

### **1. Vì sao chỉ Checkout/Payment cần rate limit trước, không phải mọi endpoint**

*~5 phút · Lý thuyết*

Không phải endpoint nào cũng đáng để rate limit ngay. Tiêu chí chọn: endpoint đó tốn bao nhiêu tài nguyên mỗi lần gọi, và hậu quả nghiệp vụ nếu bị gọi spam là gì.

- POST /api/v1/cart/checkout — mỗi lần gọi ghi 2 Aggregate (Order + Cart) trong 1 transaction (bài 2.2). Spam endpoint này tạo hàng loạt Order rác ở trạng thái Pending, làm nhiễu dữ liệu báo cáo doanh thu (bài 2.8) và tốn connection pool Postgres.
- POST /api/v1/payments/initiate — mỗi lần gọi ra ngoài tạo ảnh QR qua VietQR (bài 2.4), có độ trễ mạng thật, không phải tính toán nội bộ. Bị gọi liên tục vừa tốn băng thông vừa có thể chạm rate limit của bên VietQR.

Ngược lại, GET /api/v1/payments/{orderId}/status chỉ SELECT 1 dòng qua Dapper (bài 2.4) — rẻ, và quan trọng hơn: Next.js Student site (bài 7.5) sẽ chủ động gọi lại mỗi 3 giây để polling trạng thái thanh toán. Nếu áp cùng 1 policy chặt cho endpoint này như Checkout, chính luồng nghiệp vụ hợp lệ sẽ tự chặn chính nó.

> **⚠️ Lưu ý:** Outline bài này giới hạn phạm vi ở nhóm endpoint Checkout/Payment (Module 2). Endpoint webhook POST /api/v1/webhooks/sepay (bài 2.5) KHÔNG nằm trong phạm vi rate limit theo user ở bài này — nó không có ClaimsPrincipal (được gọi bởi server SePay, không phải người dùng đăng nhập), và đã có lớp bảo vệ riêng là xác thực chữ ký HMAC-SHA256. Rate limit endpoint này theo IP là một hướng phòng thủ sâu hợp lý, nhưng cần cân nhắc kỹ để không vô tình chặn nhầm request retry hợp lệ của SePay — đặt thành bài tập cuối bài, không làm trong phần Demo chính.

### **2. Bốn loại Limiter có sẵn trong .NET — chọn đúng loại cho đúng việc**

*~3 phút · Lý thuyết*

Microsoft.AspNetCore.RateLimiting có sẵn từ ASP.NET Core 7.0, nằm trong shared framework — không cần cài thêm gói NuGet nào, khác với Asp.Versioning ở bài 4.3 phải cài riêng.

| **Loại limiter** | **Cơ chế** | **Dùng khi nào** |
|---|---|---|
| Fixed Window | Đếm request trong 1 khung giờ cố định, hết khung reset về 0 | Giới hạn đơn giản, dễ giải thích cho học viên — dùng cho Checkout/InitiatePayment ở bài này |
| Sliding Window | Giống Fixed Window nhưng chia nhỏ khung thành segment, mượt hơn ở ranh giới khung | Cần giới hạn chính xác hơn, tránh hiện tượng dồn request ngay đầu khung mới |
| Token Bucket | Cấp lại token đều đặn theo chu kỳ, cho phép burst trong giới hạn token còn lại | Traffic có tính chất bùng nổ ngắn hạn nhưng cần throughput ổn định dài hạn |
| Concurrency | Giới hạn số request ĐANG xử lý đồng thời, không giới hạn theo thời gian | Bảo vệ tài nguyên tốn CPU/I/O lâu (ví dụ export báo cáo) — không phù hợp Checkout vì Checkout xử lý nhanh |

Bài này dùng Fixed Window cho cả 2 endpoint chính vì đơn giản, đủ dùng, và là loại phổ biến nhất trong thực tế cho nhóm endpoint ghi dữ liệu tần suất thấp như Checkout.

### **3. Cấu hình named policy, partition theo user identity thật**

*~7 phút · Demo*

Ở bài 2.2, UserId được truyền tay trong request body — đã ghi rõ khi đó là cách làm tạm, chờ OpenIddict. Từ Module 3 (bài 3.2 trở đi), Access Token đã có claim user thật. Ở bài này, ta dùng đúng claim đó để partition rate limiter theo TỪNG user, không dùng UserId client tự gửi (dễ giả mạo để né rate limit) và cũng không dùng IP (nhiều user sau NAT/proxy chung 1 IP công ty sẽ bị chặn oan).

Trong Program.cs của TeduMarket.Api, đăng ký named policy "payment-sensitive":

```csharp
using Microsoft.AspNetCore.RateLimiting;
using System.Threading.RateLimiting;
 
builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
 
    options.AddPolicy("payment-sensitive", httpContext =>
    {
        // Claim "sub" do OpenIddict cấp (bai 3.5) - id nguoi dung that,
        // khong tin request body nhu cach lam tam o bai 2.2 nua.
        var userId = httpContext.User.FindFirst("sub")?.Value ?? "anonymous";
 
        return RateLimitPartition.GetFixedWindowLimiter(
            partitionKey: userId,
            factory: _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 5,
                Window = TimeSpan.FromMinutes(1),
                QueueProcessingOrder = QueueProcessingOrder.OldestFirst,
                QueueLimit = 0,
                AutoReplenishment = true,
            });
    });
 
    options.AddPolicy("payment-status-poll", httpContext =>
    {
        var userId = httpContext.User.FindFirst("sub")?.Value ?? "anonymous";
 
        return RateLimitPartition.GetFixedWindowLimiter(
            partitionKey: userId,
            factory: _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 30,
                Window = TimeSpan.FromMinutes(1),
                QueueProcessingOrder = QueueProcessingOrder.OldestFirst,
                QueueLimit = 0,
                AutoReplenishment = true,
            });
    });
 
    options.OnRejected = async (context, cancellationToken) =>
    {
        if (context.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retryAfter))
        {
            context.HttpContext.Response.Headers.RetryAfter =
                ((int)retryAfter.TotalSeconds).ToString();
        }
 
        context.HttpContext.Response.ContentType = "application/problem+json";
        await context.HttpContext.Response.WriteAsJsonAsync(new
        {
            type = "https://tools.ietf.org/html/rfc6585#section-4",
            title = "Qua nhieu yeu cau, vui long thu lai sau.",
            status = 429,
        }, cancellationToken);
    };
});
```

Vì sao 2 policy tách riêng thay vì dùng chung 1: "payment-sensitive" giới hạn 5 lần/phút — đủ cho hành vi mua hàng thật (kể cả bấm nhầm 1-2 lần), nhưng đủ chặt để không cho bot tạo Order rác. "payment-status-poll" cho 30 lần/phút — Next.js polling mỗi 3 giây = 20 lần/phút, để dư 10 lần làm buffer cho việc user mở nhiều tab cùng lúc.

> **📘 Ghi chú giảng viên:** *Điểm hay bị hỏi: tại sao không dùng options.GlobalLimiter áp cho toàn bộ API như ví dụ đơn giản nhất trong docs Microsoft? Vì GlobalLimiter áp cho MỌI endpoint kể cả GET /api/v1/courses (endpoint công khai, không cần giới hạn chặt như vậy) — sẽ phải viết logic if/else phân biệt endpoint ngay trong hàm partition, rối hơn nhiều so với việc đăng ký nhiều named policy và gắn đúng chỗ. Named policy + RequireRateLimiting đúng tinh thần CQRS mà khóa theo từ đầu: mỗi endpoint tự khai báo rõ ràng nó cần gì, không có một khối cấu hình toàn cục âm thầm chi phối.*

### **4. Áp policy vào đúng endpoint, không áp cả nhóm**

*~6 phút · Demo/Lab*

Checkout nằm trong CartEndpoints (group /api/v1/cart từ bài 2.2), cùng nhóm với AddToCart — endpoint AddToCart KHÔNG cần giới hạn chặt như Checkout, nên gắn RequireRateLimiting trực tiếp lên từng MapPost, không gọi ở cấp group:

```csharp
// TeduMarket.Api/Endpoints/CartEndpoints.cs
var cartApi = app.NewVersionedApi("Cart");
var cartV1 = cartApi.MapGroup("api/v{version:apiVersion}/cart").HasApiVersion("1.0");
 
cartV1.MapPost("/items", AddToCartAsync)
    .WithName("AddToCart");
    // KHONG RequireRateLimiting - them 1 khoa hoc vao gio hang la thao tac re,
    // khong can gioi han chat nhu Checkout.
 
cartV1.MapPost("/checkout", CheckoutAsync)
    .WithName("Checkout")
    .RequireRateLimiting("payment-sensitive");
```

Tương tự cho PaymentEndpoints (group /api/v1/payments từ bài 2.4) — 2 endpoint trong cùng group nhưng nhận 2 policy khác nhau:

```csharp
// TeduMarket.Api/Endpoints/PaymentEndpoints.cs
var paymentsApi = app.NewVersionedApi("Payments");
var paymentsV1 = paymentsApi.MapGroup("api/v{version:apiVersion}/payments").HasApiVersion("1.0");
 
paymentsV1.MapPost("/initiate", InitiatePaymentAsync)
    .WithName("InitiatePayment")
    .RequireRateLimiting("payment-sensitive");
 
paymentsV1.MapGet("/{orderId:guid}/status", GetOrderPaymentStatusAsync)
    .WithName("GetOrderPaymentStatus")
    .RequireRateLimiting("payment-status-poll");
```

> **📘 Ghi chú giảng viên:** *Đã học nhóm route "api/v1/cart" và "api/v1/payments" viết cứng lần lượt ở bài 2.2 và 2.4, giờ đã đi qua NewVersionedApi() từ bài 4.3, nên ở bài này viết thẳng theo dạng đã chuẩn hóa — không quay lại dạng string literal cũ nữa. Nếu học viên nào chưa làm bài tập refactor ở bài 4.3, cứ tạm dùng "api/v1/cart" viết cứng, RequireRateLimiting vẫn hoạt động y hệt vì đây là 2 cơ chế độc lập nhau — versioning và rate limiting không phụ thuộc lẫn nhau.*

### **5. Vị trí app.UseRateLimiter() trong pipeline**

*~3 phút · Demo*

Microsoft Learn quy định UseRateLimiter() phải gọi sau UseRouting khi rate limit theo endpoint cụ thể (RequireRateLimiting). Ở đây có thêm 1 ràng buộc thực tế nữa: hàm partition đọc httpContext.User.FindFirst("sub") — claim này chỉ tồn tại SAU KHI UseAuthentication() đã chạy. Đặt UseRateLimiter() trước UseAuthentication sẽ khiến mọi request rơi vào nhánh ?? "anonymous", tất cả user dùng chung 1 partition — sai hoàn toàn ý đồ thiết kế:

```csharp
// Program.cs - thu tu middleware (bo sung tiep vao pipeline da co tu bai 0.9, 3.9)
app.UseHttpsRedirection();
app.UseCors();
 
app.UseRouting();
 
app.UseAuthentication();   // phai truoc UseRateLimiter - can httpContext.User
app.UseAuthorization();
 
app.UseRateLimiter();      // phai sau UseRouting (yeu cau cua middleware)
 
app.MapCartEndpoints();
app.MapPaymentEndpoints();
// ...
app.Run();
```

> **⚠️ Lưu ý:** Đặt sai thứ tự không báo lỗi biên dịch, không throw exception lúc chạy — endpoint vẫn trả response bình thường, chỉ là rate limit áp nhầm theo 1 partition chung cho tất cả user thay vì theo từng người. Loại bug này rất dễ lọt qua test thủ công vì mọi thứ trông vẫn "chạy được", chỉ sai khi có nhiều user thật cùng lúc — đúng loại lỗi 'không throw exception, không crash, chỉ âm thầm sai' mà tôi hay nhấn mạnh học viên phải tự kiểm chứng bằng cách đọc log hoặc test có chủ đích, không suy luận từ việc code build thành công.

### **6. Test bằng vòng lặp curl**

*~3 phút · Lab*

Test nhanh không cần dựng UI, gọi liên tiếp 7 lần vào endpoint đã áp policy 5 lần/phút (thay TOKEN bằng access token thật lấy từ bài 3.3):

```
for i in $(seq 1 7); do
  echo "Lan goi $i:"
  curl -s -o /dev/null -w "  HTTP %{http_code}\n" \
    -X POST http://localhost:5000/api/v1/cart/checkout \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{}'
done
```

Kết quả mong đợi: 5 lần đầu trả về mã trạng thái nghiệp vụ bình thường (201 nếu giỏ hàng có sản phẩm, 400 nếu giỏ hàng rỗng — không quan trọng ở bài này), lần thứ 6 và 7 trả về 429 Too Many Requests kèm header Retry-After. Đổi $TOKEN sang access token của user khác (đăng nhập tài khoản thứ 2) và chạy lại — 5 lần đầu lại thành công bình thường, chứng minh partition theo user hoạt động đúng, không bị user A làm ảnh hưởng user B.

## **Bài tập thực hành**

> **✏️ Thực hành:** Endpoint POST /api/v1/webhooks/sepay (bài 2.5) không có ClaimsPrincipal vì được SePay gọi trực tiếp, không qua OpenIddict. Hãy thiết kế 1 named policy rate limit theo IP (dùng httpContext.Connection.RemoteIpAddress) cho endpoint này, với mức giới hạn đủ rộng để không chặn nhầm request hợp lệ. Viết ra: bạn chọn loại limiter nào (Fixed Window, Sliding Window, Token Bucket, hay Concurrency) và giải thích vì sao loại đó phù hợp hơn Fixed Window đã dùng cho Checkout.

Hint: webhook có thể gọi lại nhiều lần liên tiếp khi SePay retry cho cùng 1 giao dịch (đã học idempotency chặn trùng ở tầng DB tại bài 2.5) — rate limit ở đây chỉ nhằm chặn traffic bất thường (không phải SePay thật), không nhằm giới hạn tần suất giao dịch hợp lệ. Vì vậy PermitLimit nên đặt cao hơn hẳn mức traffic thật mà bạn ước tính, khác hẳn tư duy "giới hạn chặt" dùng cho Checkout.

> **✏️ Thực hành:** Áp thêm policy tương tự "payment-status-poll" cho GetOrderHistoryQuery và GetInstructorRevenueQuery (bài 2.8) — 2 endpoint này cũng được React Admin (bài 6.4) gọi khá thường xuyên khi user mở dashboard. Kiểm tra lại bằng curl loop giống bước 6.

## **Tổng kết**

> **✅** Không rate limit toàn bộ API cùng 1 mức — chọn đúng endpoint tốn tài nguyên/nhạy cảm nghiệp vụ (Checkout, InitiatePayment), và tách policy riêng cho endpoint polling hợp lệ tần suất cao (GetOrderPaymentStatus).
>
> **✅** Fixed Window Limiter đủ dùng cho nhóm endpoint ghi dữ liệu tần suất thấp; 4 loại limiter khác nhau phục vụ 4 tình huống khác nhau, không có loại nào là mặc định đúng cho mọi trường hợp.
>
> **✅** Partition theo claim user thật ("sub" từ OpenIddict, bài 3.5) thay vì UserId client tự gửi (bài 2.2, đã lỗi thời) hoặc theo IP — tránh cả việc giả mạo lẫn việc chặn oan nhiều user chung IP.
>
> **✅** app.UseRateLimiter() phải đứng sau UseRouting VÀ sau UseAuthentication khi partition phụ thuộc httpContext.User — sai thứ tự không gây lỗi rõ ràng, chỉ âm thầm sai logic partition.
>
> **✅** RequireRateLimiting gắn ở cấp từng MapPost/MapGet cụ thể, không gắn ở cấp MapGroup, để các endpoint rẻ tiền trong cùng nhóm (như AddToCart) không bị giới hạn oan theo endpoint đắt tiền (Checkout).

**Bước tiếp theo:** Bài 4.5 — Chuẩn hóa response & error format toàn hệ thống. Response 429 viết tay ở OnRejected của bài này (type/title/status theo dạng ProblemDetails) sẽ được rà soát lại cho nhất quán 100% với format ProblemDetails chuẩn dùng ở mọi endpoint khác kể từ bài 0.9 — chuẩn bị sạch schema trước khi generate API client ở Module 5.
