## 1. "api/v1/..." viết tay không phải là API Versioning

*5 phút · Lý thuyết ngắn*

Từ bài 0.7, mọi endpoint TEDU Market đã tuân theo đúng convention ở mục 7 của outline: /api/v1/{số nhiều thực thể} — ví dụ POST /api/v1/categories. Nhưng nhìn kỹ vào code, "api/v1/categories" chỉ là một chuỗi string literal truyền vào MapGroup(). Đây là quy ước đặt tên, không phải một cơ chế versioning thật do framework quản lý.

Khi hệ thống có 2 frontend client sống lâu dài cùng gọi 1 backend (React Admin ở Module 6, Next.js Student site ở Module 7), việc chỉ viết tay chuỗi "v1" gây ra 3 vấn đề thật sự:

- Không có cơ chế nào báo cho client biết server đang hỗ trợ version nào — không có response header kiểu api-supported-versions.
- Muốn thêm v2 cho 1 endpoint (ví dụ đổi shape CourseDto ở Module 1) phải tự tay viết một route group song song, rất dễ quên đồng bộ Validator/Handler giữa v1 và v2.
- OpenAPI (bài 4.1) và Scalar (bài 4.2) chỉ thấy 1 path string bất kỳ — không hiểu "v1" là một API version, nên không thể tự động nhóm hay đánh dấu endpoint nào đã deprecated.

ASP.NET Core có OpenAPI built-in từ .NET 9 (Microsoft.AspNetCore.OpenApi), nhưng KHÔNG có API Versioning built-in. Thư viện chuẩn của cộng đồng .NET — và cũng là thư viện được đội ngũ ASP.NET Core giới thiệu chính thức cho .NET 10 — là Asp.Versioning (repo dotnet/aspnet-api-versioning). Bản v10 là bản đầu tiên hỗ trợ chính thức .NET 10 và tích hợp thẳng với Microsoft.AspNetCore.OpenApi.

> **📘 Ghi chú giảng viên:** *Học viên hay ngạc nhiên khi biết .NET 10 có OpenAPI built-in nhưng lại không có Versioning built-in. Đây là câu hỏi tốt để dừng lại giải thích: OpenAPI là chuẩn mô tả tài liệu, còn versioning là quyết định thiết kế API mang tính nghiệp vụ (khi nào breaking change, hỗ trợ song song bao lâu) — nên Microsoft để ngỏ cho thư viện chuyên biệt xử lý, thay vì áp một chính sách cứng vào framework.*

## 2. Cài đặt Asp.Versioning.Http

*3 phút · Demo*

Minimal API cần 2 package: Asp.Versioning.Http (core versioning cho Minimal API) và Asp.Versioning.Mvc.ApiExplorer (cần cho AddApiExplorer(), giúp endpoint hiện đúng theo version trong OpenAPI/Scalar ở bài 4.1–4.2).

```bash
dotnet add TeduMarket.Api package Asp.Versioning.Http
dotnet add TeduMarket.Api package Asp.Versioning.Mvc.ApiExplorer
```

Trong Program.cs của TeduMarket.Api, đăng ký versioning trước khi build app:

```csharp
using Asp.Versioning;
 
builder.Services.AddApiVersioning(options =>
{
    // Version mặc định khi client không chỉ định rõ
    options.DefaultApiVersion = new ApiVersion(1, 0);
 
    // Trả header api-supported-versions cho client tự dò version
    options.ReportApiVersions = true;
 
    // Đọc version từ URL segment: /api/v1/..., /api/v2/...
    options.ApiVersionReader = new UrlSegmentApiVersionReader();
})
.AddApiExplorer(options =>
{
    // Format nhóm version khi liệt kê trong OpenAPI/Scalar: v1, v2...
    options.GroupNameFormat = "'v'VVV";
});
```

Giải thích từng dòng:

- DefaultApiVersion: chỉ có tác dụng khi client gọi 1 route không kèm version rõ ràng. Với UrlSegmentApiVersionReader, client luôn phải gõ rõ /v1/ trong URL, nên option này chủ yếu để làm rõ ý định — v1.0 là version mặc định của hệ thống.
- ReportApiVersions: bật header api-supported-versions trong response — hữu ích để React Admin hay Next.js Student tự kiểm tra server đang hỗ trợ version nào.
- UrlSegmentApiVersionReader: đọc version từ chính segment trong URL (v1, v2...), khác với đọc từ query string (?api-version=1.0) hay header (X-Api-Version).
- AddApiExplorer + GroupNameFormat: cần thiết để mỗi endpoint tự khai báo đúng version của nó khi OpenAPI/Scalar liệt kê route — chuẩn bị sẵn cho việc mở rộng tài liệu API theo version sau này.

## 3. Refactor CategoryEndpoints sang NewVersionedApi()

*5 phút · Demo/Lab*

Trước — route viết cứng từ bài 0.7:

```csharp
app.MapGroup("api/v1/categories")
   .MapCategoryEndpoints();
```

Sau — đúng chuẩn Asp.Versioning:

```csharp
var categoriesApi = app.NewVersionedApi("Categories");
 
var categoriesV1 = categoriesApi
    .MapGroup("api/v{version:apiVersion}/categories")
    .HasApiVersion("1.0");
 
categoriesV1.MapPost("", CreateCategoryAsync)
    .WithName("CreateCategory");
 
categoriesV1.MapGet("", GetCategoriesAsync)
    .WithName("GetCategories");
```

NewVersionedApi("Categories") tạo một "API Version Set" riêng cho nhóm endpoint Category — cho phép sau này gắn thêm .HasApiVersion("2.0") mà không đụng vào endpoint v1 đang chạy. Route template bắt buộc phải có token {version:apiVersion} khi dùng UrlSegmentApiVersionReader — đây là route constraint có sẵn của thư viện Asp.Versioning, không cần đăng ký thêm gì trong Program.cs.

Với client (Postman, React Admin), URL gọi ra vẫn y hệt trước đây — POST /api/v1/categories — nhưng giờ request được route qua middleware versioning thật, không còn là một chuỗi string tình cờ trùng chữ "v1".

> **📘 Ghi chú giảng viên:** *Đã học route "api/v1/categories" như một chuỗi cố định ở bài 0.7, giờ làm đúng chuẩn hơn: chuỗi đó được tách thành route template có version constraint, do Asp.Versioning quản lý thật sự. Tôi hay cho học viên thử gọi POST /api/v99/categories ngay tại đây — sẽ nhận về 400 Bad Request (Unsupported API version) thay vì 404 Not Found như route thường. Đây là bằng chứng trực quan nhất để chứng minh middleware versioning đang thật sự hoạt động, không phải học viên tự tưởng tượng.*

## 4. Áp dụng cho CourseEndpoints

*4 phút · Demo*

Course (Module 1) là nhóm endpoint phức tạp hơn — có nhiều handler (CreateCourse, UpdateCourse, GetCoursesQuery, GetCourseDetailQuery, UpdateCourseThumbnail). Áp cùng pattern:

```csharp
var coursesApi = app.NewVersionedApi("Courses");
 
var coursesV1 = coursesApi
    .MapGroup("api/v{version:apiVersion}/courses")
    .HasApiVersion("1.0");
 
coursesV1.MapPost("", CreateCourseAsync)
    .WithName("CreateCourse");
 
coursesV1.MapPut("{id:guid}", UpdateCourseAsync)
    .WithName("UpdateCourse");
 
coursesV1.MapGet("", GetCoursesAsync)
    .WithName("GetCourses");
 
coursesV1.MapGet("{id:guid}", GetCourseDetailAsync)
    .WithName("GetCourseDetail");
```

Endpoint lồng bên trong Course như quản lý Lesson (bài 1.3, route dạng /api/v1/courses/{courseId}/lessons) đi theo cùng pattern — tạo thêm 1 group con bằng coursesV1.MapGroup("{courseId:guid}/lessons"), version vẫn được kế thừa từ coursesV1 vì nó nằm trong cùng API Version Set.

Lưu ý quan trọng: endpoint của OpenIddict (Module 3) như /connect/token, /connect/authorize, /connect/userinfo KHÔNG đi qua versioning này. Đó là các endpoint theo đúng chuẩn OAuth2/OIDC cố định do OpenIddict tự định nghĩa, không thuộc domain nghiệp vụ TEDU Market — giữ nguyên route như OpenIddict quy định, không thêm {version:apiVersion} vào.

> **📘 Ghi chú giảng viên:** *Mở rộng (không bắt buộc trong Deliverable bài này): Asp.Versioning có gói Asp.Versioning.OpenApi cho phép sinh nhiều OpenAPI document theo từng version bằng app.MapOpenApi().WithDocumentPerVersion(), tích hợp thẳng với bài 4.1 và Scalar UI ở bài 4.2. Tại thời điểm biên soạn bài giảng này, gói đó vẫn ở bản release candidate cho .NET 10 — nên giới thiệu như hướng mở rộng cho học viên tò mò, nhắc các bạn kiểm tra lại trạng thái phát hành ổn định trước khi cân nhắc dùng cho production thật.*

## Bài tập thực hành

Input: Solution TeduMarket hiện tại (tính đến bài 4.2), gồm các endpoint group: Category (0.7), Course + Lesson (1.2–1.8), Instructor (1.9), Order/Cart/Coupon (2.2, 2.3), Payment (2.4), Order History/Revenue (2.8).

Yêu cầu: áp dụng đúng pattern NewVersionedApi() + HasApiVersion("1.0") + route template "api/v{version:apiVersion}/..." cho toàn bộ endpoint group còn lại — trừ endpoint OpenIddict (/connect/...) giữ nguyên như hiện tại.

Expected output: mở /scalar (bài 4.2), toàn bộ path hiển thị đúng dạng /api/v1/{...}, không còn nhóm endpoint nào lệch chuẩn viết tay so với Category/Course vừa refactor.

> **✏️ Thực hành:** Hint 1 — Nếu build báo lỗi trùng route hoặc "ambiguous route": kiểm tra lại đã xóa route cứng "api/v1/..." cũ trước khi thêm route qua NewVersionedApi(), tránh map trùng 2 lần cho cùng 1 endpoint.
>
> **✏️ Thực hành:** Hint 2 — Muốn kiểm tra nhanh server đang hỗ trợ version nào mà không cần đọc code: gọi bất kỳ endpoint đã refactor và xem response header api-supported-versions (nhờ ReportApiVersions = true đã bật ở bước 2).

| **Trước bài 4.3** | **Sau bài 4.3** |
|---|---|
| Route "api/v1/categories" là string literal viết tay | Route "api/v{version:apiVersion}/categories" do Asp.Versioning quản lý qua HasApiVersion("1.0") |
| Gọi sai version → 404 Not Found (route không khớp) | Gọi version không hỗ trợ → 400 Bad Request kèm thông báo rõ ràng |
| Không có cách nào để client tự dò version server hỗ trợ | Response luôn kèm header api-supported-versions |
