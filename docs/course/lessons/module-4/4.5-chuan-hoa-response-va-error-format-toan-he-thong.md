# Nội dung chính

## Phần 1 — Vì sao phải chuẩn hóa NGAY BÂY GIỜ

*Thời lượng: 10 phút | Loại: Lý thuyết*

Bài 4.1–4.4 vừa làm sạch phần "khung" của OpenAPI: annotate đúng kiểu dữ liệu (4.1), có UI test trực tiếp (4.2), chuẩn hóa version /api/v1 (4.3), chặn spam ở endpoint nhạy cảm (4.4). Nhưng openapi.json chỉ trung thực phản ánh những gì code thực sự trả về. Nếu code không nhất quán, schema sinh ra cũng không nhất quán — và bài 5.2 sẽ generate type TypeScript thẳng từ schema đó, dùng chung cho cả apps/admin lẫn apps/web. Một chỗ lệch chuẩn ở backend sẽ nhân đôi thành 2 chỗ code xấu ở frontend.

**Ví dụ đã âm thầm tồn tại trong chính project TEDU Market của bạn:** bài 0.7 trả CategoryDto trực tiếp cho 1 resource; bài 1.6 (GetCoursesQuery) đã có phân trang OFFSET/FETCH nhưng có thể tự đặt tên field khác; bài 2.8 (GetOrderHistoryQuery, GetInstructorRevenueQuery) là 2 endpoint report được viết sau, rất dễ tự chế lại field phân trang riêng. Nếu 3 endpoint "danh sách có phân trang" trả về 3 shape khác nhau, học viên tự làm React Query hook (Module 6.3) và Next.js Server Component (Module 7.2) sẽ phải viết 3 kiểu unwrap khác nhau cho cùng một khái niệm — đây chính là loại lỗi mà bài 4.5 phải chặn trước khi nó lan sang Module 5.

### Quyết định A — Chuẩn response thành công

- 1 resource / 1 lệnh ghi (Command): trả thẳng DTO tương ứng — KHÔNG bọc thêm { success, data }. HTTP status code (200/201/204) đã đóng vai trò báo hiệu thành công; bọc thêm field success là dư thừa, và khiến openapi-ts (bài 5.2) phải sinh ra 1 generic type khó dùng thay vì type cụ thể rõ ràng.
- Danh sách có phân trang (mọi Query dạng "list"): LUÔN dùng chung 1 kiểu PagedResult\<T> — định nghĩa 1 lần ở tầng Application, mọi Query List tham chiếu lại, không tự định nghĩa lại field riêng.

### Quyết định B — Chuẩn response lỗi

- 100% lỗi trả về đều là ProblemDetails (RFC 7807) — không có endpoint nào tự trả JSON lỗi tùy biến riêng. Bao gồm cả lỗi 403 từ Policy/Resource-based Authorization ở bài 3.7, 3.8 — đây là điểm hay bị bỏ sót vì Authorization middleware của ASP.NET Core xử lý tách biệt với luồng exception.
- Lỗi validation (từ ValidationBehavior — bài 0.5) dùng đúng shape HttpValidationProblemDetails (field errors kiểu Dictionary\<string, string[]>) qua Results.ValidationProblem — không tự viết lại cấu trúc lỗi validation riêng.
- Mọi ProblemDetails đều có thêm 2 field mở rộng: traceId (map từ HttpContext.TraceIdentifier, phục vụ tra log Serilog/Seq ở bài 9.7) và errorCode (mã nghiệp vụ ổn định dạng snake_case, ví dụ course_not_found — để FE switch-case theo mã, không phụ thuộc câu chữ ở title/detail vốn có thể đổi bất kỳ lúc nào).

> **📘 Ghi chú giảng viên:** *Học viên hay mang thói quen từ code cũ (ASP.NET MVC/Web API truyền thống, hoặc Node/Express) là bọc mọi response thành công trong 1 envelope generic kiểu { success: true, data: {...} }. Tôi hay dừng đúng chỗ này và hỏi thẳng lớp: "Đã có status code 200 rồi thì field success:true để làm gì?" — im lặng vài giây rồi mới giải thích: envelope generic không sai về mặt chạy được, nhưng nó xóa mất tính cụ thể của type trong OpenAPI schema, và ở bài 5.2 khi hey-api generate client, mọi endpoint sẽ cùng trả về 1 type Envelope\<T> phải unwrap tay ở FE thay vì nhận thẳng type cụ thể — đúng phần "trade-off kiến trúc" mà khóa học nhấn mạnh từ bài 0.1.*

## Phần 2 — Demo: Chuẩn hóa thật trên TEDU Market

*Thời lượng: 20 phút | Loại: Demo*

### Bước 1 — Tạo PagedResult\<T> dùng chung

Vị trí: TeduMarket.Application/Common/Models/PagedResult.cs — namespace TeduMarket.Application.Common.Models. Đây là type duy nhất mọi Query List trong toàn khóa từ giờ về sau phải tham chiếu lại.

```csharp
namespace TeduMarket.Application.Common.Models;
 
public sealed record PagedResult<T>(
    IReadOnlyList<T> Items,
    int TotalCount,
    int Page,
    int PageSize)
{
    public int TotalPages => PageSize <= 0
        ? 0
        : (int)Math.Ceiling(TotalCount / (double)PageSize);
}
```

### Bước 2 — Rà và sửa lại 3 nhóm Query List đã viết trước đó

- GetCategoriesQuery (bài 0.8): outline gốc chỉ yêu cầu "trả dữ liệu qua Dapper", chưa bắt phân trang thật. Vẫn bọc kết quả trong PagedResult\<CategoryDto> (Page=1, PageSize=int.MaxValue nếu số Category còn ít) — để React Query hook ở bài 6.3 dùng chung đúng 1 kiểu list cho mọi resource, không phải viết riêng 1 nhánh code cho Category.
- GetCoursesQuery (bài 1.6): đã có OFFSET/FETCH thật — đổi tên field trả về đúng theo PagedResult\<CourseDto> (Items/TotalCount/Page/PageSize) nếu trước đó bạn lỡ tự đặt tên khác (ví dụ Data/Total).
- GetOrderHistoryQuery, GetInstructorRevenueQuery (bài 2.8): đây là 2 endpoint report viết sau, rủi ro tự chế lại field cao nhất — bọc trong PagedResult\<OrderHistoryDto> và PagedResult\<InstructorRevenueDto>.

> **📘 Ghi chú giảng viên:** *Đây là bài học viên rất dễ chủ quan bỏ qua vì "chạy được rồi mà, đổi tên field làm gì cho mất công". Tôi luôn nhấn: bài 4.5 không phải viết feature mới, mà là kỷ luật kiến trúc — cái giá của việc bỏ qua nó không lộ ra ngay hôm nay, mà lộ ra đúng ở bài 5.4 (demo type-safe end-to-end), khi tự nhiên trong 1 file api-client xuất hiện 3 kiểu list khác nhau cho cùng 1 khái niệm "danh sách phân trang".*

### Bước 3 — Chuẩn hóa ProblemDetails: thêm traceId và errorCode

Bài 0.9 đã dựng GlobalExceptionHandler (IExceptionHandler) + AddProblemDetails + UseExceptionHandler/UseStatusCodePages. Giờ mở rộng thêm CustomizeProblemDetails trong Program.cs để mọi ProblemDetails — dù sinh ra từ nhánh nào — đều có traceId và errorCode:

```csharp
builder.Services.AddProblemDetails(options =>
{
    options.CustomizeProblemDetails = context =>
    {
        context.ProblemDetails.Extensions.TryAdd(
            "traceId", context.HttpContext.TraceIdentifier);
 
        if (context.Exception is DomainException domainEx)
        {
            context.ProblemDetails.Extensions.TryAdd(
                "errorCode", domainEx.ErrorCode);
        }
    };
});
```

Để errorCode có giá trị, cần 1 base class DomainException dùng chung (đặt ở TeduMarket.Domain) — đây là điểm bổ sung mới của bài 4.5: mọi exception nghiệp vụ theo đúng quy ước đặt tên mục 7 ({Thực thể}{LoạiLỗi}Exception) từ giờ kế thừa DomainException và tự khai errorCode dạng snake_case ngay tại nơi khai báo:

```csharp
namespace TeduMarket.Domain.Exceptions;
 
public abstract class DomainException : Exception
{
    public string ErrorCode { get; }
 
    protected DomainException(string errorCode, string message)
        : base(message)
    {
        ErrorCode = errorCode;
    }
}
 
public sealed class CourseNotFoundException : DomainException
{
    public CourseNotFoundException(Guid courseId)
        : base("course_not_found", $"Course '{courseId}' không tồn tại.")
    {
    }
}
```

Việc cố tình khai errorCode bằng tay (thay vì suy ra tự động qua reflection từ tên class) là chủ đích: đổi tên class CourseNotFoundException sau này sẽ không làm vỡ errorCode mà FE đang switch-case theo — errorCode là hợp đồng với frontend, tên class C# là chi tiết nội bộ, hai thứ không nên gắn chết vào nhau.

### Bước 4 — Kiểm tra 403 từ Policy/Resource-based Authorization (3.7, 3.8)

Vì bài 0.9 đã bật app.UseStatusCodePages(), lỗi 403 Forbid từ [Authorize(Policy = "InstructorOnly")] (3.7) và từ CourseOwnerRequirement handler (3.8) phải tự động trả về ProblemDetails 403 đầy đủ — không phải body rỗng. Đây là nhánh lỗi KHÔNG đi qua exception, nên rất dễ bị bỏ sót nếu ở bài 0.9 bạn chỉ gọi UseExceptionHandler() mà quên UseStatusCodePages(). Test lại bằng cách gọi UpdateCourseCommand với 1 Instructor không sở hữu Course — response phải là ProblemDetails 403 có traceId, không phải chuỗi rỗng kèm status 403.
